## 1. 开场：Why — 为什么需要 Ace（5 min）

### 开场话术

> "在座各位应该都用过或者听说过 Claude Code。它确实很强大——能读代码、写代码、跑命令、甚至自主完成复杂任务。但我在深度使用了几个月后发现了一个问题：**它的表现很不稳定**。"

### 核心论点展开

**引子——不稳定的三个表现**（用自己踩过的坑举例）：

1. **思考深度波动**
   - "有时候一个简单的变量重命名，它给你写了 500 字的分析报告；但一个涉及 3 个模块交互的 Bug，它两行代码直接改完，也不验证。"
   - 关键词：**缺乏元认知**——它不知道什么时候该深想，什么时候该快做。

2. **代码质量不一致**
   - "同一个项目，上午写的代码干净优雅，下午写的就是意面代码。因为它没有持续加载的质量标准。"
   - 关键词：**无持久规则**——每次会话都是白纸一张。

3. **复杂任务容易迷失**
   - "给它一个需要 20 步完成的目标，做到第 12 步时上下文被压缩了，之前做的决策全丢了，开始重复工作甚至推翻之前的设计。"
   - 关键词：**工作记忆有限**——上下文窗口不是无限的。

4. **没有安全护栏**
   - "有一次让它清理临时文件，它 `rm -rf` 了整个目录。从那以后我再也不敢在没有保护的情况下给它太多自主权。"
   - 关键词：**缺乏防护**——信任需要安全网。

### 过渡到解决方案

> "所以我想：能不能有一套配置，让 Claude Code **始终**保持专业水准？不是偶尔好用，而是**稳定地好用**？"
>
> "这就是 Ace——AI Coding Environment。一条命令，把 Claude Code 从'通用助手'调校为'专业开发伙伴'。"

### 定位公式（可做一张 Slide）

```
Ace = Claude Code 官方最佳实践 × 认知科学 × 软件工程 × 一键部署
```

## 3. 架构：How — 五层认知增强体系（8-10 min）

### 话术引入

> "Demo 看完了效果，现在来看看它是怎么做到的。Ace 的架构分为五层，每一层解决一个具体问题。"

### 3.1 架构全景图（1 min）

**展示架构图**：

```
┌─── Layer 5: Skills（智能技能层）── 复杂任务的结构化认知协议
├─── Layer 4: Rules（认知规则层）── 始终加载的行为标准
├─── Layer 3: Memory（记忆层）──── 跨会话的知识持久化
├─── Layer 2: Hooks（角色钩子层）── 编译/类型检查的自动化
└─── Layer 1: Hookify（安全层）─── 运行时危险操作拦截
```

**话术**：
> "从底层到顶层：安全 → 自动化 → 记忆 → 规范 → 智能。每层独立，可选启用。"

---

### 3.2 Rules 层——持久规则注入（2 min）

**核心问题**：Claude Code 没有"持久人格"，每次会话都是白纸。

**解决方案**：8 条规则通过 `CLAUDE.md` 的 `@` 引用机制，在每次会话启动时自动加载到上下文。

| 规则 | 一句话描述 | 解决什么问题 |
|------|-----------|-------------|
| thinking | 六字原则：序验深广辨简 | 思考深度不稳定 |
| clean-code | 6 条核心原则 + 反模式表 | 代码质量波动 |
| code-quality | 详细质量检查清单 | 细节层面的质量把控 |
| context-hygiene | 上下文压缩保护策略 | 长任务状态丢失 |
| memory-policy | 记忆保存的严格准入门槛 | 记忆膨胀、噪音过多 |
| task-recovery | 任务恢复协议 | 中断后无法续做 |
| reporting | 自动报告输出 | 分析结果格式不规范 |
| interactive-clarify | 批量澄清规则 | 打断用户次数过多 |

**话术**：
> "这 8 条规则就像 Claude 的'职业素养'——不管什么任务，这些底线始终在。最关键的是 thinking 规则——'宁可慢一步想清楚，不要快一步做错了'。"

---

### 3.3 Skills 层——认知协议（3 min）

**核心问题**：复杂任务需要结构化的思考框架，不能让 AI 随意发挥。

**四个 Skills**：

| Skill | 定位 | 核心机制 |
|-------|------|---------|
| **auto-goal** | 复杂目标自主完成 | 首轮对齐 + OODA 循环 + 状态外化 + 经验进化 |
| **coding** | 代码域认知协议 | 三意图路由(实现/测试/审查) + 复杂度适配(轻量/标准/深度) |
| **skill-creator** | 创建新 Skills | 生命周期管理 + Eval 框架 + Benchmark |
| **skill-optimize** | 优化现有 Skills | 七条优化原则 + 四维诊断 |

**重点讲解 auto-goal 的设计**：

> "auto-goal 有三条硬规则：
> 1. **首轮对齐不可跳过**——理解 → 澄清 → 确认，三步完成才能动手
> 2. **替用户做选择时必须暂停**——如果用户看到你的决策会惊讶，就该停下来问
> 3. **长任务外化状态**——超过 10 步的任务，创建 .tasks/ 目录持久化进度"

**渐进式加载模型**：

```
Metadata (100 词)     ← 始终在上下文，用于匹配触发
Trigger (50 词)       ← 始终在上下文，判断是否激活
Cognitive (500 行)    ← 触发时加载 SKILL.md 核心协议
Resource (不限)       ← 按需加载参考文件（如 implement-guide.md）
```

> "这个四层加载模型的设计哲学是：**上下文是稀缺资源**。不需要的信息不加载，需要的时候才拉进来。"

---

### 3.4 Memory + Hooks + Hookify（2-3 min）

**Memory 层**（快速带过）：
> "三层记忆架构——工作记忆（当前对话）、短期记忆（.tasks/ 状态文件）、长期记忆（~/.claude/memory/）。跨会话保存开发者画像、项目上下文、行为反馈。"

**Hooks 层**（快速带过）：
> "基于角色的自动化检查。比如 backend 角色会装一个 Java 编译检查 Hook——每次修改 .java 文件后自动编译，失败了立即告诉你。"

**Hookify 层**（已在 Demo 展示，简要回顾）：
> "7 个运行时守卫：命令级拦截（rm -rf、force push）、文件级保护（.env、密钥）、流程级验证（提交前检查）。"

---

### 3.5 核心设计理念（2 min）

**三个关键词**：

1. **非侵入式**
   - 命名空间隔离：所有文件用 `ace` 前缀
   - 智能合并：CLAUDE.md 用 `<!-- ace:managed:start/end -->` 标记，settings.json 深度合并
   - 可逆安装：`ace uninstall` 一键恢复原状

2. **渐进式增强**
   - 每一层独立可选，minimal preset 只装 core + rules + plugin
   - 从简单开始，按需增加复杂度

3. **认知经济**
   - 信息分层加载，不浪费上下文
   - 探索性工作隔离到 sub-agent
   - 已完成阶段压缩保留决策和结论

### 过渡到 aspec

> "刚才讲的是'写代码'阶段的增强。但真实开发中，写代码之前还有一个更关键的环节——**需求理解和设计决策**。跳过这一步直接写代码，就是在赌运气。这就是 aspec 要解决的问题。"

## 4. aspec：规范驱动开发工作流（7-8 min）

### 话术引入

> "我们都知道一个道理：**需求没理解清楚就写代码，大概率要返工**。人类开发者是这样，AI 开发者更是如此——因为 AI 不会像人一样'犹豫'，它会非常自信地基于假设往前冲，冲错了你才发现。"
>
> "aspec 就是解决这个问题的：**强制澄清，再动手**。"

---

### 4.1 核心理念（1 min）

**一句话**：跳过澄清 = AI 基于假设实现 = 高概率返工

**三命令流程**：

```
/opsx:proposal  ──→  /opsx:apply  ──→  /opsx:archive
  创建提案              代码实现            归档复盘
```

**话术**：
> "整个开发流程浓缩成三步：先搞清楚要做什么（proposal），再写代码（apply），最后复盘总结（archive）。听起来很简单，但每一步里面都有严格的质量门禁。"

---

### 4.2 双重门禁机制（3 min）

**这是 aspec 最核心的设计——不可跳过的门禁**

#### 门禁 1：需求澄清

> "当你给 AI 一个需求时，它不会立刻开始设计。它会先从 6 个维度分析这个需求有哪些不确定性。"

**6 个需求澄清维度**：

| 维度 | 关注点 | 例子 |
|------|--------|------|
| 功能完整性 | 核心功能是否说清了？ | "用户登录"——密码登录还是 OAuth？ |
| 数据关注 | 数据从哪来？格式？量级？ | "导入用户"——CSV 还是 API？10 条还是 10 万条？ |
| 用户体验 | 交互方式？反馈？ | "提交表单"——成功后跳转还是 toast？ |
| 边界/异常 | 极端情况怎么处理？ | "上传文件"——超过 100MB 怎么办？ |
| 集成依赖 | 和哪些系统交互？ | 需要调哪些外部 API？ |
| 优先级/范围 | MVP 还是完整版？ | 先做哪些、后做哪些？ |

**流程**：
1. AI 分析不确定性 → 写入 `issues/requirement-issues.md`
2. 批量向你提问（不是一个一个问，而是把问题组织好一次性问）
3. 你回答后，AI 呈现"对齐摘要"——复述它的理解让你确认
4. **确认通过才能进入下一步**

> "这个过程是强制的。不管你多着急说'快点写代码'，它都会先完成这一步。因为我们的经验告诉我们：**花 5 分钟澄清，能省 5 小时返工**。"

#### 门禁 2：设计澄清

> "需求搞清了，接下来是设计。同样有 7 个维度的分析。"

**7 个设计澄清维度**：

| 维度 | 关注点 |
|------|--------|
| 架构决策 | 分层？模式？组件划分？ |
| 技术选型 | 用什么框架/库/工具？ |
| 接口设计 | API 格式？入参出参？ |
| 数据/状态 | 数据结构？状态管理？ |
| 安全/合规 | 认证？授权？数据隐私？ |
| 性能/可靠性 | 并发？缓存？降级？ |
| 部署/运维 | 环境？配置？监控？ |

> "同样的流程：分析 → 提问 → 对齐确认 → 通过后才生成设计文档。"

#### Surprise Test

> "还有一个有趣的规则叫 **Surprise Test**：当 AI 要替你做一个决策时，它会问自己——'如果用户看到这个决策，会不会惊讶？'如果答案是'会'，它就会停下来问你。"

---

### 4.3 寄生模式设计（1 min）

**话术**：
> "技术上有个巧妙的设计——aspec 不是一个独立的框架，而是'寄生'在 OpenSpec 上的增强。它不修改 OpenSpec 的 schema，只通过 config.yaml 的 context 和 rules 字段注入额外行为。"

```yaml
# config.yaml 片段
context:
  dimensions: "@openspec/dimensions.md"
  experience: "@openspec/experience-template.md"

rules:
  proposal:
    PRE: "读取 experience.md 中相关经验..."
    GATE: "issues/requirement-issues.md 已澄清 + 对齐确认通过"
  design:
    PRE: "读取技术相关经验..."
    GATE: "issues/design-issues.md 已澄清 + 对齐确认通过"
```

> "好处是：OpenSpec 升级时不受影响，aspec 的增强独立演进。"

---

### 4.4 经验进化系统（2 min）

**话术引入**：
> "aspec 最有价值的部分，不是门禁，而是每次实现后的**复盘和知识积累**。"

**机制**：每次 `/opsx:apply` 完成后，**强制**触发经验进化（不可跳过）：

1. **提取四类知识**：
   - 技术决策记录（ADR）：选了什么方案、为什么、排除了哪些替代方案
   - 领域词汇表：这个项目的专有术语
   - 风险地图：哪些代码是"地雷区"
   - 复盘记录：澄清阶段哪些问题命中了真实问题、哪些是噪音

2. **主动应用**：下次做类似任务时，AI 会主动说"根据经验 E3，建议..."

3. **验证反馈**：每次应用经验后标记 ✓有效 / ✗无效 / — 不适用

4. **收敛机制**：条目超过 20 条时，合并相似、淘汰无效

**话术**：
> "这就像一个不断学习的团队——每次项目结束都复盘，把踩过的坑记下来，下次新人来了也能受益。只不过这里的'团队'是 AI，它的经验文件是共享的。"

## 5. 理论基础：Why it works（3-5 min）

### 演讲者笔记

> 这一部分不要讲太深，给听众一个"这不是拍脑袋做的"的感觉即可。重点是建立可信度。

### 话术引入

> "Ace 的设计不是凭感觉写的，背后有一套跨学科的理论支撑。我快速过一下核心的几个。"

---

### 5.1 认知科学（1.5 min）

**三个关键理论**：

1. **元认知（Metacognition）**
   > "对思考的思考。人类专家和新手的区别，不在于知识量，而在于元认知——知道什么时候该慢下来仔细想、什么时候可以快速执行。Ace 的 thinking 规则就是给 Claude 装上元认知。"

2. **认知负荷理论（Cognitive Load Theory）**
   > "工作记忆是有限的。AI 的上下文窗口同理。所以 Ace 用渐进式披露——只在需要时加载信息，而不是一次性全塞进去。"

3. **延展心灵（Extended Mind）**
   > "Clark & Chalmers 的论文说：如果一个外部工具在功能上等价于内部认知过程，那它就是心灵的延伸。.tasks/ 目录就是 Claude 的'外部记忆'——把状态外化到文件，扩展了它的工作记忆。"

---

### 5.2 控制论（1 min）

**两个核心概念**：

1. **OODA 循环（John Boyd）**
   > "军事决策理论：Observe-Orient-Decide-Act。比简单的'计划-执行'多了一个关键步骤——Orient（定向），也就是'我观察到了，但我怎么理解它？'Ace 的 coding skill 完整实现了 OODA：Sense-Orient-Decide-Act-Observe-Adapt。"

2. **必要多样性定律（Ashby's Law）**
   > "控制器的复杂度必须≥被控系统的复杂度。翻译成大白话：简单任务用简单策略，复杂任务用复杂策略。这就是 coding skill 三层复杂度适配的理论来源——轻量/标准/深度三种路径。"

---

### 5.3 软件工程（1 min）

> "最后是软件工程的老朋友：Clean Code（Robert C. Martin）、SOLID 原则、TDD。这些不需要多说，大家都熟悉。Ace 做的事情是**把这些原则编码成可执行的规则**，让 AI 每次都按照这些标准输出，而不是时灵时不灵。"

---

### Q&A 预备问题

准备以下可能被问到的问题：

| 问题 | 回答要点 |
|------|---------|
| "会不会让 Claude 变慢？" | Rules 加载增加几百词上下文，对性能影响微乎其微。反而因为方向更准确，减少了来回修改的时间。 |
| "和 Cursor / Windsurf 等 IDE 集成方案有什么区别？" | Ace 增强的是底层 Claude 的认知能力，不绑定特定 IDE。任何使用 Claude Code CLI 的场景都受益。 |
| "能和团队现有的 .cursorrules 等共存吗？" | 可以。Ace 用命名空间隔离（ace/ 前缀），不覆盖现有配置。 |
| "openspec/aspec 对小需求会不会太重？" | aspec 是项目级的可选功能（ace spec init），不影响日常开发。日常小任务用 coding skill 即可。 |
| "如何升级？" | `npm update -g @shirayner/ace && ace init`，智能合并保留你的自定义内容。 |
| "token 消耗会增加吗？" | Rules 层增加约 2000 tokens 的上下文（一次性加载）。Skills 按需加载，不触发不消耗。整体增加约 5-10%，但因为减少了返工，总消耗通常反而更低。 |

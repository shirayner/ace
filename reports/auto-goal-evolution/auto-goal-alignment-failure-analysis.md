# 首轮对齐失效问题：根因分析与修复方案

> 分析日期: 2026-04-22
> 分析主题: auto-goal 规则 1"首轮对齐"在实际使用中被模型"滑过去"的根因诊断与结构性修复
> 核心问题: 模型呈现理解后直接执行，不调用 AskUserQuestion 创建阻塞点，用户被迫等它跑完再纠正

---

## 1. 症状与五层根因分析

### 1.1 症状描述

用户提供目标后，模型的实际行为：

```
用户: "帮我实现 X"
模型: "我的理解是... 计划方向是... 假设是..."  ← 呈现了对齐内容
      [立即开始调用工具、写代码、执行任务]      ← 没有停下来等确认
      ...执行完毕...
用户: "不对，我要的不是这个"                    ← 用户只能事后纠正
模型: [重新执行]                                ← 浪费了第一轮全部工作
```

模型**形式上遵守了指令**（呈现了理解），但**实质上违反了意图**（没有等待确认就执行了）。

### 1.2 五层根因追问

| 层级 | 问题 | 回答 |
|------|------|------|
| **L1 症状** | 为什么模型没有停下来等确认？ | 因为它没有调用 AskUserQuestion，只是输出了文本 |
| **L2 直接原因** | 为什么没调用 AskUserQuestion？ | 因为指令说"呈现理解"，不是"调用 AskUserQuestion" |
| **L3 机制缺失** | 为什么仅"呈现"不够？ | 因为文本输出不创建阻塞点；只有工具调用才能强制模型停下来等待用户响应 |
| **L4 设计冲突** | 为什么模型倾向于跳过等待？ | 因为 Auto Mode 系统指令说"Execute immediately, Minimize interruptions"，与"等待确认"直接冲突 |
| **L5 架构根因** | 为什么 Auto Mode 能压过 Skill 指令？ | 因为 Claude Code 的 Prompt 栈中，System Prompt（含 Auto Mode）在第 1 层，Skill 在第 4 层。**层级高的指令在冲突时胜出** |

### 1.3 根因 A：机制未指定（L2-L3）

当前规则 1 的关键表述：

```
接收目标后，**必须先确认对齐**。
简单明确的目标一句话确认即可；复杂模糊的目标完整呈现...
有歧义时先用 AskUserQuestion 澄清...
用户确认后进入执行。
```

三个致命漏洞：

1. **"确认对齐"没有指定机制** — 模型将"确认对齐"解释为"输出对齐文本"，而非"调用 AskUserQuestion 工具"。文本输出完成后，模型的下一个 token 自然是继续执行。
2. **"一句话确认即可"给了逃逸路径** — 模型在 Auto Mode 压力下，将大部分目标判定为"简单明确"，用一句话带过，然后立即执行。弹性表述变成了逃逸通道。
3. **"有歧义时"限定词削弱了强制性** — AskUserQuestion 只在"有歧义时"被提及。模型只要自认为"理解清楚了"，就绕过了 AskUserQuestion。

**类比**：这就像告诉司机"转弯前必须减速"，但没有安装减速带。司机（模型）在赶时间（Auto Mode）时，会认为"我已经减速了"然后继续全速通过。

### 1.4 根因 B：Prompt 栈层级冲突（L4-L5）

Claude Code 的 Prompt 栈优先级：

```
Layer 1: System Prompt     ← 含 Auto Mode: "Execute immediately, Minimize interruptions"
Layer 2: Tool Definitions
Layer 3: Runtime Instructions
Layer 4: Project Context   ← 含 SKILL.md: "必须先确认对齐"
Layer 5: Conversation History
Layer 6: User Input
```

当 Layer 1 说"立即执行、减少打断"，Layer 4 说"停下来等确认"时，模型面临矛盾。解决方式是**选择阻力最小的行为**：

- 输出对齐文本（满足 Layer 4 的"呈现理解"要求）
- 立即继续执行（满足 Layer 1 的"Execute immediately"要求）
- 不调用 AskUserQuestion（满足 Layer 1 的"Minimize interruptions"要求）

模型找到了一个"两全其美"的行为：**形式遵从 + 实质跳过**。这不是"不听话"，而是在矛盾指令下的理性最优响应。

### 1.5 根因总结

```
首轮对齐失效
  ├── 根因 A：机制未指定
  │     ├── "确认对齐" ≠ "调用 AskUserQuestion"
  │     ├── "一句话确认即可" = 逃逸通道
  │     └── "有歧义时" = 条件限定削弱强制性
  │
  └── 根因 B：层级冲突
        ├── Auto Mode (Layer 1) > Skill (Layer 4)
        ├── "Execute immediately" vs "等待确认"
        └── 模型选择阻力最小路径：形式遵从 + 实质跳过
```

**两个根因是耦合的**：如果指令明确指定了 AskUserQuestion 作为机制（根因 A 修复），模型在 Auto Mode 下仍然可能跳过它（根因 B 存在）。必须同时解决两个根因。

## 2. 跨学科洞察：为什么文字指令无法创建阻塞行为

### 2.1 实施意图 vs 目标意图（心理学 — Gollwitzer）

Peter Gollwitzer 的研究发现了一个关键区分：

| 类型 | 示例 | 执行率 |
|------|------|--------|
| **目标意图** (Goal Intention) | "我要坚持锻炼" | ~30% |
| **实施意图** (Implementation Intention) | "周一早上 7 点，我穿好跑鞋去公园跑步" | ~90% |

区别在于：实施意图指定了 **when + where + how**，将决策从执行时刻前移到规划时刻。执行时不需要再做判断，只需要识别触发条件并执行预定行为。

**映射到 auto-goal**：

| 当前指令（目标意图） | 应有指令（实施意图） |
|---------------------|---------------------|
| "必须先确认对齐" | "接收目标后，**第一个动作**必须是调用 **AskUserQuestion** 工具" |
| when: 模糊（"接收目标后"） | when: 精确（"第一个动作"） |
| what: 模糊（"确认对齐"） | what: 精确（"调用 AskUserQuestion"） |
| how: 未指定 | how: 工具名 + 呈现内容明确 |

**洞察**：当前指令是目标意图，模型需要在每次执行时判断"如何确认对齐"，在 Auto Mode 压力下选择了阻力最小的方式（输出文本）。改为实施意图后，模型只需要识别触发条件（接收到目标）并执行预定行为（调用 AskUserQuestion），不需要运行时判断。

### 2.2 Poka-yoke 防错设计（工程 — 新乡重夫）

丰田生产系统的 Poka-yoke（防错）原则：

> 不要依赖人的注意力和纪律来防止错误；设计系统使错误在结构上不可能发生。

三种防错级别：

| 级别 | 方法 | 在 auto-goal 中的映射 |
|------|------|---------------------|
| **Level 1: 消除** | 使错误不可能 | 无法实现（不能阻止模型生成 token） |
| **Level 2: 替代** | 使正确行为成为默认 | ✅ **让 AskUserQuestion 成为唯一合规路径** |
| **Level 3: 检测** | 错误发生时立即发现 | 次优方案（已经太晚了） |

**当前设计是 Level 3**："用户确认后进入执行"——如果模型不停下来，用户只能事后发现。
**目标设计是 Level 2**：使 AskUserQuestion 成为唯一的"确认对齐"机制，模型只有调用它才算完成了"首轮对齐"。

### 2.3 Affordance 理论（认知科学 — Gibson/Norman）

James Gibson 的 Affordance（可供性）理论：环境中的物体"邀请"特定的行为。门把手邀请拉，平板邀请推。

**当前指令的 Affordance 分析**：

| 指令表述 | 模型感知到的 Affordance | 实际行为 |
|----------|----------------------|----------|
| "呈现理解" | 输出文本（最自然的 affordance） | 写一段文字 |
| "等待确认" | 模糊（没有对应的工具 affordance） | 被忽略或解释为"用户可以打断" |
| "AskUserQuestion" | 调用工具（明确的工具 affordance） | 调用工具并等待响应 |

**洞察**：AskUserQuestion 工具本身就是一个结构性 affordance——调用它就自然产生"等待"行为。不需要额外告诉模型"等待"，因为工具的机制就是等待用户响应。指定工具名 = 指定 affordance = 指定行为。

### 2.4 Performative vs Constative 语言行为（语言哲学 — Austin）

J.L. Austin 区分了两种语言行为：

| 类型 | 定义 | 示例 | 效果 |
|------|------|------|------|
| **Constative（陈述性）** | 描述事实或期望状态 | "用户确认后进入执行" | 模型可能遵从，也可能不遵从 |
| **Performative（施行性）** | 语言本身就是行动 | "调用 AskUserQuestion" | 指令本身就是行动指令 |

当前规则 1 使用大量 constative 表述（"必须先确认对齐"、"等待确认后进入执行"）。这些表述描述了**期望的状态**，但没有执行**具体的动作**。

修复方向：用 performative 替代 constative。"调用 AskUserQuestion" 是一个直接的行动指令，比"等待确认"更有执行力。

### 2.5 信号竞争与优先级解决（控制论）

在控制系统中，当多个控制信号冲突时，系统通过**优先级仲裁**解决。Claude Code 的优先级架构：

```
Auto Mode (Layer 1): "Execute immediately"    → 权重: 高
Skill Rule (Layer 4): "等待确认"              → 权重: 中
```

当前 Skill 指令无法在权重上胜过 Auto Mode。但可以在**框架**上化解冲突：

> 关键洞察：首轮对齐不是"打断"，而是"用户选择 auto-goal skill 时已经授权的行为"。
> 用户选择了 auto-goal = 用户选择了首轮对齐。遵守首轮对齐 IS 遵守用户意图。

如果在指令中将首轮对齐**重新框架为用户授权的行为**（而非对 Auto Mode 的违反），模型就不需要在两者间做取舍。

## 3. 修复方案设计

### 3.1 设计原则

基于以上分析，修复必须同时解决两个根因：

| 根因 | 修复策略 | 理论支撑 |
|------|----------|----------|
| **A: 机制未指定** | 明确指定 AskUserQuestion 为唯一合规机制 | 实施意图、Poka-yoke Level 2、Affordance |
| **B: 层级冲突** | 重新框架为"用户授权行为"，化解与 Auto Mode 的矛盾 | 控制论信号框架 |

### 3.2 修复方案：新版规则 1

**核心变更**：

1. **指定 AskUserQuestion 为唯一的对齐机制** — 用 performative 替代 constative
2. **"第一个动作"约束** — 实施意图的 when 精确化
3. **移除逃逸通道** — 删除"一句话确认即可"，改为"内容可精简但工具调用不可省略"
4. **Auto Mode 兼容框架** — 用户选择 auto-goal = 用户授权首轮对齐

**新版规则 1 设计**：

```markdown
### 规则 1：首轮对齐（MANDATORY — 优先于 auto mode）

接收目标后，**第一个动作必须是调用 AskUserQuestion 工具**呈现对齐内容。
在 AskUserQuestion 之前，禁止调用任何其他工具或开始执行。

AskUserQuestion 中呈现：
1. **我的理解** — 复述目标核心意图
2. **计划方向** — 打算怎么做（高层策略）
3. **关键假设** — 不确定的假设，标注出来
4. **完成标准** — "我认为完成的标志是..."（必须可测试）

简单目标可精简呈现内容，但 **AskUserQuestion 调用本身不可省略**。
用户通过 AskUserQuestion 确认后才能开始执行。
```

### 3.3 每个设计决策的理由

| 设计决策 | 解决的根因 | 理论支撑 | 替代方案为什么不行 |
|----------|-----------|----------|-------------------|
| 明确写 "AskUserQuestion 工具" | A: 机制指定 | Performative 语言行为、Affordance | "等待确认"太模糊，模型用文本输出满足 |
| "第一个动作" | A: 时序锁定 | 实施意图的 when | "先确认"不够精确，模型可能插入其他动作 |
| "禁止调用任何其他工具" | A: 消除逃逸 | Poka-yoke Level 2 | 没有禁止条款，模型会"顺便"先调个工具 |
| "优先于 auto mode" | B: 层级冲突 | 控制论框架重构 | 不写明则 Auto Mode 默认胜出 |
| "调用本身不可省略" | A: 消除弹性逃逸 | 防止"简单目标"成为跳过借口 | "一句话确认即可"被滥用为不调工具 |

### 3.4 预期效果与风险

**预期效果**：
- 模型在接收目标后的第一个工具调用必须是 AskUserQuestion
- AskUserQuestion 本身的机制保证模型停下来等待用户响应
- 用户在确认前可以纠正理解偏差，避免浪费一轮执行

**风险评估**：

| 风险 | 概率 | 缓解措施 |
|------|------|----------|
| 极简任务也要等确认，降低效率 | 中 | 内容可精简（一句话概括），确认本身只需用户点一下 |
| Auto Mode 仍然压过 Skill 指令 | 低 | "优先于 auto mode" 明确了优先级；AskUserQuestion 是具体工具名不是模糊描述 |
| 模型在 AskUserQuestion 前输出大量分析文本 | 低 | "第一个动作"+"禁止在之前调用其他工具"限制了前置行为 |

## 4. 实施与验证

### 4.1 具体修改

修改文件：`skills/auto-goal/SKILL.md`

修改内容：仅修改规则 1 段落（约 10 行变更），其余部分不变。

### 4.2 变更对比

| 维度 | 修改前 | 修改后 |
|------|--------|--------|
| 机制指定 | "必须先确认对齐" (constative) | "第一个动作必须是调用 AskUserQuestion 工具" (performative) |
| 逃逸通道 | "简单明确的目标一句话确认即可" | "AskUserQuestion 调用本身不可省略" |
| Auto Mode 关系 | 未提及（隐含冲突） | "优先于 auto mode"（显式声明） |
| AskUserQuestion 角色 | 仅在"有歧义时"提及 | 作为唯一的对齐确认机制 |
| 弹性保留 | 内容弹性 + 机制弹性 | **内容弹性保留，机制强制** |

### 4.3 验证方法

修改后，通过以下场景验证：

1. **简单目标**："帮我修复这个 typo" → 预期：模型调用 AskUserQuestion 简短确认，用户点确认后执行
2. **复杂目标**："设计并实现认证系统" → 预期：模型调用 AskUserQuestion 完整呈现 4 项内容，用户确认后执行
3. **Auto Mode 下**：开启 auto mode 后给目标 → 预期：模型仍然首先调用 AskUserQuestion
4. **模糊目标**："优化性能" → 预期：模型在 AskUserQuestion 中标注关键假设和需要澄清的点

### 4.4 如果仍然失效的兜底方案

如果修改后模型仍然跳过 AskUserQuestion，还有更重的手段：

1. **Hook 方案**：通过 hookify 配置 pre-tool-use hook，检查首次工具调用是否为 AskUserQuestion，不是则阻止
2. **重复强调**：在 SKILL.md 的多个位置重复提及（标题、正文、注释），利用重复曝光效应
3. **反面示例**：在指令中加入"错误示例 vs 正确示例"，用 contrast 强化理解

但这些都是兜底。正确设计的实施意图 + 明确工具名 + Auto Mode 框架解决，应该能解决绝大多数情况。

## 5. 修复方案 v2（最终版）

### 5.1 用户反馈与方案修正

v1 方案过于粗暴——"在 AskUserQuestion 之前禁止调用任何其他工具"阻止了模型进行必要的初步分析。实际上，模型需要先读代码、理解上下文，才能给出高质量的对齐内容。

用户期望的流程：

```
接收目标
  → Step 1: 初步分析（Read/Grep/Glob 探索上下文）     ← 允许探索性工具
  → Step 2: 批量澄清（AskUserQuestion 批量提问）       ← 有歧义时
  → Step 3: 对齐确认（AskUserQuestion 呈现对齐内容）   ← 不可跳过
  → 用户确认
  → 开始执行（Edit/Write/Bash 等执行性操作）
```

### 5.2 关键设计决策

**区分探索性操作 vs 执行性操作**：

| 类型 | 工具 | 对齐前 | 对齐后 |
|------|------|--------|--------|
| 探索性 | Read, Grep, Glob, Agent(explore) | ✅ 允许 | ✅ 允许 |
| 执行性 | Edit, Write, Bash | ❌ 禁止 | ✅ 允许 |
| 交互性 | AskUserQuestion | ✅ 必须调用 | ✅ 允许 |

这个区分是合理的：探索不改变世界状态，执行改变世界状态。对齐的目的是确保方向正确，在方向确认前不应改变任何东西。

**两次 AskUserQuestion 的分工**：

- Step 2（澄清）：消除歧义，获取缺失信息。可跳过（无歧义时）。
- Step 3（对齐）：呈现完整理解和计划，获取执行授权。不可跳过。

### 5.3 最终版规则 1 全文

```markdown
### 规则 1：首轮对齐（MANDATORY — 优先于 auto mode）

接收目标后，**必须完成以下三步才能开始执行**。在对齐确认前，禁止任何执行性操作（Edit/Write/Bash）。

**Step 1: 初步分析** — 用探索性工具（Read/Grep/Glob/Agent）理解上下文，形成对目标的理解。

**Step 2: 批量澄清** — 如果存在歧义或需要用户决策，**调用 AskUserQuestion 工具**批量提问（1-4 个问题）。无歧义则跳过此步。

**Step 3: 对齐确认（不可跳过）** — **调用 AskUserQuestion 工具**呈现对齐内容，等待用户确认：
1. **我的理解** — 复述目标核心意图
2. **计划方向** — 打算怎么做（高层策略）
3. **关键假设** — 不确定的假设，标注出来
4. **完成标准** — "我认为完成的标志是..."（必须可测试）

**Step 3 的 AskUserQuestion 调用不可省略**，简单目标可精简内容但必须调用。
用户通过 AskUserQuestion 确认后才能开始执行。
```

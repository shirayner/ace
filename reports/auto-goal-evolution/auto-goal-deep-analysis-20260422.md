# Auto-Goal Skill 深度优化方向分析

> 分析日期: 2026-04-22
> 分析主题: 以"只做模型不会自发做的事"为第一原则，基于 Claude Code 设计哲学、OpenAI Agent 最佳实践、认知科学/控制论/Flow 理论/延展心灵/行动哲学/社会心理学/系统思维的综合优化方向
> 分析对象: 当前 SKILL.md (~100 行简化版)
> 前序分析: v1 (差距识别), v2 (详细方向), v3 (极简方案)。本轮是独立的第一性原理分析，不是前序的增量修补
> 研究基础: 四路并行研究 — Claude Code 源码/设计哲学 + OpenAI Agent 指南 + 跨学科理论 + 当前 SKILL.md 审计

## 1. 当前版本评估：从第一性原理审计

### 1.1 设计演化轨迹

Auto-goal 经历了显著的设计演化：

| 版本 | 特征 | 行数 | 设计风格 |
|------|------|------|----------|
| 早期版本 | OODA 六阶段、信息分级(FACT/INFER/ASSUME)、深度调节(1-4)、策略工具箱、反模式表 | ~300 行 | 枚举式规则密集 |
| **当前版本** | 思考罗盘(6字)、三条硬规则、四条生成式原则、上下文纪律、恢复协议 | **~100 行** | **生成式原则主导** |

这一演化方向是正确的——从 v1/v2 分析中提炼的最重要洞察"处方悖论"已被部分解决：认知约束从 ~85% 降至 ~40%，生成式原则替代了大量枚举规则。

### 1.2 当前版本的设计优势

| 设计要素 | 对齐的理论/最佳实践 | 评级 |
|----------|---------------------|------|
| **"信任模型的推理能力，只做模型不会自发做的事"** | Anthropic "98.4% infrastructure, 1.6% AI logic"、生态理性 | ★★★★★ 哲学方向完全正确 |
| **"对齐优先于效率"** | Common Ground Theory、OpenAI "most failures are routing errors" | ★★★★★ 正确的价值排序 |
| **思考罗盘（序验深广辨简）** | 元认知监控、Dewey 反思性思维 | ★★★★☆ 优秀的生成式元认知工具 |
| **三条硬规则** | Poka-yoke 防错设计、BDI 意图稳定性 | ★★★★☆ 正确区分了"硬约束"和"软指导" |
| **四条生成式原则** | 生态理性、Anytime 算法、认知负荷理论 | ★★★★☆ 方向正确，信息密度高 |
| **上下文纪律（隔离/压缩/外化）** | 分布式认知、延展心灵、Anthropic context engineering | ★★★★☆ 覆盖三大上下文管理策略 |
| **恢复协议** | Stigmergy、认知连续性 | ★★★☆☆ 功能正确，但可深化 |
| **介入模式** | Flow 理论的挑战-技能平衡 | ★★★☆☆ 覆盖两端，缺中间态 |

### 1.3 核心问题诊断

基于四路研究的交叉比对，当前版本存在以下关键差距（按影响排序）：

| # | 差距 | 本质问题 | 理论根因 |
|---|------|----------|----------|
| **G1** | **缺少验证闭环的结构性保障** | 模型知道应该验证，但缺乏"验证什么、如何判定完成"的结构 | Anthropic: "验证是最高杠杆操作"；TOTE 模型：Test-Operate-Test-Exit |
| **G2** | **首轮对齐产出不含完成标准** | 对齐确认了"做什么"，但没有锁定"做到什么程度算完成" | 目标设定理论：明确+可测量的目标 >> 模糊的"尽力而为" |
| **G3** | **状态文件是日志而非可恢复的世界模型** | state.md 记录"发生了什么"，但新 agent 难以从中重建决策上下文 | 延展心灵：外化质量 = 认知连续性质量 |
| **G4** | **缺少目标状态描述（只有行动序列）** | 计划描述"做什么"而非"完成后世界的样子" | PCT(感知控制论)：行为由"当前状态-期望状态"的差异驱动 |
| **G5** | **对齐是一次性事件而非持续过程** | 首轮对齐后，执行过程中的目标漂移无结构性检测 | Common Ground Theory：共同基础需要持续维护而非一次建立 |
| **G6** | **复杂度无差别对待** | 简单任务承受完整协议开销 | 双过程理论：System 1/2 按需切换；Ashby 必要多样性的反面 |

这六个差距不是独立的——它们共享一个根因：**当前 skill 在"做什么"的引导上做得好，但在"做到什么程度"和"如何判定做到了"的结构上缺失**。

## 2. 第一性原理：Skill 的精确边界

### 2.1 模型原生能力 vs Skill 应补的缺口

"只做模型不会自发做的事"是 auto-goal 的第一原则。要落地这个原则，必须先精确划分**模型天然擅长什么**和**模型天然缺什么**。

**Claude Opus 级模型的原生强项**（随模型迭代持续增强，skill 不应干预）：

| 能力 | 说明 | Skill 应有态度 |
|------|------|----------------|
| 推理与规划 | 多步逻辑推理、方案设计、技术分析 | **完全信任**，不用指令规定如何推理 |
| 代码生成与理解 | 编写、阅读、调试代码 | **完全信任** |
| 知识调用 | 技术栈知识、最佳实践、设计模式 | **完全信任** |
| 工具使用 | 选择正确的工具、构造正确的参数 | **基本信任**，工具描述本身是足够的引导 |
| 错误分析 | 从错误信息推断原因、生成修复方案 | **基本信任** |
| 自然语言理解 | 理解用户意图、处理模糊表达 | **基本信任**，但复杂意图需要澄清结构 |

**模型的系统性弱点**（无论模型多强都不会自发改善，skill 必须补偿）：

| 弱点 | 根因 | 表现 | Skill 应做的事 |
|------|------|------|----------------|
| **不知道自己不知道** | 缺乏校准元认知 | 对模糊目标自信地给出确定性回答 | 提供**对齐结构**，强制暴露假设 |
| **无法跨上下文边界** | 有限的上下文窗口 | 长任务后期遗忘早期决策；新会话从零开始 | 提供**状态外化协议**，保障认知连续性 |
| **缺乏完成判定** | 没有"完成"的内在信号 | 要么过早声称完成，要么无限深入 | 提供**退出条件结构**，锚定完成标准 |
| **上下文不自管理** | 不会主动管理自己的上下文窗口 | 大量低价值信息占满上下文 | 提供**上下文纪律**，规定隔离/压缩策略 |
| **目标漂移无感** | 缺乏对目标一致性的持续监控 | 执行中逐渐偏离原始目标，或过度扩展范围 | 提供**对齐检查点**，检测漂移 |
| **干预阈值不稳定** | 缺乏何时该问/何时该做的稳定判断 | 要么每步都问（低效），要么从不问（危险） | 提供**干预启发式**，校准问/做的平衡 |

### 2.2 Skill 的精确职责定义

综合以上分析，auto-goal 的职责可以精确定义为六个字：

> **结构、边界、连续性**

- **结构** — 为模型提供它不会自发创建的认知结构（对齐模板、状态文件格式、决策记录框架）
- **边界** — 标定模型应该暂停的边界（干预阈值、完成判定、范围界限）
- **连续性** — 保障跨上下文、跨会话的认知连续性（状态外化、恢复协议、压缩保护）

**不应做的事**（模型原生能力已覆盖）：
- 不规定如何推理（六字罗盘已经是最轻量的指引，不应更重）
- 不规定如何使用工具（Claude Code 的工具描述本身是足够的引导）
- 不规定如何分解任务（HTN 递归分解是模型原生能力）
- 不规定如何处理错误（模型自带错误分析和重试能力）

### 2.3 "信任但验证"原则

这并非盲目信任模型。而是：

```
信任模型的推理能力 → 不用指令规定如何推理
不信任模型的元认知 → 用结构强制暴露盲点

信任模型解决问题     → 不用指令规定解题步骤
不信任模型判断完成   → 用结构锚定完成标准

信任模型的工具使用   → 不规定何时用什么工具
不信任模型的上下文管理 → 用纪律规定隔离/外化策略
```

**关键洞察**：模型能力会持续增强，但系统性弱点（上下文有限、跨会话失忆、缺乏完成信号）是架构约束，不会因模型变强而消失。Skill 应聚焦在这些**架构约束**上，而非**能力不足**上。

## 3. 优化方向一：验证闭环与完成判定 [最高杠杆]

> "Give Claude a way to verify its work. This is the single highest-leverage thing you can do."
> — Anthropic Claude Code Best Practices

### 3.1 问题本质

当前 auto-goal 有一条优秀的生成式原则："验证 ∝ 风险 — 验证力度匹配错误成本"。但这解决的是"验证多深"的问题，没有解决三个更基本的问题：

1. **验证什么？** — 缺乏从目标到验收标准的推导结构
2. **如何判定"完成"？** — OpenAI 研究发现：模型在判断"已完成"方面比判断"下一步做什么"更容易出错
3. **首轮对齐没有锁定退出条件** — 对齐确认了"做什么"和"怎么做"，但没有确认"做到什么程度算完成"

### 3.2 理论基础

**TOTE 模型（Test-Operate-Test-Exit）** — Miller, Galanter & Pribram 1960：

目标导向行为的原子单位是 TOTE 循环：测试当前状态是否匹配目标 → 不匹配则操作 → 再次测试 → 匹配则退出。关键洞察：**Exit 条件必须在 Test 之前定义，否则循环无法终止。**

映射到 auto-goal：
- Test = 验证当前产出是否满足目标
- Operate = 执行下一步行动
- **Exit = 完成标准** ← 这是当前缺失的

**目标设定理论** — Locke & Latham：

明确且可测量的目标产生的绩效，显著高于模糊的"尽力而为"目标。原因是明确目标提供了四个机制：引导注意力、调动努力、增加坚持性、激发策略开发。**如果完成标准模糊，这四个机制全部失效。**

**OpenAI Agent 最佳实践**：

> "退出条件的设计与目标分解同等重要。多数 Agent 失败来自路由/工具选择错误而非推理错误。"

### 3.3 优化方向

**方向 A：首轮对齐增加"完成的样子"**

当前首轮对齐呈现三项内容：
1. 我的理解 — 复述目标核心意图
2. 计划方向 — 打算怎么做
3. 关键假设 — 不确定的假设

建议增加第四项：

4. **完成标准** — "我认为完成的标志是..."

这一项必须是**可测试的**。不是"实现认证功能"（无法测试），而是"用户能通过 JWT 登录，token 正确签发和验证，测试通过"（可测试）。

对于非代码任务（分析、学习、调研），完成标准可以是：
- "产出包含 X、Y、Z 三个部分"
- "回答了用户提出的三个问题"
- "覆盖了 A、B、C 三个维度的分析"

**方向 B：状态文件中维护"完成检查清单"**

在 state.md 中增加一个结构化的完成检查项：

```markdown
## 完成标准（首轮对齐时锁定）
- [ ] JWT token 生成和验证逻辑实现
- [ ] 认证过滤器集成到 Spring Security 链
- [ ] 单元测试覆盖核心路径
- [ ] 手动测试：login → token → protected endpoint
```

这个清单：
- 在首轮对齐时与用户确认
- 执行过程中逐项勾选
- 提供明确的终止信号：全部勾选 = 完成
- 对恢复场景友好：新 agent 看到清单立即知道哪些已完成、哪些未完成

**方向 C：生成式原则的增强表述**

当前："验证 ∝ 风险"

建议增强为：**"先定义完成的样子，再开始执行。验证力度 ∝ 错误成本。"**

第一句话确保每个目标都有可测试的退出条件。第二句话保持原有的风险匹配逻辑。

### 3.4 为什么这是最高杠杆

- **Anthropic 明确声明**这是"单一最高杠杆操作"
- **解决 G1 + G2 两个差距**（验证闭环 + 完成判定）
- **不增加模型认知负担**：完成标准是对齐的自然产物，不是额外的认知约束
- **强化首轮对齐**：让对齐从"确认理解"升级为"确认理解 + 确认完成标准"
- **利用文件系统**：完成清单写入 state.md，强化跨会话协调层
- **模型不会自发做这件事**：模型会推理、规划、执行，但不会在开始前主动定义"做到什么程度算完成"

## 4. 优化方向二：目标表征与执行架构

### 4.1 状态描述 vs 行动序列 [G4]

**问题本质**：

模型天然产生的"计划"是行动序列："先做 A，再做 B，然后做 C"。这种表征有两个根本缺陷：

1. **脆性**：任何一步意外（A 的结果不如预期）都可能让后续步骤失效
2. **不含判定条件**：行动序列不告诉你"A 做到什么程度算完成"

**PCT（感知控制论）的洞察**：

William Powers 的 Perceptual Control Theory 提出了一个根本不同的行为模型：行为不是由"行动计划"驱动，而是由**"当前感知 vs 期望状态"的差异**驱动。控制系统持续感知当前状态，将其与参考标准（期望状态）比较，通过行动消除差异。

映射到 agent 规划：

```
行动序列式（当前默认）：
  Step 1: 创建 JwtTokenProvider 类
  Step 2: 实现 generateToken 方法
  Step 3: 实现 validateToken 方法
  Step 4: 创建 AuthFilter

状态描述式（PCT 启发）：
  目标状态 1: JwtTokenProvider 存在，能生成和验证 JWT token
  目标状态 2: AuthFilter 存在，集成到 Spring Security 过滤链
  目标状态 3: 所有核心路径有单元测试覆盖
  每个状态有验证方法：编译通过 / 测试通过 / 手动验证
```

**核心差异**：状态描述式计划天然包含退出条件（达到目标状态就退出），天然容错（实现方式灵活，只要达到目标状态），天然可验证（当前状态 vs 目标状态的差距可测量）。

**优化方向**：在规划阶段，引导模型用**期望状态**而非**行动步骤**来描述子目标。这不需要新增硬规则，可以通过 state.md 模板结构来引导：

```markdown
## 子目标（状态描述）
| # | 期望状态 | 验证方式 | 当前状态 | 差距 |
|---|----------|----------|----------|------|
| 1 | JWT 生成/验证可用 | 单测通过 | 未开始 | 全部 |
| 2 | 过滤器集成完成 | 请求能被拦截 | 未开始 | 全部 |
| 3 | 核心路径测试覆盖 | mvn test 通过 | 未开始 | 全部 |
```

**与"只做模型不会自发做的事"的关系**：模型天然产生行动序列，不会自发产生状态描述。这是一个通过**模板结构**（而非过程指令）引导的优化——给模型一个表格结构，它就会用状态描述来填充。

### 4.2 复杂度自适应 [G6]

**问题本质**：

当前 auto-goal 对所有任务走同一条路径。"解释什么是闭包"和"设计分布式认证系统"承受相同的协议开销。这违反了两条理论：

- **双过程理论**（Kahneman）：System 1（快速模式匹配）处理简单/已知任务，System 2（慢速分析）处理复杂/陌生任务。健康的认知系统在两者间动态切换。
- **Ashby 必要多样性反面**：响应的复杂度不应超过必要。对简单任务施加复杂流程是资源浪费。

**但这里有一个微妙的张力**：

v2 分析已经提出了复杂度路由器方案。但如果我们严格遵守"只做模型不会自发做的事"，需要追问：**模型是否天然能判断任务复杂度并自适应？**

答案是：**部分能，但不可靠。** 模型在收到 SKILL.md 中的完整协议后，倾向于对所有任务执行完整协议（因为指令要求如此）。但如果不要求完整协议，模型对简单任务确实会自然采用更轻量的处理。

**优化方向**：不是添加显式的复杂度路由器（增加指令复杂度），而是**修改硬规则的表述使其内含弹性**：

当前规则 1：
> "接收目标后，**必须先向用户呈现理解，等待确认后再执行**。"

优化为：
> "接收目标后，**必须先确认对齐**。简单明确的目标，一句话确认即可；复杂模糊的目标，完整呈现理解、计划方向、关键假设和完成标准。"

这样，对齐是不可跳过的（硬约束），但形式是自适应的（弹性）。模型可以自行判断"一句话确认"还是"完整呈现"——这是模型原生能力覆盖的判断。

### 4.3 持续对齐 vs 一次性对齐 [G5]

**问题本质**：

Clark & Brennan 的 Common Ground Theory（共同基础理论）指出：人类沟通中的共同基础不是一次建立就永久有效的，而是需要**持续维护**的。沟通参与者通过三种手段维护共同基础：

1. **Grounding**（接地）：确认对方理解了自己的意思
2. **Repair**（修复）：当误解出现时主动修正
3. **Monitoring**（监控）：持续检测是否出现了理解偏差

当前 auto-goal 的首轮对齐对应 Grounding，规则 2（"替用户做选择时暂停"）部分对应 Monitoring。但缺少**显式的 Repair 机制**——当执行过程中发现目标理解有偏差时，如何回到对齐状态？

**现实场景**：
- 执行过程中发现用户的目标不可行 → 需要重新对齐目标
- 执行过程中发现更好的方案但偏离原始方向 → 需要确认是否调整
- 用户中途提供新信息改变了上下文 → 需要评估对当前计划的影响

**优化方向**：增加一条生成式原则（或增强现有原则）：

> **"对齐不是一次性事件。发现目标理解偏差时，回到对齐。"**

这比枚举"何时重新对齐"更好——它是一条方向性指引，模型可以自行判断何时触发。

具体的"偏差信号"不需要枚举（模型能感知），但可以在 state.md 模板中提供结构：

```markdown
## 对齐状态
- 上次对齐: 首轮 / Step 12 重新对齐
- 当前置信度: 高 / 中 / 低
- 偏差信号: 无 / [描述]
```

### 4.4 渐进承诺 [补充 BDI 洞察]

**问题本质**：

Bratman 的 BDI 架构强调**意图稳定性**：一旦形成执行计划（意图），不应在每次新信息到来时都推翻它。但也不应僵化——需要定义"何时修正是合理的"。

当前 auto-goal 没有对计划稳定性提供指引。这导致两种极端风险：
- **过度稳定**：即使发现前提错误也继续执行原计划（沉没成本谬误）
- **过度灵活**：每次新发现都重新规划（计划震荡，永远无法深入执行）

**优化方向**：将"卡住时换方向"这条生成式原则扩展为**渐进承诺策略**：

> "承诺当前计划，除非：（1）前提假设被推翻，（2）发现目标本身需要修正，（3）连续三次失败表明方向错误。新信息更新信念，不自动更新计划。"

这是 BDI 的核心洞察：**信念（对世界的理解）和意图（行动计划）应该正交更新**。新信息改变信念，但只有当信念变化推翻了计划的前提假设时，才修改计划。

## 5. 优化方向三：认知连续性与上下文工程

### 5.1 State.md 作为可恢复的世界模型 [G3]

**问题本质**：

Clark & Chalmers 的延展心灵论证：如果一个外部资源以与内部认知相同的功能角色参与认知过程，它就是认知的一部分。state.md 不是"进度日志"，而是 agent 心智模型的外化形式。

当前 state.md 的必备项是："目标（含验收标准）、当前进度、下一步行动、已修改文件列表"。这足以回答"做到哪了"，但不足以回答**"为什么做到这一步"和"此刻的决策上下文是什么"**。

一个新 agent 读到 "Phase 2 完成，Phase 3 进行中" 知道进度，但不知道：
- Phase 2 的哪些发现影响了 Phase 3 的设计？
- 有哪些已确认的约束和假设？
- 用户的偏好和重点是什么？

**理论依据**：

- **延展心灵**：外化质量 = 认知连续性质量。state.md 应该让新 agent 能**重建决策上下文**，而非仅恢复进度
- **Good Regulator Theorem**（控制论）：一个有效的调节器必须包含被调节系统的模型。state.md 就是这个模型
- **Stigmergy**：文件不仅是记录，更是行为触发器

**优化方向**：重新定义 state.md 的设计目标和推荐结构。

设计目标从"记录进度"变为**"让一个全新 agent 在读完 state.md 后，能以 80% 的效率继续工作"**。

推荐结构增强：

```markdown
---
id: auto-goal-{id}
status: in-progress
created: 2026-04-22T10:30:00
last-updated: 2026-04-22T14:15:00
---

## 目标
[用户确认的目标描述 + 完成标准清单]

## 决策上下文
[影响当前执行的关键决策和理由，最多 5 条]
- 选择 JWT 而非 Session 因为用户要求无状态
- Spring Security 过滤链顺序：JWT filter 在 UsernamePassword filter 之前

## 当前状态
[此刻的世界是什么样子]
- Phase 1 完成：JwtTokenProvider 已实现，单测通过
- Phase 2 进行中：AuthFilter 实现到一半
- 已修改文件：[列表]

## 下一步
[紧接着要做的事]

## 未确认假设
[还没有被验证的假设，新 agent 应该优先确认]
- token 过期时间 30 分钟是否合适（未与用户确认）
```

**关键变化**：
1. 增加 **frontmatter 元数据**（机器可读，恢复时快速解析）
2. 增加 **"决策上下文"** 段（保存"为什么"，而非仅保存"做了什么"）
3. 增加 **"未确认假设"** 段（对新 agent 的行动优先级指引）
4. **"为陌生读者而写"** 的原则保留并强化

### 5.2 信息流架构 [Meadows 杠杆点]

**问题本质**：

Donella Meadows 的系统杠杆点理论中，"信息流的结构"是比"参数调整"高几个数量级的杠杆点。映射到 agent 设计：

> 决定 agent 质量的不是 prompt 措辞（参数），而是 agent 在做决策时能看到什么信息（信息流结构）。

当前 auto-goal 的上下文纪律（隔离/压缩/外化）解决了"信息过多"的问题。但没有解决**"关键信息缺失"**的问题——agent 是否在每个关键决策点都看到了必要的信息？

**三类信息流问题**：

| 问题 | 表现 | 当前覆盖 |
|------|------|----------|
| 信息过载 | 上下文被低价值信息填满 | ✅ 隔离/压缩/外化策略 |
| **信息缺失** | 关键决策时缺少必要信息 | ❌ 没有"确保看到 X 再做 Y"的结构 |
| **信息过时** | 依赖过时的假设做决策 | ❌ 没有假设有效期/刷新机制 |

**优化方向**：

不是增加枚举规则"做 X 前先看 Y"（这违反"只做模型不会自发做的事"），而是通过**文件结构**使关键信息自然可见：

1. **state.md 的"未确认假设"段** → 每次读取 state.md 时，未确认假设自然进入视野
2. **decisions.md 的存在性** → 有历史决策时，恢复 agent 自然会先读取（stigmergic 信号）
3. **完成清单在 state.md 顶部** → 优先级最高的信息在最显眼的位置

这就是"让正确行为成为最简路径"——通过文件结构设计，使关键信息在 agent 需要时自然出现，而非依赖 agent 主动去找。

### 5.3 上下文纪律的补充：压缩保护清单

当前 auto-goal 的上下文纪律提到"压缩时必须保留：当前目标、关键决策及理由、已修改文件、未完成待办"。

这是正确的方向，但可以更精确。Anthropic 的 compaction 机制允许用户自定义压缩行为。auto-goal 可以利用这一点。

**优化方向**：在 state.md 中维护一个"压缩保护"段，明确标注哪些信息在上下文压缩时必须保留：

```markdown
## 压缩保护（compaction 时必须保留）
- 目标：[一句话]
- 完成标准：[清单]
- 当前阶段：Phase 2 / Step 3
- 关键决策：JWT + 无状态、过滤链顺序
- 已修改文件：[列表]
- 未确认假设：[列表]
```

这段信息同时服务两个目的：
1. 作为 compaction 的保留指引
2. 作为恢复时的快速概览

## 6. 优化方向四：对齐的持续性与自适应干预

### 6.1 失败分类学：不同失败需要不同响应

**问题本质**：

当前 auto-goal 的"卡住时换方向"是一条优秀的生成式原则。但所有失败都被同等对待——"换方向"。实际上，不同类型的失败需要根本不同的响应：

| 失败类型 | 例子 | 正确响应 | 错误响应 |
|----------|------|----------|----------|
| **工具故障** | 文件不存在、命令报错 | 修正参数/换工具 | 质疑整体方向 |
| **假设错误** | 以为用 Maven 实际用 Gradle | 修正假设，评估对计划的影响 | 仅修复当前步骤 |
| **方向错误** | 优化了错误的瓶颈 | 回到分析阶段重新评估 | 继续优化更多 |
| **目标错误** | 用户要的不是我理解的 | 回到对齐阶段 | 继续执行当前理解 |

**Heidegger 上手/在手的洞察**：

工具故障（breakdown）不仅是需要修复的错误，更是**认知升级的契机**——它暴露了 agent 心智模型与现实之间的差距。"为什么我预期这个文件存在？"这个问题可能揭示了更深层的假设错误。

**优化方向**：不增加枚举规则（模型能判断失败类型），而是增强"卡住时换方向"的表述：

> "卡住时换方向，不换力度。三次失败后质疑前提。**每次意外失败都问：这揭示了我的哪个假设是错的？**"

最后一句是关键增量——它不规定如何处理失败（模型原生能力），但引导模型从失败中**提取认知价值**（模型不会自发做的事）。

### 6.2 反 Scope Creep 机制 [G5 补充]

**问题本质**：

模型有一个微妙的倾向：在执行过程中逐步扩展范围。写认证功能时"顺便"加了日志、"顺便"优化了错误处理、"顺便"重构了相关代码。每一步扩展看起来都合理，但累积起来就是 scope creep。

Claude Code 系统提示明确警告：

> "Don't add features, refactor code, or make 'improvements' beyond what was asked."

当前 auto-goal 的规则 2（"范围超出原始目标描述"时暂停）部分覆盖了这个问题。但 scope creep 的危险在于它是**渐进的**——每一步扩展都不明显"超出范围"，但累积效果显著。

**优化方向**：通过 state.md 的完成标准清单自然防止 scope creep。

如果完成标准是明确的清单，那么任何不在清单上的工作都是 scope creep。模型在准备做"额外工作"时，对照清单就能自我检查。

这不需要新规则——完成标准清单本身就是反 scope creep 的结构性防护。这是"环境结构引导行为"的又一个例子。

### 6.3 干预阈值的自适应 [介入模式增强]

**问题本质**：

当前介入模式是二元的：协作（默认）或全自动。但实际需求是一个**光谱**：

- 新会话开始时：不确定性高，应多确认 → 高干预
- 连续成功几步后：对齐置信度上升 → 降低干预
- 遇到意外时：不确定性回升 → 提高干预
- 用户明确说"你自己决定"时 → 临时降低干预

**Flow 理论的启示**：

Csikszentmihalyi 的 Flow 理论指出，当挑战与技能匹配时人进入心流状态——过多干扰（过度确认）和过少反馈（沉默执行）都破坏 Flow。

**优化方向**：不是显式建模干预阈值（太重），而是在现有规则 2 的"一句话判断"上增加**方向性指引**：

> "如果用户此刻看到我的决策会惊讶 → 暂停询问。**连续成功对齐后可以降低确认频率，遇到意外时重新提高。**"

加粗部分是增量——它给出了干预阈值**动态调节**的方向，但不规定具体规则。模型可以自行判断"连续成功几次"和"何为意外"。

```
  O7 (持续对齐)              ←── 独立
  O8 (渐进承诺)              ←── 独立

P2 层（独立可做，锦上添花）：
  O9, O10, O11 无强依赖
```

### 7.3 实施原则

1. **增量而非重写**：每次只修改 SKILL.md 的一个段落，验证效果后再进入下一个
2. **结构优先于指令**：能通过模板/文件结构解决的，不要用过程指令解决
3. **减法优先于加法**：每增加一行，问"能否通过修改现有行来覆盖"
4. **总行数不增长**：优化后的 SKILL.md 应 ≤ 当前行数（~100 行）。如果增长了，说明方向偏了
5. **可回滚**：每次修改保留 git 历史，效果不佳可回滚

### 7.4 不可动摇的三个核心（红线）

无论如何优化，以下三点不可削弱：

| 核心 | 在优化中的定位 | 如何被优化方向增强 |
|------|---------------|-------------------|
| **交互式澄清** | 硬约束，不可变为可选 | O6 使其弹性化（但不可跳过） |
| **首轮对齐** | 硬约束，不可跳过 | O1 增加完成标准，O6 使形式自适应 |
| **文件系统状态外化** | 硬约束，长任务必须执行 | O2/O4/O5 增强 state.md 的信息质量 |

## 8. 元反思：这份分析自身的局限

### 8.1 已知局限

1. **理论到实践的鸿沟**：跨学科洞察在理论上成立，但在 LLM agent 的实际行为中是否生效，需要实验验证
2. **过度优化风险**：11 个优化方向如果全部实施可能超过"~100 行"的约束。需要取舍
3. **模型依赖性**：生成式原则的有效性依赖模型的推理质量。对 Claude Opus 可能有效，对较弱模型可能不足
4. **基线效应**：当前版本已经相当精炼。进一步优化的边际收益可能递减

### 8.2 验证建议

| 优化方向 | 验证方法 |
|----------|----------|
| O1-O3（完成标准） | 在 5 个不同类型的真实任务中对比"有完成标准 vs 无完成标准"的完成质量 |
| O4-O5（state.md 增强） | 模拟恢复场景：用新会话读取 state.md 后继续任务，对比恢复效率 |
| O6（弹性对齐） | 在 10 个不同复杂度的任务中观察对齐形式是否自然适配 |
| O7-O8（持续对齐+渐进承诺） | 在长任务（>20 步）中观察目标漂移和计划震荡的频率 |

### 8.3 未来方向

随着模型能力增强，auto-goal 应持续"做减法"：

- **短期**（当前模型）：实施 P0 优化，观察效果
- **中期**（下一代模型）：如果模型的元认知能力增强，思考罗盘可能变为冗余 → 评估删除
- **长期**（未来模型）：如果模型原生支持跨会话记忆和自我校准，skill 可能收缩到仅保留"首轮对齐"和"文件协议"两个核心

**终极目标**：auto-goal 的行数趋向于零，但三个核心永远保留——因为它们解决的是**架构约束**（上下文有限、跨会话失忆、用户意图不确定），而非**能力不足**。

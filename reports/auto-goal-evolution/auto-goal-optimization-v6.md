## 2. D1：指令诅咒（The Curse of Instructions）

### 2.1 实证基础

**来源**：ICLR 2025 多指令遵从研究。

**核心发现**：当模型面对 N 条独立指令时，全部遵从的概率近似为：

```
P_all ≈ P_one ^ N
```

其中 P_one 是单条指令的遵从率（对 GPT-4 约 0.85-0.95）。

| 指令数 | 全部遵从概率（P_one=0.9） | 全部遵从概率（P_one=0.85） |
|--------|--------------------------|---------------------------|
| 3 | 73% | 61% |
| 5 | 59% | 44% |
| 7 | 48% | 32% |
| 10 | 35% | 20% |
| 15 | 21% | 9% |
| 20 | 12% | 4% |

**实际上限**：~7±2 条核心指令，超过后遵从率急剧下降。

### 2.2 对 auto-goal 的映射

当前缓存版 SKILL.md（157 行）包含的"指令"清单（模型需要记住并在适当时机执行的行为）：

**硬规则（3 条）**：
1. 首轮对齐三步流程
2. 替用户做选择时暂停（5 个触发条件）
3. 长任务创建状态文件（含触发时机、分层架构、模板结构）

**生成式原则（5 条）**：
4. 先定义完成
5. 承诺当前计划，卡住时换方向
6. 永不空手而归
7. 对齐不是一次性事件
8. 上下文是稀缺资源

**上下文纪律（3 条）**：
9. 隔离策略
10. 压缩策略
11. 外化策略

**经验进化（4 条行为）**：
12. 任务完成时写入经验
13. 应用经验时告知用户
14. 记录验证结果
15. 3+ 有效后提议全局提升

**恢复协议（6 步）**：
16-21. 六个恢复步骤

加上状态文件模板的结构要求、阶段折叠规则、Tier 2 索引维护等隐含指令，实际指令数估计在 **25-30 条**。

按照指令诅咒公式，假设 P_one = 0.9：
```
P_all(25) ≈ 0.9^25 ≈ 7.2%
```

**这意味着模型完全遵从 SKILL.md 所有指令的概率约为 7%。** 这解释了"状态文件不创建"的问题——不是模型"忘了"，而是在 25+ 条指令的注意力竞争中，state file creation 没有赢得足够的注意力权重。

### 2.3 核心洞察

**每条新增指令都是对所有既有指令的"注意力税"。**

这不是说指令无用，而是说：
1. 指令有"预算"——超出预算的指令不仅自己不被执行，还拖累其他指令
2. 结构性执行（工具阻断）不受指令诅咒影响——AskUserQuestion 是工具调用，不是"记住要做的事"
3. 优化方向应该是 **减少指令数、提升每条指令的执行保障**，而非"发现缺失，添加指令"

### 2.4 v2 的验证

回看 v2 的核心洞察——"85% 认知约束 vs Anthropic 98.4% 基础设施"——现在有了实证支持。v2 说的"删除认知约束"本质上就是"减少指令数以降低指令诅咒效应"。v3 的极简化（296→85 行）是正确方向，但 v4-v5 又逐步回涨。

**本轮核心命题：v3 的方向是对的，但需要更精确的理论指导来决定保留什么、删除什么。**

## 3. D2：渐进式披露架构（Progressive Disclosure）

### 3.1 理论基础

**来源**：Anthropic Context Engineering 范式 + 认知负荷理论（Sweller 1988）。

认知负荷理论区分三种负荷：
- **内在负荷**（intrinsic）：任务本身的复杂度，不可消除
- **外在负荷**（extraneous）：不良设计带来的额外负担，应消除
- **关联负荷**（germane）：促进学习/理解的有益负担，应保留

映射到 SKILL.md：
- **内在**：三条硬规则——这是 auto-goal 核心价值，不可消除
- **外在**：所有在当前阶段不需要的信息（如：执行阶段加载恢复协议、创建 state.md 时加载经验进化规则）
- **关联**：当前阶段需要的指导（如：创建 state.md 时加载模板和分层架构说明）

**关键洞察**：当前 SKILL.md 把所有阶段的指令一次性加载，这意味着 **每个阶段都承受了其他阶段的外在负荷**。

### 3.2 对 auto-goal 的映射

Anthropic 的 "Progressive Disclosure" 原则：**不在第一句话就倾倒所有信息，按需逐层展开。** 这正是 Tier 1/Tier 2 分层架构在 state.md 上做的事——同样的原则应该应用到 SKILL.md 本身。

**当前结构**（一次性全量加载）：
```
SKILL.md (157 行) → 全部内容在 skill 触发时加载
```

**目标结构**（渐进式按需加载）：
```
SKILL.md (核心, ~60-80 行)
  → 3 条硬规则（结构性执行）
  → 5 条生成式原则（方向性引导）
  → 加载指令：按需读取 references/

references/
  state-guide.md    → 创建 state.md 时加载（分层架构、模板、阶段折叠）
  experience-guide.md → 任务完成时加载（经验进化协议）
  recovery-guide.md   → 恢复任务时加载（恢复协议、Tier 2 加载策略）
```

### 3.3 预期效果

| 指标 | 当前 | 目标 |
|------|------|------|
| 核心 SKILL.md 指令数 | ~25 条 | ~8 条 |
| 预期全部遵从率 | ~7% | ~43%（P_one=0.9, N=8） |
| 上下文消耗 | 157 行（始终） | 60-80 行 + 按需 |
| 信噪比 | 低（大量当前不需要的内容） | 高（只有当前阶段相关内容） |

### 3.4 与 coding skill 的类比

coding skill 已经在使用这个模式：
```
SKILL.md → 意图路由后按需加载：
  references/implement-guide.md
  references/unit-test-guide.md
  references/code-review-guide.md
  references/code-smells.md
```

auto-goal 应该学习这个模式，而不是把所有内容塞进一个文件。

## 4. D3：WHAT-WHY vs HOW 分离（持久层与易变层）

### 4.1 理论基础

**来源**：适应性脚手架理论（Vygotsky 最近发展区 + 教育心理学）+ v5 N16 三层稳定性。

教育心理学发现 **专家逆转效应（Expertise Reversal Effect）**：对初学者有效的脚手架，对专家反而产生干扰。详细步骤指导帮助新手但限制专家。

映射到 AI：
- **弱模型**（GPT-3.5 级别）：需要详细的 HOW — "先做 X，再做 Y，验证 Z"
- **强模型**（Claude Opus 级别）：只需要 WHAT 和 WHY — "确保完成标准可执行"，HOW 由模型自主决定
- **未来更强模型**：可能连 WHAT 的某些方面也不需要

### 4.2 当前 SKILL.md 的分层审计

| 内容 | 层级 | 持久性 | 模型是否本身会做？ |
|------|------|--------|-------------------|
| "对齐优先于效率" | WHY | 永久 | 不会——模型倾向于效率优先 |
| "用 AskUserQuestion 阻断" | HOW（结构性） | 永久 | 不会——这是工具构造 |
| "分层架构（懒加载）" | HOW | 中期 | 可能——随模型改进 |
| "Phase N: {name} [done\|active\|pending]" | HOW（模板） | 短期 | 很可能——模型能自主设计格式 |
| "条目 >20 条时合并相似" | HOW（细节） | 短期 | 几乎确定——常识性判断 |
| "压缩时必须保留：当前目标..." | HOW（清单） | 中期 | 可能——但遗漏风险高 |

### 4.3 分离原则

**WHAT（保留在 SKILL.md 核心）**：
- 完成什么：目标对齐、用户确认、状态外化
- 为什么：对齐优先于效率、上下文是稀缺资源

**WHY（保留在 SKILL.md 核心）**：
- 为什么要暂停：模型最危险的特征是自信地做错事
- 为什么要外化：让全新 agent 能继续

**HOW（移入 references 或删除）**：
- 具体模板格式
- 具体阈值（>20 条、3+ 有效、≤40 行）
- 具体步骤序列
- 常识性判断（合并相似条目）

### 4.4 实际含义

**现在删除的 HOW**不会消失——它们从"显式指令"变为"模型原生能力"。如果某个 HOW 对当前模型仍然必要（模型不会自发做），就保留在 references 中按需加载。如果模型已经能自发做到，就彻底删除。

这实现了用户的核心约束：**"信任模型原生能力，只做模型不会自发做的事"**——不是一次性判断，而是持续的评估和退化。

## 5. D4：注意力经济学（The 20% Test）

### 5.1 理论基础

**来源**：满意化理论（Simon 1956）+ 生态理性（Gigerenzer 2007）。

Herbert Simon 的核心洞察：在有限理性下，**"足够好"优于"最优"**。每次追求完美都有机会成本。

Gerd Gigerenzer 更进一步：在不确定环境下，**简单启发式（3-5 条规则）的表现往往优于复杂策略**。原因：复杂策略过拟合已知情况，简单策略对未知情况更鲁棒。

### 5.2 20% 测试

每条指令都应该通过这个测试：

> **这条指令在 ≥20% 的 auto-goal 调用中会改善结果吗？**

如果答案是"否"，这条指令的 **注意力税**（降低其他指令的遵从率）超过了它偶尔带来的价值。

### 5.3 当前 SKILL.md 的 20% 审计

| 指令/内容 | 适用频率 | 通过 20% 测试？ |
|----------|---------|----------------|
| 首轮对齐 | 100%（每次调用） | **YES** |
| 暂停替用户做选择 | ~60%（多数任务有选择点） | **YES** |
| 创建状态文件 | ~40%（>10 步的任务） | **YES** |
| 验证 ∝ 风险 | ~80%（几乎所有执行任务） | **YES** |
| 卡住时换方向 | ~30%（遇到困难时） | **YES** |
| 永不空手而归 | ~20%（任务被中断时） | **边界** |
| 对齐不是一次性事件 | ~25%（长任务中） | **YES** |
| 上下文是稀缺资源 | ~50%（长任务） | **YES** |
| 分层架构详细说明 | ~15%（创建 state.md 时） | **NO** → 移入 references |
| 经验进化全部规则 | ~5%（任务完成时） | **NO** → 移入 references |
| 恢复协议 | ~10%（恢复中断任务时） | **NO** → 移入 references |
| 上下文纪律表格 | ~30%（长任务） | **YES** |
| 阶段折叠模板 | ~15%（创建 state.md 时） | **NO** → 移入 references |
| Tier 2 索引维护 | ~15%（创建 state.md 时） | **NO** → 移入 references |

### 5.4 结论

通过 20% 测试的核心指令约 **8-9 条**。恰好在认知科学建议的 7±2 范围内。

未通过的内容不是"无用"，而是"不应该在每次调用时占用注意力预算"。它们应该被移到 references 中，在需要时按需加载。

## 6. D5：结构性执行的泛化

### 6.1 观察

当前三条硬规则的执行保障极不均匀：

| 规则 | 执行机制 | 抗指令诅咒 | 实际遵从 |
|------|---------|-----------|---------|
| Rule 1（首轮对齐） | AskUserQuestion 工具阻断 | **免疫** — 工具调用不是"记住的事" | 高 |
| Rule 2（暂停做选择） | 文本指令 + 触发条件列表 | **脆弱** — 依赖模型"记住"5个触发条件 | 中 |
| Rule 3（创建状态文件） | 文本指令 + 触发时机 | **脆弱** — 依赖模型"记住"触发时机 | 低（用户报告的问题） |

**Rule 1 有效是因为 AskUserQuestion 是一个结构性门控——不调用这个工具就无法完成对齐。** 这不受指令诅咒影响，因为它不是模型需要"记住的事"，而是工作流中的必经之路。

### 6.2 泛化原则

> **能转化为工具/结构的行为，就不应该停留在文本指令层。**

这是 N7（"验证不是指令，是工具构造"）的泛化版本。N7 只关注验证，这里扩展到所有关键行为。

### 6.3 可泛化的候选

| 行为 | 当前层 | 可能的结构化方案 |
|------|-------|----------------|
| 创建 state.md | 指令 | 在 alignment AskUserQuestion 返回后，提示"下一步：创建 state.md"——嵌入工作流而非依赖记忆 |
| 暂停做选择 | 指令 | 难以完全结构化——决策点识别本身需要推理。但可以降低触发条件数量（5→2-3） |
| 经验写入 | 指令 | 任务完成检查清单中嵌入"回顾经验" |
| 恢复协议 | 指令 | 检测到 `.tasks/` 目录存在时自动触发——stigmergic 信号（v5 N9） |

### 6.4 结构化预算

不是所有行为都值得结构化。结构化有成本（增加工具调用、增加流程复杂度）。只有满足以下条件的行为才值得：
1. **高影响**：不执行会导致显著后果
2. **低自发率**：模型不太会自主做到
3. **可结构化**：存在工具/流程可以嵌入

Rule 3（state file）满足所有三条。Rule 2（暂停选择）满足 1 和 2 但 3 较弱。经验写入满足 2 但不满足 1（不写经验的后果较轻）。

## 7. D6：自消减 Skill（Self-Diminishing Skill）

### 7.1 理论基础

**来源**：适应性脚手架（Vygotsky）+ 专家逆转效应 + 用户核心约束（"信任模型原生能力"）。

Vygotsky 的脚手架理论：**脚手架应该随着学习者能力增长而逐步撤除**。如果脚手架永远不撤，它就变成了拐杖。

映射到 AI 模型：随着模型能力代际提升（GPT-3.5 → GPT-4 → Claude Opus → 未来模型），曾经需要的指令会变得多余。多余的指令不是"无害"的——根据指令诅咒，它们积极地伤害其他指令的遵从率。

### 7.2 当前问题

auto-goal 经过 5 轮优化，积累了针对 **当前模型能力** 的指令。但没有机制来回答：

> **这条指令是否仍然必要？还是模型已经能自主做到了？**

例如：
- "承诺当前计划，卡住时换方向" — 强模型可能已经自然做到了
- "探索性工作用 sub-agent 隔离" — 强模型可能已经学会了上下文管理
- "三次失败后质疑前提" — 强模型可能有更好的自省机制

### 7.3 自消减机制设计

**经验进化系统已经提供了信号基础。** 如果某条生成式原则在多个任务中都被模型自然遵循（不需要经验提醒），那么这条原则可能已经被模型内化了。

**自消减流程**：
1. 经验系统跟踪：哪些行为模型自发做到了？哪些需要 skill 提醒？
2. 连续 N 个任务中模型自发做到的行为 → 标记为"候选退化"
3. 通知用户："原则 X 在最近 N 个任务中都自发被遵循，建议移入 references 或删除"
4. 用户确认后执行退化

**这是经验进化的逆向操作**：经验进化是"发现模式 → 固化为经验"，自消减是"发现冗余 → 退化为按需加载或删除"。

### 7.4 与 v5 N16 的关系

v5 N16 提出了"三层稳定性"：永久层、长期层、衰减层。自消减机制是 N16 的具体实现方案：
- **永久层**：结构性执行的硬规则（Rule 1 的 AskUserQuestion）——不衰减
- **长期层**：生成式原则——缓慢衰减，需要证据支持
- **衰减层**：HOW 层指令——模型能力提升后自然退化

## 8. 综合：Auto-Goal v7 北极星设计

### 8.1 设计哲学转变

| 维度 | v5 思维 | v6 思维 |
|------|---------|---------|
| 优化方向 | 发现缺失 → 添加指令 | 指令是税 → 只保留高 ROI 的 |
| SKILL.md 角色 | 完整的认知协议 | **最小可行脚手架** + 按需加载 |
| 复杂度态度 | "这个功能有价值所以加进去" | "这个功能的注意力税超过其价值了吗？" |
| 模型关系 | 引导模型 | 信任模型，只补盲区 |
| 时间视角 | 为当前模型优化 | 为模型持续增强而设计退化路径 |

### 8.2 核心架构：7±2 模型

**SKILL.md 核心**（~60-80 行，≤9 条指令）：

```markdown
# Auto Goal Skill
```

## 10. 元反思

### 10.1 优化的悖论

本轮分析的核心发现是：**"优化 auto-goal" 这个活动本身可能是问题的一部分**。

每轮优化都发现新的有价值方向，每个方向都有充分的理论支撑和实际需要。但累积效果是 SKILL.md 越来越复杂，指令诅咒越来越严重。

**这就是 Second System Effect（Brooks 1975）在 AI skill 设计中的体现**：第一版往往太简单，但第二版往往过度补偿，变得过于复杂。

### 10.2 走出悖论

出路不是"停止优化"，而是 **改变优化的度量标准**：

- **旧标准**：auto-goal 覆盖了多少场景？处理了多少边界情况？
- **新标准**：auto-goal 的核心指令遵从率是多少？每条指令的 ROI 是多少？

**一句话原则**：如果你不能用 8 条指令说清楚 auto-goal 的核心，你可能还不够理解它。

### 10.3 最终判断

auto-goal 的下一步不是"找到更多要加的东西"，而是：

1. **承认指令诅咒是物理定律**，不是可以靠"更好的指令"克服的
2. **接受 7±2 的预算约束**，像管理代码行数一样管理指令数
3. **用架构（渐进式披露）解决复杂度问题**，而非用更多指令
4. **为退化而设计**，而非为永恒而设计

这恰好呼应了用户的核心约束：**信任模型原生能力，只做模型不会自发做的事**。未来的模型会自发做到越来越多的事。auto-goal 的最终形态，可能只剩下三个结构性门控和一句话的核心信念。

## 1. 分析方法与研究基础

## 2. 核心发现：处方悖论（The Prescription Paradox）

> 这是本分析中最深层的架构性洞察。如果只读一节，请读这节。

### 2.1 发现

Claude Code 架构论文揭示了一个惊人的比例：**98.4% 是运维基础设施（上下文管理、工具路由、权限执行、恢复逻辑），仅 1.6% 是 AI 决策逻辑。** 设计论点是：

> "Advanced foundation models need a rich, Unix-like operational environment, not cognitive constraints. Trust the model to reason; engineer the harness to enforce boundaries, manage context, and ensure safety."

现在看 auto-goal 的构成：

| 类别 | 占比（估算） | 内容 |
|------|-------------|------|
| **认知约束**（如何思考、何时检查、考虑什么） | ~85% | OODA 循环详细步骤、对齐门控三问、偏差检测规则、深度调节信号、推理模式选择、验证精度分级… |
| **操作结构**（文件格式、状态模板、协调协议） | ~15% | 记忆架构、state.md 结构、恢复验证 |

**这与 Claude Code 的设计哲学形成了精确的反比。**

### 2.2 为什么这是一个悖论

auto-goal 的认知约束设计是**出于正确的动机**——LLM 确实会过度自信、目标漂移、假设累积。但 Claude Code 团队的实证发现表明：**用过程指令约束模型推理，效果不如用环境结构引导模型行为。**

类比：
- **处方式**（当前 auto-goal）：告诉司机"转弯前检查后视镜、打转向灯、减速到 30km/h、确认盲区…"
- **环境式**（Claude Code 哲学）：设计道路弯道使司机自然减速（窄路、路面纹理变化、视觉引导线）

处方式在司机（模型）完全遵守时有效。但：
1. **指令竞争**：每条认知约束都消耗模型的"注意力带宽"。297 行指令中，模型在每步决策时能有效激活的不超过 5-7 条（认知负荷理论的 chunk 限制）
2. **创造力压制**：过多的"应该如何思考"限制了模型发挥其原生推理优势的空间
3. **遵从退化**：在长会话中，随着上下文压力增大，模型对详细指令的遵从度会逐步下降

### 2.3 处方悖论的解决方向

**不是删除认知约束，而是将认知约束转化为环境结构。**

| 当前（处方式） | 优化方向（环境式） |
|---------------|-------------------|
| "每个方向性决策前自问三个问题…" | 设计一个 `decision-checkpoint.md` 模板，方向性决策时填写模板并呈现用户 |
| "追踪未经用户确认的假设数量，>3 个时暂停" | 在 state.md 中维护 `## 未确认假设` 列表，列表长度自然触发审查 |
| "深度调节 1-4，升级信号：偏离/新复杂度/验证失败" | 在 state.md 开头维护 `Depth: 2` 字段 + `## 深度调节日志`，使深度变化可追踪 |
| "FACT/INFER/ASSUME 分级" | 在 observations.md 中用结构化前缀 `[FACT]` `[INFER]` `[ASSUME]` 标记，使分级成为书写格式而非思维要求 |

**核心原则：让正确行为成为最简路径（path of least resistance），而非最规范路径。**

### 2.4 与三个不可妥协核心的关系

处方悖论的解决方向完全兼容三个核心：

1. **交互式澄清** — 不变。但触发条件可以从"检查 8 条触发器"简化为"未确认假设列表 ≥ 3 → 澄清"
2. **无条件首轮对齐** — 不变。但呈现格式可以结构化为模板而非过程描述
3. **文件系统跨会话协调** — **增强**。更多认知约束外化到文件结构中，实际上强化了协调层

### 2.5 理论支撑汇总

| 理论 | 支撑点 |
|------|--------|
| **延展心灵** (Clark & Chalmers) | 外部结构不是记忆的备份，而是认知过程的一部分。外化到文件中的检查清单 IS 认知，不是认知的副产品 |
| **防错设计 (Poka-yoke)** (Anthropic ACI) | 通过结构消除错误可能性，而非依赖提示。模板约束 > 过程指令 |
| **情境认知** (Lave, Suchman) | 计划是行动的资源，不是程序。真正的行动总是情境化的——适应环境实际呈现的内容 |
| **生态理性** (Gigerenzer) | 在不确定环境中，简单启发式往往优于复杂优化。更少的规则 + 更好的结构 > 更多的规则 |
| **认知负荷** (Sweller) | 每条无关指令都消耗工作记忆。指令的最优数量不是"越多越全"，而是"恰好足够" |

## 3. 架构层优化方向

### 3.1 复杂度路由器：从单一流水线到自适应路径 [P0]

**问题根因**：auto-goal 的所有任务走同一条 OODA 路径。"解释什么是闭包"和"设计分布式认证系统"消耗相同的协议开销。这违反了 Ashby 必要多样性定律的**反面**——响应的复杂度不应**超过**任务所需的复杂度。

**深层洞察**：这不仅是效率问题，更是**注意力分配**问题。对简单任务施加完整 OODA，不是"多做了一点"，而是**稀释了模型对核心任务的注意力**。认知负荷理论表明，外在负荷（不必要的流程开销）直接挤占生成性负荷（真正有价值的思考）。

**优化方向**：

```
接收目标 → 快速复杂度感知（≤3 个信号，不消耗大量上下文）
  │
  ├─ 🟢 Clear 域 + EXPLICIT 意图 → 轻量路径
  │    首轮对齐（精简版：一句话确认）→ 直接执行 → 验证
  │
  ├─ 🟡 Complicated 域 或 ALIGNED 意图 → 标准路径
  │    首轮对齐 → 规划 → 执行循环 → 验证
  │
  └─ 🔴 Complex/Chaotic 域 或 GUESSING 意图 → 完整路径
       首轮对齐（含澄清）→ 完整 OODA → 试探/执行 → 深度验证
```

**关键约束**：
- 路由判断本身必须轻量（<50 tokens 的内部推理）
- 路由可升级不可降级：执行中发现复杂度超预期 → 自动升级到更重路径
- **首轮对齐在所有路径中保留**，但精简版只需一句话确认而非完整呈现

**与双过程理论的映射**：轻量路径 = System 1（快速、模式匹配），完整路径 = System 2（慢速、审慎分析）。切换信号 = 惊讶、困难、不确定性。

### 3.2 渐进式指令披露：从全量加载到按需展开 [P1]

**问题根因**：当前 SKILL.md 约 297 行全量加载到上下文第 4 层（Project Context）。对简单任务，其中约 60% 的内容（韧性机制详细规则、反模式完整表、记忆架构细节）完全不会被用到。

**理论支撑**：Anthropic 官方数据显示渐进式披露可节省 47%-85% 的 token。CLAUDE.md 黄金法则："删掉它会导致犯错吗？不会就删。"

**优化方向**：

**核心层（始终加载，目标 ~100 行）**：
- 核心信念 + 六字原则
- 执行循环（精简骨架：域路由 + 首轮对齐 + OODA 概要）
- 澄清机制（Must-Ask 触发器）
- 策略工具箱（四策略概要）
- 上下文工程核心纪律
- 记忆架构骨架（文件路径 + 恢复入口）

**扩展层（按条件激活）**：
- 韧性机制全文（Reflect-then-Retry 详细流程、降级层级）→ 验证失败或深度 ≥ 3 时激活
- 反模式详细表 → 检测到疑似反模式行为时作为 reminder 注入
- 记忆架构详细结构 → 长任务（预估 > 10 步）时激活
- 完整 OODA 机制描述 → Complex/Chaotic 域路由时激活

**实现考量**：
- 扩展内容可放在独立文件中，通过注释路径引用（`<!-- 详见 resilience-details.md -->`）
- 或使用条件加载注释（如果 skill 系统支持的话）
- **风险**：分层本身增加复杂度。需评估实际 token 节省量（预估：简单任务节省 ~150 行 ≈ 2000-3000 tokens）

### 3.3 缓存友好布局：静态在前，动态在后 [P2]

**问题根因**：Claude Code 的六层 Prompt 栈中，Skills 处于第 4 层。在该层内部，内容排列顺序直接影响 prompt cache 命中率。当前 SKILL.md 未考虑这一点。

**优化方向**：重排内容从最稳定到最动态：

1. 核心信念 + 六字原则（永不变）
2. 澄清机制（极少变动）
3. 策略工具箱（半稳定）
4. 执行循环骨架（半稳定）
5. 上下文工程（半稳定）
6. 介入模式（可能按任务切换）
7. 韧性机制（参考性）
8. 记忆架构（仅长任务使用）
9. 反模式表（最低频引用）

**预期收益**：对同一项目的连续 auto-goal 调用，前 4-5 层内容命中 prompt cache，减少延迟和成本。

### 3.4 可生存系统模型（VSM）映射：补全缺失的 System 4 [P1]

**问题根因**：Beer 的可生存系统模型包含五个必要子系统。映射到 auto-goal：

| VSM 子系统 | 功能 | auto-goal 对应 | 完备性 |
|-----------|------|---------------|--------|
| **System 1** | 执行 | Execute 策略、Act 阶段 | ✅ 完整 |
| **System 2** | 协调 | sub-agent 隔离、上下文工程 | ✅ 基本完整 |
| **System 3** | 运营控制/审计 | 熔断器、验证精度分级 | ✅ 完整 |
| **System 4** | 环境扫描（外部变化） | ⚠️ **弱信号检测（仅内部扫描）** | ❌ 缺失外部扫描 |
| **System 5** | 身份/政策 | 核心信念、六字原则、介入模式 | ✅ 完整 |

**缺失**：System 4 负责扫描**外部环境变化**——在 auto-goal 语境中，这意味着：
- 用户的操作环境发生了什么变化？（新文件出现、git 状态变化、外部依赖更新）
- 用户是否在并行做其他事？（文件被外部修改）
- 会话的时间/上下文约束发生了什么变化？（接近上下文限制、长时间运行）

当前弱信号检测只扫描**内部信号**（进展减速、假设累积、复杂度上升），不扫描**外部信号**。

**优化方向**：在 OODA 的 Sense 阶段增加环境感知维度：
- 内部信号（现有）：进展、假设、复杂度
- **外部信号（新增）**：文件变化（git status）、工具可用性、上下文剩余空间、会话时长

## 4. 认知模型层优化方向

### 4.1 Orient 深化：从检查点到认知引擎 [P0]

**问题根因**：Boyd 的 OODA 循环中，Orient 是**最关键**的阶段——它不是一个"检查步骤"，而是持续构建和更新心智模型的**认知引擎**。Boyd 的关键洞察是 Orient 包含 **Implicit Guidance and Control (IGC)**——当 Orient 足够强时，可以**跳过**显式的 Decide 阶段直接 Act。

当前 auto-goal 的 Orient 仅是两个问题："距目标多远？心智模型需要更新吗？"这将一个应该最丰富的阶段压缩成了最贫乏的检查点。

**优化方向**：将 Orient 从问题升级为结构化过程：

```
Orient（每个循环）：
  1. 信息整合 — 新观察 + 已有信念 → 更新世界模型
  2. 差距评估 — 当前状态 vs 目标状态 → 识别关键差距
  3. 模式匹配 — 这像不像我见过的模式？（IGC 启动点）
     → 模式命中 + 高置信度 → 快速路径（System 1）
     → 模式不匹配或低置信度 → 深度路径（System 2）
  4. 假设审计 — 哪些假设需要更新？哪些被新信息推翻？
```

**关键：Orient 的强度决定了整个循环的质量。** 弱 Orient 产生错误的 Decide 和无效的 Act。投资 Orient 是最高杠杆的优化。

**理论支撑**：Boyd 的原始论文强调 Orient 包含五个输入——文化传统、新信息、以往经验、遗传因素、分析/综合。映射到 agent：
- 文化传统 → 用户的领域惯例和偏好（需要 user model）
- 新信息 → 最新的 Observe 结果
- 以往经验 → reflections.md 中的历史反思
- 分析/综合 → 当前推理过程

### 4.2 BDI 分离：信念、欲求、意图的正交管理 [P1]

**问题根因**：当前 auto-goal 隐式混合了三种认知状态——"我知道什么"（信念）、"用户要什么"（欲求）、"我打算做什么"（意图）。这导致：
- 新信息更新信念时，可能不必要地动摇意图（计划震荡）
- 用户目标细化时，可能不必要地推翻已执行的计划（过度重启）
- 三种状态混在 state.md 中，恢复时无法选择性更新

**理论支撑**：Bratman 的 BDI 架构正是为解决这个问题而设计的。核心洞察：
- **信念应自由更新**——每步观察都可能改变对环境的理解
- **意图应保持稳定**——承诺当前计划，除非有充分理由修正（避免频繁切换的消耗）
- **欲求可以冲突**——用户可能同时想要"快速完成"和"高质量"，agent 需要通过审议选择

**优化方向**：在 state.md 中显式分离三层：

```markdown
## Beliefs（持续更新）
- [FACT] 项目使用 Spring Boot 3.2 + Java 21
- [INFER] 用户偏好函数式风格（基于已有代码观察）
- [ASSUME] 测试框架是 JUnit 5（未确认）

## Desires（用户目标，对齐后锁定）
- 核心：实现用户认证模块
- 约束：使用 JWT，不引入新依赖
- 偏好：简洁 > 完备

## Intentions（当前计划，承诺但可修正）
- Phase 1: 实现 token 生成和验证 ← 当前
- Phase 2: 实现认证过滤器
- Phase 3: 集成测试
- 修正触发条件：Phase 1 验证失败 / 用户纠正 Desires
```

**关键机制**：
- Beliefs 更新不自动触发 Intentions 修改（除非推翻 Intentions 的前提假设）
- Desires 修改（用户纠正方向）→ 重新审议 Intentions
- Intentions 修改需要记录到 decisions.md（可追溯）

### 4.3 注意力分配：非均匀深度 [P1]

**问题根因**：当前深度调节（1-4）是**全局**的——对整个任务设定一个深度级别。但同一任务的不同部分可能需要不同深度。这违反了认知经济原则（有限理性 + satisficing）。

**类比**：象棋大师在开局（已知理论，System 1）、中局（复杂计算，System 2）、残局（精确技术，System 1）之间动态切换深度。他们不会对整盘棋用同一个思考强度。

**优化方向**：引入**局部深度**概念——任务的不同组件可以有不同的深度分配：

| 组件特征 | 分配深度 | 理由 |
|----------|---------|------|
| 已知模式、已有最佳实践 | 浅（快速执行 + 轻量验证） | 模式匹配置信度高时，深度分析是浪费 |
| 核心路径、高风险操作 | 深（完整分析 + 深度验证） | 错误成本高，值得投资 |
| 探索性工作、信息收集 | 中等（适度分析 + 标准验证） | 过早深入可能方向错误 |
| 收尾工作、边缘清理 | 浅（快速执行 + 微验证） | 主要价值已交付，边际收益递减 |

**实现思路**：在规划阶段，为每个子任务标注深度预算。执行时按预算分配注意力，但保留动态调整能力。

### 4.4 时间感知：引入节奏意识 [P2]

**问题根因**：auto-goal 在一个"无时间"的空间中运作——它不感知：
- 会话已运行多长时间
- 上下文窗口剩余多少空间
- 用户是否在等待（交互延迟）
- 是否存在时间约束（截止日期）
- 当前进度的速度趋势

Boyd 的 OODA 强调**节奏（tempo）**——不是更快，而是让自己的决策节奏与环境节奏匹配。缺乏时间感知的 agent 无法管理节奏。

**优化方向**：在 state.md 中增加 tempo 维度：

```markdown
## Tempo
- 会话步数: 15 / 估计总步数: ~30
- 上下文压力: 中（已触发一次 compaction）
- 进度速度: 正常（Phase 1 完成耗时 8 步，符合预期）
- 时间约束: 无显式约束
- 节奏调整: 保持当前节奏
```

**关键机制**：
- 上下文压力高时 → 增加外化频率、压缩已完成阶段、考虑降级交付
- 进度减速时 → 升级深度或切换策略（而非盲目加速）
- 接近估计总步数的 80% 时 → 评估是否需要降级到 L1/L2 交付

### 4.5 用户模型：适应性交互 [P2]

**问题根因**：auto-goal 对所有用户使用同一种交互方式。但不同用户需要不同的协作姿态：
- 专家用户：需要速度和自主性，过多确认是打扰
- 新手用户：需要解释和引导，沉默执行是不透明
- 压力下的用户：需要快速可用的结果，完美主义是障碍
- 探索中的用户：需要宽泛的探索，过早收敛是限制

**理论支撑**：认知科学中的 Theory of Mind——理解他人心智状态的能力。一个不能适应用户状态的 agent 就像一个不看观众反应的演讲者。

**优化方向**：不是显式建模用户画像（太重），而是通过**信号检测**动态适应：

| 信号 | 推断 | 适应 |
|------|------|------|
| 用户回复简短、直接 | 偏好效率 | 减少解释，增加自主行动 |
| 用户追问"为什么" | 偏好理解 | 增加解释，展示推理过程 |
| 用户催促"快点"/"直接做" | 时间压力 | 减少确认频率，快速交付 |
| 用户说"让我想想"/"等一下" | 需要思考空间 | 暂停推进，等待明确指示 |
| 用户纠正方向 | 对齐偏差 | 增加确认频率，降低自主度 |

**实现思路**：不需要写入 state.md，而是在每次用户交互后隐式更新交互姿态。这是一种 System 1 式的动态适应，不需要显式规则。

## 5. 协调层优化方向

### 5.1 Stigmergic 协调协议：从状态存储到环境协调 [P0]

**问题根因**：当前 `.tasks/auto-goal-{id}/` 是**状态存储**——记录 agent 的内部状态供自己或后续 agent 读取。但在 stigmergy（蚁群协调理论）中，环境不仅存储信息，更**触发行为**。蚁群不通过直接通信协调，而是通过修改环境（信息素）来影响后续 agent 的行为。

**当前设计**的局限：
- 文件是"被动记录"——需要 agent 主动决定读取
- 文件格式面向"理解"——需要 agent 解析含义后决定行为
- 缺少"行为触发"机制——文件的存在/状态不能直接驱动 agent 行为

**优化方向**：将文件系统从"记忆仓库"升级为"协调协议"：

**1. 文件存在即信号（Presence as Signal）**

```
.tasks/auto-goal-{id}/
├── state.md              # 始终存在 — agent 活跃信号
├── BLOCKED.md            # 仅在阻塞时存在 — 需要人工介入的信号
├── NEEDS_CLARIFICATION   # 仅在需要澄清时存在 — 空文件，纯信号
├── decisions.md          # 有内容时存在 — 有关键决策待审阅
├── observations.md       # 有内容时存在
└── reflections.md        # 有内容时存在 — 有失败需要复盘
```

一个新 agent 通过 Glob `.tasks/*/BLOCKED.md` 就能知道哪些任务被阻塞，无需读取任何文件内容。

**2. 结构化 frontmatter 实现机器可读**

```markdown
---
id: auto-goal-20260422-auth
status: in-progress
phase: execute
depth: 2
domain: complicated
alignment: aligned
created: 2026-04-22T10:30:00
last-updated: 2026-04-22T11:45:00
unconfirmed-assumptions: 2
modified-files:
  - src/auth/JwtTokenProvider.java
  - src/auth/AuthFilter.java
---
```

恢复 agent 读取 frontmatter 即可重建上下文，无需解析自由文本。

**3. 命名约定作为路由规则**

| 文件名模式 | 语义 | 恢复行为 |
|-----------|------|----------|
| `state.md` 中 `status: blocked` | 任务被阻塞 | 展示阻塞原因，询问用户 |
| `state.md` 中 `phase: clarify` | 等待澄清 | 直接进入澄清流程 |
| `state.md` 中 `phase: execute` | 执行中被中断 | 验证产出 → 继续执行 |
| `reflections.md` 存在且非空 | 有历史失败 | 先读取反思 → 避免重蹈覆辙 |

**理论支撑**：
- **Stigmergy** (Grassé)：间接协调——修改环境来影响后续行为者。文件系统是 agent 的"信息素"
- **延展心灵** (Clark & Chalmers)：文件不是认知的记录，是认知的组成部分。设计文件结构就是设计认知过程
- **Anthropic 设计哲学**：trust the model, engineer the harness。文件协议就是 harness 的一部分

### 5.2 环境感知协议：感知操作环境的 affordance [P1]

**问题根因**：auto-goal 假设一个通用的执行环境，但实际环境差异巨大：
- 有些项目有完整测试套件（验证成本低），有些没有（验证需要手动确认）
- 有些环境有 MCP 服务器可用（能力扩展），有些只有基础工具
- 有些代码库有 CLAUDE.md（上下文丰富），有些是全新项目
- 项目语言、框架、构建工具各不相同

缺乏环境感知的 agent 就像在黑暗中行动——不知道自己有什么工具可用、环境支持什么操作。

**优化方向**：在首轮分析阶段增加**环境扫描**（轻量，~3 步）：

```
环境扫描（首轮分析的一部分）：
  1. 项目感知 — CLAUDE.md 存在？语言/框架？构建工具？测试框架？
  2. 工具感知 — 可用的 MCP 服务器？特殊工具？
  3. 历史感知 — .tasks/ 下有历史任务？git log 显示什么？
  → 输出：环境画像（写入 state.md 的 Environment 部分）
```

**关键约束**：环境扫描必须轻量。不是穷举环境信息，而是感知**对当前任务有影响的**环境特征。Gigerenzer 的生态理性：用最少的线索做出足够好的判断。

### 5.3 通信协议：进度可见性 [P2]

**问题根因**：auto-goal 没有规定 agent 如何向用户通信执行进度。这导致两个极端：
- 沉默执行：用户不知道 agent 在做什么，焦虑感上升
- 过度报告：每步都解释推理过程，信噪比极低

**理论支撑**：
- **HRO 对运营的敏感性**：组织必须实时了解一线状态
- **Flow 理论的即时反馈条件**：持续的反馈是维持 flow 状态的必要条件
- **Anthropic 最佳实践的透明度原则**：展示 agent 的规划步骤

**优化方向**：引入**通信节奏**规则（简单，不过度规范）：

| 事件 | 通信方式 |
|------|----------|
| 阶段开始 | 一句话简报："开始 Phase 2: 实现认证过滤器" |
| 阶段完成 | 摘要 + 验证结果："Phase 2 完成。AuthFilter 已实现，测试通过 ✓" |
| 遇到意外 | 透明报告 + 选项："遇到 X，我打算 A/B/C，建议 A 因为..." |
| 方向性决策 | 呈现 + 等待确认（对齐门控） |
| 长时间执行中 | 定期心跳（可选）："正在执行中，预计还需 ~5 步" |

**核心原则**：通信量 ∝ 不确定性 + 用户等待感知。确定性高、执行顺利时少说；不确定性高、需要决策时多说。

## 6. 韧性与适应层优化方向

### 6.1 元稳定性：在结构与灵活之间动态平衡 [P1]

**问题根因**：当前 auto-goal 有大量规则（OODA 7 步、对齐门控 3 问、Must-Ask 5 条、Should-Ask 3 条、反模式 8 项…）。规则越多，系统越"有序"但也越"脆性"——面对规则未覆盖的情况时，模型不知如何处理。

**理论支撑**：
- **复杂适应系统（CAS）**：系统在"边缘混沌"——秩序与混乱的临界点——达到最优适应性。过多秩序 = 脆性；过少秩序 = 混乱
- **生态理性** (Gigerenzer)：在不确定环境中，简单启发式往往优于复杂优化模型。原因：复杂模型过拟合已知情况，简单规则在未知情况中更鲁棒
- **必要多样性反面**：控制器的规则不应超过必要。多余规则是认知负债

**优化方向**：**规则精简 + 生成式原则**

当前的枚举式规则（"不要做 X、不要做 Y、不要做 Z"）可以替换为更少的**生成式原则**——能自行推导出具体行为的高层原则。

示例：

| 枚举式（当前） | 生成式（优化方向） |
|---------------|-------------------|
| "偏差累积检测：追踪未确认假设数量，>3 暂停" + "对齐门控三问" + "意图 GUESSING 必须问" + "Must-Ask 5 触发器" | **"在替用户做选择时，必须暂停确认。"** （一条规则，生成以上所有行为） |
| "微验证/标准验证/深度验证 三级" + "验证精度匹配风险级别" | **"验证投入 ∝ 错误成本。"** （一条规则，自动校准验证深度） |
| "同一子问题重试 > 3 次换策略" + "探索超预算强制转向" + "每 5 步检查目标漂移" | **"停滞时换方向，不换力度。"** （一条规则，覆盖所有熔断场景） |

**风险评估**：生成式原则依赖模型的推理能力来"展开"具体行为。如果模型推理不足，可能遗漏关键检查。**缓解策略**：核心安全规则（不可逆操作确认、首轮对齐）保持枚举式（防错设计），其余切换为生成式。

### 6.2 工具故障的认知价值：从错误恢复到认知升级 [P2]

**问题根因**：当前 Reflect-then-Retry 将工具故障视为"需要恢复的错误"。但 Heidegger 的上手/在手分析揭示了一个更深的洞察：**故障（breakdown）是认知升级的契机**。

正常执行中，工具是"透明的"（上手状态）——agent 用 Read 读文件，注意力在文件内容而非工具本身。但当 Read 失败时（文件不存在），工具突然"显现"（在手状态）——agent 必须反思：为什么我预期这个文件存在？我的心智模型哪里错了？

**优化方向**：在 Reflect-then-Retry 中增加**认知升级维度**：

```
工具失败 → 不仅问"怎么修"，更问"这揭示了什么"

分类：
  1. 预期内失败（已知可能失败）→ 执行预设恢复路径
  2. 预期外失败（不应该失败但失败了）→ 心智模型有偏差
     → 哪个假设被推翻了？
     → 推翻这个假设后，还有哪些依赖它的决策需要重新审视？
     → 更新后的理解是否改变了接下来的计划？
  3. 意外成功（不该成功但成功了）→ 理解有盲区
     → 为什么我预期会失败？我遗漏了什么？
```

**理论支撑**：
- **Heidegger 上手/在手**：故障使隐含的前提"显现"，是反思的天然入口
- **HRO 对失败的执念**：每个异常都是学习信号，不仅是恢复目标
- **Dewey 反思性思维**：困惑/意外是反思的起点，不是终点

### 6.3 Anytime 增强：从降级兜底到持续可交付 [P2]

**问题根因**：当前的优雅降级（L0→L3）是一个**事后兜底**机制——在目标无法完成时才激活。但 Anytime 算法的真正含义是：**任意时刻中断都有最优可用产出**。这意味着不仅在失败时降级，而是在每一步都维持可交付性。

**优化方向**：将 Anytime 原则从"降级策略"提升为"执行纪律"：

| 当前（降级兜底） | 优化方向（持续可交付） |
|----------------|---------------------|
| 失败时按 L0→L3 降级 | 每步产出都独立可用 |
| "永不空手而归" | "任何时刻都有最优产出" |
| 降级是异常处理 | 可交付性是正常状态 |

**实现思路**：
- 规划阶段：按价值递减排序子任务（核心功能 > 辅助功能 > 优化 > 美化）
- 执行阶段：每完成一个子任务，更新 state.md 的"当前可交付物"描述
- 如果被中断：state.md 中的"当前可交付物"就是交付内容

**理论支撑**：
- **Anytime 算法**（CS）：算法质量随计算时间单调递增，任意时刻可中断并返回当前最优解
- **目标设定理论的近端目标**（Locke & Latham）：近端目标提供即时反馈和成就感，每个完成的子目标就是一个可用的交付物

## 7. 指令工程优化方向

### 7.1 生成式原则 vs 枚举规则：指令的信息密度 [P0]

**问题根因**：当前 auto-goal 的指令风格以**枚举规则**为主——详细列出每种情况下应该做什么。这有三个成本：

1. **Token 成本**：~297 行 ≈ 4000-5000 tokens。每次调用都消耗这些 token
2. **注意力稀释**：模型的注意力分散在大量具体规则上，可能忽略最关键的几条
3. **覆盖盲区**：枚举不可能穷尽所有情况。规则列表外的场景，模型没有指导

**生成式原则**的优势：一条好的原则能**生成**（推导出）多条具体规则，同时覆盖未枚举的场景。

**优化方向**：提炼 auto-goal 的**生成式原则核心集**——最少的原则，覆盖最多的行为。

**候选生成式原则集（7 条，替代当前 ~30 条具体规则）**：

| # | 生成式原则 | 生成的行为 |
|---|-----------|-----------|
| 1 | **对齐优先于效率** | 首轮对齐、对齐门控、GUESSING 必问、偏差检测 |
| 2 | **验证投入 ∝ 错误成本** | 三级验证、终态证伪、不可逆操作确认 |
| 3 | **在替用户做选择时，暂停** | Must-Ask 触发器、方向性决策确认、偏好依赖检查 |
| 4 | **上下文是最稀缺资源** | sub-agent 隔离、压缩保护、外化策略、按需加载 |
| 5 | **停滞时换方向，不换力度** | 熔断器、Reflect-then-Retry、策略升级链 |
| 6 | **环境结构引导行为** | 文件模板、stigmergic 信号、防错设计 |
| 7 | **任意时刻可交付** | Anytime 原则、降级层级、价值递减排序 |

**关键约束**：
- 六字原则（序验深广辨简）已是优秀的生成式原则集，**保留不变**
- 三个不可妥协核心（澄清、首轮对齐、文件协调）作为**硬性规则保留**（防错设计）
- 生成式原则替代的是中间层的具体操作规则，不是顶层原则和底层硬规则

**风险评估**：生成式原则要求模型有足够强的推理能力来"展开"行为。对 Opus 级别模型，这通常不是问题。但对较弱模型，可能需要保留更多枚举规则。**缓解策略**：核心层保留 ~100 行（含关键枚举规则），扩展层按需加载。

### 7.2 删除测试：每条指令的 ROI 审计 [P1]

**问题根因**：Anthropic 的 CLAUDE.md 黄金法则——"删掉这条指令后，会导致犯错吗？如果不会，删掉它。"当前 auto-goal 未经过系统性的删除测试。

**优化方向**：对 SKILL.md 每一段进行三问审计：

1. **删掉它会导致什么错误？**（能描述具体错误场景 → 保留）
2. **模型的原生行为已经覆盖了吗？**（Claude Opus 已经有强推理和自我纠正能力 → 可能冗余）
3. **能用更少的 token 表达同样的约束吗？**（压缩 → 精简）

**候选删除/精简项**（基于初步评估）：

| 当前内容 | 评估 | 建议 |
|----------|------|------|
| 推理模式选择（不可逆→备选评估，置信度低→多角度推理…） | 模型原生能力已覆盖 | 删除或压缩为一句话 |
| 反模式完整表（8 项 + 解药） | 有参考价值但极少被激活 | 移到扩展层 |
| 域感知路由详细表格（4 域 × 策略） | 核心框架需要保留 | 压缩为更精炼的描述 |
| 介入模式详细对比表 | 大部分时间用协作模式 | 压缩，全自动模式仅一句描述 |
| 信息分级 + 意图置信度（双正交维度） | 核心机制但描述冗长 | 压缩为一个表格 |
| 探索策略的"觅食启发" | 生动但增加认知负荷 | 压缩或删除 |

### 7.3 示例驱动：用 worked example 替代抽象描述 [P2]

**问题根因**：Anthropic ACI 原则之一："工具文档应包含使用示例、边界情况"。当前 auto-goal 几乎没有具体示例——全是抽象描述。模型看到抽象描述后的行为比看到具体示例后的行为更不可预测。

**理论支撑**：
- **认知负荷理论的 worked example 效应**：对学习者来说，看完整的解决示例比自己推理抽象规则更高效
- **Anthropic 工具设计**：好的工具文档 = 描述 + 示例 + 边界

**优化方向**：在关键机制处增加精简的 worked example：

```markdown
### 首轮对齐示例

用户: "优化这个 API 的性能"

分析: 域=Complicated, 对齐=GUESSING（"优化"是多义词，性能指标不明确）
```

### 8.3 不可动摇的核心（红线）

无论如何优化，以下三个核心**不可削弱、不可删除、不可变为可选**：

| 核心 | 为什么不可动摇 | 优化中如何保持 |
|------|---------------|---------------|
| **交互式澄清** | Agent 最危险的特征是"自信地做错事"。澄清是唯一的对齐修复手段 | 触发条件可以简化（从 8 条规则 → 1 条生成式原则），但触发后的行为不变 |
| **无条件首轮对齐** | Agent 不知道自己不理解什么。首轮对齐是结构性安全网，不是条件性判断 | 呈现格式可以模板化，轻量路径可以精简，但"呈现理解 → 等待确认"的流程不可跳过 |
| **文件系统跨会话协调** | 文件系统是跨会话的唯一持久化通道。没有它，每次会话都从零开始 | 从状态存储升级到协调协议（实际上是增强），文件结构可以优化但功能不可削减 |

### 8.4 优化的元原则

在实施以上所有优化方向时，遵守以下元原则：

1. **一次改一层**：不要同时重构架构 + 认知模型 + 协调 + 指令。每次优化一个层次，验证效果后再进入下一层
2. **可逆优先**：先做可以回滚的优化（指令精简、格式调整），后做不可逆的（架构重构）
3. **观察再优化**：每次优化后，在实际任务中观察效果。预期收益 ≠ 实际收益
4. **简是金标准**：优化的目标不是"添加更多功能"，而是"用更少的东西实现更好的效果"。如果优化后的 SKILL.md 比优化前更长，需要审视是否偏离了目标
5. **信任模型**：Claude Opus 是一个极其强大的推理引擎。skill 的角色是**引导方向**和**提供结构**，不是**替代推理**。好的 skill 像好的教练——指出方向，提供工具，然后让运动员发挥

## 附录：跨学科理论快速参考

| 理论 | 核心主张 | 在 auto-goal 中的应用 |
|------|----------|---------------------|
| 认知负荷 (Sweller) | 工作记忆容量有限（~4 chunks），减少外在负荷释放容量 | 精简指令、渐进披露、sub-agent 隔离 |
| 必要多样性 (Ashby) | 控制器的响应多样性 ≥ 系统扰动多样性 | 策略库丰富度、复杂度路由 |
| 可生存系统 (Beer) | 五个递归子系统：执行/协调/控制/环境扫描/身份 | 补全 System 4 环境扫描 |
| Flow (Csikszentmihalyi) | 挑战与能力匹配时进入心流状态 | 深度动态调节、即时反馈 |
| 延展心灵 (Clark & Chalmers) | 外部结构是认知过程的一部分 | 文件系统即认知，模板即思维工具 |
| 情境认知 (Lave, Suchman) | 知识嵌入情境，计划是行动资源非程序 | 环境感知、action-based 理解 |
| 有限理性 (Simon) | 满意即止 > 最优搜索 | Satisficing 停止标准、搜索预算 |
| 生态理性 (Gigerenzer) | 不确定环境中简单启发式 > 复杂优化 | 生成式原则、规则精简 |
| OODA (Boyd) | Orient 是认知引擎，不是检查步骤。IGC 可跳过 Decide | Orient 深化、模式匹配快速路径 |
| Stigmergy (Grassé) | 通过环境修改间接协调 | 文件存在即信号、命名约定即路由 |
| BDI (Bratman) | 信念/欲求/意图正交管理，意图保持稳定 | 信念自由更新不动摇计划 |
| 双过程理论 (Kahneman) | System 1（快）+ System 2（慢），按需切换 | 复杂度路由的快慢切换 |
| 反思性思维 (Dewey) | 困惑→定义→分析→假设→验证，非线性 | Reflect-then-Retry、假设驱动行动 |
| 上手/在手 (Heidegger) | 故障使隐含前提显现 | 工具故障 = 认知升级契机 |
| Poka-yoke (丰田) | 通过结构消除错误可能性 | 模板约束 > 过程指令 |
| Anytime 算法 (CS) | 任意时刻可中断并返回当前最优解 | 持续可交付性 |
| HRO (Weick & Sutcliffe) | 对失败的执念、拒绝简化、韧性承诺 | 弱信号检测、深度根因分析 |
| 目标设定 (Locke & Latham) | 明确+挑战性目标 > 模糊"尽力" | 目标层级、近端目标即时反馈 |

# Auto-Goal Skill 第五轮优化方向分析：超越已知的新维度

> 分析日期: 2026-04-22
> 分析主题: 在 v2(架构洞察)/v3(极简化)/v4(差距填补) 基础上，挖掘尚未识别的优化维度
> 分析对象: 当前已安装版本 (~139 行，已合并 v4 部分建议)
> 研究基础: Claude Code 设计哲学 + OpenAI Agent 指南 + 认知科学/控制论/Flow 理论/延展心灵/生态理性/stigmergy + 四轮迭代实践经验
> 核心约束: 交互式澄清 + 无条件首轮对齐 + 文件系统跨会话协调层 — 不可动摇
> 设计第一原则: 信任模型原生能力，只做模型不会自发做的事

### 1.3 本轮分析的精确定位

前四轮分析的共同特征：**都在 SKILL.md 文本层面做优化**——增删改文字、调整结构、精炼表述。这条路的边际收益已经非常低。

本轮需要跳出"修改 SKILL.md 措辞"的框架，从更高维度审视 auto-goal 的优化空间：

- **元层**：SKILL.md 本身的架构问题（重复、耦合、context 预算）
- **系统层**：auto-goal 与 ace 生态系统中其他组件的关系
- **交互层**：对齐机制的认知科学本质，而非表面形式
- **演化层**：如何设计一个随模型增强而自然"退化"的 skill
- **度量层**：没有评估基础设施，一切优化都是猜测

**一句话概括本轮视角**：不是"SKILL.md 还能怎么改"，而是"auto-goal 作为一个系统，还有哪些结构性机会"。

## 2. 元层优化：Skill 自身的结构性问题

> 前四轮都在优化 SKILL.md 的"内容"。本章优化 SKILL.md 的"架构"。

### 2.1 新发现 N1：思考罗盘的系统性重复

**问题**：六字思考罗盘（序验深广辨简）同时存在于三个位置：

| 位置 | 加载时机 | 上下文开销 |
|------|----------|-----------|
| `~/.claude/rules/ace/thinking.md` | **每次会话都加载**（全局规则） | ~300 tokens |
| `auto-goal/SKILL.md` | auto-goal 触发时加载 | ~200 tokens |
| `coding/SKILL.md` | coding skill 触发时加载（间接引用） | ~50 tokens |

当 auto-goal 被触发时，六字原则被**双重加载**——全局规则已经注入了完整版本，SKILL.md 又注入了一个精简版本。这不仅是 ~200 tokens 的浪费，更违反了 DRY 原则（Single Source of Truth）。

**根因分析**：这是一个经典的"层次污染"问题。Anthropic 的设计哲学明确提出"Push Knowledge Down the Stack"——能用 Hook 就不用 Skill，能用 Skill 就不放 CLAUDE.md。六字原则作为全局思考原则，它的正确位置是全局规则层（thinking.md），不应该在 SKILL.md 中重复。

**优化方向 N1**：从 SKILL.md 中**删除思考罗盘整个章节**。理由：
1. 全局 thinking.md 已经保证每次会话都加载
2. 释放 ~200 tokens 的上下文空间
3. 消除双重加载时的潜在注意力干扰
4. 遵循 Anthropic "Push Down the Stack" 原则

**风险评估**：极低。thinking.md 的加载优先级高于 SKILL.md，删除后行为不变。

**节省**：~200 tokens，~10 行。对于目标 ≤100 行的 skill，这是 10% 的空间。

### 2.2 新发现 N2：Skill 的 Context Budget 盲区

**问题**：auto-goal 的 SKILL.md 占用 ~1500 tokens。在一个 ~200K token 的上下文窗口中，这看似微不足道。但实际的"有效工作记忆"远小于名义窗口：

```
名义上下文窗口:              ~200K tokens
- 系统提示 (Claude Code):    ~8K tokens
- 全局规则 (rules/):         ~3K tokens  
- SKILL.md:                  ~1.5K tokens
- 工具描述:                  ~5K tokens
- 会话历史 (平均):           ~50-100K tokens
────────────────────────────────
有效剩余工作空间:            ~80-130K tokens
```

SKILL.md 占有效工作空间的 ~1-2%。这不是问题。

**真正的问题在别处**：认知科学的"注意力稀释效应"（Dilution Effect, Nisbett et al. 1981）。当诊断信息（高价值）和非诊断信息（低价值）混合呈现时，非诊断信息会**稀释**决策者对诊断信息的注意力。

映射到 SKILL.md：每一行低价值指令（模型本来就会做的事）不仅浪费 tokens，还会**分散模型对高价值指令（三条硬规则）的注意力**。

**这意味着：SKILL.md 的优化目标不仅是"减少 tokens"，更是"提高信噪比"。**

**优化方向 N2**：对 SKILL.md 进行**信噪比审计**。标准：

| 信号强度 | 特征 | 处理 |
|----------|------|------|
| **强信号** | 删除后模型行为会明显退化 | 保留，置于顶部 |
| **中信号** | 删除后偶尔退化 | 评估是否可合并到强信号中 |
| **弱信号** | 删除后无可观测变化 | 删除 |
| **噪音** | 模型原生覆盖的能力 | 立即删除 |

具体到当前版本（已是简化版）的信噪比评估：

| 模块 | 信号强度 | 判据 |
|------|----------|------|
| 核心信念（2行） | **强** | 定义价值排序，模型不会自发产生 |
| 思考罗盘（10行） | **噪音** | 全局规则已加载（N1） |
| 规则1：首轮对齐（15行） | **强** | 核心硬约束 |
| 规则2：暂停决策（8行） | **强** | 核心硬约束 |
| 规则3：状态外化（25行） | **强** | 核心硬约束 + 文件协议 |
| 生成式原则（10行） | **中→强** | 方向性指引，密度高 |
| 上下文纪律（8行） | **中** | 模型部分覆盖，但不稳定 |
| 恢复协议（5行） | **强** | 跨会话协调，模型不会自发做 |
| 介入模式（4行） | **中** | 提供有用的模式切换 |

**结论**：删除思考罗盘后，当前版本的信噪比已经相当高。剩余的优化空间在"中信号"模块的精炼上。

### 2.3 新发现 N3：Skill Composition 架构缺失

**问题**：当前 ace 生态中，skill 间的关系是**隐式的**：

```
auto-goal ←── coding skill（在文本中声明"继承 auto-goal 六字原则和 OODA 循环"）
auto-goal ←── 全局规则（在 thinking.md 中定义六字原则，auto-goal 中重复）
```

这种隐式继承有三个结构性问题：

**问题 A：耦合脆弱性**
coding skill 说"继承 auto-goal 的六字原则和 OODA 循环"——但当前安装版本的 auto-goal 已经没有 OODA 循环了（v3 删除了）。coding skill 还在引用一个不存在的东西。这不会立即报错，但模型可能会被误导去寻找一个不存在的概念。

**问题 B：context 重复加载**
如果用户的任务同时触发了 auto-goal 和 coding skill（比如"帮我实现一个认证模块"），两个 SKILL.md 都被加载到上下文中。共同的内容（对齐规则、状态外化）被加载两次。

**问题 C：演化不同步**
修改 auto-goal 的规则后，coding skill 不会自动同步。依赖者必须手动更新。这在 skill 数量增长后会变成维护噩梦。

**理论依据**：

- **软件工程的 DRY 原则**：知识应该只表达一次
- **Anthropic "Push Down the Stack"**：共享的基础原则应该在更低的层级（全局规则），而非在每个 skill 中重复
- **控制论的子系统独立性**（Beer's Viable System Model）：子系统应该能独立运作，通过共享协议而非共享状态协调

**优化方向 N3**：设计 **Skill Composition 架构**。

```
当前架构（隐式继承）：
  auto-goal.SKILL.md [六字原则 + 对齐规则 + 状态协议 + ...]
  coding.SKILL.md    ["继承 auto-goal" + 代码域适配]

目标架构（显式组合）：
  全局规则层（rules/）：
    thinking.md        → 六字原则（唯一定义点）
    interactive-clarify.md → 交互式澄清协议
    context-hygiene.md → 上下文纪律

  Skill 层（每个 skill 只包含自己的差异化内容）：
    auto-goal.SKILL.md → 三条硬规则 + 生成式原则 + 状态文件协议 + 恢复协议
    coding.SKILL.md    → 代码域特定规则 + 代码域状态文件适配

  不共享、不继承。每个 skill 读取全局规则，加上自己的差异化内容。
```

**收益**：
1. 消除重复（六字原则只在 thinking.md 中定义一次）
2. 消除耦合（coding skill 不依赖 auto-goal 的具体文本）
3. 修改全局规则自动对所有 skill 生效
4. 每个 SKILL.md 更短、信噪比更高

**实施成本**：中等。需要重构 coding.SKILL.md，从"继承 auto-goal"改为"引用全局规则 + 自身差异"。

### 2.4 新发现 N4：state.md 模板的"编译器"思维

**问题**：当前 SKILL.md 中 state.md 的模板占了 ~25 行（约 18%）。这是一个完整的 markdown 模板，包含 frontmatter、段落标题、表格结构。模型每次创建状态文件时都要"参照"这个模板。

**深层问题**：这个模板是**声明式的**（描述了最终形态）还是**过程式的**（描述了如何创建）？

当前是声明式的——给了一个完整模板，模型去"填空"。这看似正确，但有一个微妙的认知科学问题：

**Einstellung 效应**（Luchins 1942）：当给定一个固定模板时，问题解决者倾向于机械地填充模板，而非思考"这个具体任务真正需要什么结构"。

例如：一个 3 步的小任务，模型可能仍然创建包含"子目标表、决策上下文、未确认假设"的完整 state.md——因为模板要求了这些字段。这是过度结构化。

**优化方向 N4**：将 state.md 从"固定模板"转变为"设计目标 + 最小必备项"。

当前（模板驱动）：
```markdown
state.md 结构：[完整模板，~20行]
```

优化为（目标驱动）：
```markdown
state.md 设计目标：让一个全新 agent 读完后能以 80% 效率继续。
必备项：目标 + 完成标准 + 当前进度 + 下一步 + 已修改文件。
其余段落按任务复杂度自行决定。
```

**收益**：
1. SKILL.md 减少 ~15 行
2. 模型根据任务复杂度自适应 state.md 的详略程度
3. 避免 Einstellung 效应——简单任务不会被迫创建过度结构化的状态文件
4. 与"信任模型"原则一致——模型知道如何组织信息，只需要告诉它"为谁写、写什么"

**风险**：中低。设计目标（"80% 效率继续"）是一个强约束，模型会自发包含必要信息。必备项清单防止遗漏关键要素。

## 3. 对齐机制的深层重构

> 前四轮优化了对齐的"内容"（加了完成标准、弹性表述、持续对齐）。本章重构对齐的"本质"。

### 3.1 新发现 N5：对齐的认知科学本质——共同基础建构

**重新定义问题**：

前四轮把"对齐"理解为"呈现理解并等待确认"。这是对的，但不够深。

Herbert Clark 的 Common Ground Theory 区分了三种共同基础：

| 类型 | 含义 | auto-goal 中的对应 |
|------|------|-------------------|
| **Communal Common Ground** | 来自共同社群的背景知识 | 用户是 Java 后端开发者（from memory） |
| **Personal Common Ground** | 来自之前互动的共享经历 | 上次会话的决策、之前的偏好 |
| **Situational Common Ground** | 当前场景中的共享感知 | 当前代码状态、git history、项目文件 |

当前 auto-goal 的首轮对齐只处理了 **Situational Common Ground**（当前目标的理解确认）。完全忽略了另外两种。

**为什么这重要**：

想象两个场景：
1. 新用户第一次使用 auto-goal，说"帮我重构这个服务"
2. 老用户第十次使用，说同样的话

理论上，场景 2 的对齐应该**更轻量**——因为存在丰富的 Personal Common Ground（之前的偏好、风格、决策模式都在 memory 中）。但当前 auto-goal 对两个场景执行**完全相同的对齐流程**。

**这就是 v4 提出但未合并的 O6（对齐弹性）的更深层原因。**

对齐的弹性不只是"简单任务少确认"（复杂度维度），还应该是"熟悉的用户少确认"（关系维度）。

**优化方向 N5**：将对齐规则从"固定流程"升级为"目标 + 信号"。

当前：
```
接收目标后，必须完成以下三步才能开始执行：
Step 1: 初步分析
Step 2: 澄清
Step 3: 对齐确认（不可跳过）
```

优化为：
```
接收目标后，必须确保充分对齐后才能开始执行。

对齐的目标：双方对"做什么、做到什么程度、关键假设"达成一致。

对齐的形式由不确定性决定：
- 目标明确 + 完成标准可推导 → 一句话确认即可
- 目标有歧义 → 先用 AskUserQuestion 澄清
- 复杂/高风险 → 完整呈现：理解 + 方向 + 假设 + 完成标准

不可跳过的底线：至少用 AskUserQuestion 让用户确认或补充。
```

**关键变化**：
1. 从"三步流程"变为"目标 + 信号"——告诉模型对齐的**目的**，而非**步骤**
2. 模型根据不确定性自适应形式——信任模型的判断力（与设计第一原则一致）
3. 保留不可跳过的底线——AskUserQuestion 必须被调用（硬约束）
4. 释放了"固定三步"带来的 Einstellung 效应

**风险**：中。模型可能在"目标明确"时倾向于跳过确认。底线（至少调用 AskUserQuestion）是防护网。需要通过 eval 验证。

### 3.2 新发现 N6：对齐的"交易成本"与用户疲劳

**问题**：经济学中有一个概念叫"交易成本"（Coase 1937）。每次对齐交互都有成本：

| 成本项 | 描述 |
|--------|------|
| **用户注意力成本** | 用户需要阅读对齐呈现、思考、回复 |
| **时间成本** | 等待用户响应的延迟 |
| **上下文成本** | 对齐文本占用上下文空间 |
| **认知切换成本** | 用户从"提出需求"模式切换到"审查方案"模式 |

如果对齐的"交易成本"持续高于用户感知到的"对齐价值"，用户会采取两种策略：
1. **绕过**：不用 auto-goal，直接用 coding skill 或原始 Claude Code
2. **橡皮图章**：对所有对齐确认盲目回复"好的"（对齐形式化，失去实质意义）

**Flow 理论的映射**：Csikszentmihalyi 指出，当挑战远低于技能时产生无聊（对齐对简单任务来说是无聊的）。当反馈延迟时 Flow 被打断（等待用户确认是延迟）。auto-goal 的对齐机制应该让用户保持在 Flow 状态，而非反复打断 Flow。

**优化方向 N6**：设计"对齐成本 ∝ 不确定性"的自适应机制。

这不是一个新的硬规则，而是一个**设计原则**，指导模型如何选择对齐形式：

| 不确定性 | 对齐形式 | 用户成本 | 示例 |
|----------|----------|----------|------|
| **极低** | 一句话 + AskUserQuestion 确认 | ~10秒 | "我理解你要给 UserService 加缓存。用 Redis，接口不变。确认？" |
| **低** | 2-3 句话摘要 + AskUserQuestion 确认 | ~30秒 | "我理解你要重构支付模块。方向是提取公共接口，保留两个实现。假设：不改数据库。确认？" |
| **中** | 完整呈现 + AskUserQuestion | ~2分钟 | 理解 + 方向 + 假设 + 完成标准 |
| **高** | 先 AskUserQuestion 澄清，再完整呈现 | ~5分钟 | 多轮澄清 + 方案对比 |

**关键洞察**：对齐的**内容**是固定的（理解 + 方向 + 假设 + 完成标准），但**呈现密度**是可变的。低不确定性时，一句话可以包含所有四项。高不确定性时，需要分项展开。

这与 N5 是一体两面：N5 改变了规则的表述，N6 提供了具体的认知模型。

### 3.3 新发现 N7：验证不是指令，是工具构造

**问题**：

v4 的最高杠杆方向（O1-O3）聚焦于"完成标准"。当前版本已经合并了"完成标准"到首轮对齐和生成式原则中。但这里有一个被忽略的深层问题：

**"定义完成标准"和"执行验证"之间有一条鸿沟。**

模型知道完成标准是"所有测试通过"。但从"知道"到"验证"需要：
1. 知道运行什么命令（`mvn test`? `npm test`? `pytest`?）
2. 知道如何判读输出（全绿 = 通过？覆盖率 ≥ 80%？）
3. 知道在什么时机运行（每步之后？阶段结束？最终交付？）

**Anthropic 的原文**是：
> "**Give Claude a way to verify its work.** This is the single highest-leverage thing you can do."

关键词是 **"give a way"**——不是"告诉 Claude 要验证"，而是"给 Claude 验证的手段"。

当前 auto-goal 告诉模型"要验证"（指令层），但没有帮助模型"构造验证手段"（工具层）。

**优化方向 N7**：在首轮对齐中，要求完成标准必须是**可执行的验证命令或可观测的验证条件**，而非抽象的完成描述。

当前风格：
```
完成标准：
- [ ] 认证模块实现
- [ ] 测试通过
- [ ] 文档更新
```

目标风格：
```
完成标准：
- [ ] `mvn test -pl auth-module` 全绿
- [ ] POST /api/login 返回 200 + JWT token
- [ ] README.md 的 Auth 章节已更新
```

**关键差异**：第一种是"描述性的"——模型要自己推断如何验证。第二种是"可执行的"——验证手段已经内嵌在标准中。

这不需要修改 SKILL.md 的硬规则。可以通过增强 state.md 的**设计目标描述**来实现：

```
完成标准必须可执行——每条标准对应一个可运行的命令、可观测的输出、或可检查的文件状态。
```

**一句话就够**。模型理解"可执行的验证"意味着什么——这是模型原生能力覆盖的。skill 的工作只是**提醒**它这么做。

### 3.4 新发现 N8：对齐的"预热"——利用已有上下文

**问题**：

当前首轮对齐的第一步是"初步分析——用探索性工具理解上下文"。模型从零开始理解。

但实际上，在 auto-goal 被触发之前，上下文中可能已经存在大量有用信息：

| 上下文来源 | 包含的信息 | 当前利用率 |
|-----------|-----------|-----------|
| **Memory 文件** | 用户角色、偏好、之前的反馈 | ❌ 未被对齐流程显式利用 |
| **CLAUDE.md** | 项目约定、技术栈、构建命令 | ❌ 对齐不会主动参考 |
| **git status** | 当前分支、未提交变更、最近 commit | ⚠️ 在系统提示中，但对齐不会主动关联 |
| **之前的对话** | 用户在本会话中说过的话 | ✅ 模型自然利用 |

**情境认知**（Situated Cognition, Suchman 1987）的核心主张：行动不是计划的执行，而是对情境的即时响应。对齐应该**嵌入**当前情境，而非在真空中进行。

**优化方向 N8**：不是修改 SKILL.md，而是建议模型在对齐前**利用已有上下文预热**。

这可以通过一个微调的 Step 1 表述实现：

当前：
```
Step 1: 初步分析 — 用探索性工具理解上下文
```

优化为：
```
Step 1: 初步分析 — 结合已有上下文（memory、CLAUDE.md、git status、会话历史）和探索性工具，形成对目标的理解
```

增加的只是"结合已有上下文"这几个字。但这是一个重要的**注意力引导**——提醒模型利用已经在上下文中的信息，而非每次都从零开始。

**为什么模型不会自发做这件事**：模型会利用上下文中的信息进行推理（这是原生能力），但在"对齐"这个特定任务中，模型倾向于按照 SKILL.md 规定的流程执行，可能会忽略已有上下文的丰富性。这是**流程遮蔽情境**的问题——详细的流程指令反而让模型忽略了情境信息。

（这也是 N5 "从固定流程到目标+信号"的又一个论据：固定流程遮蔽情境感知。）

## 4. 状态外化的范式升级：从记录到触发

> v4 将 state.md 从"日志"升级为"可恢复的世界模型"。本章将其升级为"行为触发器"。

### 4.1 新发现 N9：Stigmergy 的未充分利用

**理论背景**：

Stigmergy（间接协调，Grassé 1959）是蚁群智能的核心机制：蚂蚁不直接通信，而是通过在环境中留下信息素来间接协调行为。关键特征：

1. **信息嵌入环境**：协调信号存在于物理环境中，而非个体记忆中
2. **行为触发**：环境中的信号直接触发行为，无需"理解"
3. **自组织**：全局秩序从局部规则涌现

**映射到 auto-goal**：

`.tasks/auto-goal-{id}/` 目录结构本身就是一个 stigmergic 系统——文件的存在/缺失/内容是"信息素"，新 agent 读取这些信号并触发相应行为。

**但当前设计只利用了 stigmergy 的第一个特征（信息嵌入环境），忽略了第二个（行为触发）。**

当前文件结构：
```
.tasks/auto-goal-{id}/
├── state.md          # 世界模型
├── decisions.md      # 关键决策（按需创建）
└── reflections.md    # 失败分析（按需创建）
```

这些文件是**信息容器**——新 agent 必须读取、理解、然后决定做什么。

stigmergic 设计应该是：**文件的存在本身就是行为信号**。

**优化方向 N9**：增强文件结构的 stigmergic 信号性。

```
.tasks/auto-goal-{id}/
├── state.md          # 总是存在 → 触发："读取并继续"
├── decisions.md      # 存在 → 触发："读取后再做决策"
├── reflections.md    # 存在 → 触发："读取后避免重蹈覆辙"
├── BLOCKED.md        # 存在 → 触发："不要继续执行，先解决阻塞"（新增）
└── NEEDS_ALIGNMENT.md # 存在 → 触发："不要执行，先重新对齐"（新增）
```

**BLOCKED.md** 和 **NEEDS_ALIGNMENT.md** 是纯 stigmergic 信号文件：

- **BLOCKED.md**：当任务被阻塞时创建，内容描述阻塞原因和解除条件。新 agent 看到这个文件就知道"不能继续，先解决阻塞"。阻塞解除后删除文件。
- **NEEDS_ALIGNMENT.md**：当执行过程中发现目标理解偏差时创建，内容描述偏差信号。新 agent 看到这个文件就知道"先重新对齐，再继续"。对齐完成后删除文件。

**为什么这比"在 state.md 中标注状态"更好**：

1. **即时可见性**：`ls .tasks/auto-goal-{id}/` 就能看到是否有阻塞/对齐需求，不需要解析 state.md 内容
2. **行为直接触发**：文件存在 = 行为信号，不需要理解和推理
3. **自清除**：问题解决后删除文件，信号自然消失

**但这个方向需要谨慎**：

过度设计文件结构会增加 SKILL.md 的复杂度（更多文件 = 更多规则来解释何时创建/删除）。这可能违反"简"原则。

**建议**：不在 SKILL.md 中规定这些额外文件，而是作为一个**生成式建议**——"状态文件的结构应该让新 agent 从文件名就能判断下一步行为"。模型可以自行决定是否创建额外的信号文件。

### 4.2 新发现 N10：恢复协议的"冷启动"问题

**问题**：

当前恢复协议假设新 agent 从 state.md 开始恢复。但现实中，"恢复"发生在多种场景：

| 场景 | state.md 状态 | 恢复难度 |
|------|-------------|----------|
| **会话中断** | 最新（刚更新过） | 低 |
| **次日继续** | 可能过时（代码已被手动修改） | 中 |
| **一周后继续** | 高概率过时 | 高 |
| **不同用户继续** | state.md 中的假设可能不适用 | 极高 |

当前恢复协议的第二步是"验证声称的产出是否真实存在"。这覆盖了"state.md 声称的文件是否还在"，但没有覆盖更微妙的问题：

- **代码已被手动修改**：state.md 说"Phase 2 完成"，但用户在此期间手动修改了 Phase 2 的代码
- **依赖已变化**：state.md 说"使用 Spring Boot 3.2"，但 pom.xml 已经升级到 3.3
- **目标已漂移**：用户的需求已经变了，但 state.md 还记录着旧目标

**优化方向 N10**：增强恢复协议的**过时检测**能力。

当前：
```
恢复中断的任务时：
1. 读取 state.md
2. 验证声称的产出是否真实存在
3. 用 TaskCreate 重建 UI 进度
4. 从"下一步行动"继续
```

优化为：
```
恢复中断的任务时：
1. 读取 state.md
2. 验证产出是否存在且未被外部修改（git diff 检测变更）
3. 如发现 state.md 与现实不一致 → 更新 state.md 后重新对齐
4. 用 TaskCreate 重建 UI 进度
5. 从"下一步行动"继续
```

增加的是第 2 步的"且未被外部修改"和第 3 步的"不一致时重新对齐"。

这是一个**低成本高收益**的增强：
- `git diff` 是轻量操作
- 不一致时触发重新对齐，复用已有的对齐机制
- 防止在过时假设上继续执行（高风险）

### 4.3 新发现 N11：state.md 的"设计目标"优于"模板"

（此方向在 N4 中已提出。这里从跨会话协调的角度补充论证。）

**跨会话协调的核心挑战**：

state.md 的读者不是"提醒自己的同一个 agent"，而是"一个陌生的新 agent"。这两种读者有根本不同的信息需求：

| 读者 | 需要的信息 | 不需要的信息 |
|------|-----------|-------------|
| **同一 agent（上下文内恢复）** | 下一步是什么 | 目标、已完成阶段的细节 |
| **新 agent（跨会话恢复）** | 为什么做这件事、之前做了哪些关键决策、当前世界状态 | 过程细节、失败过的尝试 |

当前 state.md 模板对两种读者没有区分。一个固定模板无法同时服务这两种根本不同的需求。

**优化方向**（已在 N4 中提出）：用**设计目标**替代**固定模板**。设计目标覆盖了两种读者场景：

> "让一个全新 agent 读完 state.md 后能以 80% 效率继续。"

这个目标隐含了对"新 agent"场景的优先考虑——因为"同一 agent"不需要 state.md（上下文已经有了），只有"新 agent"才真正依赖 state.md。

## 5. 被忽略的维度：四个从未被分析的优化面

### 5.1 新发现 N12：评估基础设施的缺失——没有度量，一切优化都是猜测

**问题**：

auto-goal 已经经过四轮优化，产生了大量分析报告。但**没有一轮优化是基于实证数据的**。所有优化都基于：
1. 理论推导（"认知科学说 X，所以应该 Y"）
2. 主观判断（"这段指令模型已经会了"）
3. 类比推理（"Anthropic 这样做，所以我们也应该"）

科学方法的核心是**可证伪性**（Popper）。当前的优化方法缺乏反馈闭环——我们不知道：

| 问题 | 现状 |
|------|------|
| 首轮对齐的执行率是多少？ | 不知道 |
| v3 简化后，任务完成质量变了吗？ | 不知道 |
| 哪条生成式原则被模型实际使用了？ | 不知道 |
| 用户对对齐过程的满意度如何？ | 不知道 |
| state.md 在恢复场景中的实际效果？ | 不知道 |

**这是 auto-goal 优化的最大盲区——不是 SKILL.md 的内容问题，而是优化方法论本身的问题。**

**理论依据**：

- **Deming 的 PDCA 循环**：Plan-Do-Check-Act。前四轮做了大量 Plan 和 Do，但几乎没有 Check 和 Act
- **双环学习**（Argyris & Schön）：单环学习修正行动，双环学习修正假设。没有评估数据，连单环学习都做不到
- **OpenAI Agent 指南**："Tracing is essential — full decision and tool-call history for debugging unexpected behavior"

**优化方向 N12**：建立 auto-goal 的评估基础设施。

ace 生态中已经有 skill-creator 提供的评估框架（evals.json、grader agent、benchmark 脚本）。但**这些工具从未被用于 auto-goal**。

建议的评估维度：

| 维度 | 评估方法 | 数据来源 |
|------|----------|----------|
| **对齐执行率** | auto-goal 被触发后，是否实际调用了 AskUserQuestion？ | 会话日志 |
| **对齐质量** | 用户在对齐确认时修正了多少内容？（0 修正 = 过度确认或完美理解；多修正 = 分析不充分） | 会话日志 |
| **目标完成率** | 完成标准清单的勾选比例 | state.md |
| **Scope creep 率** | 最终产出超出原始完成标准的频率 | 对比首轮对齐 vs 实际交付 |
| **恢复成功率** | 跨会话恢复后，任务继续到完成的比例 | state.md 跨会话对比 |
| **用户干预频率** | 用户主动纠正方向的次数 | 会话日志 |

**最小可行评估方案**：

不需要复杂的自动化。最简单的做法：

1. 在 state.md 中增加一个 `## 复盘` 段，任务完成时由模型填写关键指标
2. 积累 10-20 个任务的复盘数据后，进行趋势分析
3. 基于数据调整 SKILL.md

这与 auto-goal 的现有机制完全兼容——state.md 已经是外化记忆，增加一个复盘段的边际成本极低。

### 5.2 新发现 N13：Skill Description 的触发准确率问题

**问题**：

SKILL.md 的 frontmatter `description` 字段决定了 skill 何时被触发。当前描述：

```yaml
description: |
  自主完成目标的AI Skill。当用户需要完成复杂目标、项目、任务或学习需求时使用此skill。
  触发词："帮我实现..."、"完成...目标"、"搞定...任务"、"自动完成..."、"逐步完成..."、
  "学习..."、"教程"、"入门"、"深入理解..."、"掌握..."、"什么是XXX"、"如何学习XXX"、"请讲解XXX"
  核心：六字原则 + 对齐优先 + 上下文工程 + 状态外化。信任模型原生能力，只做模型不会自发做的事。
```

**四个潜在问题**：

**P1：与 coding skill 的触发边界模糊**

当用户说"帮我实现一个认证模块"——这应该触发 auto-goal 还是 coding skill？

auto-goal 的触发词包含"帮我实现..."，coding skill 的触发词也包含"实现"、"implement"。**谁赢？**

Claude Code 的 skill 触发是由模型判断的。当两个 skill 的描述都匹配时，模型可能：
- 选错 skill
- 每次选择不一致
- 浪费 tokens 在决策上

**P2：学习类触发词可能导致误触发**

"什么是XXX"、"如何学习XXX"、"请讲解XXX"——这些触发词的范围非常广。"什么是 CORS"这种简单问题也会触发完整的 auto-goal 流程？这是过度设计。

**P3：描述中的"核心"行是内部实现细节**

"六字原则 + 对齐优先 + 上下文工程 + 状态外化"——这是 skill 的内部机制，不是触发信号。把实现细节放在触发描述中是噪音。

**P4：缺乏否定触发词**

描述没有说明"什么情况下不应该触发"。coding skill 有明确的排除规则，但 auto-goal 没有。

**优化方向 N13**：优化 description 字段。

```yaml
description: |
  自主完成目标的AI Skill。当用户提出需要多步骤才能完成的复杂目标时使用。
  触发场景："帮我实现/完成/搞定..."、复杂任务分解、需要跨步骤协调的项目。
  不触发：单步骤的代码编辑（→ 直接工具）、纯代码域任务（→ coding skill）、
  简单问答（→ 直接回答）。
```

**关键变化**：
1. 删除学习类触发词（简单学习问题不需要 auto-goal 的完整协议）
2. 增加否定触发词（明确排除规则）
3. 删除内部实现细节（"六字原则 + ..."）
4. 与 coding skill 划清边界

**验证方法**：使用 skill-creator 的 eval 框架，构造 20 个测试用例（10 个应该触发，10 个不应该触发），测量触发准确率。

### 5.3 新发现 N14：Sub-Agent 编排的缺失策略

**问题**：

当前 auto-goal 的上下文纪律规定了"探索性工作用 sub-agent 隔离"。但**何时、如何**使用 sub-agent 是完全未指定的。

Claude Code 的 Agent 工具支持多种 sub-agent 类型：
- `general-purpose`：通用 agent
- `Explore`：快速代码探索
- `Plan`：架构规划

auto-goal 没有指导模型**何时使用哪种 sub-agent**，也没有指导**如何构造 sub-agent 的 prompt**。

**这重要吗？**

重要。因为 sub-agent 的使用质量直接影响上下文管理效果：
- 一个好的 sub-agent prompt 返回精炼的摘要 → 上下文高效
- 一个差的 sub-agent prompt 返回大量原始数据 → 上下文浪费

**但应该在 SKILL.md 中指导吗？**

根据"只做模型不会自发做的事"原则，需要判断：**模型是否天然知道如何高效使用 sub-agent？**

答案：**部分知道，但不稳定。** Claude Code 的系统提示中已经有详细的 Agent 工具使用指南。模型在大多数情况下能正确使用。但在 auto-goal 的长任务场景中，模型可能：
- 为了"效率"跳过 sub-agent，直接在主上下文中做探索（上下文污染）
- 发送过于简短的 sub-agent prompt（sub-agent 缺乏上下文，返回低质量结果）

**优化方向 N14**：不增加新规则，而是在上下文纪律中**强化"隔离"策略的具体性**。

当前：
```
隔离 — 搜索/读大文件/查资料用 sub-agent | 会污染主上下文的工作
```

可选优化：
```
隔离 — 产出超过 ~50 行的探索性工作用 sub-agent。brief sub-agent 如同 brief 同事：交代目标、已知信息、期望输出格式
```

增加的内容：
1. **量化触发条件**（~50 行），减少模型的判断负担
2. **prompt 质量提示**（"如同 brief 同事"），利用模型的类比推理能力

**但要谨慎**：这可能是"模型已经知道但不稳定"的情况。如果添加后没有可观测的改善，应该删除（回到 N12 的评估基础设施需求）。

### 5.4 新发现 N15：学习用例的结构性缺口

**问题**：

auto-goal 的触发描述包含大量学习类触发词（"学习..."、"教程"、"入门"、"深入理解..."）。但 SKILL.md 的所有机制都是为**执行类任务**（编码、分析、构建）设计的。

学习类任务与执行类任务有根本不同的结构：

| 维度 | 执行类任务 | 学习类任务 |
|------|-----------|-----------|
| **目标** | 产出可观测的产物 | 改变用户的心智模型 |
| **完成标准** | 测试通过、文件存在 | 用户理解了概念（难以测试） |
| **交付物** | 代码、文档、配置 | 解释、示例、类比、练习 |
| **反馈循环** | 工具输出验证 | 用户的理解程度反馈 |
| **state.md 内容** | 技术进度 | 知识图谱进展 |

当前 auto-goal 的机制（完成标准清单、状态外化、PCT 子目标）天然适配执行类任务，但**对学习类任务几乎无适配**。

**有两条路可走**：

**路径 A：从 auto-goal 中移除学习触发词**

让学习类需求不触发 auto-goal，由模型的原生对话能力直接处理。

**理由**：学习类对话本质上是交互式的，不需要状态外化、完成标准清单、sub-agent 隔离等重型机制。auto-goal 的完整协议对学习场景是过度设计。

**路径 B：为学习类任务增加轻量适配**

保留触发词，但增加一条生成式原则：

> "学习类目标：完成标准是用户的理解而非代码产出。交付物包含概念解释、类比映射和实操练习。"

**建议**：选择路径 A。原因：
1. 学习类需求触发 auto-goal 的完整对齐流程（首轮对齐、AskUserQuestion）是过度设计
2. 模型的原生对话能力完全覆盖学习场景
3. 减少触发范围 = 减少误触发 = 提高触发准确率（N13）
4. 如果用户的学习需求确实复杂（"帮我系统学习分布式系统"），模型可以自行触发 auto-goal 或用户可以显式调用

## 6. 未来兼容性架构：设计一个随模型增强而自然退化的 Skill

### 6.1 核心命题

auto-goal 的设计第一原则是"信任模型原生能力，只做模型不会自发做的事"。这个原则有一个时间维度的推论：

> **随着模型能力增强，auto-goal 应该自然变短。**

如果模型未来版本原生支持了某些当前需要 skill 补偿的能力，skill 中对应的指令就变成了噪音（甚至干扰）。

### 6.2 新发现 N16：三层稳定性模型

auto-goal 的各个组成部分并不是等速演化的。可以按稳定性分为三层：

| 层 | 内容 | 稳定性 | 与模型能力的关系 |
|----|------|--------|-----------------|
| **永久层** | 首轮对齐（AskUserQuestion）、文件系统状态外化协议、恢复协议 | **永久** | 解决的是**架构约束**（上下文有限、跨会话失忆、用户意图不确定），与模型能力无关 |
| **长期层** | 上下文纪律（隔离/压缩/外化）、介入模式 | **长期** | 当模型原生支持上下文自管理时可能退化。预计 2-3 代模型后 |
| **衰减层** | 思考罗盘、生成式原则（验证∝风险、卡住换方向、永不空手而归） | **衰减** | 当模型的元认知和自我校准能力增强时自然过时。思考罗盘已经可以删除（N1：全局规则已覆盖） |

**优化方向 N16**：在 SKILL.md 中按稳定性组织内容，永久层在前，衰减层在后。

当前结构：
```
1. 核心信念
2. 思考罗盘          ← 衰减层（应删除/移到末尾）
3. 三条硬规则        ← 永久层
4. 生成式原则        ← 衰减层
5. 上下文纪律        ← 长期层
6. 恢复协议          ← 永久层
7. 介入模式          ← 长期层
```

优化后的组织：
```
1. 核心信念          ← 永久
2. 三条硬规则        ← 永久
3. 恢复协议          ← 永久
4. 上下文纪律        ← 长期
5. 介入模式          ← 长期
6. 生成式原则        ← 衰减（最后，最容易删除）
```

**收益**：
1. 模型的注意力优先级与内容重要性一致（顶部 = 最重要 = 永久层）
2. 未来精简时，从底部删除即可，不影响顶部结构
3. 信噪比自然优化——永久层内容少而关键，注意力集中

### 6.3 新发现 N17：从"规则"到"约束"的范式转变

**深层洞察**：

当前 SKILL.md 是一组**规则**（rules）——告诉模型"做什么"和"不做什么"。

更未来兼容的设计是**约束**（constraints）——定义模型"不能做什么"的边界，让模型在边界内自由行动。

```
规则式（当前）：
  "接收目标后，必须完成以下三步..."
  → 告诉模型怎么做对齐

约束式（目标）：
  "未经用户确认不能开始执行"
  → 定义边界，模型自行决定如何对齐
```

**理论依据**：

- **Ashby 的必要多样性定律**：调节器（skill）不需要规定所有行为，只需要约束行为的边界
- **自组织理论**：给定约束条件，系统会自发找到最优行为模式
- **Anthropic 设计哲学**："Trust the model to reason; engineer the harness to enforce boundaries"——模型推理，harness 强制边界

**约束式 auto-goal 的终极形态**（概念验证，非立即实施）：

```markdown
# Auto Goal Skill

信任模型。只定义模型不能自行保障的约束。

## 硬约束

1. 未经用户确认（AskUserQuestion）不能开始执行
2. 替用户做方向性选择时必须暂停确认
3. 预估 >10 步的任务必须在 .tasks/ 中外化状态
4. 探索性工作不得污染主上下文

## 协议

state.md 设计目标：新 agent 读完后能以 80% 效率继续。
必备项：目标 + 完成标准 + 进度 + 下一步 + 已修改文件。

## 恢复

1. 读取 state.md → 2. 验证产出存在 → 3. 重建进度 → 4. 继续
```

**这个版本只有 ~20 行。**

它可能太激进了——删除了所有生成式原则、所有上下文纪律的具体策略、所有介入模式的描述。但它代表了一个**方向**：随着模型增强，auto-goal 的终极形态就是一组**纯约束** + **一个文件协议**。

**当前不建议实施**。但建议将这个终极形态作为"北极星"——每次优化都问："这次修改是在向北极星靠近还是远离？"

### 8.2 本轮的已知局限

1. **N5（对齐重构）的风险评估不充分**：从固定流程到目标+信号是一个重大变化，可能导致模型在某些场景下跳过关键对齐步骤。需要严格的 A/B 测试
2. **N12（评估基础设施）未给出具体实施方案**：指出了问题，但构建评估体系本身是一个独立项目
3. **N17（规则→约束）太激进**：~20 行版本是否真的能让模型产生同等质量的行为，完全未经验证
4. **跨学科理论的适用性**：Stigmergy、Common Ground Theory、Einstellung 效应在 LLM agent 上下文中的有效性是类比推理，不是实证结论

### 8.3 推荐的下一步

1. **立即执行 P0**：N1 + N4 + N13 + N15。这四项低风险、高确定性、净减少行数
2. **设计 N5 的 A/B 测试**：构造 10 个不同复杂度的任务，对比"固定三步"vs"目标+信号"的对齐质量
3. **启动 N12**：即使只是在 state.md 中增加一个"复盘"段，也比什么都不做好
4. **将 N17 的"北极星"记录在案**：作为 auto-goal 的长期愿景，指导每次迭代的方向

## 附录：本轮新发现的理论根源速查

| 新发现 | 核心理论 | 理论要点 |
|--------|----------|----------|
| N1 重复 | DRY (Hunt & Thomas) / Anthropic "Push Down the Stack" | 知识只表达一次，能用低层就不放高层 |
| N2 信噪比 | 注意力稀释效应 (Nisbett et al. 1981) | 非诊断信息稀释对诊断信息的注意力 |
| N3 组合 | Viable System Model (Beer) / DRY | 子系统独立运作，通过协议协调 |
| N4 Einstellung | Einstellung Effect (Luchins 1942) | 固定模板导致机械填充而非适应性思考 |
| N5 对齐本质 | Common Ground Theory (Clark & Brennan 1991) | 共同基础有三种：社群、个人、情境 |
| N6 交易成本 | Transaction Cost Theory (Coase 1937) / Flow (Csikszentmihalyi) | 对齐有成本；过度对齐破坏 Flow |
| N7 验证工具化 | Anthropic "give Claude a way to verify" | 验证需要工具/手段，不只是指令 |
| N8 情境认知 | Situated Cognition (Suchman 1987) | 行动嵌入情境，而非计划的执行 |
| N9 Stigmergy | Stigmergy (Grassé 1959) | 文件存在=行为信号，不需理解 |
| N10 冷启动 | Good Regulator Theorem (Conant & Ashby) | 调节器的模型必须与现实同步 |
| N12 评估 | PDCA (Deming) / 可证伪性 (Popper) | 没有度量的优化是猜测 |
| N13 触发精度 | 信号检测论 (Tanner & Swets 1954) | 提高命中率，降低虚报率 |
| N15 职责边界 | 单一职责原则 (Martin) | 一个 skill 只因一个理由而改变 |
| N16 三层稳定性 | 架构约束 vs 能力不足 | 永久/长期/衰减分层，衰减层自然退化 |
| N17 约束>规则 | Ashby 必要多样性 / 自组织理论 | 定义边界，不规定行为 |

### 6.4 N3：Skill Composition 架构——消除耦合 — ✅ 已实施

**问题**：coding skill 声明 "继承 auto-goal 的六字原则（序验深广辨简）和 OODA 循环"，但：
- **Problem A（陈旧引用）**：缓存版 auto-goal 已无 OODA 循环（v3 删除），引用已失效
- **Problem B（重复加载）**：若同时触发两个 skill，共享内容双重加载
- **Problem C（演化不同步）**：修改 auto-goal 不会自动同步到 coding skill

三个问题的根因一致：**隐式继承**。coding skill 不应依赖 auto-goal 的内部实现。

**目标架构**（显式组合，每层独立）：
```
全局规则层（rules/）：
  thinking.md        → 六字原则（唯一定义点）
  interactive-clarify.md → 交互式澄清协议
  context-hygiene.md → 上下文纪律

Skill 层（每个 skill 只包含自己的差异化内容）：
  auto-goal → 三条硬规则 + 生成式原则 + 状态外化协议
  coding    → 代码域 OODA + 意图路由 + 复杂度适配 + 交付规范
```

**实施**：
- **coding skill 开头**：`继承 auto-goal 的六字原则和 OODA 循环，适配代码域特性` → `代码域的核心特性：`
- **coding skill Section 3**：`在 auto-goal 的 OODA 基础上，注入代码域特有认知` → `代码域的感知-定位-决策-行动循环：`
- **同时更新**：缓存版和源码版的 coding SKILL.md

**效果**：
- coding skill 的 OODA 循环现在是**自有内容**，不声称继承自任何地方
- 全局规则（六字原则、clean-code）自动加载，不需要 skill 层引用
- auto-goal 的任何后续变更不再影响 coding skill

**变更文件**：
- `plugins/cache/.../coding/SKILL.md` — 移除继承声明
- `plugin/skills/coding/SKILL.md` — 移除继承声明

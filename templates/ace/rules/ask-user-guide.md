# AskUserQuestion 使用规范

> 需要向用户澄清歧义、确认方向或获取决策时，按本规范交互。

**Other 选项由工具自动附加**：不要手动在 options 中添加"Other"或"自由输入"。用户选 Other 表示自由输入文本，读取该文本并据此行动。

---

## 模式一：问题澄清

多个独立问题需用户选择（设计决策、范围确认、策略选择）时使用。

```
AskUserQuestion(questions: [
  {
    header: "简短标签（≤12 字符）",
    question: "具体问题？",
    options: [
      {label: "选项 A (推荐)", description: "推荐理由"},
      {label: "选项 B", description: "权衡说明"},
      {label: "选项 C", description: "权衡说明"}   // 可选第三项
    ]
    // 系统自动附加 Other 选项，用户可自由输入
  },
  // ... 更多问题（单次 ≤4）
])
```

- 每个 question = 一个独立问题（独立 tab）；有依赖关系的问题拆到下一轮
- options = 2-4 个预设选项，推荐项加"(推荐)"并置首，description 写理由/权衡
- 单次最多 4 个 question，超出则分多轮
- 方案取舍难以用文字说清时，用 `preview` 字段展示具体差异（代码/布局/配置对比）

## 模式二：审批确认

已展示完整内容、需要"通过/不通过"决策时使用。**先用 markdown 呈现完整内容**（四要素、设计摘要、计划概览等），再在同一 response 中：

```
AskUserQuestion(questions: [{
  header: "确认",
  question: "以上内容是否准确？",
  options: [
    {label: "通过", description: "确认正确，继续下一步"},
    {label: "拒绝", description: "有偏差，需要重新调整"}
  ]
  // 用户选 Other 并输入内容 = 有补充的通过（视为通过 + 补充事项）
}])
```

- 通过 → 继续下一步
- Other（输入补充内容）→ 读取补充 → 更新内容 → 继续
- 拒绝 → 回退到前一步重新执行

---

## 反模式

| 错误做法                         | 正确做法                             |
| -------------------------------- | ------------------------------------ |
| 把长文本塞进 question 字段       | 先 markdown 输出，再用审批模式确认   |
| 澄清与审批混在同一次调用         | 分开：先澄清得到答案，再基于答案审批 |
| 问题过于开放（"你觉得怎么样？"） | 给具体选项 + 推荐项                  |
| 手动添加"Other"选项              | 系统自动提供，不要重复               |

---

## 其他平台

其他 AI 编码平台应创建对应规则文件，映射到各自的交互工具；无等价工具时降级为同语义 Markdown 提问（保留选项、推荐项与自由补充入口），不得退化为开放式问题墙。

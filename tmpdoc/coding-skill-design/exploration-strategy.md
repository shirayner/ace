# 阶段探索策略深度分析

> 本文档分析 spec-coding 各阶段需要什么上下文、如何探索、如何确定边界。
> 是主设计方案 (design.md) 的补充参考。

---

## 1. 阶段合并决策

### 从 7 阶段 → 6 阶段

```
旧：understand → clarify → propose → design → plan → build → archive
新：understand → propose → design → plan → build → archive
```

**合并理由**：
- 用户视角只看到"在理解需求" — 不需区分内部分析和交互提问
- 两者是同一认知活动的两步（分析 → 验证），不应人为切割
- 无人会在"分析完"和"开始提问"之间中断恢复
- Superpowers brainstorming 也是一个连续流程

**保留的纪律**：阶段内部仍有严格顺序：
```
Phase 1: Understand
  ├── Step A: 内部深度分析（先想）
  │     探索 + 苏格拉底追问 + 维度分析 + 范围检测 + Defeater
  │     → 产出 unknowns + scope_assessment
  └── Step B: 交互对齐（后问）
        基于 unknowns 提问 → AskUserQuestion → 四要素确认
```

## 2. 两个主要探索阶段对比

| 维度 | Phase 1: Understand | Phase 3: Design |
|------|---------------------|-----------------|
| **核心问题** | 做什么？为什么？不做什么？ | 怎么做？放哪里？影响谁？ |
| **信息源** | 用户头脑 + 高层项目状态 | 代码库 + 技术文档 |
| **探索深度** | 浅（只看结构和 spec，不读实现） | 深（读实现、追调用链、学模式） |
| **交互对象** | 用户（AskUserQuestion） | 代码库（Read/Grep/Agent） |
| **产出** | unknowns → 对齐确认 → proposal 输入 | 架构理解 → 方案选择 → design.md |
| **边界类型** | 功能边界（什么做什么不做） | 技术边界（改哪里不改哪里） |
| **时间** | 快（几轮问答） | 慢（深度代码探索） |
| **范围检测** | 主检测（分不分解？） | 不做（Phase 1 已决定） |

**关键原则**：
- Phase 1 不应深入代码 — 在知道"做什么"之前，不知道该探索哪里
- Phase 3 不应再问需求 — 发现需求不清应回退 Phase 1，不在 Design 中夹杂澄清

## 3. Phase 1: Understand — 上下文需求与探索策略

### 3.1 需要什么上下文？

| 上下文类型 | 来源 | 获取方式 | 解决什么问题 |
|-----------|------|---------|------------|
| **用户意图** | 用户输入 | 解析 ARGUMENTS | 表面需求是什么 |
| **历史经验** | `openspec/experience.md` | Read | 同类需求踩过什么坑 |
| **已有规范** | `openspec/specs/` | Read/Glob | 当前系统已承诺什么行为 |
| **项目方向** | Git log / README | Bash/Read | 近期在做什么，大方向 |
| **业务领域知识** | 用户头脑 | AskUserQuestion | 只有用户知道的隐含约束 |
| **范围边界** | 用户输入 + 代码结构 | 分析 + 提问 | 做多大？包括/不包括什么？ |

### 3.2 如何探索？

```
Phase 1 探索是"鸟瞰式"的，目的是决定问什么问题，不是理解代码实现。

并行探索（≥3 源时并行 Agent）：
├── openspec/experience.md → 历史经验（坑、模式）
├── openspec/specs/ 目录 Glob → 已有规范领域
├── openspec/specs/ 相关领域 Read → 当前行为承诺
├── 项目结构 Glob → 技术栈、分层概览
└── Git log --oneline -20 → 近期方向
```

### 3.3 如何确定功能边界？

```
边界判断四问：

1. 包括什么？（功能范围）
   "用户认证" = 登录 + 注册 + 忘记密码 + 第三方登录？
   → AskUserQuestion 确认范围

2. 不包括什么？（显式排除）
   权限管理？审计日志？多租户？
   → 写入 proposal "Out of Scope"

3. 在哪里停？（深度边界）
   只做 API 层？还是到前端？到部署配置？
   → AskUserQuestion 确认层次

4. 与什么衔接？（接口边界）
   这个变更完成后，下一步是什么？
   → 决定本次预留什么接口
```

### 3.4 信息充分性检查

```
按优先级检查，产生 unknowns：

1. 意图清晰吗？
   → "添加认证"是 OAuth？JWT？Session？SSO？
   → 不清晰 → unknown

2. 范围明确吗？
   → 只是 API 认证？包括前端？包括权限？
   → 模糊 → unknown + 范围信号检测

3. 约束已知吗？
   → 性能要求？兼容性？时间约束？技术栈限制？
   → 未知 → unknown

4. 成功标准明确吗？
   → 用户怎么判断"做完了"？
   → 模糊 → unknown
```

### 3.5 关键原则

- **不读代码实现** — 只看结构和高层信息
- **unknowns 驱动提问** — 不是"我该问什么"，而是"我不知道什么"
- **AskUserQuestion 是唯一验证方式** — 内部分析再充分也需要确认
- **范围检测在这里做** — 问细节前先评估范围是否需要分解

## 4. Phase 3: Design — 上下文需求与探索策略

### 4.1 需要什么上下文？

| 上下文类型 | 来源 | 获取方式 | 解决什么问题 |
|-----------|------|---------|------------|
| **架构全貌** | 项目结构 | Glob + 关键文件 Read | 分层？模块划分？入口点？ |
| **相关模块** | 代码搜索 | Grep 关键词 | 哪些模块需要改？ |
| **现有模式** | 相似功能代码 | Read 示例 | 团队怎么做类似的事？ |
| **接口契约** | API/Interface 定义 | Read + Grep | 上下游期望什么？ |
| **技术约束** | 配置/依赖 | package.json/pom.xml | 版本限制？可用库？ |
| **测试基础设施** | 测试目录 | Glob + Read 示例 | 怎么测试？覆盖率要求？ |
| **性能约束** | 配置/监控 | Read + 经验 | 延迟要求？并发量？ |
| **集成点** | 调用方/被调用方 | Grep 引用 | 改这里会影响谁？ |

### 4.2 代码库探索：分层策略

```
Level 1: 全局鸟瞰（~5 秒）
  目的：了解项目是什么
  工具：Glob + Read(README/CLAUDE.md)
  产出：技术栈、分层模式、入口点
  问题：
    - 这是什么类型的项目？（Web/CLI/库/服务）
    - 用什么技术栈？
    - 代码怎么组织的？（按层/按域/按功能）

Level 2: 领域定位（~30 秒）
  目的：找到和需求相关的代码在哪
  工具：Grep(领域关键词) + Grep(路由/端点)
  产出：受影响文件列表
  问题：
    - 相关代码在哪些目录/文件？
    - 从哪个入口进入？（路由？命令？事件？）
    - 有多少文件可能需要改？

Level 3: 模式学习（~1-2 分钟）
  目的：理解团队怎么做类似的事
  工具：Read(一个完整的类似实现)
  产出：编码约定、可复用模式
  问题：
    - 类似功能的完整实现长什么样？
    - 命名约定？错误处理方式？日志方式？
    - 测试怎么写的？
    - 有什么可以直接复用的？

Level 4: 接口与边界分析（~1 分钟）
  目的：确定改动的影响范围
  工具：Grep(接口定义) + Grep(调用方)
  产出：约束清单、影响面
  问题：
    - 谁调用了我要改的代码？
    - 接口契约是什么？（输入/输出类型）
    - 改接口会破坏什么？
    - 数据库 schema 需要变吗？
```

### 4.3 并行化时机

```
L1: 单次操作（太快，不并行）
L2: ≥3 个独立关键词/方向 → 并行 Grep Agent
L3: ≥3 个类似功能模块 → 并行 Read Agent
L4: ≥3 个上下游接口 → 并行分析 Agent
```

### 4.4 如何确定技术边界？

```
边界判断四问：

1. 改什么模块？（变更范围）
   → Grep 关键词 → 定位受影响文件
   → Read 确认是否真的需要改
   → 原则：能不改就不改

2. 不改什么？（影响隔离）
   → Grep 调用方 → 列出依赖此模块的代码
   → 接口不变 = 不影响
   → 接口变 = 评估影响 + 可能需要通知上游

3. 新代码放哪？（位置决策）
   → 遵循现有模式：相似功能在哪个目录？
   → 新文件 vs 修改现有文件的判断：
     - 新职责 → 新文件
     - 扩展已有职责 → 修改现有文件
     - 文件已过大 → 拆分（但在 plan 中说明）

4. 怎么验证不破坏？（安全网）
   → 现有测试覆盖了什么？
   → 需要新增什么测试？
   → 有无集成测试/E2E 测试可以运行？
```

### 4.5 现有代码库工作原则（Superpowers 借鉴）

```
1. 先探索再提议
   → 不要基于假设设计。实际读代码。

2. 遵循现有模式
   → 团队用 Repository Pattern？你也用。
   → 团队用函数式？你也用。
   → 不引入不一致的新风格。

3. 只改进影响当前工作的问题
   → 发现 spaghetti code？如果不影响你的变更，不碰。
   → 发现代码质量问题？只改你路过的地方。
   → "顺便改好" ≠ "专门重构"

4. 设计隔离性
   → 每个单元：单一目的、定义良好的接口、可独立测试
   → 判断标准：能否不看内部就理解做什么？能否改内部不破坏消费者？
```

## 5. 两阶段的信息流

```
Phase 1: Understand
  输入：用户描述 + 高层项目信息
  探索：鸟瞰式（结构、spec、经验）
  产出：scope_assessment + unknowns → 对齐确认 → 功能边界

      │
      ▼ proposal.md（功能边界 = design 的约束输入）

Phase 3: Design
  输入：proposal（做什么）+ 代码库（现在什么样）
  探索：深入式（实现、调用链、模式）
  产出：技术边界 + 架构方案 → design.md

      │
      ▼ design.md（技术方案 = plan 的约束输入）

Phase 4: Plan
  输入：design.md（怎么做）
  探索：几乎不需要（design 已确定）
  产出：tasks.md（原子步骤）
```

## 6. 各阶段需要考虑的问题清单

### Phase 1: Understand 问题清单

```
意图理解：
□ 用户表面需求是什么？
□ 背后的根本问题/目标是什么？
□ 有没有更好的问题框架？

范围判断：
□ 这是一个独立变更还是需要分解？
□ 涉及几个独立子系统？
□ 范围信号：≥2 独立子系统？"平台"等宏大词汇？

约束识别：
□ 时间约束？（急不急？）
□ 技术约束？（必须用什么？不能用什么？）
□ 兼容约束？（不能破坏什么？）

经验检索：
□ 以前做过类似的吗？踩过什么坑？
□ experience.md 中有相关经验吗？
□ 已有 spec 对相关领域说了什么？

对齐准备：
□ 还有什么不确定？（unknowns 列表）
□ 我的假设中哪些需要确认？
□ 用户可能对什么惊讶？
```

### Phase 3: Design 问题清单

```
架构理解：
□ 项目整体分层是什么？
□ 请求从哪里进入？经过哪些层？
□ 数据怎么流动的？

定位与影响：
□ 需要改哪些文件？
□ 谁依赖这些文件？改了会影响谁？
□ 数据库 schema 需要变吗？

模式学习：
□ 团队怎么做类似的事？（找一个示例）
□ 命名约定是什么？
□ 错误处理模式？日志模式？
□ 测试怎么写的？

方案设计：
□ 有几种可行方案？
□ 各方案的权衡是什么？
□ 推荐哪个？为什么？

设计质量：
□ 每个单元职责单一吗？
□ 接口定义清晰吗？
□ 可以独立测试吗？
□ YAGNI：有没有加了不需要的东西？

风险评估：
□ 什么可能出错？
□ 性能影响？
□ 回滚策略？
```

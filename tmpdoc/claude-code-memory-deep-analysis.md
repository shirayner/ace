> 分析日期: 2026-04-15
> 分析主题: Claude Code auto memory 完整机制解析 + 全局高价值记忆收集方案

## 1. Memory 机制全景

### 1.1 定位：Claude 的跨会话学习系统

Claude Code 的 auto memory 是一个**文件驱动的、跨会话持久化学习系统**。它解决的核心问题是：

> 每次新会话启动时，Claude 对用户一无所知。Memory 让 Claude 能够积累对用户、项目和工作方式的理解，避免重复犯错、重复提问。

**类比理解：**

| 人类记忆系统 | Claude Code 对应 |
|-------------|-----------------|
| 工作记忆（短期） | 上下文窗口（单次会话） |
| 长期记忆 | auto memory（`MEMORY.md` + 主题文件） |
| 习惯/肌肉记忆 | `CLAUDE.md` + `rules/`（用户编写的指令） |
| 外部笔记本 | `.tasks/state.md`（任务进度） |

### 1.2 存储架构

```
~/.claude/
├── memory/                          ← 全局 memory（需配置 autoMemoryDirectory）
│   ├── MEMORY.md                    ← 索引文件（每次会话自动加载）
│   ├── user_profile.md              ← 主题文件（按需加载）
│   ├── feedback_*.md
│   └── reference_*.md
│
├── projects/
│   └── <project-hash>/memory/       ← 默认的项目级 memory（按项目隔离）
│       ├── MEMORY.md
│       └── *.md
```

**两层结构的设计逻辑：**

- **MEMORY.md（索引层）** — 始终加载，是 Claude 的"记忆目录"，每条记录是一行链接+摘要
- **主题文件（详情层）** — 按需读取，存储具体内容，支持 YAML frontmatter 元数据

### 1.3 加载机制

```
会话启动
  │
  ├─→ 加载 MEMORY.md（前 200 行 / 25KB，先到者为准）──→ 注入系统上下文
  │
  └─→ 主题文件 NOT 加载（仅当 Claude 判断需要时，通过 Read 工具按需读取）
```

**关键数字：**

| 参数 | 值 | 说明 |
|------|-----|------|
| MEMORY.md 自动加载上限 | 200 行 或 25KB | 先到者为准，超出部分静默忽略 |
| 主题文件加载方式 | 按需 Read | 不在启动时加载 |
| 存储位置 | 机器本地 | 不跨设备同步 |
| 作用域（默认） | 按项目隔离 | 同 git 仓库内所有目录共享 |

### 1.4 生命周期

```
触发条件满足 → Claude 自主决策保存
                ↓
         创建/更新主题文件 + 更新 MEMORY.md 索引
                ↓
         后续会话加载 MEMORY.md → 按需读取主题文件
                ↓
         Claude 可更新已有主题文件（追加、修正）
                ↓
         ❌ 不会主动删除过时记忆（需用户手动维护）
```

**保存时的 UI 信号：** 终端会显示 `Writing memory` 或 `Recalled memory`，表示 Claude 正在读写 memory 文件。

## 2. 五种记忆类型详解

Claude Code 系统提示中定义了四种正式记忆类型，加上一种隐性的"元记忆"：

### 2.1 类型矩阵

| 类型 | 核心问题 | 触发场景 | 衰变速度 | 跨项目价值 |
|------|---------|---------|---------|-----------|
| **user** | "这个用户是谁？" | 暴露角色、偏好、技术背景 | 极慢（角色稳定） | ★★★★★ 最高 |
| **feedback** | "用户想要什么样的协作方式？" | 纠正做法 / 确认非显而易见的做法 | 慢 | ★★★★★ 最高 |
| **project** | "这个项目有什么特殊情况？" | 提到决策、截止日期、约定 | 快（状态变化快） | ★★☆☆☆ 低 |
| **reference** | "信息在哪里可以找到？" | 提到外部资源位置 | 中等 | ★★★☆☆ 中 |

### 2.2 各类型深度解析

#### user 类型 — 用户画像

**目的：** 让 Claude 理解"我在跟谁说话"，从而调整协作风格。

**高价值示例：**
```markdown
---
name: User Profile
type: user
---
- 后端开发 10 年经验，Java 为主
- 第一次接触 React 前端
```
→ 效果：解释前端概念时会用后端类比，不会过度解释 Java 知识。

**低价值示例：**
- "用户今天心情不好" — 临时状态，下次会话无意义
- "用户在 D 盘工作" — 环境信息可从系统自动获取

#### feedback 类型 — 协作偏好

**目的：** 记录用户的纠正和确认，避免同一错误重复发生。

**这是最关键的高价值记忆类型。** 系统提示明确要求：
- 纠正（"不要这样做"）→ 自动保存
- 确认非显而易见的做法（"对，就这样"）→ 自动保存

**高价值示例：**
```markdown
---
name: No Mock DB in Tests
type: feedback
---
集成测试必须连接真实数据库，不使用 mock。
**Why:** 上季度 mock 测试全通过但 prod 迁移失败的事故。
**How to apply:** 写测试时检查是否涉及 DB 操作，如是则用 testcontainers。
```

**结构建议：** 规则 + **Why**（原因）+ **How to apply**（应用场景）

#### project 类型 — 项目状态

**目的：** 记录项目级的非代码信息（谁在做什么、为什么、什么时候截止）。

**注意：** 这是衰变最快的类型。决策可能被推翻，截止日期可能延期。

**高价值示例：**
```markdown
---
name: Auth Rewrite Motivation
type: project
---
认证中间件重写由法务合规驱动（session token 存储不合规），
不是技术债清理。范围决策应优先合规而非开发体验。
```

**低价值示例：**
- "本周五发布" — 过了就失效
- "张三在改登录页" — 状态很快变化

#### reference 类型 — 信息指针

**目的：** 记录"去哪里找信息"，而非信息本身。

**高价值示例：**
```markdown
---
name: Oncall Dashboard
type: reference
---
grafana.internal/d/api-latency 是值班延迟看板。
改动请求处理路径代码前应查看此看板。
```

### 2.3 记忆分级框架

可用于评估一条记忆是否值得保存：

| 维度 | 高价值 | 低价值 |
|------|--------|--------|
| 复用频率 | 每次会话都可能用到 | 仅单次会话相关 |
| 可推导性 | 无法从代码/git/文档推导 | 看代码就知道 |
| 影响范围 | 影响整体协作风格或决策 | 仅影响单个操作 |
| 时效性 | 长期有效（> 1 个月） | 几天后失效 |
| 独特性 | 反直觉的、踩过坑的 | 常识性的、显而易见的 |

## 3. 系统内建的记忆质量控制

### 3.1 系统提示中已有的"不保存"规则

Claude Code 的系统提示中**已经内建了一套过滤规则**，明确列出了 NOT to save 的内容：

| 不保存的类型 | 原因 |
|-------------|------|
| 代码模式、架构、文件路径 | 从代码本身可推导 |
| Git 历史、最近变更 | `git log` / `git blame` 是权威源 |
| 调试方案、修复步骤 | 修复在代码中，commit message 有上下文 |
| CLAUDE.md 中已有的内容 | 避免重复 |
| 临时任务状态 | 属于 `.tasks/` 的职责 |

### 3.2 系统提示中的保存触发规则

| 触发场景 | 记忆类型 | 自动程度 |
|---------|---------|---------|
| 用户说"记住 X" | 最合适的类型 | **立即保存** |
| 用户说"忘掉 X" | — | **立即删除** |
| 用户纠正做法 | feedback | **自动保存** |
| 用户确认非显而易见做法 | feedback | **自动保存**（但信号弱，容易遗漏） |
| 暴露角色/偏好 | user | 自动保存 |
| 提到外部资源 | reference | 自动保存 |
| 提到项目决策/截止日期 | project | 自动保存 |

### 3.3 内建规则的局限

系统提示给出的是**意图指导**，不是硬编码的 if-else 逻辑。Claude 的实际保存行为是**概率性的**：

- 有时会保存不够高价值的记忆（假阳性）
- 有时会遗漏值得保存的信息（假阴性）
- **确认信号**（用户说"对"）比**纠正信号**（用户说"不要"）更容易被忽略
- 复杂的长对话中，后期的信号可能被 attention 稀释

**这就是为什么需要额外的 rules 声明来强化记忆质量控制。**

## 4. autoMemoryDirectory 全局化方案

### 4.1 配置方式

在 `~/.claude/settings.json`（用户级设置）中添加：

```json
{
  "autoMemoryDirectory": "~/.claude/memory"
}
```

| 配置位置 | 是否支持 | 说明 |
|---------|---------|------|
| `~/.claude/settings.json`（用户级） | ✅ | 推荐，影响所有项目 |
| `.claude/settings.local.json`（本地） | ✅ | 仅影响当前项目 |
| `.claude/settings.json`（项目级） | ❌ | 安全限制，防止共享仓库劫持 memory 路径 |
| 策略配置（managed policy） | ✅ | 组织级管控 |

### 4.2 行为变化

| 方面 | 默认行为 | 配置 autoMemoryDirectory 后 |
|------|---------|---------------------------|
| 存储位置 | `~/.claude/projects/<hash>/memory/` | `~/.claude/memory/` |
| 项目隔离 | 每个项目独立 memory | **所有项目共享同一份** |
| MEMORY.md 加载 | 加载项目级索引 | 加载全局索引 |
| 写入目标 | 写入项目级目录 | 写入全局目录 |

### 4.3 Trade-off 分析

**收益：**
- ✅ 跨项目积累用户偏好和协作模式
- ✅ 切换项目时不丢失已积累的反馈记忆
- ✅ 一处维护，所有项目受益
- ✅ 高价值的通用经验（编码习惯、审查偏好）自然积累

**代价：**
- ⚠️ 项目特定记忆混入全局空间（"项目 A 用 Gradle"出现在项目 B 中）
- ⚠️ MEMORY.md 可能膨胀更快（多项目写入同一索引）
- ⚠️ 200 行上限在多项目场景下更容易触达

**缓解策略：**
1. 通过 rules 声明只保存高价值、跨项目通用的记忆
2. 项目特定信息放在项目级 `CLAUDE.md` 而非 memory
3. 定期手动修剪 MEMORY.md（将其视为需要维护的代码）

## 5. 高价值记忆筛选策略

### 5.1 核心问题

默认的系统提示已有基础过滤，但不够精确。用户需要**额外声明**来告诉 Claude：

> "在全局 memory 场景下，提高保存门槛，只记录真正跨项目、高复用、反直觉的信息。"

### 5.2 声明位置选择

| 方案 | 位置 | 优缺点 |
|------|------|--------|
| A. 写在 `~/.claude/rules/memory-policy.md` | 全局 rules | ✅ 推荐。模块化、不污染 CLAUDE.md、始终生效 |
| B. 写在 `~/.claude/CLAUDE.md` | 全局指令 | ⚠️ 可行但增加 CLAUDE.md 长度（官方建议 < 60 行） |
| C. 写在 MEMORY.md 自身 | memory 索引 | ❌ 不推荐。占用 200 行配额且语义混乱 |

**结论：使用 `~/.claude/rules/memory-policy.md` + 在 CLAUDE.md 中 `@` 引用。**

### 5.3 推荐的 Memory Policy 规则

```markdown
# Memory 质量策略

## 保存门槛（全局 memory 场景）

Memory 是跨项目共享的，保存前必须通过以下检验：

### 必须满足（AND）
1. **跨会话价值** — 这条信息在未来的会话中会被用到吗？（仅当前会话有用的不保存）
2. **不可推导** — 这条信息无法从代码、git history、文档中推导出来吗？

### 至少满足一项（OR）
3. **反直觉** — 这是踩过坑才知道的经验？还是常识？（只保存非显而易见的）
4. **高复用** — 这条规则会在 >3 个不同会话中适用吗？
5. **纠错信号** — 用户明确纠正了我的行为，且这个纠正适用于未来场景？

### 绝不保存
- 项目特定的构建命令、文件结构、技术栈（放项目级 CLAUDE.md）
- 临时状态（当前任务进度、临时决策）
- 代码模式、架构细节（从代码推导）
- Git 历史摘要（从 git log 获取）

### 保存时的格式要求
- feedback 类型必须包含 **Why** + **How to apply**
- 标题必须一看就知道内容（不要用 "记忆1" 这样的名字）
- 每条记忆控制在 10 行以内
- 定期检查已有记忆是否过时，过时则更新或删除
```

### 5.4 为什么 rules 声明有效？

Claude Code 的规则加载优先级：

```
系统提示（内建）
  ↓ 叠加
~/.claude/CLAUDE.md → @rules/*.md（全局用户级）
  ↓ 叠加
项目级 CLAUDE.md → 项目 rules/（项目级）
```

`rules/*.md` 中的指令与系统提示中的 auto memory 指令**叠加生效**。实测表明：
- 5 个 30 行规则文件的遵循率约 **96%**
- 单个 150 行 CLAUDE.md 的遵循率约 **92%**
- 高优先级指令放在文件开头，效果更好

因此，在 rules 中声明记忆策略是**有效的、推荐的做法**。它不是"硬编码"（Claude 仍可能偶尔违反），但能显著提升记忆质量。

## 7. 关键结论

1. **Memory 机制是"软"控制** — 基于系统提示引导 Claude 的自主判断，不是 if-else 硬编码。因此需要通过 rules 声明来**强化**质量标准。

2. **全局 memory 的核心价值在于 feedback 类型** — user profile 变化少（设一次就够），reference 偶尔更新，但 feedback（纠正 + 确认）是持续积累的高价值资产。

3. **必须在 rules 中声明 Memory Policy** — 否则默认行为会保存过多低价值记忆，在全局共享场景下尤其有害（多项目噪声叠加）。

4. **MEMORY.md 是稀缺资源** — 200 行上限意味着每条索引记录都要精练。把 MEMORY.md 当作代码来维护：定期 review、refactor、prune。

5. **记忆的理想状态** — 经过 3-6 个月的日常使用后，全局 memory 应该沉淀出：
   - 1 份稳定的用户画像
   - 10-20 条高价值 feedback（纠错经验 + 确认的好做法）
   - 5-10 个外部资源指针
   - 总计 < 100 行 MEMORY.md 索引

# 对抗深挖技法库（重档）

> 何时用：某个决策点命中了升级触发器（见 clarify-leveling.md 的惊讶测试）。
> 用这里的技法把这一个高风险点彻底问透，再回到本 skill 主流程 frontier。
> 原则不变：重档点串行单问（不与其他点合并）、自带推荐答案与选项、能自查的事实不问用户。格式仍守 `ask-user-guide.md` 的结构化提问契约。

## 1. 决策树遍历

把这个高风险点继续往下拆成子决策，沿依赖分支逐个下降，一次解一个。先答的子决策会重塑后面要问什么。

例（"加个搜索功能"是高风险点）：
```
搜什么？──► 商品 / 订单 / 用户？（先定这个）
  └─定为"商品"──► 按什么搜？名称 / SKU / 分类 / 标签？
        └─定为"名称+SKU"──► 要模糊匹配吗？拼音/错别字容错？
              └─► 结果怎么排序？相关度 / 销量 / 价格？
                    └─► 无结果时怎么办？推荐 / 空态 / 纠错提示？
```
每个箭头都是一次提问（附推荐答案）。走到没有子分支为止。

## 2. 术语压测

需求里的词往往被重载或歧义。逼出精确定义：
- **术语冲突即时点破**："你前面说的'用户'和这里的'账号'是同一个东西吗？"
- **重载词逼精确**："'账号'指的是 Customer（付费主体）还是 User（登录个体）？一个 Customer 下可以有多个 User 吗？"
- **建 glossary**：确认下来的定义即时记入术语表，后续统一用词。

术语不清 → 后面所有讨论都是各说各话。这一步优先做。

## 3. 边界反例

用具体的极端/边界场景去压测，暴露没考虑到的情况：
- "如果用户同时在两个设备登录，购物车怎么合并？"
- "订单金额为 0（全额优惠券）时，这个流程还成立吗？"
- "列表有 10 万条时，这个默认排序还能用吗？"
- "用户没有任何历史数据（新用户），这个页面显示什么？"

反例逼出的答案，往往是原始需求里完全没提的关键规则。

## 4. 假设攻破（Defeater）

主动找自己/用户理解里的隐含前提，尝试推翻它：
- 列出你正在依赖的假设："我假设这个功能只给内部员工用。"
- 主动质疑："如果外部用户也能访问呢？前提还成立吗？"
- 前提被攻破 → 明确告诉用户："我注意到 [某断言] 的前提可能不成立，因为 [原因]，需要你确认。"

这是暴露盲区最有力的一招——攻破的往往是双方都默认、却从没说出口的假设。

## 5. 5 Whys 溯因

用户常直接给方案，而非真实问题。连问为什么，穿透到根因，区分"想要的方案"和"真正的问题"（避免 XY 问题）：
```
用户："我要一个导出 Excel 的按钮。"
  为什么要导出？──"要把数据发给财务。"
    为什么发给财务？──"他们每月要对账。"
      为什么手动对账？──"因为两个系统数据不通。"
→ 真问题可能是"系统对账"，导出 Excel 只是绕路的方案。
```
挖到根因后，回来和用户确认："真正要解决的是不是 X？导出只是其中一种做法？"

## 6. 交叉验证

把用户的陈述与可查证的事实对照，找矛盾：
- 与现有代码/系统行为对照：用户说"现在没有这个限制"，但代码里明明有 → 点破。
- 前后陈述对照：用户前面说"只给管理员"，后面又说"客服也要用" → 请求澄清。
- 与已定决策对照：新答案是否和 glossary/已定决策冲突？

矛盾即信号——要么理解错了，要么需求本身没想清。

---

## 7. 何时停

对这个决策点的深挖，满足即停、回到主流程：
- 该点的所有子分支都走过（决策树遍历完）。
- 相关术语已精确定义、无冲突。
- 关键边界场景有了明确规则。
- 依赖的假设都被显式确认过。

不要为深挖而深挖。挖透这一个点 → 回轻档节奏，取 frontier 下一个点。

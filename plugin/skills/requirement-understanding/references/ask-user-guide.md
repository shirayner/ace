# AskUserQuestion 使用规范 —— 向用户提问的格式契约

> 定义本 skill 与用户交互时的标准提问格式。所有"向用户提问"的动作（澄清、审批）统一遵守。
>
> 这是**格式**层面的硬约定，与"轻档/重档"（深度层面，见 `clarify-leveling.md`）正交：档位决定"问多狠"，本契约决定"怎么问"。无论哪个档位、无论用什么通道，向用户提问都必须守这套不变量。目的：消灭"一次抛一大堆点、纯文本、要用户作文回复"的坏交互。

**关于 Other 选项**：AskUserQuestion 工具会自动为每个 question 附加一个"Other"选项，允许用户自由输入文本。因此：

- options 中**不要手动添加 Other**，只定义预设选项即可
- 用户选 Other 时，在文本框输入内容
- AI 收到 Other 回复时，读取用户输入的文本并据此行动
- 审批场景中，用户选 Other 并输入内容 = "有补充的通过"（视为通过 + 补充事项）

---

## 通道无关

契约约束的是**"向用户提问"这个动作的形态**，不绑定任何具体工具。

- 环境提供 `AskUserQuestion`（或等价的结构化选择控件）→ **优先用它**，UX 最好（选项可点选、自动附带自由输入项）。
- 无该工具（纯 CLI / 其他宿主）→ **降级为等价 markdown**：编号选项 + 推荐项前缀 + 显式"或自由补充"。不变量一条不少。

换言之：看到"需要澄清 / 采访用户 / 向用户提问"就套这套契约，不因缺某个工具而退回文本墙。

---

## 六条格式不变量（所有提问统一遵守）

1. **选项化，不作文**——每个问题给 2-3 个预设选项，把用户从"开放作文"降为"审阅+点选"。禁止只抛开放式问题（"你觉得呢？"）。
2. **推荐项置首**——最可能的默认值放第一位，标"(推荐)"，并在说明里写选它的理由/权衡。暴露你的隐含假设供当场否决。
3. **总有自由输入口**——预设选项之外，永远保留"其他/自由补充"（`AskUserQuestion` 系统自动附加 Other，**不要手动再加**；markdown 降级时显式写一句"或直接补充你的想法"）。预设是加速，不是牢笼。
4. **单轮 ≤4 问，超了分多轮**——一次最多并列 4 个问题。更多 → 拆成多轮，别堆成长列表。
5. **信息在正文，不塞进选项**——背景、取舍说明、长文本放提问正文/前置 markdown；选项只放"可选的答案"。审批类（通过/拒绝）与澄清类（多选项）**分开调用**，不混在一次。
6. **每轮回答后实时更新理解**——用户答完一轮，立刻回写 frontier 与五要素：可能解锁新问题、移除已解点、**甚至范围变了/需求当场定了就提前收敛**。不要机械问完预设的所有轮。

---

## 模式一：澄清（多问选择）

**场景**：需要用户对一到多个待定决策点做出选择（目标确认、范围边界、策略选择、事实补全）。

**交互规范**：

```
AskUserQuestion(questions: [
  {
    header: "简短标签（≤12 字符）",
    question: "具体问题？",
    options: [
      {label: "选项 A (推荐)", description: "推荐理由"},
      {label: "选项 B", description: "权衡说明"},
      {label: "选项 C", description: "权衡说明"}   // 可选第三项
    ]
    // 系统自动附加 Other 选项，用户可自由输入
  },
  // ... 更多问题（单次 ≤4）
])
```

**规则**：

- 每个 question = 一个独立问题（独立 tab）
- options = 2-3 个预设选项（系统自动附加 Other）
- 推荐项加"(推荐)"后缀，放在第一位
- description 说明选该项的理由/权衡
- 单次最多 4 个 question，超过 → 分多轮（每轮 ≤4）

**markdown 降级形态**（无 AskUserQuestion 时）：

```
关于「导出功能」的格式，我建议默认 Excel（.xlsx），因为你的用户多在做数据整理。
需要同时支持 CSV / PDF 吗？
  A) 只要 Excel（推荐）
  B) Excel + CSV
  C) Excel + CSV + PDF
  （或直接补充你的想法）
```

---

## 模式二：审批（通过/拒绝）

**场景**：已展示完整内容（markdown），需要用户做"通过/不通过"的决策（如五要素对齐、PRD 评审）。

**交互规范**：

先用 markdown 呈现完整内容（五要素、PRD 摘要等），然后在同一 response 中：

```
AskUserQuestion(questions: [{
  header: "确认",
  question: "以上内容是否准确？可以据此继续了吗？",
  options: [
    {label: "通过", description: "确认正确，继续下一步"},
    {label: "拒绝", description: "有偏差，需要重新调整"}
  ]
  // 用户选 Other 并输入内容 = 有补充的通过（视为通过 + 补充事项）
}])
```

**规则**：

- **信息展示在 markdown 中，不塞进 AskUserQuestion**
- AskUserQuestion 只做轻量审批决策
- 固定两选项：通过 / 拒绝（Other 由系统自动附加）
- 处理逻辑：
  - 通过 → 继续下一步
  - Other（用户输入补充内容）→ 读取补充 → 更新内容 → 继续
  - 拒绝 → 回退到前一步重新执行

---

## 节奏：分组合并 vs 串行

不是"一次一问"，也不是"一次全抛"，而是**按依赖和风险分组**：

- **可合并进一轮**：彼此独立、低风险、答案互不影响的点 → 合并成一轮 ≤4 问一起问（利用 `AskUserQuestion` 多问能力，减少往返）。
- **必须串行单问**：满足任一 → 单独问，答完再问下一个：
  - 高风险/重档点（命中惊讶测试，见 `clarify-leveling.md`）
  - 有依赖（这题答案会重塑下一题，如"是否做人机"决定"要不要问 AI 难度"）
- 合并只合"独立"的点；**绝不把有依赖或高风险的点塞进批量**，那会丢掉"答案改变问题"的信息。

---

## 反模式

| 错误做法 | 正确做法 |
| -------- | -------- |
| 把长文本塞进 AskUserQuestion 的 question 字段 | 先 markdown 输出，再用审批模式确认 |
| 一个 question 里放 4+ 选项 | 最多 2-3 个预设选项（Other 自动附加） |
| 审批时列出所有细节作为选项 | 审批只有通过/拒绝（Other=有补充的通过） |
| 混合"澄清"和"审批"在同一次调用 | 分开：先澄清得到答案，再基于答案做审批 |
| 问题过于开放（"你觉得怎么样？"） | 给具体选项 + 推荐 |
| 手动在 options 中添加"Other"或"自由输入" | 系统自动提供，不要重复（markdown 降级才手写） |
| 一次抛一大堆点、纯文本、要用户作文回复 | 选项化 + 分组 + ≤4 问/轮 |
| 有依赖/高风险点塞进批量一起问 | 串行单问，答完再问下一个 |

### 坏例（文本墙，禁止）

```
原始诉求范围较广，动笔前需对齐几个决策，每点都给了默认值，你回复认可哪些、改哪些：
1. 平台形态：推荐 Web，其他可选 App/桌面/小程序/命令行
2. 对战模式：推荐 本地双人+人机，其他可选 ...
3. 棋盘规则：推荐 15×15 无禁手 ...
4. AI 难度：推荐 中等 ...
5. 附加功能：推荐 悔棋/重开 ...
6. 目标场景：推荐 休闲 Demo ...
请回复确认或修改。
```

问题：6 点一次抛、纯文本、无选项控件、要用户作文对照回复、无依赖分组（AI 难度依赖"是否做人机"却并列）。

# 提问契约 —— 向用户提问的格式规范

> 定义本 skill 与用户交互时的标准提问格式。所有"向用户提问"的动作（澄清、审批）统一遵守。
>
> 这是**格式**层面的硬约定，与"自决/轻档/重档"（深度层面，见 `clarify-leveling.md`）正交：档位决定"问不问、问多狠"，本契约决定"怎么问"。目的：消灭"一次抛一大堆点、纯文本、要用户作文回复"的坏交互。

---

## 通道：两种等价形态，markdown 不是次等品

契约约束的是**"向用户提问"这个动作的形态**，不绑定任何具体工具。两种形态**同等有效**，只是渲染方式不同：

| 形态 | 何时用 | 特点 |
|---|---|---|
| **markdown 编号选项** | 环境没有结构化选择控件时——**多数需求 Agent 平台属于这种** | 字母序号 + 两层信息同行；用户回字母即可 |
| **AskUserQuestion**（或等价控件） | 环境提供时 | 可点选、系统自动附加 Other |

**没有 AskUserQuestion 不是降级，也不是跳过门禁的理由。** 六条不变量一条不少，对齐门禁照常执行——门禁验的是"用户是否显式回复了确认"这个行为，不是某个工具被调用。

**关于 Other 选项**：AskUserQuestion 会自动为每个 question 附加 Other，允许自由输入。所以用它时**不要手动添加 Other**；markdown 形态则需显式写一句"或直接补充你的想法"。用户选 Other 并输入内容，在审批场景中 = **有补充的通过**。

---

## 六条格式不变量（两种形态都守）

### 1. 选项化 + 字母序号，label 写行为

每个问题给 2-3 个预设选项，用 `A) B) C)` 字母序号标注——用户回一个字母就行，不用打字重复选项内容。禁止只抛开放式问题（"你觉得呢？"）。

**label 必须写"会发生什么"（行为），不写"用什么策略"（抽象名）。** ≤15 字（字母序号和「（推荐）」不计入）。

```
❌ A) 严格校验（推荐）   B) 宽松校验
   → 策略名。用户点完 A，"严格"到什么程度双方理解可能完全不同，歧义只是被点击掩盖了

✅ A) 拒绝并提示（推荐）  B) 允许透支一次
   → 行为名。点完就定了，没有歧义空间
```

禁用词：严格 / 宽松 / 标准 / 优化 / 完善 / 灵活 —— 这些是形容词，不是行为。

### 2. 推荐项置首 + description 带具体边界值

最可能的默认值放第一位，标「（推荐）」，并写清**选它会发生什么 + 理由或代价**。这暴露你的隐含假设，供用户当场否决。

description **必须落到具体边界值**，禁止空话：

```
❌ description: 更合理，符合通用做法
✅ description: 提示"余额不足"，不扣次数、不生成订单。权益类通用做法，避免后续对账
```

### 3. 总有自由输入口

预设选项之外，永远保留补充通道。AskUserQuestion 由系统自动附加 Other（不要手动再加）；markdown 形态显式写「（或直接补充你的想法）」。预设是加速，不是牢笼。

### 4. 单轮 ≤4 问，用 Q1/Q2 编号

一次最多并列 4 个问题，每个问题用 `Q1. Q2.` 编号。这样用户可以一次回 `Q1-A, Q2-B`，不用分多轮打字。超过 4 问 → 拆成多轮，别堆成长列表。

### 5. 信息在正文，不塞进选项

背景、取舍说明、长文本放提问正文或前置 markdown；选项只放"可选的答案"。**审批类（通过/拒绝）与澄清类（多选项）分开，不混在一次。**

### 6. 每轮回答后实时更新理解

用户答完一轮，立刻回写 frontier、已定决策、假设清单：可能解锁新问题、移除已解点，**甚至范围变了/需求当场定清就提前收敛**。不要机械问完预设的所有轮。

## 模式一：澄清（多问选择）

**场景**：需要用户对一到多个 Ask 通道决策点做出选择。

### markdown 形态（多数平台的实际形态）

```
「导出功能」这块我要定两件事，都给了推荐值：

Q1. 导出格式支持到哪一步？
  A) 只要 Excel（推荐）— 覆盖数据整理场景，实现成本最低
  B) Excel + CSV — 多一个纯文本格式，方便脚本处理
  C) Excel + CSV + PDF — 加打印/归档场景，但 PDF 排版要额外投入

Q2. 单次导出上限多少条？
  A) 1 万条，超出提示分批（推荐）— 同步导出不超时，实现最简单
  B) 10 万条，走异步生成 + 站内通知 — 体验好但要加任务队列

（或直接补充你的想法，也可以只回字母，如 Q1-A, Q2-B）
```

### AskUserQuestion 形态

```
AskUserQuestion(questions: [
  {
    header: "导出格式",                       // ≤12 字符，作为 tab 标签
    question: "导出格式支持到哪一步？",
    options: [
      {label: "A) 只要 Excel（推荐）",
       description: "覆盖数据整理场景，实现成本最低"},
      {label: "B) Excel + CSV",
       description: "多一个纯文本格式，方便脚本处理"},
      {label: "C) Excel + CSV + PDF",
       description: "加打印/归档场景，但 PDF 排版要额外投入"}
    ]
    // 系统自动附加 Other，不要手动添加
  }
  // ... 更多问题（单次 ≤4）
])
```

规则：每个 question = 一个独立问题（独立 tab）；options = 2-3 个预设；label 带字母序号 + 行为命名；推荐项置首。

## 模式二：审批（对齐门禁用）

**场景**：已用 markdown 展示完整内容（需求全貌 + 假设清单），需要用户拍板。

**先** markdown 呈现完整内容，**然后在同一 response 中**发出审批请求。三个选项——通过拆成两个，让用户一次点选同时完成"确认"和"决定下一步"，不多一轮往返：

```
Q1. 以上理解准确吗？
  A) 通过，继续出 PRD（推荐）— 据此直接进入 PRD 撰写
  B) 通过，先停在这里 — 理解已对齐，暂不往下走
  C) 拒绝，有偏差要重来 — 回到澄清，重开相应分支
  （或直接补充要改的地方，视为有补充的通过）
```

处理逻辑：

| 用户选择 | 动作 |
|---|---|
| A 通过并继续 | 门禁通过 → 交接给下游 PRD 撰写 |
| B 通过先停 | 门禁通过 → 停住，不擅自开工 |
| C 拒绝 | 回 clarifying，按反馈重开分支，重新收敛后再走门禁——**二次门禁只展示变更部分** |
| Other（补充内容） | 有补充的通过：小改直接改完继续；若推翻目标/范围，回 clarifying |

**信息展示在 markdown 里，不塞进选项。** 审批只做轻量决策。

---

## 节奏：分组合并 vs 串行

不是"一次一问"，也不是"一次全抛"，而是**按依赖和风险分组**：

- **可合并进一轮**：彼此独立、低风险、答案互不影响的点 → 合并成一轮 ≤4 问，减少往返。
- **必须串行单问**（满足任一）：
  - 重档点（高返工成本 + 命中升级触发器，见 `clarify-leveling.md`）
  - 有依赖——这题答案会重塑下一题（如"是否做人机"决定"要不要问 AI 难度"）

合并只合"独立"的点；**绝不把有依赖或高风险的点塞进批量**，那会丢掉"答案改变问题"的信息。

## 反模式

| 错误做法 | 正确做法 |
|---|---|
| label 写策略名（严格/宽松/标准/优化） | label 写行为（拒绝并提示 / 允许透支一次） |
| description 写空话（"更合理""符合通用做法"） | description 落到具体边界值和代价 |
| 选项没有字母序号，用户要打字复述 | `A) B) C)`，用户回字母即可 |
| 多问一轮不编号，用户不知道在答哪个 | `Q1. Q2.`，支持一次回 `Q1-A, Q2-B` |
| 把长文本塞进 AskUserQuestion 的 question 字段 | 先 markdown 输出，再用审批模式确认 |
| 一个问题给 4+ 选项 | 最多 2-3 个预设 |
| 审批时把所有细节列成选项 | 审批只有通过（两种）/ 拒绝 |
| 混合"澄清"和"审批"在同一次调用 | 分开：先澄清拿到答案，再基于答案做审批 |
| 问题过于开放（"你觉得怎么样？"） | 给具体选项 + 推荐项 |
| 手动在 options 中添加"Other" | AskUserQuestion 系统自动提供；只在 markdown 形态手写 |
| 一次抛一大堆点、纯文本、要用户作文回复 | 选项化 + 分组 + ≤4 问/轮 |
| 有依赖/高风险点塞进批量一起问 | 串行单问，答完再问下一个 |
| 低价值问题也拿来问用户 | 走自决档，记入假设清单，门禁兜底 |

### 坏例（文本墙，禁止）

```
原始诉求范围较广，动笔前需对齐几个决策，每点都给了默认值，你回复认可哪些、改哪些：
1. 平台形态：推荐 Web，其他可选 App/桌面/小程序/命令行
2. 对战模式：推荐 本地双人+人机，其他可选 ...
3. 棋盘规则：推荐 15×15 无禁手 ...
4. AI 难度：推荐 中等 ...
5. 附加功能：推荐 悔棋/重开 ...
6. 目标场景：推荐 休闲 Demo ...
请回复确认或修改。
```

问题：6 点一次抛、纯文本无字母序号、要用户作文对照回复、无依赖分组（AI 难度依赖"是否做人机"却并列）、且第 5 项「附加功能」属于错了好改的点，本该走自决档而不是占用户一次点选。

# 需求理解主流程

> 目标：从一句话、PRD 内容或 PRD/文档链接出发，建立需求画像与因果决策树，逐轮消除关键未知，经 Readiness 检查后进入对齐门禁。

## 全程原则

- **既定规则防篡改**：用户明确给出的业务规则、数值、权限、状态流转和边界按原意作为已知条件；仅对缺口、冲突、歧义提问。引用或压缩时不得改变条件强度。
- **事实由执行者查**：现有系统行为、接口、代码、文档和可访问外部资料由执行者读取或检索。用户只负责其掌握的组织私有事实，以及必须由其拍板的价值取舍。
- **不把用户当搜索引擎**：能自己查到的内容不问；链接无法访问时，先说明已尝试及受阻原因，再请用户授权访问或提供原文，而非要求用户代查结论。
- **不制造中间文档**：推理可留在当前上下文，但不得包装成 Requirement Canvas、迷你 PRD、需求规格或其他待确认产物。

## 流程总览

```text
读取输入
  → 解析进料
  → 建立需求画像并判断是否拆分
  → 建因果决策树
  → 每轮动态派生 Frontier
  → 事实查证 / 用户决策
  → 更新因果决策树
  → Readiness 纵横检查
      ├─ 未通过：回到 Frontier
      └─ 通过：进入 alignment-gate.md
```

## Step 0：解析输入

支持三种入口，均先完整读取再判断，不把分类问题抛给用户。

| 输入             | 处理方式                                               |
| ---------------- | ------------------------------------------------------ |
| 一句话或口头想法 | 提取显式诉求与约束；未知保持未知，不补写方案           |
| PRD 内容         | 抽取既定规则、目标、边界及内部冲突；既定内容不重复确认 |
| PRD/文档链接     | 先读取链接内容再抽取；保留来源语境和条件强度           |

输入可能混合成熟与空白内容。不要用固定“成熟度档位”替代逐项判断：明确项进入树的已知节点，真正的缺口、冲突和歧义才进入后续推导。

## Step 1：建立需求画像与拆分判断

需求画像只用于控制澄清策略，不作为独立产物提交用户。至少判断：

1. **业务域**：需求所解决问题归属的业务领域，例如会员、活动、CRM、CDP、多语言、行程、机票、酒店等。根据核心目标、主要业务规则和成功指标确定一个主业务域；只有其他业务域会提供业务规则、承担职责或构成关键依赖时才标为关联域，不因需求涉及某个系统或技术组件就机械列入。
2. **研发交付类型**：需求预计涉及的研发技术栈或交付团队，可选 Web 前端、客户端、服务端、数据、AI/算法及其他专项。允许多选，并将负责实现和保障核心业务行为的类型标为主类型，不按代码量或工作量判断；只有次类型会带来额外范围、依赖或验收要求时才记录。Web 前端包括 PC Web、H5、运营后台和小程序前端；客户端包括 iOS、Android 和桌面客户端。该判断只用于识别责任、协作边界和适用的澄清视角，不代替技术方案设计。
3. **规模**：判定为 `Micro` 或 `Normal`。
   - `Micro`：单一目标、单一主场景、边界局部，关键决策很少。
   - `Normal`：存在多角色、多阶段、跨域依赖、显著例外或多项相互制约的目标。
4. **必要拆分**：仅当子目标可独立产生价值、拥有不同责任人/成功标准，或不拆会导致决策树无法有效收敛时拆分。涉及多个研发交付类型、技术分层、页面分区或实现模块不同，本身都不是拆分理由。

需要拆分时，说明拆分依据与建议顺序，并按 `ask-user-guide.md` 调用 `AskUserQuestion`，让用户选择先处理哪个子需求；每个子需求独立完成本流程。无需拆分时直接继续。

## Step 2：建立因果决策树

决策树表达“为什么做、改变什么、靠什么成立”，而不是功能目录。树根是用户原始诉求，沿因果关系展开：

```text
原始诉求
  └─ 根因 / 机会：为什么值得解决？
      └─ 目标结果：要让谁在什么场景发生什么变化？
          ├─ 成立条件：结果出现必须满足什么？
          ├─ 能力与边界：需要覆盖什么，明确不覆盖什么？
          ├─ 关键假设 / 风险：哪些判断若不成立会推翻方向？
          └─ 完成证据：观察到什么即可判定目标达成？
```

每个节点只记录当前对话所需的最小信息，并标识为：

- **已知**：用户明确给出，或已由可靠来源查证；
- **未知**：尚无答案；
- **冲突**：已有信息互不兼容；
- **依赖**：其结论要等待父节点或其他前置节点。

先问“为什么/要改变什么”，再问“需要什么能力”。不要从用户给出的解法直接反推其目标已经明确；也不要下沉到 UI、字段、接口或技术实现，除非它们本身是用户不可变更的业务约束。

## Step 3：每轮派生 Frontier

每轮提问前，从最新因果决策树重新计算 Frontier；回答后即失效，下轮重新派生。**不得把 Frontier 保存为长期状态、清单对象或独立产物。**

一个节点仅在同时满足以下四个条件时进入 Frontier：

1. **未决**：它是未知或冲突，尚无可信结论；
2. **前置已解**：其父节点和必要依赖已确定，本轮答案不会因上游未决而立即作废；
3. **影响实质**：不同答案会改变目标、范围、关键假设、完成标准或必要拆分；
4. **责任属用户**：它需要价值判断、业务取舍或授权，无法由输入、代码、文档或环境事实查证解决。

不满足第 4 条的节点进入执行者事实查证，查证后直接更新树；查不到时明确证据缺口，再判断是请求访问/原文，还是转为需用户确认的假设。

## Step 4：责任边界与低价值过滤

派生后再过滤，避免“问题越多越专业”的错觉。

### 责任边界

- **执行者负责**：检索事实、读取链接与代码、识别矛盾、给出有依据的推荐项、说明取舍后果。
- **用户负责**：业务目标、优先级、风险容忍、范围取舍、组织私有事实与最终确认。
- 不要求用户设计提问选项、补齐行业常识、查找执行者可获得的信息，也不把推荐值伪装成用户既定决定。

### 低价值过滤

若一个问题的不同答案不会实质改变五段式对齐卡，也不会改变是否拆分，则不单独询问。可逆、局部、低风险的实现细节留给下游；不能静默默认却暂不值得追问的内容，只有在可能影响共识时才作为关键假设暴露。

严禁把业务关键项以“低价值”为由过滤，例如权限边界、资金/合规风险、不可逆操作、核心口径和决定成功与否的例外场景。

## Step 5：逐轮提问与更新

每一轮都必须读取并遵守 `ask-user-guide.md`，由它统一规定通道、选项、推荐项、分组数量、串并行和审批格式；本文件不复制这些格式规则。

执行顺序：

1. 先处理可查事实，并把证据更新到树中。
2. 发现目标、场景、规则、术语、边界、可验证性、偏好或冲突信号时，按需读取 `packs.md` 的对应检查包。对 `Normal`，出现多角色、多阶段，或角色、状态、时间、金额等条件共同决定行为时，读取“条件组合”；出现取消、失败、重试、超时、重复、部分成功、无权限、依赖失败或降级时，读取“边界与半成功”；新信息与既有规则互不兼容时，读取“冲突裁决”。方法只生成候选缺口并更新因果树，不生成确认附件；候选缺口仍须通过 Frontier 四条件与低价值过滤。
3. 按因果依赖选择本轮问题：上游优先；答案会改变后题时串行，互不依赖时才合并。
4. 用户回答后立即更新已知、未知、冲突和依赖关系；新范围或反例出现时重塑相关分支。
5. 重新派生 Frontier，而不是沿用上一轮问题清单。

用户要求停止追问时，不等于 Readiness 自动通过。基于现有信息执行 Step 6；若仍有关键缺口，明确指出后由用户选择继续澄清或撤回本次对齐，不得用静默假设强行完成。

## Step 6：Readiness 纵横检查

只有纵向与横向同时通过，才允许生成需求对齐卡。

### 纵向检查：因果链是否成立

从诉求沿每条关键路径检查到完成证据：

- 根因/机会能够解释为什么要做；
- 目标结果回应根因，而非只复述解法；
- 必要能力和范围能够促成目标结果；
- 关键假设一旦失败时，其影响已被看见；
- 完成标准能够证明目标结果，而非仅证明“功能上线”。

任一关键跳跃只能靠执行者猜测连接，则纵向未通过，回到对应上游节点。

### 横向检查：同层信息是否闭合

跨分支检查：

- 主/关联业务域、主/次研发交付类型和 `Micro`/`Normal` 判断与实际范围一致；
- 目标、非目标、关键假设和完成标准彼此不冲突；
- 核心用户/场景及高影响边界没有遗漏；
- 对 `Normal`，已按实际画像检查适用的复杂性：多角色决策与交接、条件组合、状态与失败补偿，以及数据、权限、时间、并发、历史兼容、重要质量或合规约束；不适用项无需为填清单而追问；
- 已有 PRD 或用户既定规则均被保留，冲突和歧义已解决；
- 必要拆分已处理，未把多个可独立价值目标强塞进一张卡；
- 没有仍满足 Frontier 四条件的节点；低价值项确实不会改变共识。

任何一项不成立，回到相应分支继续澄清。

### 通过条件

纵向因果链无关键断点，横向无实质冲突或遗漏，且不存在可改变共识的待决用户决策，Readiness 才通过。随后立即读取并执行 `alignment-gate.md`；在此之前不得展示或预生成需求对齐卡。

# 需求理解与澄清对齐 —— 主流程

> 目标：把一个需求（从零想法 / 已有 PRD / 半成品）建模成决策树，逐点澄清，直到与用户对齐目标。
> 收敛判据：决策树 frontier 清空（不是"问够 N 个"）。

---

## 核心心法

1. **不把用户当搜索引擎**——能从环境/代码/文档查到的**事实**，自己查（可派子 Agent）；只有需要用户**拍板的决策**才问。
2. **按依赖分组提问**——独立低风险的点可合并进一轮（≤4 问）；有依赖（答案会重塑下一题）或高风险的点串行单问。批量只合"独立"的点。每轮答完实时更新问题。（格式细则见 `ask-user-guide.md` 的结构化提问契约）
3. **每问自带推荐答案 + 选项**——把用户从"开放作文"降为"审阅+点选"，认知负担骤降，同时暴露你的隐含假设供当场纠偏。
4. **对齐优先**——理清与执行硬隔离。用户确认前不写 PRD。

## Step 0: Intake — 识别输入成熟度（建树前先分类）

需求不是只有"从零构思"一种进料。**读完用户输入后，先判定它属哪种成熟度**——这决定了建决策树时的方向与防线。三档：

| 进料模式 | 特征 | 建树方向 | 主防线 |
|----------|------|----------|--------|
| **从零构思** | 原始/口头/模糊想法，大量空白 | 按典型维度**发散**列决策点，头脑风暴 | **防下沉**——别替用户编造他没说的方案/规则 |
| **已有约束/PRD** | 输入已含明确规则、条件、方案 | 从输入**抽取**既定内容填进树，视为已定 | **防篡改**——既定规则/约束**原样保留**，不当空白重澄清、不改写、不定性化 |
| **半成品** | 部分明确、部分空白（最常见） | **混合**：已定处抽取保留，空白处发散澄清 | 两者都要——分清哪些既定、哪些真空白 |

**判定靠读输入自己识别，不进门问用户**（多数需求开头就分得清；分不清按"半成品"走最安全）。判错代价小：抽取多了会多问一轮，抽取少了在澄清中会暴露。

**关键铁律（防篡改）**：用户已明确陈述的业务规则/逻辑（数值门槛、权限条件、状态流转，如"VIP 才可见""退款超 7 天人工审核""分页每次 20 条"）是**需求本身**，属既定内容。抽取后原样记入「已定决策」，**不得**当作待澄清空白重新发问，**不得**改写或定性化成模糊表述。只对其中的 **gap / 冲突 / 歧义** 发起澄清。

## Step 1: Scope Check（范围检查）

先判断需求大小。**若诉求里含多个相对独立的子系统/能力**（如"做个后台，要有权限、报表、审批"），先不急着细化：
- 拆成子需求列表，告知用户："我把它拆成 A/B/C 三块，建议逐块理清，先从哪块开始？"
- 每个子需求独立走一遍本 skill。

避免一上来对一个庞杂需求做深度追问——会失焦。

## Step 2: 建决策树 frontier

把需求拆成一组**决策点**，每个决策点是一个待用户拍板的问题；决策点之间有依赖（先答的会重塑后面的）。

**建树方式随 Step 0 的进料模式而变**：
- 从零构思 → 按下列典型维度发散列点。
- 已有约束/PRD → **先抽取**：把输入里已明确的规则/边界/约束逐条录入「已定决策」（标注归属=输入既定），**不进 frontier**；frontier 只放输入没覆盖的空白、冲突、歧义。
- 半成品 → 两者并行。

**frontier** = 当前所有"前提已经确定、可以问了"的决策点集合。既定内容不入 frontier——它已定，不需再问。

典型决策点维度（据需求裁剪）：
- 目标与动机：解决谁的什么问题？为什么现在做？（用 JTBD：当\_\_\_时，用户想\_\_\_，以便\_\_\_）
- 范围边界：哪些明确要做？哪些明确不做（Non-goals）？
- 用户与场景：主要用户是谁？核心使用场景？异常/边界场景？
- 约束：技术/时间/合规/依赖上的硬约束？
- 优先级：哪些 Must、哪些 Could？（MoSCoW）
- 成功标准：怎样算做成了？可测量吗？

## Step 3: 逐点/分组澄清

从 frontier 取一个决策点：
1. **先自查**——是事实类（现有系统怎么做的、某接口是否存在）？自己查/派子 Agent，不问用户。
2. **需拍板的才问**——按结构化提问契约提问（`ask-user-guide.md`）：选项化 + 推荐项置首 + 保留自由输入口；独立低风险点合并一轮（≤4），有依赖/高风险点串行。有 `AskUserQuestion` 优先用，无则降级等价 markdown。**禁止把多个点摊成纯文本长列表让用户作文回复。**
3. **分级**——命中惊讶测试或高风险 → 重档（`grill-techniques.md`）；否则轻档（`clarify-leveling.md`）。
4. 用户回答后，**立即更新 frontier**：解锁新决策点、移除已解点、必要时重塑后续问题；**若范围变了或需求已当场定清，提前收敛**。

## Step 4: 收敛判据

**frontier 清空** = 每个分支都走过、没有被你静默假设的东西。此时才收敛。

无问题数量上限。但用户可随时说"够了，就按现在的理解来"——尊重，直接进对齐门禁。

## Step 5: 复述 + 对齐门禁

收敛后 → 读 `alignment-gate.md`，复述"用户诉求—目标—非目标—关键假设—完成标准"五要素，调 AskUserQuestion 确认。

## 产出（随聊随记）

本 skill 过程中维护三样，作为对齐依据，也是留给后续工作的成果：
- **已定决策**：每个决策点的最终答案 + 归属（用户定 / 用户认可推荐值 / 输入既定）。输入既定的业务规则原样保留，不改写。
- **术语表 glossary**：需求里的关键术语精确定义（尤其歧义/重载词）。
- **待答清单**：frontier 里还没解的点。

这三样在对齐门禁复述时会用到，对齐通过后固化进会话上下文，供任意后续场景取用。

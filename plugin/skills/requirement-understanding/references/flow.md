# 需求理解与澄清对齐 —— 主流程

> 目标：把一个需求（从零想法 / 已有 PRD / 半成品）建模成决策点集合，逐点定夺，直到与用户对齐目标。
> 收敛判据：**Ask 通道清零**（不是"问够 N 个"，也不是"一个假设都不剩"）。

---

## 核心心法

1. **不把用户当搜索引擎**——能从环境/代码/文档查到的**事实**，自己查（可派子 Agent）；只有需要用户**拍板的决策**才问。
2. **只把高价值问题递给用户**——决策点分两条通道：错了要返工的进 **Ask 通道**（问用户），错了好改的进 **Assume 通道**（自己定，攒到门禁批量兜底）。用户的注意力是稀缺资源，花在低价值问题上，高价值问题就会被草率点过。
3. **按依赖分组提问**——独立低风险的点可合并进一轮（≤4 问）；有依赖（答案会重塑下一题）或高风险的点串行单问。每轮答完实时更新。（格式细则见 `ask-user-guide.md`）
4. **每问自带推荐答案 + 选项**——把用户从"开放作文"降为"审阅+点选"，认知负担骤降，同时暴露你的隐含假设供当场纠偏。
5. **说不清就给他看**——用户连续给低信息量回答（"你定就行""差不多"）时，继续追问是无效的。改用低保真制品让他批注（读 `prototyping.md`）。一张样例数据表能顶三轮抽象追问。
6. **对齐优先**——理清与执行硬隔离。门禁通过前不进入下游动作。

## Step 0: Intake — 识别输入成熟度（建树前先分类）

需求不是只有"从零构思"一种进料。**读完用户输入后，先判定它属哪种成熟度**——这决定了建树方向与主防线。

| 进料模式 | 特征 | 建树方向 | 主防线 |
|----------|------|----------|--------|
| **从零构思** | 原始/口头/模糊想法，大量空白 | 按典型维度**发散**列决策点，头脑风暴 | **防下沉**——别替用户编造他没说的方案/规则 |
| **已有约束/PRD** | 输入已含明确规则、条件、方案 | 从输入**抽取**既定内容填进树，视为已定 | **防篡改**——既定规则/约束**原样保留**，不当空白重澄清、不改写、不定性化 |
| **半成品** | 部分明确、部分空白（最常见） | **混合**：已定处抽取保留，空白处发散澄清 | 两者都要——分清哪些既定、哪些真空白 |

**判定靠读输入自己识别，不进门问用户**（多数需求开头就分得清；分不清按"半成品"走最安全）。

### 输入不在上下文里，先取再判

用户给了文件路径 / 链接 / 附件 → **先读取，再判定成熟度**。读不到就直说读不到、请用户贴内容，**不要凭需求标题猜着往下走**——那会让整棵树建在幻觉上。

### 防篡改铁律

用户已明确陈述的业务规则/逻辑（数值门槛、权限条件、状态流转，如"VIP 才可见""退款超 7 天人工审核""分页每次 20 条"）是**需求本身**，属既定内容。抽取后记入「已定决策」，归属标 `输入既定`，**不得**当作待澄清空白重新发问，**不得**改写或定性化成模糊表述。只对其中的 **gap / 冲突 / 歧义** 发起澄清。

**抽取用引号原文，不用你自己的话。**

```
✅ 输入既定："退款超 7 天需人工审核"
❌ 输入既定：退款有审核机制
```

归纳就是篡改的第一步——一旦归纳，你自己都无法事后区分哪句是用户原文、哪句是你的润色，下游更不可能。原文引用是这条铁律唯一可验证的形态。

### 区分「规则」与「断言」

- 既定的**规则**（"超 7 天人工审核"）→ 原样保留，不许追问、不许改写。
- 既定的**断言**（"用户都希望能批量导出""这个功能大家都在用"）→ 是**待验证前提**，可以追问证据（"这个判断有数据支撑吗？"）。追问断言不算篡改。

把断言当规则原样抽取，等于把 PM 的主观判断锁成需求事实，后面全建在它上面。

## Step 1: Scope Check（范围检查）

先判断需求大小。**若诉求里含多个相对独立的子系统/能力**（如"做个后台，要有权限、报表、审批"），先不急着细化：
- 拆成子需求列表，告知用户："我把它拆成 A/B/C 三块，建议逐块理清，先从哪块开始？"
- 每个子需求独立走一遍本 skill。

避免一上来对一个庞杂需求做深度追问——会失焦。

## Step 2: 建 frontier + 双通道分流

把需求拆成一组**决策点**，每个决策点是一个待定夺的问题；决策点之间有依赖（先答的会重塑后面的）。

**frontier** = 当前所有"前提已经确定、可以处理了"的决策点集合。既定内容不入 frontier——它已定。

建树方式随 Step 0 的进料模式而变：
- 从零构思 → 按下列典型维度发散列点。
- 已有约束/PRD → **先抽取**：把输入里已明确的规则/边界/约束逐条录入「已定决策」（归属 `输入既定`），**不进 frontier**；frontier 只放输入没覆盖的空白、冲突、歧义。
- 半成品 → 两者并行。

典型决策点维度（据需求裁剪）：
- 目标与动机：解决谁的什么问题？为什么现在做？（用 JTBD：当\_\_\_时，用户想\_\_\_，以便\_\_\_）
- 范围边界：哪些明确要做？哪些不做——且是**废弃**还是**分期**？
- 用户与场景：主要用户是谁？核心使用场景？异常/边界场景？
- 约束：技术/时间/合规/依赖上的硬约束？
- 优先级：哪些 Must、哪些 Could？（MoSCoW）
- 成功标准：怎样算做成了？可测量吗？

### 分流：每个点必须有去处

**第一步，先自查是不是事实类**——现有系统怎么做的、某接口是否存在、库里有没有这张表？是 → 自己查/派子 Agent 查到答案，**不占任何通道，也不问用户**。

剩下的是真决策点，按**返工成本 × 可推断性**分流：

| | 能推断出高置信答案 | 推断不出 / 低置信 |
|---|---|---|
| **错了要返工**<br>数据模型、对外接口、合规、核心业务规则、影响面广、难回退 | **Ask** —— 带上你的推断值作推荐项，让用户一键确认 | **Ask** —— 命中升级触发器则走重档深挖 |
| **错了好改**<br>文案、默认值、样式、局部交互、易改的边界处理 | **Assume** —— 用推断值，记一条 | **Assume** —— 记一条并标"我猜的"，门禁里排前面 |

两个维度分工不同：**返工成本决定问不问，可推断性决定怎么问 / 怎么记。**

拿不准返工成本 → 按 Ask 走。多问一句的代价远小于返工。

### Assume 通道的记录格式

自答的每一条都要留痕，否则到门禁时你想不起来自己默认过什么。一行一条：

```
<场景> → <行为>   ｜理由：<一句>   ｜返工成本：低/中
```

例：

```
余额为 0 时点兑换 → 拒绝并提示，不扣次数   ｜理由：权益类通用做法，避免对账麻烦   ｜返工成本：低
列表默认排序     → 按创建时间倒序        ｜理由：无用户偏好信号，最常见默认      ｜返工成本：低
```

**Assume 不是偷懒的垃圾桶。** 两条自检：写不出理由的，说明你没想清；返工成本写到"中"以上的，说明它该在 Ask 通道。任一命中 → 移回 Ask。

## Step 3: 逐点/分组处理

从 frontier 取一批前提已定的 **Ask 通道**决策点：

1. **按契约提问**——见 `ask-user-guide.md`：字母序号 `A)/B)/C)` + label 写行为（≤15 字）+ 破折号后接具体边界值和理由 + 保留自由输入口；独立低风险点合并一轮（≤4，用 `Q1/Q2` 编号），有依赖/高风险点串行。**禁止把多个点摊成纯文本长列表让用户作文回复。**
2. **分档**——高返工成本或命中升级触发器 → 重档（`grill-techniques.md`）；否则轻档（`clarify-leveling.md`）。
3. **答不出就换形态**——连续两轮低信息量回答，或问题本身涉及数据形态 / 流程分支 / 页面结构 / 规则组合 → 别再追问，给低保真制品让他批注（`prototyping.md`）。
4. **答完立即更新 frontier**——解锁新决策点、移除已解点、必要时重塑后续问题；**若范围变了或需求已当场定清，提前收敛**。

Assume 通道的点不占提问轮次，随手自答并记入清单即可。

## Step 4: 收敛判据

**Ask 通道清零** = 该递给用户的都问过了。

**Assume 通道有残留是正常终态，不是未收敛。** 那些条目正是门禁存在的理由——它们会在门禁里一次性亮给用户做 last call。追求"一个假设都不剩"会把低价值问题全推给用户，制造疲劳，反而降低他对高价值问题的注意力。

无提问数量上限。但用户可随时说"够了，就按现在的理解来"——尊重，此时：

- Ask 通道剩余项**降级转入 Assume 通道**，逐条标 `未澄清·返工成本高`；
- 直接进对齐门禁，这些条目在假设清单里**排最前**。

不要把未澄清的高风险项静默混进普通假设——那等于用一次点击掩盖一堆雷。

## Step 5: 复述 + 对齐门禁

Ask 通道清零后 → 读 `alignment-gate.md`，复述需求全貌 + 假设清单，请用户显式确认。

## 产出（随聊随记）

本 skill 过程中维护四样，既是门禁依据，也是交给下游（PRD 撰写）的成果：

- **已定决策**：每个决策点的最终答案 + 归属，三种之一——`用户定` / `用户认可推荐值` / `输入既定`。`输入既定`的业务规则用引号原文保留。
- **假设清单**（Assume 通道）：`<场景> → <行为>｜理由｜返工成本`，一行一条。
- **术语表 glossary**：需求里的关键术语精确定义（尤其歧义/重载词）。
- **Ask 待答清单**：Ask 通道里还没解的点。

**交给下游的标注约定**（同会话串联，下游直接读上下文，不落盘）：

- 每条决策/规则标 `confirmed`（用户拍板或认可推荐值）或 `assumed`（AI 自答、门禁批准）。下游据此判断哪些能直接写成验收标准、哪些要挂 Open Question。
- 范围分三态：`in-scope`（本期做）/ `<废弃>`（作废，下游完全不提）/ `<分期>`（后续期次，下游可在后续规划中提及）。

# 需求对齐卡与确认门禁

> 前置条件：`flow.md` 的 Readiness 纵向、横向检查均已通过。未通过时禁止生成本页产物。

## 唯一确认产物

向用户展示且供其确认的产物只能是以下固定五段式**需求对齐卡**。不得增加“背景、方案、功能清单、术语表、已定决策、待办”等段落，也不得另附 Requirement Canvas、准 PRD 或其他确认附件。

```markdown
## 需求对齐卡

**用户诉求**
[谁在什么场景遇到什么问题或机会，希望产生什么改变。表达诉求，不写实现方案。]

**目标**
[本次需求要达成的结果；必要时包含可理解的优先顺序，但不展开功能设计。]

**非目标**
- [本次明确不解决、不覆盖或不承诺的事项]

**关键假设**
- [若不成立会显著改变目标、范围或完成判断，且当前作为成立条件接受的假设]

**完成标准**
- [可观察、可判定，能够证明目标结果达成的标准]
```

填写规则：

- 仅使用已通过 Readiness 的结论，不在成卡时新增推断。
- 用户诉求与目标分开：前者描述问题/机会与期望变化，后者描述本次承诺达成的结果。
- 非目标写明确边界；若确无排除项，写“除上述目标外，本次不扩展其他范围”，不得留空。
- 关键假设只放影响共识且已显式暴露的成立条件，不把已确认事实、待调查事项或实现偏好伪装成假设；若无关键假设，写“无”。
- 完成标准须能判定结果，不以“开发完成”“功能上线”代替业务或用户结果。
- 保留用户既定规则的原意与条件强度；压缩表达不得改变含义。

## HARD-GATE：显式确认

展示完整需求对齐卡后，必须在同一轮调用 `AskUserQuestion`，并遵守 `ask-user-guide.md` 的审批模式。审批问题固定为：

> 以上《需求对齐卡》是否准确，可以作为本次需求共识？

审批选项固定为：

- `通过，需求已对齐`
- `拒绝，需要修正`

只有用户选择或明确表达等价于“通过，需求已对齐”，门禁才通过。以下情况均不算确认：

- 用户沉默、未反对或只说“继续”；
- 用户补充、修正、附带条件或选择拒绝；
- 执行者代替用户推断“应该没问题”；
- 只展示卡片但未调用 `AskUserQuestion`。

## 结果分流

- **显式通过**：可以宣告“需求已对齐”，本 skill 完成并停止。不得自动开始 PRD、设计或实现。
- **拒绝或提供修正**：视影响回到 `flow.md` 对应因果分支，更新树并重新执行 Readiness；通过后生成一张完整的新卡，再次调用 `AskUserQuestion`。旧卡失效。
- **含条件的同意**：条件本身是新信息，不视为通过；先纳入主流程重新检查并再次确认。

每个新需求、拆分后的每个独立子需求，以及目标或范围发生实质变化后的需求，都必须分别通过本门禁；历史确认不能复用。

# 对齐门禁 —— 收敛后的五要素复述与确认

> 前置：本 skill 的决策树 frontier 已清空（或用户主动喊停接受现状）。
> 目标：把理解显式化，与用户达成**可确认的共识**，通过门禁即完成需求理解。

---

## HARD-GATE

<HARD-GATE name="对齐门禁">
本 skill 完成（对用户宣告"需求已对齐"）前，对齐必须通过。
证据 = AskUserQuestion 已调用，且用户回复了确认。
无证据 = 禁止宣告对齐。
</HARD-GATE>

**违反形式 = 违反精神。** 写了对齐内容但没调 AskUserQuestion = 未通过。

---

## Step 1: 先用 markdown 复述五要素

在调 AskUserQuestion **之前**，先用 markdown 展示，让用户看到完整理解（标题独占一行，内容换行写。括注是给你的填充指引，复述时替换成真内容，不展示给用户）：

```
**用户诉求**
（1-2 句：谁，在什么场景下，想达成什么、以便什么。写诉求与结果，不写解法；
  做过 5 Whys 则写根因。这是 JTBD，不是技术缺陷。）

**目标**
（1-2 句：做成后达到什么状态 + 高层方向。不展开解法。）

**非目标（本期明确不做）**
- 明确排除项 1
- 明确排除项 2
（这是最强的对齐工具——把边界写死，防范围蔓延。取自澄清阶段已定的排除项。）

**关键假设**
- 假设 1：X 默认用 A
- 假设 2
（这里装 AI 未追问、替用户默认的低风险隐含选择——澄清阶段没单独问的。
  不放已问过的决策，不放待验证存疑；目的：把静默假设一次性亮出，给用户最后否决机会。）

**完成标准（可判定）**
- 可测试条件 1
- 可测试条件 2
（粗粒度、可判定的"做成什么样"，供对齐用；细粒度 Given-When-Then 留到后续文档撰写。）
```

格式禁忌：标题和内容写在同一行；把复述内容塞进 AskUserQuestion 选项里（复述要用户能完整看到）。

## Step 2: 同一 response 内调 AskUserQuestion 确认

复述之后，紧接着在**同一 response** 调 AskUserQuestion，让用户审批。这是**审批确认**（非多问澄清）：固定两选项，Other 由系统自动附加。

```
问题：以上理解准确吗？可以据此对齐、进入后续工作了吗？
选项：
  A) 通过，需求已对齐
  B) 拒绝
  Other （用户需要补充时，手动输入内容，按补充修正后再重新对齐一遍）
```

## Step 3: 依结果分流

- **通过（A）** → 门禁通过，本 skill 完成。五要素/glossary/已定决策留在会话上下文中，供任意后续工作直接取用。告知用户："需求已对齐，五要素 / glossary / 已定决策已就绪。"
- **Other（用户输入补充内容）** → 视为"有补充的通过"：按补充修正五要素，无需推翻重来的小改直接改完继续；若补充推翻了目标/范围，回 clarifying 对应分支重开。
- **拒绝（B）** → 回到 `clarifying` 阶段，按反馈重开相应决策分支，重新收敛后再走一次门禁。

---

## Red Flags —— 正在跳过对齐

| 念头                 | 真相                                 |
| -------------------- | ------------------------------------ |
| "复述了就等于对齐了" | 复述 ≠ 确认，必须调 AskUserQuestion |
| "用户没反对就是同意" | 沉默不是确认，要显式回复             |
| "小需求不用走门禁"   | 越小越容易藏隐含决策                 |
| "先写着，边写边对"   | 门禁在动笔之前，不是之后             |

---

## 与状态的衔接

门禁通过这一刻，把 glossary + 已定决策 + 五要素 作为需求理解的成果固化下来（记入会话状态）。后续任何工作直接基于这份共识展开，不再重新发明。

# 对齐门禁 —— 收敛后的全貌复述与确认

> 前置：Ask 通道已清零（或用户主动喊停接受现状）。
> 目标：把理解显式化，与用户达成**可确认的共识**，通过门禁即完成需求理解。

---

## HARD-GATE

<HARD-GATE name="对齐门禁">
本 skill 完成（对用户宣告"需求已对齐"）前，对齐必须通过。
证据 = 已向用户发出**结构化确认请求**（有 AskUserQuestion 用它；无该工具用 markdown 编号选项），且用户已**显式回复**。
无证据 = 禁止宣告对齐。
</HARD-GATE>

**违反形式 = 违反精神。** 写了复述内容但没请用户拍板 = 未通过。环境里没有 AskUserQuestion **不是**跳过门禁的理由——门禁验的是"用户是否显式回复了确认"这个行为，两种提问形态同等有效。

---

## 门禁的定位（先想清这个，再看模板）

高价值问题已经在澄清阶段被逐个确认过了。门禁**不是**为了让用户重新审一遍那些结论，而是干两件事：

1. **把全貌拼起来给用户看**——逐点确认时看不见的缺口，在整体呈现时会暴露。用户看到全貌常会想起没说的东西。
2. **给假设清单一次统一 last call**——那些走自决档、用户从没见过的默认决策，这是他唯一的否决机会。

所以门禁的设计目标是**扫一眼就能点通过**，不是让用户读几分钟。信息要完整，长度要克制。**用户扫的时候视线只会落在前几行——所以把最危险的放最前面，而不是假装他会读完。**

---

## Step 1: markdown 复述（两段分区）

在请用户确认**之前**，先用 markdown 展示。分两段，明确标注哪段是复述、哪段是新信息，让用户自己分配注意力。

**长度约束：整份渲染后 ≤20 行。下面模板中的括注是给你的填充指引，不计入输出、不展示给用户。**

```
## 需求全貌（复述，扫一眼确认没跑偏）

**JTBD** 当<情境>，<谁>想<做什么>，以便<为什么>
（一行装完 who/what/why。做过 5 Whys 则写根因，不写解法）

**本期做**
- 要点 1
- 要点 2
- 要点 3
（≤3 条，写范围要点不写实现）

**本期不做**
- <废弃> …
- <分期> …
（必须区分两类：<废弃>=作废内容，下游完全不提；<分期>=后续期次，下游可在后续规划提及。
  这是最强的对齐工具——把边界写死，防范围蔓延）

**完成标准**
- 可判定条件 1
- 可判定条件 2
（≤3 条，粗粒度可判定即可；细粒度验收标准留给下游 PRD）

## 我替你定的（新信息，请重点看）

1. <场景> → <行为>
2. <场景> → <行为>
3. <场景> → <行为>
（取自假设清单，只展示前两段，剥掉理由和返工成本两栏。
  按返工成本降序——最可能踩雷的排第一。≤7 条）
```

### 假设清单的展示规则

- **只装用户没见过的**：走自决档、AI 自行决定的默认值。**不放已经问过的决策**（那是复述，不是新信息），**不放待验证存疑项**。
- **按返工成本降序**，最危险的排第一。
- **写成 `<场景> → <行为>` 一行式**，不写散句。一行一条，用户横扫一次即可，比读段落快得多。

```
✅ 余额为 0 兑换 → 拒绝并提示，不扣次数
❌ 关于余额为 0 的情况，我默认采用了拒绝策略并给出提示，同时不扣减次数
```

- **上限 7 条（软约束）**：超过 7 条时，必须补一句说明为什么这些都是低价值。写不出来 = 你把该问的塞进了假设通道，回 `flow.md` Step 2 重新分流。
  > 不硬砍到 7 条——为凑数把三条假设揉成一条模糊的，比超标更糟。
- **喊停场景**：用户中途说"够了"时，Ask 通道剩余项转入此清单并标 `未澄清·返工成本高`，**排在最前面**。不要静默混进普通假设。

格式禁忌：标题和内容写在同一行；把复述内容塞进选项里（复述要用户能完整看到）；输出括注指引。

---

## Step 2: 同一 response 内请用户确认

复述之后，紧接着在**同一 response** 发出审批请求。通过拆成两个选项——用户一次点选同时完成"确认"和"决定下一步"，不多一轮往返。

```
Q1. 以上理解准确吗？
  A) 通过，继续出 PRD（推荐）— 据此直接进入 PRD 撰写
  B) 通过，先停在这里 — 理解已对齐，暂不往下走
  C) 拒绝，有偏差要重来 — 回到澄清，重开相应分支
  （或直接补充要改的地方，视为有补充的通过）
```

有 AskUserQuestion 时用它承载这三个选项（Other 由系统自动附加，不要手动加）；没有时上面这段 markdown 就是最终形态。

---

## Step 3: 依结果分流

| 用户选择 | 动作 |
|---|---|
| **A 通过并继续** | 门禁通过 → 告知"需求已对齐"→ 交接给下游 PRD 撰写。四样产出留在会话上下文，下游直接取用 |
| **B 通过先停** | 门禁通过 → 告知"需求已对齐"→ **停住，不擅自开工** |
| **C 拒绝** | 回 `clarifying` 阶段，按反馈重开相应决策分支，重新收敛后再走一次门禁 |
| **Other（补充内容）** | 视为"有补充的通过"：按补充修正，无需推翻的小改直接改完继续；若补充推翻了目标/范围，回 `clarifying` 重开分支 |

### 二次门禁只给 diff

被拒绝或有补充后重走门禁时，**只展示变更的部分**，不重复全文：

```
## 已按你的反馈调整（其余未变）

**本期不做** 新增
- <分期> 批量导入（改到二期）

**我替你定的** 第 2 条已改
2. 列表默认排序 → 按更新时间倒序（原：创建时间倒序）
```

然后照常发出 Step 2 的三选项。

原因很实在：整份重贴一遍，第二遍用户就开始疲劳，第三遍就闭眼点通过了——那时门禁已经失效。**diff 形态是保住门禁有效性的机制，不是省字数的偷懒。**

## Red Flags —— 正在跳过对齐

| 念头 | 真相 |
|---|---|
| "复述了就等于对齐了" | 复述 ≠ 确认，必须请用户显式拍板 |
| "用户没反对就是同意" | 沉默不是确认，要显式回复 |
| "小需求不用走门禁" | 越小越容易藏隐含决策 |
| "先写着，边写边对" | 门禁在动笔之前，不是之后 |
| "假设太琐碎，不列了" | 假设清单是门禁存在的全部理由。不列 = 门禁退化成纯复述 |
| "环境没有 AskUserQuestion，门禁没法走" | 门禁是行为不是工具，用 markdown 编号选项 |
| "第二遍了，全文再贴一次稳妥" | 重复全文制造疲劳，二次门禁只给 diff |

## 交给下游

门禁通过这一刻，四样产出（已定决策 / 假设清单 / 术语表 / Ask 待答清单）即为需求理解的成果，留在会话上下文，供下游直接取用。**同一会话内串联，不落盘文件。**

给下游的两组标注必须齐备，否则下游只能猜：

- **决策状态**：`confirmed`（用户拍板或认可推荐值）/ `assumed`（AI 自答、门禁批准）。下游据此决定哪些能直接写成验收标准、哪些要挂 Open Question。
- **范围三态**：`in-scope`（本期做）/ `<废弃>`（作废，下游完全不提）/ `<分期>`（后续期次，下游可在后续规划中提及）。

后续工作直接基于这份共识展开，不再重新发明，也不重复一遍对齐。

# 需求理解 Skill

**核心信念：对齐优先于一切。理解对了，后面才不白做。**

把一个需求（从零想法 / 已有 PRD / 半成品）建模成决策点集合、逐点定夺，直到与用户达成**可确认的共识**。本 skill 只做一件事——**把需求理解透、与用户对齐**。

**关键取舍：不是所有问题都递给用户。** 决策点按返工成本分两条通道——错了要返工的问用户，错了好改的自己定并记入假设清单，到门禁一次性亮出来兜底。问得少不等于挖得浅，问得准才是。用户的注意力是稀缺资源，浪费在低价值问题上，高价值问题就会被草率点过。

**进料模式（读完输入先判定，不进门问用户）**：从零构思（发散建树，防下沉——别编用户没说的方案/规则）/ 已有约束或 PRD（抽取既定内容填树，防篡改——既定业务规则用引号原文保留，只澄清 gap/冲突/歧义）/ 半成品（两者混合）。分不清按半成品走。详见 `references/flow.md` 的 Step 0。

---

## 定位

- **本 skill 做什么**：识别进料模式 → 范围检查 → 建 frontier 并双通道分流 → 处理 Ask 通道（命中高返工成本升级对抗深挖；用户说不清则给低保真制品）→ Ask 通道清零 → 复述全貌 + 假设清单 → 对齐门禁。
- **本 skill 不做什么**：不擅自进入下游动作（写 PRD、出技术方案、开始编码）。但门禁里提供衔接选项，让用户一次点选决定是否继续。
- **产出**：已定决策 + 假设清单 + 术语表 + 范围三态，留在会话上下文，供下游直接取用。

## 硬门禁（不可跳过）

<HARD-GATE name="对齐门禁">
对用户宣告"需求已对齐"前，目标对齐必须通过。
证据 = 已向用户发出**结构化确认请求**（有 AskUserQuestion 用它；无该工具则用 markdown 编号选项，见 `references/ask-user-guide.md`），且用户已**显式回复**。
无证据 = 禁止宣告对齐。
</HARD-GATE>

**违反形式 = 违反精神。** "这需求很清楚了" = 你以为的清楚，不是对齐。"上一个需求对齐过了" = 新需求要新对齐。**门禁约束的是"有没有让用户显式拍板"这个行为，不绑定任何具体工具**——环境里没有 AskUserQuestion 不是跳过门禁的理由，是改用 markdown 形态的理由。

### Red Flags —— 正在跳过澄清/对齐

以下念头一旦出现，立即停手：

| 你的念头 | 真相 |
|----------|------|
| "这需求很简单" | 简单 = 隐含决策被忽略，恰恰最该澄清 |
| "用户说得很清楚了" | 说清楚 ≠ 你理解 100% 正确 |
| "先往下走边做边对" | 对齐在动作之前；错误理解会锚定后续方向 |
| "我大概知道用户要什么" | 大概 ≠ 验证，去让用户显式拍板 |
| "补上这个假设就能对齐了" | 先判返工成本：错了要返工 → 进 Ask 通道去问；错了好改 → 记入假设清单等门禁兜底。**不允许既不问、也不记** |
| "这些假设太琐碎，不用列出来" | 假设清单是门禁存在的全部理由。不列 = 门禁退化成纯复述 |
| "写了对齐内容了" | 写了 ≠ 请用户拍板了，缺显式确认请求无效 |
| "环境没有 AskUserQuestion，门禁走不了" | 门禁是行为不是工具，降级用 markdown 编号选项 |

### 惊讶测试（带价值前置）

**一句话判断**：如果用户此刻看到我的决策会惊讶，**且这个决策错了要返工** → 去问。

会惊讶但**错了好改** → 不问，记入假设清单，门禁兜底。这是本 skill 控制提问量的核心阀门。

触发场景：多个方案各有取舍 / 决策依赖用户偏好 / 范围超出原始诉求 / 正在填补用户没说明的部分 / 术语有歧义——**这些都还要再过一道返工成本判断**，判据见 `references/flow.md` Step 2 的分流表。

## 主流程

**入口** → 读 `references/flow.md`（含完整状态机与双通道分流判据）。

按需加载：

| 需要做什么 | 读哪个文件 |
|------------|-----------|
| 走完整理解流程（识别进料→scope→建 frontier 分流→处理→收敛） | `references/flow.md` |
| 判断某个决策点用自决档 / 轻档 / 重档 | `references/clarify-leveling.md` |
| 向用户提问的格式契约（字母序号、两层选项、分组、多轮、审批） | `references/ask-user-guide.md` |
| 升级到对抗深挖后，具体怎么问 | `references/grill-techniques.md` |
| 用户答不出/敷衍，需要给他看东西 | `references/prototyping.md` |
| 收敛后复述全貌 + 执行对齐门禁 | `references/alignment-gate.md` |

**收敛判据**：不是"问够 N 个"，也不是"一个假设都不剩"，而是 **Ask 通道清零**——该递给用户的都问了。假设清单有残留是**正常终态**，那些条目正是门禁要亮出来的东西。用户可随时喊停接受现状。

## 产出（随聊随记）

理解过程中维护四样，既是门禁依据，也是交给下游的成果：

- **已定决策**：每个决策点的最终答案 + 归属，三种之一——`用户定` / `用户认可推荐值` / `输入既定`。`输入既定`的业务规则用引号原文保留，不改写、不归纳。
- **假设清单**（Assume 通道）：`<场景> → <行为>｜理由｜返工成本`，一行一条。门禁通过 = 这些条目被批准。
- **术语表 glossary**：需求里的关键术语精确定义（尤其歧义/重载词）。
- **Ask 待答清单**：Ask 通道里还没解的点。

**交给下游的标注约定**（同会话串联，下游直接读上下文）：
- 每条决策/规则标 `confirmed`（用户拍板或认可推荐值）或 `assumed`（AI 自答、门禁批准）。下游据此决定哪些能直接写成验收标准、哪些要挂 Open Question。
- 范围分三态：`in-scope`（本期做）/ `<废弃>`（作废，下游完全不提）/ `<分期>`（后续期次，下游可在后续规划中提及）。**不要把后两者揉成一个"非目标"**——下游对它们的处理方式不同。

## 完成

对齐门禁通过后：
1. 告知用户："需求已对齐。已定决策 / 假设清单 / 术语表 / 范围三态已就绪。"
2. 按用户在门禁里的选择走：选了「继续出 PRD」→ 交接给下游 PRD 撰写；选了「先停这里」→ 停住，不擅自开工。

---

## 状态与恢复

本 skill 面向单次会话内走完（理解 → 对齐 → 交接下游）。跨轮次时用四样产出跟踪进度。

用户说"继续"时：
1. 回看 Ask 待答清单，确认 Ask 通道是否清零。
2. 未清零 → 从未解的点继续。
3. 已过门禁 → 本 skill 已完成，按用户当时的选择衔接下游。

若对话很长、四样产出可能已被压缩丢失 → **重印一次**（已定决策 + 假设清单 + Ask 待答清单，一行一条），再继续。不要凭残缺记忆往下走。

---

## 进度心跳

- 完成 scope / 完成一批澄清 / 收敛 → 一句话报告。
- 连续多次工具调用无文本 → 插入说明当前在做什么。
- 方向变化（升级重档、改用原型、发现需求需拆分）→ 立即告知用户。

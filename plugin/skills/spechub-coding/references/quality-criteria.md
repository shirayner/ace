# 产出物质量标准

按需 Read。生成 proposal/design/tasks 时参照。

---

## Proposal 质量标准

| 维度 | 合格条件 |
|------|----------|
| 问题陈述 | 清晰描述要解决的问题（不是解决方案） |
| 范围界定 | 明确包含/不包含，与 G0 scopeDecision 一致 |
| 成功标准 | ≥2 个可测试的验收条件 |
| 约束声明 | 列出技术/业务/时间约束 |
| Scope 一致性 | Scope Out 的功能点不出现在 proposal 中 |

## Design 质量标准

| 维度 | 合格条件 |
|------|----------|
| 决策清单 | 每个决策带编号（D1, D2...），含选项对比和选择理由 |
| 接口契约 | 关键接口有输入/输出/错误定义 |
| 数据流 | 数据从哪来、经过什么处理、到哪去 |
| 变更影响 | 列出受影响的现有模块/接口 |
| 可追踪性 | 每个决策可追溯到 proposal 中的需求 |
| 必要性标注 | 每个决策标注驱动它的需求/约束 |

## Tasks 质量标准

| 维度 | 合格条件 |
|------|----------|
| 原子性 | 每个 task 可独立验证完成 |
| 关联性 | 每个 task 标注关联的决策点（如 D1, D3） |
| 顺序性 | 依赖关系明确（DDL→DAO→SOA→QMQ→...） |
| 可验证 | 每个 task 有明确的"做完了"标准 |
| 完整性 | tasks 覆盖 design 中所有决策点 |
| Scope 一致性 | 不包含 Scope Out 功能点对应的 task |

## 通用原则

1. **具体胜于抽象** — "响应时间 < 200ms" 胜于 "性能好"
2. **决策可追踪** — 从 proposal → design → tasks → code 每步可追溯
3. **产物是输入不是答案** — SpecHub 产物可能有错，需独立验证
4. **必要性优先** — YAGNI，每个功能点必须有明确需求驱动

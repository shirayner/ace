# Spec 产出物质量标准

按需 Read。当生成 proposal/design/tasks 时参照本文件判断质量。

---

## Proposal 质量标准

| 维度 | 合格条件 |
|------|----------|
| 问题陈述 | 清晰描述要解决的问题（不是解决方案） |
| 范围界定 | 明确包含/不包含的内容，**与 G0 scopeDecision 一致** |
| 成功标准 | ≥2 个可测试的验收条件 |
| 约束声明 | 列出技术/业务/时间约束 |
| 风险识别 | ≥1 个已识别风险及其缓解策略 |
| 产物溯源 | 标注哪些内容源自 SpecHub 产物、哪些是澄清补充 |
| Scope 一致性 | Scope Out 的功能点不出现在 proposal 中 |

**反模式**：
- 直接复制平台 proposal 而不经过澄清验证
- 范围模糊（"优化性能""改善体验"无量化）
- 验收条件不可测试
- 包含用户已明确 Scope Out 的功能点

## Design 质量标准

| 维度 | 合格条件 |
|------|----------|
| 决策清单 | 每个架构决策带编号（D1, D2...），含选项对比和选择理由 |
| 接口契约 | 关键接口有输入/输出/错误定义（可引用平台 contracts） |
| 数据流 | 数据从哪来、经过什么处理、到哪去 |
| 变更影响 | 列出受影响的现有模块/接口 |
| 可追踪性 | 每个决策可追溯到 proposal 中的需求 |
| Playbook 标注 | 涉及中间件的决策标注对应 playbook 场景 |
| 必要性标注 | 每个决策标注驱动它的需求/约束（不可"以后可能需要"） |

**反模式**：
- 只有结论没有理由
- 决策点无编号
- 直接照搬 architecture.md 而不做本地化适配
- 引入未被需求明确驱动的复杂度

**决策清单格式**：
```
D1: [决策标题]
- 选项: A) ... B) ... C) ...
- 选择: B
- 理由: ...
- 驱动需求: [引用 proposal 中的具体需求点]
- 影响: ...
- Playbook: xxx.md#section（如适用）
```

## Tasks 质量标准

| 维度 | 合格条件 |
|------|----------|
| 原子性 | 每个 task 可独立验证完成 |
| 关联性 | 每个 task 标注关联的决策点（如 D1, D3） |
| Playbook 标注 | 涉及中间件的 task 标注 `<!-- playbook: xxx.md#section -->` |
| 顺序性 | 依赖关系明确（拓扑顺序：DDL→DAO→SOA→QMQ→...） |
| 可验证 | 每个 task 有明确的"做完了"标准 |
| 完整性 | tasks 覆盖 design 中所有决策点 |
| Scope 一致性 | 不包含 Scope Out 功能点对应的 task |

## Defeater 质量标准 ⟵ 优化③

| 等级 | 条件 | 进入验证清单 |
|------|------|-------------|
| **Strong** | 附带 ≥1 条具体证据（代码路径/数据事实/文档引用） | ✅ 作为 ⚠️-conflict 或 ✗ |
| **Weak** | 纯逻辑推演，无实证 | ❌ 仅记录，不影响流程 |

**证据类型**：
- 代码证据：grep/read 结果（文件路径 + 行号 + 代码片段）
- 数据证据：配置文件/文档的具体引用
- 业务证据：PRD 原文引用 + 与产物声明的矛盾点

---

## 验证清单标记语义 ⟵ 优化⑥

| 标记 | 语义 | 用户处理建议 |
|------|------|-------------|
| ✓ | 与代码现状一致 / 确认不存在重复 | 无需关注 |
| ⚠️-conflict | 存在具体矛盾（附代码证据） | **必须解决**：修正产物方案或确认覆盖现有 |
| ⚠️-missing | 信息不足，无法确认 | 补充信息或接受为假设 |
| ⚠️-suspect | 疑似不需要/过度设计（D5 审计结果） | 建议裁剪为 Scope Out |
| ✗ | 明确错误（产物声明与代码事实矛盾） | 必须修正，禁止采纳产物原方案 |

---

## 通用原则

1. **具体胜于抽象** — "响应时间 < 200ms" 胜于 "性能好"
2. **决策可追踪** — 从 proposal 到 design 到 tasks 到 code，每一步可追溯
3. **面向验证设计** — 写 spec 时问自己："这条标准，apply 后能验证吗？"
4. **产物是输入不是答案** — SpecHub 产物提供基础，但可能有错，需要独立验证
5. **必要性优先** — 每个决策/功能点必须有明确的需求驱动，YAGNI 原则

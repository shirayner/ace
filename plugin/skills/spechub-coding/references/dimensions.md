## 需求澄清维度

| 维度 | 关注点 |
|------|--------|
| **产物完整性** | 平台产物是否覆盖所有场景？有无遗漏的边界情况？ |
| **产物一致性** | PRD 与 architecture 是否一致？contracts 与 proposal 是否匹配？ |
| **产物与现状冲突** | 产物提议的方案与现有代码/架构是否冲突？ |
| 功能完整性 | 核心流程 + 边界情况 + 异常处理 |
| 数据关切 | 数据来源、格式、量级、一致性要求 |
| 用户体验 | 交互流程、反馈机制、错误呈现 |
| 边界异常 | 并发、超时、重试、幂等、降级 |
| 集成依赖 | 上下游服务、外部 API、中间件 |
| 优先级范围 | MVP vs 完整版、分期策略 |

## 设计澄清维度

| 维度 | 关注点 |
|------|--------|
| **Playbook 选型** | 对于每个命中的中间件，playbook 决策树的哪个分支适用？ |
| **契约验证** | API 契约 JAR 是否已发布？版本是否正确？ |
| **平台架构约束** | architecture.md 中的设计决策是否可直接采纳？需要调整吗？ |
| 架构决策 | 分层、模式选择、关注点分离 |
| 技术选型 | 框架/库/中间件的选择及理由 |
| 接口设计 | 契约定义、版本策略、兼容性 |
| 数据状态 | 存储选型、schema 设计、迁移策略 |
| 安全合规 | 认证/授权、数据脱敏、审计 |
| 性能可靠性 | SLA 目标、容量规划、故障恢复 |
| 部署运维 | 发布策略、监控告警、回滚方案 |

## 方案必要性审计维度 ⟵ 优化⑤⑦

| 维度 | 关注点 |
|------|--------|
| **最简实现基准** | 对每个功能点/设计决策：最简实现是什么？当前方案比最简多出的复杂度由什么需求驱动？ |
| **YAGNI 检测** | 产物中是否存在"以后可能需要"驱动的功能？这些功能是否可以延后？ |
| **复杂度-收益比** | 额外复杂度带来的收益是否由当前需求明确要求？还是预防性设计？ |
| **范围蔓延信号** | 产物功能点数量 vs 用户原始描述的功能点数量——差异是合理延伸还是范围越界？ |
| **新建 vs 扩展判定** | 现有模块是否可通过 ≤5 个方法级变更达成同一业务目标？如果是，新建 = 过度设计 |
| **分离驱动力校验** | "逻辑不同"不是分离理由。真正的驱动力只有：独立部署、故障隔离、不同数据生命周期、量级差异 SLA |
| **复杂度增量对比** | 新建方案 vs 扩展方案的增量实体数/配置数/运维关注点对比，选择总成本更低者 |

## 元认知触发器

澄清时强制回答（内部思考，不输出）：
1. **返工成本最高的误解是什么？** — 聚焦于此处深挖
2. **什么让我仍不确定？** — 将不确定性转化为澄清问题
3. **用户的隐含约束是什么？** — 业务环境、团队能力、时间压力
4. **平台产物的隐含假设是什么？** — 产物生成时的上下文可能已变化
5. **如果用最简方案实现，用户会满意吗？** — 如果会，当前方案可能过度设计 ⟵ 优化⑤
6. **我是在论证"新建合理"还是在验证"是否可以扩展"？** — 若是前者，停下来反转思路 ⟵ 优化⑪
7. **我的结论是否被产物的 [新增] 标签锚定了？** — 产物标签是待验证输入，不是事实 ⟵ 优化⑪

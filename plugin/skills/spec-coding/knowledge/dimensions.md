# 需求分析维度库

Phase 1 Understand 阶段使用此文件对照检查，识别需求描述中可能遗漏的维度。

---

## 8 个需求维度

| # | 维度 | 关注问题 | 常见遗漏信号 |
|---|------|---------|------------|
| 1 | **功能性** | 做什么？输入/输出是什么？边界情况？ | 只描述了 happy path |
| 2 | **性能** | 响应时间？吞吐量？数据量级？ | 未提及并发/大数据量场景 |
| 3 | **安全** | 认证？授权？数据保护？输入校验？ | 未提及权限/数据脱敏 |
| 4 | **可用性** | 用户交互？错误提示？无障碍？ | 只考虑后端，未考虑用户体验 |
| 5 | **兼容性** | 向后兼容？多版本共存？数据迁移？ | 未提及已有 API/数据的影响 |
| 6 | **可维护性** | 可读性？可测试性？模块化？ | 未考虑未来扩展点 |
| 7 | **可测试性** | 如何验证？自动化测试？回归策略？ | 未定义验收标准 |
| 8 | **可运维性** | 部署？监控？日志？告警？回滚？ | 未考虑运行时可观测性 |

---

## 使用方式

1. 逐维度检查用户需求描述
2. 标记已覆盖（✓）和未提及（?）的维度
3. 未提及的维度 → 生成 unknowns（可能需要向用户澄清）
4. 不强制每个维度都显式回答——但每个维度都应有意识地考虑

---

## 常见盲区表

| 场景类型 | 最容易遗漏的维度 |
|---------|----------------|
| CRUD 功能 | 性能（大数据量）、兼容性（已有 API） |
| 认证/授权 | 安全（token 过期）、可运维性（审计日志） |
| 数据处理 | 性能（批量）、可靠性（重试/幂等） |
| UI 功能 | 可用性（边界状态）、可测试性（E2E） |
| 集成/对接 | 兼容性（版本）、可运维性（超时/重试） |
| 重构 | 兼容性（行为不变）、可测试性（回归） |

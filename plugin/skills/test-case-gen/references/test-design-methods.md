## 方法选择决策树

```
需求特征分析
├─ 有明确输入域？
│  ├─ 数值型 → 边界值分析
│  └─ 枚举/分类型 → 等价类划分
├─ 多条件组合决策？
│  ├─ ≤4 个条件 → 判定表（完整）
│  └─ >4 个条件 → 因果图 + 正交实验
├─ 有状态流转？
│  └─ 状态机测试
├─ 是用户交互流程？
│  └─ BDD 场景设计
└─ 涉及高风险？
   └─ 风险矩阵排序
```

多种方法可叠加使用。复杂需求通常需要 2-3 种方法组合。

---

## 1. 等价类划分（Equivalence Partitioning）

### 原理
将输入域划分为若干等价类，每类中任取一个值即可代表整类。

### 适用场景
- 输入有明确的有效/无效范围
- 同一等价类内的值在系统行为上等价

### 操作步骤
1. 识别每个输入参数
2. 划分有效等价类（系统应正常处理的）
3. 划分无效等价类（系统应拒绝/报错的）
4. 每个等价类至少取 1 个代表值
5. 组合时：正例覆盖所有有效类，反例每次只包含 1 个无效类

### 示例
```
输入：年龄（整数）
有效类：[1, 17] 未成年 | [18, 59] 成年 | [60, 150] 老年
无效类：[≤0] 非法 | [>150] 非法 | 非数字
代表值：10, 30, 70, -1, 200, "abc"
```

### 陷阱
- 等价类边界本身要用边界值分析单独覆盖
- 不要用"太正常"的值（如 age=25），要覆盖每个类

## 2. 边界值分析（Boundary Value Analysis）

### 原理
缺陷往往聚集在输入域的边界。对每个边界取 on/off/in 三点。

### 适用场景
- 数值范围有明确上下界
- 集合有容量限制
- 时间有截止点

### 操作步骤
1. 识别每个有效范围的边界
2. 取值：边界值本身 + 边界值-1 + 边界值+1
3. 特殊边界：0、1、空、满、MAX_INT、MIN_INT

### 示例
```
输入：密码长度 [6, 20]
测试值：5（无效）, 6（有效边界）, 7（有效）, 19（有效）, 20（有效边界）, 21（无效）
特殊：0（空密码）, 1（极短）
```

### 陷阱
- "大于"和"大于等于"要分清楚
- 浮点数边界需考虑精度
- 字符串长度边界要区分字节数 vs 字符数

## 3. 判定表（Decision Table）

### 原理
当多个条件组合决定不同行为时，用表格枚举所有可能组合。

### 适用场景
- 业务规则涉及 2-4 个条件的组合
- "如果 A 且 B 但不 C，则..."类型的规则

### 操作步骤
1. 列出所有条件（condition stub）
2. 列出所有动作（action stub）
3. 生成条件组合（2^n 列）
4. 标记每种组合对应的动作
5. 合并不影响结果的条件（简化表格）
6. 每列 = 1 个测试用例

### 示例
```
条件：
C1: 会员类型 = 黑钻
C2: 消费金额 > 10000
C3: 无违规记录

规则1: C1∧C2∧C3 → 保级成功
规则2: C1∧¬C2∧C3 → 降级
规则3: C1∧*∧¬C3 → 强制降级
...
```

### 陷阱
- 条件超过 5 个时组合爆炸，需用正交实验裁剪
- 注意"不关心"条件的标记（don't care = `-`）

## 4. 状态机测试（State Transition Testing）

### 原理
系统有有限状态，事件触发状态转换。覆盖所有合法转换 + 关键非法转换。

### 适用场景
- 订单状态流转
- 会员等级变更
- 审批流程
- 任何有"生命周期"的实体

### 操作步骤
1. 画出状态转换图（State → Event → State）
2. 列出所有合法转换 → 每个 = 1 个正例
3. 列出关键非法转换（在某状态下触发不允许的事件）→ 每个 = 1 个反例
4. 覆盖"0-switch"（每个转换至少一次）
5. 可选：覆盖"1-switch"（每个二步路径至少一次）

### 示例
```
订单状态机：
Created → [支付] → Paid → [发货] → Shipped → [签收] → Completed
Created → [取消] → Cancelled
Paid → [退款] → Refunded

非法转换：
Cancelled → [支付] → ❌ 应拒绝
Completed → [取消] → ❌ 应拒绝
```

### 陷阱
- 不要忘记"终态不可转出"的验证
- 并发场景下的状态竞争（两个事件同时触发）

## 5. BDD 场景设计（Behavior-Driven Design）

### 原理
用自然语言描述系统行为，格式为 Given-When-Then，对齐业务和技术理解。

### 适用场景
- 用户交互流程
- 验收条件本身就是行为描述
- 需要与产品/QA 对齐理解的场景

### 操作步骤
1. 从需求的每个 AC 出发
2. 用 Given-When-Then 描述正例
3. 衍生异常场景（Given 不满足 / When 失败 / Then 部分满足）
4. 参数化：同结构不同数据的场景用 Examples 表达

### 模板
```gherkin
Feature: [功能名称]
  As a [角色]
  I want [目标]
  So that [价值]

  Scenario: [场景名称]
    Given [前置条件/系统状态]
    And [附加条件]
    When [用户操作/事件触发]
    Then [预期结果/系统反应]
    And [附加验证]

  Scenario Outline: [参数化场景]
    Given 用户等级为 <grade>
    When 消费金额为 <amount>
    Then 积分为 <points>

    Examples:
      | grade    | amount | points |
      | 普通     | 100    | 100    |
      | 黑钻     | 100    | 200    |
```

### 陷阱
- 避免把实现细节写进 Given/When/Then
- Given 应描述业务状态而非技术状态（"用户已登录" ✅, "session 存在" ❌）

## 6. 风险驱动排序（Risk-Based Prioritization）

### 原理
不是所有功能都同等重要。用风险矩阵决定测试深度和优先级。

### 风险评估公式
```
风险值 = 失败影响(1-5) × 发生概率(1-5) × 检测难度(1-5)

影响：1=可忽略 2=小不便 3=功能降级 4=资金损失 5=安全事故
概率：1=极低 2=低 3=中等 4=高 5=极高
检测难度：1=立即发现 2=用户反馈 3=需主动检查 4=难以发现 5=事后才知
```

### 优先级映射
```
风险值 [75-125] → P0 (阻塞发布)
风险值 [27-74]  → P1 (高风险)
风险值 [8-26]   → P2 (中风险)
风险值 [1-7]    → P3 (低风险)
```

### 适用场景
- 测试资源有限，需要裁剪
- 确定哪些场景必须自动化
- 确定回归测试范围

### 操作步骤
1. 对每个功能点/场景评估三个维度
2. 计算风险值
3. 按风险值降序排列
4. P0/P1 必须覆盖，P2 资源允许时覆盖，P3 可选

## 方法组合策略

### 简单 CRUD
```
等价类（输入域）+ 边界值（数值边界）+ Happy Path
典型用例数：10-20 条
```

### 复杂业务逻辑
```
判定表（规则组合）+ 等价类（每个条件的值域）+ 风险排序
典型用例数：20-50 条
```

### 状态驱动流程
```
状态机（转换覆盖）+ BDD（关键路径描述）+ 边界值（触发条件边界）
典型用例数：30-60 条
```

### 全维度覆盖（深度模式）
```
所有方法按需组合 + 风险矩阵统一排序 + 非功能维度补充
典型用例数：50-100+ 条
```

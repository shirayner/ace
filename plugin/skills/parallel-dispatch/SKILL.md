# Parallel Dispatch — 通用并行代理调度

**核心原则**：每个 agent 一个独立问题域，精确构造上下文，并行执行，结果整合时检测冲突。

---

## 使用边界

| 场景 | 允许 | 说明 |
|------|------|------|
| 并行探索/调研 | ✅ | Phase 1/3 多维度探索 |
| 并行修复独立 bug | ✅ | 不同子系统、不同文件 |
| 并行实现计划任务 | ❌ | Apply 阶段必须串行 |

**为什么 Apply 不并行**（铁律）：
> "Never dispatch multiple implementation subagents in parallel (conflicts)"
- 计划阶段标记的 ⟂ 是逻辑独立，不保证运行时无文件冲突
- 并行实现后的合并冲突解决成本 > 串行实现的时间成本
- 审查流程无法对并行产物做有效交叉验证

---

## 执行流程

### Step 1: 独立性判断

输入的任务集是否真正独立？

- 修改相同文件？→ ❌ 不并行
- 共享状态？→ ❌ 不并行
- 有序依赖？→ ❌ 不并行
- 修复一个可能修复另一个？→ ❌ 先串行调查

**全部通过 → 可并行。任一不通过 → 串行执行。**

### Step 2: 构造 Agent Prompt

每个任务独立构造 prompt：

**好的 prompt 特征**：
- ✅ 聚焦 — 一个清晰问题域
- ✅ 自包含 — 所有需要的上下文直接传入
- ✅ 明确输出 — agent 应该返回什么
- ✅ 有约束 — 不修改范围外代码

**反模式**：
- ❌ 太宽泛："修复所有测试"
- ❌ 无上下文："修复竞态条件"
- ❌ 无约束：agent 可能重构整个模块
- ❌ 输出模糊："修复它"

### Step 3: 并行派遣

使用 Agent tool 在**单条 response** 中并行发出所有任务。

每个 Agent 调用包含：
- 完整任务描述
- 相关上下文（文件路径、代码片段、错误信息）
- 约束（只动哪些文件、不动哪些）
- 期望输出格式

### Step 4: 结果整合

- 读取每个 agent 的返回摘要
- 检测冲突（是否修改了同一代码？）
- 冲突 → 手动解决（报告给用户或串行化处理）
- 无冲突 → 集成

### Step 5: 验证

- 运行完整测试套件
- 抽查 agent 的工作质量
- 确认所有修复协同工作
- 执行 /verify Gate Function（证据先于声明）

---

## 适用场景

| 场景 | 示例 |
|------|------|
| 多文件测试失败 | 3 个测试文件不同 root cause |
| 多子系统 bug | 认证、支付、通知各自有 bug |
| 并行探索 | 同时分析性能、安全、架构三个维度 |
| 批量独立任务 | 多个独立 migration 脚本 |

---

## Red Flags

| 绝不 | 原因 |
|------|------|
| 并行派遣修改同文件的 agent | 冲突不可解 |
| 不做独立性判断就并行 | 隐含依赖导致翻倍工作 |
| 跳过结果整合的冲突检测 | 集成时爆炸 |
| 让 agent 自己决定是否并行 | 判断应由 Controller 做 |

---

## 失败处理

- 单个 agent 失败不影响其他（故障域隔离）
- 失败的任务记录原因，后续串行重试
- 全部失败 → 检查是否有共享根因（可能不该并行）

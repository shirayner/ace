# 差量重写

> 命中信号：`INPUT_IS_SOLUTION` —— 输入描述的是动作或方案，而非世界差量。
> 更新：`goal.intent`。

## 为什么必须重写

用户给出的往往是**他猜到的解法**，不是他要的结果。直接实现方案，会让后续所有判据围绕「方案是否写完」展开，而真正的目标是否达成从未被检验。这是目标被静默替换的第一个入口，且发生在一切开始之前。

```text
"做个批量导入"        → 方案。导入功能上线但没人用，判据仍会显示满足。
"运营不再需要每天手工录入 2 万条"  → 差量。它自带失败条件。
```

## 方法

### 1. 差量提问

对输入问一句：**这件事做成之后，世界有什么不同？**

- 谁的哪个动作不再需要做？
- 什么状态从 A 变成 B？
- 什么现在不可能的事变得可能？

答案若仍是动作，继续问。答案是可观察的世界状态时停止。

### 2. 有界 5 Whys

沿「为什么要这个」上溯，但**必须有终止条件**，否则会一路问到公司战略：

```text
停止条件（任一成立即停）：
- 已定位到可度量结果
- 已定位到真实任务（用户实际要完成的工作）
- 继续上溯只进入不影响当前决策的上层战略
- 原请求已被证明只是方案，且问题已被重定义
```

无界 5 Whys 是常见失败：把「为什么要批量导入」问到「为什么公司要盈利」，既不改变任何决策，也耗尽用户耐心。

### 3. 保留原方案作为候选

重写目标**不等于否定用户的方案**。正确做法：

```markdown
你要的结果我理解为：<差量>
你提到的 <原方案> 是达成它的一种方式。
我还看到 <备选>，取舍是 <代价对比>。
按 <推荐> 推进？
```

用户的方案往往包含未说出的约束（已有系统、团队习惯、合规要求）。直接换掉方案而不问，是另一种方向的自作主张。

## 检验

重写后的 `intent` 必须通过 `validateGoalShape()`：不得以动作动词开头（实现/开发/写/做/搭建/新增/修改/重构/优化/接入/集成/部署/设计…）。

若确实无法表述为差量，说明这是纯执行请求而非目标——此时不该走 auto-goal 流程。

## 跨领域示例

| 输入（方案） | 重写（差量） |
|---|---|
| 做个批量导入 | 运营不再需要每天手工录入 2 万条 |
| 帮我写封邮件给房东 | 锅炉恢复正常供暖 |
| 整理一下这些文件 | 任何人能在 10 秒内按年份找到指定合同 |
| 学一下 Raft | 我能独立判断某个共识实现是否安全 |
| 调研竞品 | 下周的定价决策有据可依 |
| 重构这个模块 | 改这个模块时不再需要手工回归验证 |

注意右列每一条都自带失败条件，左列没有。这就是差量形式的实际价值：**它让判据可写**。

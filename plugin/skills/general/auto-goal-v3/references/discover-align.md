# DISCOVER / ALIGN — 目标契约与不确定性

DISCOVER 与 ALIGN 阶段加载。

## 一、Goal Contract

DISCOVER 的产物不是一棵树，是一份契约：

```text
outcome      要造成的可观察世界差量（不是要执行的动作）
scope        明确 in / out
criteria     完成标准，每条可被不知情者独立判定
assumptions  显式假设 + defeat condition
unknowns     未决项及其依赖关系
```

**先写 outcome，再写别的。** 用户说的往往是方案：「加个导出按钮」背后可能是离线分析、
对账、审计留档或绕开性能问题——差量不同，方案完全不同。反推三问：要造成什么差量？
谁因此能做到原先做不到的事？什么可观察结果能证明它发生了？

## 二、unknowns 是 DAG，不是树

每个未决项：

```text
{ id, kind, owner, depends_on, impact, status }

kind   decision | fact | risk | hypothesis | constraint
owner  agent（能自己查）| user（只有用户知道）| environment（要跑才知道）
```

**为什么是 DAG 而不是树**：树要求单父、分支互斥。现实中权限、容量、兼容性、时序这类
约束会同时作用于多个决策。强行树化只有三种结果——复制节点、丢失交叉约束，或者把
"话题"伪装成"决策"。DAG 只要求 `depends_on` 是偏序，这已经足够支撑排序与提问。

**`depends_on` 的判据**：A 换一个答案，B 的**选项框架**要重写吗？要 → B 依赖 A；
不要 → 两者无边，可同轮处理。这个判断直接决定它们能否同一轮发问。

### owner 分流

| owner | 判据 | 动作 |
|---|---|---|
| agent | 答案在代码、文档、配置、日志、git 历史、网络里 | **派探索 Agent 查**，见下节 |
| user | 意图、优先级、取舍偏好、外部约束、验收口径 | 进 frontier 候选池 |
| environment | 要实际运行才知道 | 做一次最小实验，别问用户 |

**拿不准先当 agent 试一次。** 问一个本可自己查的问题，成本是用户的信任；
自己查一个查不到的，成本只是一次工具调用。**不把用户当搜索引擎。**

### 独立探索域必须派探索 Agent

`owner == agent` 的缺口不是"你逐个 Read/Grep 扫一遍"，而是**派探索 Agent**。

<HARD-GATE name="探索也要委派">
**委派（无条件）**：每个 `owner == agent` 的调研缺口都派一个探索 Agent，
**只有一个也派**——无数量门槛、无规模豁免。Controller 只汇总它们的结论。

**并行（看依赖）**：多个互不为下游的缺口 → 必须在**同一条 response** 里同时派发；
存在依赖的排到下一轮。
</HARD-GATE>

**委派与并行是两个决定**：委派是否发生与能否并行无关，缺口数量只影响后者。

两个理由，都不是风格问题：

1. **串行轰炸**：5 个独立问题域自己逐个查 = 5 倍时钟时间，而它们本来无依赖。
2. **上下文预算**：探索是最耗上下文的活动（大量 Grep 命中、大文件片段）。Controller
   的上下文要撑到 EXECUTE 与 CLOSE，把它烧在 DISCOVER 上，后面就只能靠猜。
   subagent 的上下文用完即弃，只有结论回到主线。

**"互不为下游"的判据**与同轮提问一致：A 的答案会改变 B 的**查法**吗？会 → 排到下一轮。

单个缺口：**照样委派**，只是不并行——Controller"顺手查一个点"就是把探索开销
记在最贵的那份上下文里，也让结论无独立来源。委派与实现同规格无条件
（见 `execute.md`），缺口数量只决定并行不决定委派。

探索 Agent 的 prompt 与实现 prompt 同规格（自包含、点名文件、限定返回行数），
但**只读**：明确写"不要修改任何文件，只返回发现"。

## 三、Frontier — ready selector

Frontier = 同时满足四条的 unknowns：

1. **未决** — `status` 还是 open
2. **依赖已解决** — `depends_on` 全部已定，问它不需要先猜上游答案
3. **答案会实质改变**范围 / 风险 / 计划 / 判据 —— 只改措辞的不算
4. **owner == user** — 否则回第二节自己查或跑实验

条件 3 最常被跳过。判定法：给这个问题写两个不同答案，各推一遍后续计划；
**两遍计划一样 → 这个问题不该问**，自己定即可。

Frontier 只是"就绪队列选择器"——它对任何 unknowns 集合都成立，不需要树。

### 一轮多问的正确性约束

一轮发 **1–4 个**问题（AskUserQuestion 原生上限），但：

> **同轮问题必须互不为下游** —— 任一问题的答案都不会改变另一个问题的选项框架。

违反它就退化成固定问卷：用户被迫在上游未定的情况下猜下游。有依赖关系的排到下一轮。

**成对检查**：对每两个候选问题 (A, B) 问「A 换个答案，B 的选项要重写吗？」
要重写 → 只发上游那个。

### 单个问题的形状

- **2–4 个互斥选项**，覆盖真实解空间，不是同一方案的措辞变体
- **推荐项放第一个**，标注"（推荐）"，并给出**推荐理由**
- 每个选项写清**取舍代价**——只说好处的选项等于没给用户选择
- 选项**非互斥**时开 `multiSelect`；不要自造 "Other"，工具自动附加

### 重算与退出

每次回答后 **frontier 立即重算**：答案可能让某些问题变得无意义，也可能让新的
unknowns 浮现。**不要照着上一轮列好的清单继续问。**

## 四、问题生成器

问题不够时用这些逼出隐藏的 unknowns。**不要全上**——挑对当前目标有咬合力的。

| 探针 | 形式 | 逼出什么 |
|---|---|---|
| 目标反推 | 这动作要造成什么世界差量？ | 方案伪装的需求 |
| **半成功探针** | **只成功一半时，系统应该处于什么状态？** | 事务、幂等、补偿、失败反馈 |
| 判据反问 | 交付后你会看什么来判断成了？ | 完成标准，兼验证口径 |
| 边界反问 | 明确**不**做什么？ | 范围膨胀 |
| 前提反问 | 什么情况下这个目标本身就不该做？ | 伪需求 |
| 规模/时序 | 量级多大、多久一次、峰值何时？ | 同步/异步、缓存、限流 |

**半成功探针的触发条件**：存在不可逆副作用或部分提交风险时问。它一句话能穿透一整片
通常要四五个问题才覆盖的区域。反之，风险已由既有事务规范兜住时，问它是浪费用户回合。

### 歧义扫描

发问前扫一遍。命中的项要么问，要么登记为假设：

| 类型 | 信号词 | 要定的事 |
|---|---|---|
| 量词模糊 | 大量、很快、及时、最好 | 具体数字与单位 |
| 主体缺失 | 系统会、需要被 | 谁触发、谁承担 |
| 边界开放 | 等等、类似的、相关的 | 穷举还是抽象 |
| 时序未定 | 之后、同时 | 同步/异步、顺序能否交换 |
| 失败沉默 | 只描述 happy path | 失败时的行为与可见性 |
| 范围代词 | 这个、那部分 | 指称对象 |
| 隐含全量 | 所有、全部 | 是否含历史数据、边缘 case |

## 五、可选视图：决策树

**存在明显互斥方案与条件分支时**，把相关 unknowns 画成树便于沟通：

```text
目标：让运营能拿到订单数据
├─ 用途？（决定形态，最上游）
│  ├─ 离线分析 → 全量导出 + 字段齐全
│  ├─ 日常对账 → 按日增量 + 金额精确
│  └─ 审计留档 → 不可篡改 + 保留期
└─ 数据量级？（决定同步/异步）
   ├─ ≤1 万行 → 同步下载
   └─ >1 万行 → 异步任务 + 通知
```

**它是视图，不是本体。** 研究目标是"假设→实验→更新"的循环；排障是证据逐步更新
后验概率；学习是能力依赖图；探索型目标的选项本身要靠实验才能生成。这些都不该被
强行树化，也**不存在"树深必须 ≥2"这种质量指标**——一个目标可能只有一个真正的
方向性决策，为了凑深度制造第二层只会增加虚假复杂度。

树画出来就是普通 artifact，写 `artifacts/` 即可，不进状态机。

## 六、假设与 defeat condition

未问的槽位一律登记为假设，每条写 **defeat condition**：什么现象出现说明它不成立。

```text
假设：运营只需当日增量，无需历史回溯
defeat：用户提到"对上个月的账"或要求指定日期区间
```

假设很便宜，**未记录的假设**才是事故源。

### 停止 DISCOVER

满足**任一条**即进 ALIGN：

- Frontier 空
- 剩余问题的两个答案推出**同一份计划**（条件 3 不成立）
- 已连问 3 轮且最近一轮没改变任何计划要素 —— 在问装饰性问题
- 剩余不确定性**做出来比问出来便宜**（能快速验证、可逆）

## 七、ALIGN

先在 response 里用 markdown 展示四要素（**标题各占一行**，不要塞进表格），
**然后在同一条 response 里**调用 AskUserQuestion。

```markdown
## 我的理解
<outcome 的一句话陈述——写差量，不写动作>

## 计划方向
<3–6 步。每步说做什么、产出什么>

## 关键假设
- <假设>（defeat：<什么现象说明它错了>）

## 完成标准
- [ ] <不知道本次讨论的人也能独立判定通过/失败>
```

确认用的 AskUserQuestion **不要问"我理解对吗"** —— 人会习惯性说对。改问有落点的：

- 「完成标准第 2 条，够不够严？」
- 「计划第 3 步先做 X 还是先做 Y？」
- 「假设 A 如果不成立，是改范围还是改方案？」

**完成标准的判据**：一个不知道讨论过程的人，能只靠标准文本 + 项目现场判出通过/失败。
含"合理"、"完善"、"优化"的标准不合格——它们要求判定者复现你的意图。

## 八、冻结标准

确认后立刻初始化。这一步**冻结 criterion identity**：

```bash
python3 {skill_dir}/scripts/goal.py init --root <项目根绝对路径> --name <kebab-case-2-4词> \
  --goal "<一句话目标>" --criteria "<完成标准1>" --criteria "<完成标准2>"
```

脚本会给每条标准分配稳定 ID（`C001`…）、算出文本 hash 与集合指纹 `criteria_sha256`，
VERIFY 阶段按 ID 逐条对账。因此：

- **至少一条标准**，零条会被拒绝——没有标准 = 没有验收对象 = 门禁恒真
- **逐字取自 ALIGN 里确认过的文本**，改措辞等于验收另一件事
- **不手写 state.json**。标准文本或集合指纹被手改，后续命令会直接报错

随后进 EXECUTE：用 `goal.py plan` 一次建整张 Work Graph，每个实现 item 派 fresh
subagent 并走完五步生命周期（见 `execute.md`）。**Controller 自己不实现。**

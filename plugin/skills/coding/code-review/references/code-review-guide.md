# 代码审查深度参考

> code-review skill 按需加载。本文档包含完整的分析框架、认知负荷原理和报告模板。

---

## Diff 获取

### 标准流程（分支对比）

```bash
# 自动探测远程默认分支（优先 origin/main，fallback 到 origin/master）
BASE=$(git rev-parse --verify origin/main 2>/dev/null && echo origin/main || echo origin/master)

# 找共同祖先
git merge-base HEAD $BASE

# 获取完整 diff
git diff $BASE...HEAD

# 变更文件列表
git diff --name-only $BASE...HEAD

# 变更统计
git diff --stat $BASE...HEAD
```

### 备选场景

- 无 diff 可获取 → 询问用户目标分支或请提供 diff 内容
- 用户直接提供代码片段 → 对提供的代码进行审查

## 分层分析框架

### 第一层：核心关注点（What）— 所有 effort 级别

| 维度 | 关键问题 |
|------|---------|
| **正确性** | 逻辑是否正确？边界条件？隐藏错误？ |
| **健壮性** | 异常处理？输入验证？资源释放？ |
| **安全性** | 注入风险？敏感数据处理？权限检查？ |

### 第二层：质量关注点（Why）— medium+

| 维度 | 关键问题 |
|------|---------|
| **可维护性** | 意图清晰？修改一处会破坏其他吗？ |
| **可测试性** | 容易验证吗？依赖可替换吗？ |
| **设计** | 职责清晰？耦合合理？抽象层次一致？ |

### 第三层：需求与认知（How well）— high+

| 维度 | 关键问题 |
|------|---------|
| **需求一致性** | 实现是否覆盖了所有验收条件？是否有遗漏或过度实现？ |
| **认知负荷** | 读者能在不跳转的情况下理解吗？工作记忆被占用多少槽位？ |

## 分析方法

### 数据流分析
数据从哪来 → 在哪变换 → 到哪去。
- 变换中有丢失、污染、类型不匹配吗？
- null 是否被安全传递？
- 跨边界的数据格式是否正确？

### 控制流分析
- 所有分支都覆盖了吗？
- 循环边界正确？能终止？
- 并发路径下的竞态条件？
- 异常路径是否保持一致性？

### 依赖分析
- 耦合方向正确（依赖倒置）？
- 接口稳定性——下游变更会波及这里吗？
- 循环依赖？隐式依赖（如类加载顺序）？

### 契约分析
- 前置条件：调用者保证了什么？
- 后置条件：方法承诺了什么？
- 不变量：什么在整个生命周期内恒成立？
- 异常契约：什么条件抛什么异常？

### 需求追踪分析（当提供需求时）
- 需求 AC (Acceptance Criteria) → 代码实现的映射关系
- 未覆盖的 AC → 报告为 Warning（需求偏离）
- 代码做了需求未要求的事 → 报告为 Suggestion（范围蔓延）
- 需求中的隐含约束（"最多""不超过""仅限"）→ 检查边界实现

### 认知负荷分析（max effort 时）

基于 Sweller 认知负荷理论 + Miller 的 7±2 规则：

| 类型 | 检查方法 |
|------|---------|
| **内在负荷** | 问题本身的复杂度——无法消除，但可通过分解降低单次处理量 |
| **外在负荷** | 代码组织引入的额外理解成本——可通过重构消除 |
| **关联负荷** | 读者需要建立的心智模型——通过命名和结构辅助 |

具体检查项：
- 单个函数同时活跃的变量 > 4 个 → 建议拆分
- 条件表达式嵌套 > 2 层 → 建议 early return 或提取方法
- 方法调用链 > 3 层（a.b().c().d()）→ 建议中间变量
- 布尔表达式含 > 2 个运算符 → 建议提取为命名变量
- 函数做了"两件概念上不同的事" → 建议拆分

## 审查原则

1. **正确性优先**：Bug 风险 > 坏味道 > 设计建议
2. **由抽象到具体**：先理解整体设计意图，再检查实现细节
3. **独立验证**：不假设代码正确——用 diff 证明，不用作者意图推断
4. **具体可操作**：每个问题必须有文件路径、行号、修复建议
5. **只报告该上下文特有的发现**：避免通用的"最佳实践"建议
6. **平衡**：既指出问题，也肯定好的实践
7. **分级**：区分"必须修复"、"建议修复"、"可选优化"
8. **认知友好**：单条发现可独立理解，不需要上下文跳转

## 报告模板

```markdown
# 代码审查报告

## 变更意图
> 2-3 句话概括：这次变更在做什么？核心设计决策是什么？影响哪些模块？

## 概览
| 指标 | 值 |
|------|------|
| 分支 | `<current-branch>` → `<base-branch>` |
| 审查文件 | N 个（生产代码 M 个） |
| 变更行数 | +XXX / -YYY |
| Effort | low / medium / high / max |
| 发现 | 🔴 M / 🟡 K / 🔵 J |

## 🔴 Critical — 必须修复

### C1. [文件路径:行号] 问题标题
**问题**: 一句话，可独立理解
**影响**: 可能造成什么后果（数据丢失？服务不可用？安全漏洞？）
**修复**:
```语言
// 具体修复建议
```

---

## 🟡 Warning — 强烈建议修复

### W1. [文件路径:行号] 问题标题
**问题**: 一句话描述
**风险**: 什么条件下会出问题
**建议**: 修复方向

---

## 🔵 Suggestion — 可选优化

### S1. [文件路径:行号] 建议标题
**现状**: 当前实现的不足
**建议**: 改进方向和理由

---

## ⚠️ 需求一致性（仅当提供需求时显示）

### R1. [对应需求条目] 偏差标题
**需求**: 引用原始需求文本
**现状**: 代码实际实现的行为
**差距**: 具体差异描述
**影响**: 这个差距是否会影响用户？

---

## ✅ Positive — 值得肯定

- [文件路径] 亮点描述 + 设计理由（知识传播）

## 总结
| 级别 | 数量 | 关键发现摘要 |
|------|------|-------------|
| Critical | M | 最重要的发现概括 |
| Warning | K | 最重要的发现概括 |
| Suggestion | J | — |
| 需求偏离 | R（如有） | — |
```

报告保存到 `.ace/tasks/review-{slug}/artifacts/code-review-report.md`。

## 大型变更处理

变更文件超过 20 个或代码行变化超过 1000 行时：

1. 优先审查核心逻辑变更（按风险排序，非按文件名排序）
2. 配置文件、生成代码可简化审查
3. 可建议分多次 review
4. 使用 sub-agent 并行分析不同模块

## Effort 级别详细说明

### low — 快速扫描
- 仅第一层分析（正确性 + 健壮性 + 安全性）
- 只输出 Critical 和 Warning
- 报告控制在 10 条以内
- 适用：hotfix、配置变更、小改动

### medium — 标准审查（默认）
- 第一层 + 第二层分析
- 输出全部四级
- Suggestion 控制在 5 条以内
- 适用：日常功能开发

### high — 深度审查
- 三层全覆盖
- 需求一致性分析（如有需求输入）
- 不限制条目数量
- 适用：重要功能、涉及金额/安全的变更

### max — 极致审查
- 所有 high 的内容 + 认知负荷分析
- 交叉验证：对每个 Critical 发现反问"这真的是 bug 吗？"
- 适用：核心系统变更、安全审计

## 语言特定检查要点

| 语言 | 重点关注 |
|------|---------|
| Java/Kotlin | Optional 使用、Stream API、Spring 最佳实践、自动装箱、线程安全 |
| Python | 可变默认参数、异常粒度、上下文管理器、类型注解 |
| JS/TS | 隐式转换、异步处理、any 滥用、this 绑定、内存泄漏 |
| Go | error 处理、context 使用、goroutine 泄漏、interface 设计 |

## 认知科学原理速查

以下原理指导审查维度的设计和报告格式的选择：

| 原理 | 在 code review 中的应用 |
|------|------------------------|
| **Miller's Law（7±2）** | 单次呈现信息不超过 4-5 个块 |
| **渐进式展示** | 概览 → 分级 → 单条详情，逐层深入 |
| **认知负荷理论** | 减少外在负荷（格式清晰），利用关联负荷（命名即文档） |
| **选择性注意** | 严重度标记引导注意力到最重要的发现 |
| **工作记忆** | 每条发现自包含，不依赖其他条目的上下文 |
| **锚定效应** | 变更意图摘要为后续发现提供理解锚点 |

# Test Case Gen — 需求驱动测试用例生成

> 设计哲学：从需求语义出发，而非从代码实现出发。
> 好的测试用例发现的是"需求没说清楚的地方"和"容易遗漏的边界"。

---

## 核心理念

**需求是 Oracle** — 测试用例的正确性标准来自需求，而非代码实现。
**测试设计 ≠ 测试编码** — 本 skill 关注"测什么"和"为什么测"，不关注"用哪个框架写"。
**风险驱动优先** — 不追求穷举，优先覆盖失败后果最严重的场景。

---

## 执行流程

### Phase 1: 需求获取与解析

**输入方式（自动识别）：**

| 输入形式 | 检测规则 | 处理方式 |
|---------|---------|---------|
| 飞书文档链接 | 包含 `feishu.cn` 或 `larksuite.com` | 调用 MCP feishu2md 转为 markdown |
| 文件路径 | 以 `/` `.` 或盘符开头，扩展名为 md/txt/doc | Read 文件内容 |
| 直接文本 | 以上都不匹配 | 直接作为需求文本处理 |

```
解析目标：从原始输入中提取结构化需求要素
→ 功能点列表
→ 验收条件（AC）
→ 业务规则
→ 约束条件（性能/安全/兼容性）
→ 涉及角色/权限
```

如果需求信息不足以生成有意义的用例 → AskUserQuestion 引导补充。

---

### Phase 2: 需求分析与方法选择

根据需求特征自动选择测试设计方法：

| 需求特征 | 推荐方法 | 理由 |
|---------|---------|------|
| 输入域明确（数值/字符串/枚举） | 等价类 + 边界值 | 系统化覆盖输入空间 |
| 多条件组合决策 | 判定表 / 因果图 | 避免组合爆炸下的遗漏 |
| 有状态流转（订单/工单/会员等级） | 状态机 | 覆盖所有合法转换 + 非法转换 |
| 用户交互流程 | BDD 场景 | 行为描述，对齐业务理解 |
| 涉及金额/安全/核心链路 | 风险驱动排序 | 优先覆盖高损失场景 |
| 并发/批量/大数据量 | 压力维度 | 专项异常场景 |

**方法可叠加** — 一个需求可能同时适用多种方法。

详细方法说明：Read `references/test-design-methods.md`

---

### Phase 3: 场景推导

按以下维度系统展开测试场景：

#### 3.1 正常路径（Happy Path）
- 主流程完整走通
- 每个验收条件对应至少 1 个用例

#### 3.2 异常路径（Error Path）
- 输入异常（空值/超长/非法格式/SQL注入）
- 依赖异常（下游超时/返回错误/不可用）
- 状态异常（并发冲突/幂等/重复提交）

#### 3.3 边界值（Boundary）
- 数值边界（最小值/最大值/临界值±1）
- 时间边界（跨天/跨月/跨年/时区/闰年）
- 容量边界（空集合/单元素/最大容量/溢出）

#### 3.4 业务规则验证（Business Rules）
- 每条业务规则的正例和反例
- 规则之间的优先级和冲突
- 隐含规则（需求没写但业务默认成立的）

#### 3.5 非功能维度（Non-Functional）
- 性能：响应时间、吞吐量、资源消耗
- 安全：权限校验、数据隔离、敏感信息
- 兼容性：多端/多版本/降级

---

### Phase 4: 用例生成与排序

**优先级排序规则（风险驱动）：**

```
优先级 = 失败影响 × 发生概率 × 检测难度
```

| 优先级 | 含义 | 覆盖要求 |
|--------|------|---------|
| P0 | 阻塞发布 | 必须覆盖，不可裁剪 |
| P1 | 高风险 | 强烈建议覆盖 |
| P2 | 中风险 | 资源允许时覆盖 |
| P3 | 低风险 | 可选覆盖 |

---

## 复杂度适配

### 轻量（单个功能点 / ≤3 AC）
直接推导 → 生成 → 输出。用例数通常 5-15 条。

### 标准（多功能点 / 4-10 AC）
Read references → 分功能点推导 → 合并去重 → 排序输出。用例数 15-50 条。

### 深度（复杂业务流程 / >10 AC / 跨模块）
创建 `.ace/tasks/tc-gen-{slug}/state.json` → 分模块推导 → 合并 → 交叉验证。
可并行：Read `../../shared/parallel-protocol.md`，每个 Agent 负责一个功能模块。

## 交付格式

用例模板详见：Read `references/case-template.md`

```markdown
# 测试用例文档

## 需求摘要
> 一段话概括需求目标和范围

## 测试策略
- 采用方法: [等价类 + 边界值 + BDD]
- 覆盖维度: 正常路径 / 异常路径 / 边界值 / 业务规则
- 总用例数: N 条（P0: a / P1: b / P2: c / P3: d）

## 测试用例

### 模块 A: [模块名称]

| ID | 优先级 | 场景 | 前置条件 | 操作步骤 | 预期结果 | 设计方法 |
|----|--------|------|---------|---------|---------|---------|
| TC-001 | P0 | 正常下单流程 | 用户已登录，余额充足 | 1. 选择商品 2. 确认支付 | 订单创建成功，余额扣减 | Happy Path |
| TC-002 | P0 | 余额不足下单 | 用户已登录，余额=0 | 1. 选择商品 2. 确认支付 | 提示余额不足，订单未创建 | 边界值 |

### BDD 场景（当需求适合行为描述时）

#### Scenario: [场景名称]
**Given** [前置条件]
**When** [操作]
**Then** [预期结果]
**And** [附加验证]

## 覆盖矩阵

| 需求条目 / AC | 对应用例 | 覆盖状态 |
|--------------|---------|---------|
| AC-1: 用户可以下单 | TC-001, TC-002, TC-003 | ✅ 已覆盖 |
| AC-2: 支付失败回滚 | TC-010, TC-011 | ✅ 已覆盖 |
| AC-3: 并发下单 | — | ⚠️ 未覆盖（建议补充） |

## 风险备注
- [标注未覆盖的高风险点和建议]
```

深度模式保存到：`.ace/tasks/tc-gen-{slug}/artifacts/test-cases.md`

## 质量守则

<HARD-GATE>
每个验收条件（AC）必须有至少 1 个对应用例。
覆盖矩阵中如有 AC 未覆盖 → 必须标注为 ⚠️ 并说明原因。
</HARD-GATE>

---

## 反模式

| 反模式 | 表现 | 解药 |
|--------|------|------|
| **需求鹦鹉** | 把需求描述原样改成"验证XXX" | 用例必须比需求更具体（含数据、步骤） |
| **正向偏见** | 只写 happy path | 异常路径 ≥ 正常路径数量 |
| **穷举陷阱** | 试图覆盖所有组合（10个条件×3值=59049条） | 用判定表/正交实验裁剪 |
| **脱离业务** | "输入空字符串" 但业务上不可能空 | 场景必须业务上可发生 |
| **无优先级** | 50条用例平铺无标记 | 必须按风险排序标注 P0-P3 |
| **假覆盖** | 覆盖矩阵全打 ✅ 但用例过于宽泛 | 一个用例只覆盖一个 AC 的一个维度 |

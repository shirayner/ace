# Code Review Pro — 证伪驱动的深度审查

> **审查的本质是证伪，不是匹配。**
>
> 清单匹配问的是"这段代码违反了哪一条规则"——答案往往是"都不违反"，于是产出一堆
> "建议添加注释"。证伪问的是"什么输入会让这段代码产生错误结果"——这是构造性问题，
> 是 LLM 真正的长处所在。
>
> 一条发现的价值 = 它揭示的失败场景的真实性 × 严重度。**不能构造出失败场景的发现，不是发现。**

---

## 五条元原则

这五条决定了本 skill 的每一个设计选择。冲突时按序号优先。

### 1. 可证伪性优先（Falsifiability First）

每条发现必须附带**具体失败场景**：什么输入 / 什么时序 / 什么状态 → 什么错误结果。

写不出失败场景 → 降级为 Suggestion，或直接丢弃。
"这里可能有并发问题"不是发现；"线程 A 在 L42 判空通过后被抢占，线程 B 在 L58 置 null，A 恢复后 L43 解引用 → NPE"才是发现。

### 2. 假阴优于假阳（Prefer False Negatives）

> 借鉴 alibaba/open-code-review 的核心工程判断。

漏报一个真问题，损失是一个 bug。误报十个假问题，损失是**审查者不再信任审查结果**——之后所有真问题也一起被忽略。信任是一次性资源。

**上下文不足时选择沉默，而非猜测报告。** 判据不足就用工具去查（Read/Grep 追调用链），查不到就不报。

### 3. 视角决定发现（Lens Determines Findings）

同一段代码，带着"并发"的眼睛看和带着"可扩展性"的眼睛看，会发现完全不同的问题。
覆盖率（读了多少行）不产生发现，**视角切换**才产生发现。

因此并行的切分维度是**视角**，不是文件。让 3 个 agent 各读全部代码但戴不同眼镜，优于让 3 个 agent 各读三分之一代码。

### 4. 减法也是产出（Deletion Is a Deliverable）

> 借鉴 sanyuan0704 的 removal-plan。

"这段代码可以删掉"往往比"这段代码可以优化"价值更高：删除消灭的是**未来所有**维护成本和 bug 面积。
死代码、废弃开关、为不存在的需求预留的扩展点、重复实现——都要明确报告，并区分「现在就能安全删」和「需要计划」。

### 5. 意图先于实现（Intent Before Implementation）

不理解「这次改动想解决什么问题」就开始逐行看代码，会把**作者的正确决策**误报为问题，把**真正的设计缺陷**当作合理取舍放过。
先建立意图模型，再用意图审判实现。**实现与意图的偏离**是最高价值的发现类型。

## Effort 分级

| Effort | 机制 | 适用 |
|--------|------|------|
| **low** | 单 agent，正确性视角，只报 Critical | hotfix、配置变更 |
| **medium**（默认） | 单 agent，正确性 + 设计双视角，自我反驳 P0 | 日常 review |
| **high** | **多视角并行** + P0 独立证伪 + 需求对照 | 重要功能、资金/权限相关 |
| **max** | high + 删除候选分析 + 认知负荷层 + 二轮补漏 | 核心系统、安全审计 |

**自动升级触发**（无需用户指定）：diff 触及以下任一 → 至少 high
- 资金/计费/对账逻辑
- 认证/授权/权限判断
- 并发/异步/锁/事务
- 数据迁移/删除/批量更新
- 对外 API 契约变更

## 执行流程

### Phase 1 — 范围与意图

```bash
BASE=$(git rev-parse --verify origin/main >/dev/null 2>&1 && echo origin/main || echo origin/master)
git diff --stat $BASE...HEAD
git log --oneline $BASE...HEAD
git diff $BASE...HEAD
```

无 diff → AskUserQuestion 询问审查范围。
`--requirement <path|text>` 提供需求时 Read 作为审判基准。

**产出「意图模型」**（报告开头，2-3 句）：
1. 这次改动解决什么问题？（从 commit + diff 整体推断，不是逐文件罗列）
2. 作者做了哪些关键取舍？
3. 哪些模块的**对外行为**会改变？

> 元原则 5：这一步不可跳过。没有意图模型的审查会同时产生假阳和假阴。

---

### Phase 2 — 视角审查

#### low / medium：单 agent 顺序换镜

按序执行，每一轮**重读全部变更代码**，不要试图一遍看完所有维度：

- Pass A｜正确性视角：数据流 + 控制流 + 边界 + 异常路径
- Pass B｜设计视角（medium+）：职责 / 耦合 / 命名 / 重复 / 可扩展性

#### high / max：多视角并行

Read `../../shared/parallel-protocol.md`，按下表派 Agent。**每个 agent 都拿到完整 diff**，区别只在视角。

| Lens | 关注 | 必读参考 |
|------|------|---------|
| **correctness** | 逻辑、边界、空值、异常路径、资源释放 | `references/falsification.md` |
| **concurrency** | 竞态、原子性、可见性、锁、事务边界 | `references/falsification.md` + `lang/java.md` |
| **security** | 注入、越权、敏感数据、不可信输入 | `lang/java.md`（若 Java） |
| **design** | 职责、耦合、抽象层次、可扩展性、SOLID | `references/design-lens.md` |
| **deletion** | 死代码、冗余、废弃开关、过早抽象（max） | `references/deletion.md` |
| **spec** | 需求对照（仅当提供需求） | `references/spec-drift.md` |

Agent prompt 必须自包含，且**强制要求失败场景**：

```
审查以下变更的 {lens} 维度。

变更内容：
{完整 diff}

意图模型：{Phase 1 产出}

判据参考：Read {reference 路径}

硬性要求：
1. 每条发现必须给出具体失败场景（什么输入/时序/状态 → 什么错误结果）。
   写不出失败场景的，不要报告。
2. 上下文不足以判断时，用 Read/Grep 追查调用链。查不到 → 不报告，不猜测。
3. 宁可漏报，不可误报。
4. 不报告与 {lens} 无关的问题（其他 agent 负责）。

输出（每条）：
- 文件:行号
- 问题（一句话，可独立理解）
- 失败场景（具体）
- 严重度自评 + 置信度（高/中/低）
- 修复方向
```

并行上限 8（协议硬约束）。视角数超限时按风险优先级取前 8。

---

### Phase 3 — 汇总去重

主 agent 回收结果后：

1. **合并同类项** — 同一根因在多处出现 → 一条发现 + 多个位置引用，不是多条发现
2. **跨视角交叉** — 两个 lens 独立指向同一处 → 置信度上调（独立证据）
3. **剔除低置信** — 自评置信度「低」且无失败场景 → 丢弃

---

### Phase 4 — 对抗验证（high+ 强制，medium 自我执行）

> 这是本 skill 与 code-review 的关键差异。**未经证伪的发现不进报告。**

对每条 **Critical** 发现执行：

- **high**：派 1 个独立 Agent 证伪
- **max**：派 3 个 Agent，各持不同证伪视角（能否复现 / 是否已被上游保护 / 是否误读语义），**≥2 票反驳则杀掉**

证伪者 prompt：

```
以下是一条代码审查发现。你的任务是**推翻它**。

发现：{问题描述}
声称的失败场景：{场景}
相关代码：{代码片段 + 必要上下文}

请检查：
1. 这个失败场景真的能发生吗？前置条件成立吗？
2. 是否已有上游校验/框架保证/类型约束阻止了它？
3. 报告者是否误读了 API 语义或执行顺序？
4. 这是否属于「不应报告」的情形（见 lang/java.md 的排除条件）？

不确定时倾向于「推翻」（元原则 2：假阴优于假阳）。

输出：{refuted: true/false, 理由: 一句话, 若成立则修正后的严重度}
```

被推翻的发现**从报告中移除**，但在报告末尾「已排除」区列出一行（含推翻理由）——这本身是有价值的信息，防止下次重复误报。

---

### Phase 5 — 补漏（max）

派一个 completeness critic：

```
以下是本次审查的全部发现和已覆盖视角。

发现：{列表}
已跑视角：{lens 列表}

回答：什么被漏掉了？
- 哪个视角没跑，而这次变更的性质要求它？
- 哪个文件被所有视角轻描淡写地跳过了？
- 哪条发现的失败场景其实没被真正验证？
- 变更的「非功能面」（可观测性、回滚能力、兼容性）有人看过吗？

输出：需要补审的具体项（无则明确回答「无」）。
```

有补审项 → 回到 Phase 2 针对性补跑一轮。

## 严重度（绑定阻塞语义）

> 借鉴 sanyuan0704 的 P 级 + 明确的合并阻塞含义。分级的意义在于**行动约束**，不是形容词。

| 级别 | 语义 | 阻塞 | 门槛 |
|------|------|------|------|
| **P0 Critical** | 生产事故 / 安全漏洞 / 数据损坏 | **必须修复才能合并** | 必须过对抗验证 |
| **P1 Warning** | 逻辑缺陷 / 显著设计问题 / 需求偏离 | 合并前应修复 | 必须有失败场景 |
| **P2 Suggestion** | 坏味道 / 可维护性 / 认知负荷 | 本次或后续迭代 | 必须有具体理由 |
| **P3 Nit** | 风格 / 命名 / 可选优化 | 可忽略 | 合并同类，≤5 条 |
| **Deletion** | 可删除代码 | 区分「现在删」/「计划删」 | 必须确认无引用 |
| **Positive** | 值得肯定的实践 | — | 必须具体，禁止"代码质量很好" |

## 交付格式

```markdown
# Code Review Report (Pro)

## 意图模型
> 这次改动解决什么问题 / 关键取舍 / 对外行为变化。（2-3 句）

## 概览
| 指标 | 值 |
|------|------|
| 范围 | `<branch>` → `<base>` |
| 文件 | N 个（生产代码 M 个） |
| 行数 | +X / -Y |
| Effort | high（自动升级：涉及并发） |
| 已跑视角 | correctness, concurrency, design |
| 对抗验证 | 5 条 P0 候选 → 3 条存活，2 条被推翻 |
| 发现 | 🔴 P0×3 / 🟡 P1×4 / 🔵 P2×6 / ⚪ P3×2 / 🗑 删除×2 |

## 🔴 P0 — 必须修复才能合并

### P0-1. `path/File.java:42` 标题
**问题**：一句话，可独立理解
**失败场景**：具体输入/时序/状态 → 具体错误结果
**影响**：数据损坏？服务不可用？越权？
**验证**：✅ 3 名证伪者中 3 名确认成立
**修复**：
```语言
// 具体代码
```

## 🟡 P1 — 合并前应修复
### P1-1. `path:行号` 标题
**问题** / **失败场景** / **建议**

## 🔵 P2 — 建议改进
### P2-1. `path:行号` 标题
**现状** / **理由** / **方向**

## ⚪ P3 — Nit
- `path:行号` 一行描述（合并同类）

## 🗑 删除候选
| 位置 | 内容 | 判断 | 依据 |
|------|------|------|------|
| `path:行号` | 描述 | 现在删 / 计划删 | 已确认无引用 / 需先下线开关 |

## ⚠️ 需求偏离（仅当提供需求）
### R-1. [需求条目] 标题
**需求原文** / **代码实际行为** / **差距** / **用户可感知？**

## ✅ Positive
- `path` 具体亮点 + 为什么这个决策好

## 🚫 已排除（对抗验证推翻）
| 候选发现 | 推翻理由 |
|---------|---------|
| 描述 | 上游 @Valid 已校验 / 单线程上下文 |

## 总结
| 级别 | 数量 | 关键项 |
|------|------|--------|
| P0 | 3 | 最重要 1-2 条摘要 |
| P1 | 4 | 最重要 1-2 条摘要 |

**合并建议**：阻塞 / 修复 P0 后可合并 / 可合并
```

深度审查产物：`.ace/tasks/review-{slug}/artifacts/code-review-pro-report.md`

## 复杂度适配

| 规模 | 处理 | 默认 effort |
|------|------|------------|
| <100 行 diff | 直接审，无编排 | low |
| 100-500 行 | 顺序换镜 → 报告 | medium |
| >500 行 / 架构级 | 多视角并行 + 建 state.json | high |

深度审查建 state.json（格式见 `../../shared/state-template.md`），完成后：
```bash
ace task complete review-{slug}
ace task archive review-{slug}
```

## 反模式

| 反模式 | 表现 | 解药 | 违反原则 |
|--------|------|------|---------|
| **清单朗读** | 逐条对照 checklist，产出"未发现XX问题" | 证伪驱动：构造失败场景 | 1 |
| **无场景断言** | "这里可能有并发问题" | 写出具体时序，写不出就删 | 1 |
| **噪声轰炸** | 20 条 P2 全是通用最佳实践 | 假阴优于假阳，按 effort 限量 | 2 |
| **猜测填空** | 上下文不足时凭经验推测 | Read/Grep 追查，查不到就沉默 | 2 |
| **按文件切分并行** | 3 个 agent 各审三分之一文件 | 按视角切分，每个都读全量 | 3 |
| **单镜通吃** | 一遍看完所有维度 | 顺序换镜，每轮重读 | 3 |
| **只加不减** | 从不提"可以删掉" | 删除候选是独立维度 | 4 |
| **意图缺失** | 不看 commit 直接逐行 | Phase 1 不可跳过 | 5 |
| **作者意图辩护** | "作者应该是想…"于是放过 | 用意图审判实现，不用意图开脱 | 5 |
| **未验证的 P0** | Critical 直接进报告 | P0 必须过对抗验证 | 1,2 |
| **重复条目** | 同一根因报多次 | Phase 3 合并同类项 | 2 |
| **全面肯定** | "代码质量很好，无问题" | Positive 必须具体到设计决策 | 1 |

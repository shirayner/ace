# 认知负荷层

> max effort 加载。
>
> 这一层的发现**不是 bug**，而是**未来 bug 的概率**。
> 高认知负荷的代码本身可能完全正确——但它让下一个维护者（包括三个月后的作者本人）
> 更容易改错。审查它是在为未来的正确性投资。
>
> 理论基础：Sweller 认知负荷理论、Miller 的 7±2 工作记忆容量。

---

## 三类负荷

| 类型 | 来源 | 能否消除 |
|------|------|---------|
| **内在负荷** | 问题本身的复杂度 | 不能消除，但可通过分解降低**单次**处理量 |
| **外在负荷** | 代码组织方式引入的额外理解成本 | **可以消除——这是审查的目标** |
| **关联负荷** | 读者建立心智模型所需的投入 | 应当**帮助**它（好命名、好结构） |

**报告原则**：只报告外在负荷。内在负荷高（业务本身复杂）不是缺陷；
关联负荷不足（缺少帮助理解的结构）可作为建议。

---

## 可量化的判据

> 这些阈值不是教条，而是**触发深入检查的信号**。命中阈值后仍需判断是否真的造成理解困难。

### 工作记忆超载

| 判据 | 阈值 | 原理 |
|------|------|------|
| 函数内同时活跃的变量 | > 4-5 个 | 超出工作记忆槽位，读者需要反复回看 |
| 单个布尔表达式的运算符 | > 2-3 个 | 需要"人脑编译"，且优先级易错 |
| 相似类型的连续参数 | > 3 个 | 传错位置编译器抓不到（如三个 String） |
| 嵌套回调/Promise/CompletableFuture 链 | > 3 层 | 控制流跳跃，难以追踪失败路径 |
| 方法调用链 | > 3 层（`a.b().c().d()`） | 违反得墨忒耳定律，且每层都是潜在 null 点 |
| 缩进层级 | > 3 层 | 需同时持有多个上下文条件 |

### 外在认知负荷

- 复杂条件未提取为命名布尔变量 → 读者被迫自己在脑中命名
- 同一概念在不同位置用不同名字（`user` / `account` / `member` 指同一物）
- 核心逻辑被样板代码（日志、metrics、异常包装）淹没
- 魔法值散落，读者需要跨文件查找含义
- 否定式命名 + 取反使用（`if (!isNotDisabled)`）

### 知识诅咒（作者视角盲区）

> 作者拥有读者没有的知识，因此看不出哪里需要解释。这类问题只有审查者能发现。

- 使用了只有作者/团队知道的项目黑话、缩写，无注释
- 依赖不明显的执行顺序（Spring Bean 加载顺序、静态初始化、AOP 织入时机）
- 业务规则的**"为什么"**只存在于作者脑中——代码和注释都只说了"做什么"
- 魔法数字来自外部系统约定，但没有常量名或来源注释
- 隐式契约（"这个方法必须在事务内调用"）未在签名或注释体现

**这是本层最高价值的检查项。** 它对应 Clean Code 的"注释只说为什么"——
缺失的恰恰是"为什么"。

### 注意力竞争

- 方法前半段全是 guard clause 和参数校验，核心逻辑被推到屏幕外
- 关键业务逻辑与辅助逻辑（日志/监控/缓存）交织在同一方法
- 异常处理代码量 > 正常路径代码量
- 多个不相关职责在同一方法中，读者不确定在看哪个逻辑

### 心智模型断裂（最小惊讶原则破坏）

> 这一类实际上**更接近真 bug**，因为它会直接导致调用方误用。命中时可升级为 P1。

- 方法行为与命名暗示不一致（`getX()` 有副作用、`validate()` 修改状态）
- 继承链中子类"偷偷"改变了父类的行为语义（LSP 破坏）
- 布尔参数改变方法的核心行为（`process(true)` — 读者必须查签名）
- 错误码/返回值含义与通用约定相反（返回 0 表示失败）
- 静默降级：出错时返回默认值而不告知调用方

## 报告纪律

### 门槛：必须落到具体的误改风险

不可接受：「这个方法太复杂，建议拆分」

可接受：
> 「`OrderProcessor.process` (L45-120) 内有 7 个活跃变量，其中 `tempAmount` 和
> `finalAmount` 在 L67 和 L89 各被重新赋值一次。**下一个需要在中间插入折扣逻辑的人，
> 很可能在错误的位置读取 `tempAmount`**——因为从命名无法判断该位置的值是否已终态。
> 建议：把两次赋值间的逻辑提取为返回终值的方法，消除可变中间态。」

模板：`{结构事实} → {下一个维护者会犯的具体错误}`

### 严重度

| 情形 | 级别 |
|------|------|
| 心智模型断裂（命名与行为不符、静默降级） | P1 — 会导致调用方误用 |
| 工作记忆超载 + 该处代码近期会被频繁修改 | P2 |
| 一般外在负荷 | P2 |
| 知识诅咒（缺"为什么"注释） | P2 |
| 单纯的行数/嵌套超标但逻辑线性易读 | **不报告** |

### 不报告

- 逻辑线性、无分支的长方法（如字段映射、初始化列表）——长但不复杂
- 内在复杂度高的算法实现（复杂性来自问题本身）
- 测试代码的重复与冗长（测试的可读性标准不同，显式优于抽象）
- 生成代码、迁移脚本
- 与项目一致的既存风格
- **本次 diff 未触及的历史代码**——除非本次变更明显加剧了它

## 对报告本身的认知负荷要求

> 这一层的原则同样适用于审查报告自己。一份让人读不懂的审查报告不会被采纳。

| 原理 | 应用 |
|------|------|
| **Miller 7±2** | 单次呈现的信息块 ≤ 4-5 个；发现按严重度分组 |
| **渐进式展示** | 概览 → 分级 → 单条详情，逐层深入 |
| **工作记忆** | 每条发现自包含，不依赖其他条目的上下文才能理解 |
| **锚定效应** | 意图模型放在报告最前，为后续所有发现提供理解锚点 |
| **选择性注意** | 严重度标记 + 阻塞语义引导注意力到最重要处 |
| **认知吝啬** | P3 合并同类；总结表让读者不必读完全文即可决策 |

# 需求偏离检测

> spec lens 加载（仅当用户通过 `--requirement <path|text>` 提供需求时）。
>
> 核心思想：**代码是需求的翻译，翻译失真即缺陷。**
> 这类缺陷有个特点——代码本身完全正确、可编译、测试可能都过，但**做的不是要做的事**。
> 静态检查工具永远发现不了，只有对照需求才能发现。因此这是审查独有的高价值产出。

---

## 前置动作：建立 AC 映射表

不要一边读代码一边回忆需求。先把需求拆成可核对的条目：

1. 从需求文档提取**验收条件（AC）**清单，逐条编号
2. 提取**隐含约束**：数量词（最多/至少/不超过）、时间词（当天/实时/T+1）、
   范围词（仅限/包含/排除）、条件词（如果/除非/否则）
3. 对每条 AC 在 diff 中定位实现位置

| AC | 需求原文 | 实现位置 | 状态 |
|----|---------|---------|------|
| AC-1 | 单用户每日最多提交 5 次 | `SubmitService:45` | ✅ |
| AC-2 | 超限时提示剩余等待时间 | — | ❌ 未实现 |
| AC-3 | 管理员不受限制 | `SubmitService:42` | ⚠️ 判断的是 role != USER，与需求的"管理员"范围不一致 |

**映射表本身就是产出**，放进报告。它让"覆盖了没有"变成可核对的事实而非感觉。

## 四类偏离

### 1. 功能遗漏（Missing Implementation）

- 需求明确列出的 AC 无对应代码
- 需求描述的异常场景（"如果…则…"）无对应分支
- 需求中的边界值（"最多 N 个"）无校验代码
- 需求提到的用户角色区分未在权限逻辑中体现
- 需求要求的**通知/日志/审计**未实现（最常被漏，因为不影响主流程）

严重度：P1 起。若遗漏项涉及资金/权限/合规 → P0。

### 2. 过度实现（Scope Creep）

> 容易被当作"额外的好"而放过，但它意味着**未经需求评审的行为进入了生产**。

- 实现了需求未提及的功能
- 添加了需求未要求的配置开关/扩展点（过早抽象）
- 暴露了需求未要求的 API 端点或响应字段（**尤其注意：可能泄露敏感数据**）
- 悄悄放宽/收紧了需求的限制条件

严重度：P2 起。若暴露了数据或改变了对外契约 → P1/P0。

### 3. 语义漂移（Semantic Drift）

> 最隐蔽的一类。代码逻辑自洽，但表达的业务含义和需求不是一回事。

- 命名与需求用语不一致（需求说"取消"，代码实现"删除"——**是软删还是硬删？语义完全不同**）
- 业务规则的执行顺序与需求描述不符（先校验库存还是先锁价格？）
- 数值精度/单位与业务含义不匹配（分 vs 元、含税 vs 不含税）
- "或"/"且"逻辑与需求的自然语言表述不一致
- 状态机的状态定义与需求的业务状态不对应（代码 5 个状态，需求 4 个——多出来的那个是什么？）

严重度：P1 起。语义漂移常在上线后才暴露，且数据已被污染。

### 4. 边界误解（Boundary Misinterpretation）

> 高频真 bug 来源。需求的自然语言本身有歧义时，代码只能选一种解释——检查它是否选对。

| 歧义点 | 必须确认 |
|--------|---------|
| "大于" vs "大于等于" | 阈值本身算不算？ |
| "最多 5 次" | 第 5 次允许还是拒绝？ |
| "包含" vs "排除" | 区间开闭 |
| "当天" | 00:00-23:59？哪个时区？跨天任务如何归属？ |
| "实时" | 同步返回还是异步最终一致？延迟上限？ |
| "N 天内" | 自然日还是 24h*N？含首日吗？ |
| 金额 | 单位？舍入方向？（银行家舍入 vs 四舍五入） |
| 并列条件 | "A 和 B" 是同时满足还是分别处理？ |

**处理方式**：如果需求本身歧义，代码的选择无法判定对错 → 报告为「需求歧义」，
建议向需求方确认，并指出代码当前的选择是什么。这比擅自判定对错更有价值。

## 反向检查：需求未覆盖的实现风险

除了"需求→代码"，还要做"代码→需求"：

- 代码中的异常分支，需求说过该怎么处理吗？（需求常只写正常流程）
- 并发/重复提交场景，需求提过吗？代码的选择是什么？
- 失败重试、部分成功、超时——需求空白，代码默认行为是什么？

需求空白处的代码行为**必须显式化并报告**，因为它是未经评审的业务决策。

## 输出格式

```markdown
## ⚠️ 需求一致性

### AC 覆盖映射
| AC | 需求原文 | 实现位置 | 状态 |
|----|---------|---------|------|
| AC-1 | … | `File:行号` | ✅ |
| AC-2 | … | — | ❌ 遗漏 |

覆盖率：M/N

### R-1. [AC-3] 管理员判定范围与需求不一致
**需求原文**：> "管理员不受提交次数限制"
**代码实际行为**：`SubmitService:42` 判断 `role != Role.USER`，即所有非普通用户
（含审核员、运营）均不受限
**差距**：需求限定"管理员"，代码放宽到"所有非普通用户"
**用户可感知**：是——审核员可无限提交，可能造成数据污染
**严重度**：P1

### R-2. [需求歧义] "每日最多 5 次"的边界
**需求原文**：> "单用户每日最多提交 5 次"
**代码实际行为**：`count >= 5` 时拒绝，即第 5 次成功、第 6 次被拒
**说明**：这是合理解释，但需求未明确。建议向需求方确认后在注释中固化。
**严重度**：P3（提示性）

### 需求空白处的默认行为
| 场景 | 需求 | 代码当前行为 | 建议 |
|------|------|------------|------|
| 重复提交 | 未提及 | 无幂等控制，会产生两条记录 | 需确认 |
```

---

## 报告纪律

1. **必须引用需求原文** — 不能只写"需求要求…"，要摘录。避免审查者自己的理解偏差成为新的失真源。
2. **区分「代码错」和「需求含糊」** — 后者不是开发的锅，报告方式不同（前者要求修复，后者要求确认）。
3. **判断用户可感知性** — 不可感知的偏离降级处理，避免为纯内部实现差异阻塞合并。
4. **不越界评审需求本身** — "这个需求设计得不好"不属于代码审查范围（除非它导致实现不可能正确）。

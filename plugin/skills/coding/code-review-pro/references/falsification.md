# 证伪方法论 — 如何构造失败场景

> correctness / concurrency lens 加载。
>
> 本文档不是坏味道清单。清单告诉你"看什么"，本文档告诉你"**怎么让代码露出破绽**"。

---

## 核心手法：从「读代码」到「攻代码」

审查者的默认模式是顺着作者的思路读——这会继承作者的**盲点**。
证伪模式是逆着走：假设这段代码是错的，我的任务是找出证据。

对每个函数/分支问三个构造性问题：

1. **什么输入会让它产生错误结果？**（不是崩溃，是**静默的错误结果**——更危险）
2. **什么时序会让它产生错误结果？**（并发、重试、乱序、超时）
3. **什么状态会让它产生错误结果？**（缓存陈旧、部分失败、迁移中间态）

写不出以上任一，这段代码在本视角下就是干净的。**不要为了产出而产出。**

---

## 输入维度攻击面

对每个入参、每个外部数据源，逐一试探：

| 攻击输入 | 典型后果 |
|---------|---------|
| `null` / 未初始化 | NPE，或更糟：被当作合法默认值 |
| 空集合 / 空字符串 | 循环不执行 → 返回空结果被当作"无数据" |
| 单元素集合 | 边界逻辑（首/尾特殊处理）暴露 |
| 恰好在边界上（=N, =N-1, =N+1） | off-by-one |
| 0 / 负数 | 除零、负索引、`Math.abs(Integer.MIN_VALUE)` |
| 极大值 | 整数溢出、内存耗尽、超时 |
| 重复元素 | 去重假设失效、Map 覆盖 |
| 乱序 | 隐式依赖顺序的逻辑失效 |
| 超长字符串 | 截断、DB 字段溢出、乱码（多字节被切断） |
| 特殊字符 | 注入、转义失效、序列化异常 |
| 不同时区 / 跨天跨月跨年 | 时间边界计算错误 |
| 精度边界（浮点、金额） | 累积误差、分与元混用 |

**关键**：不是把这张表当清单跑一遍，而是问「哪些**在本次变更的实际调用路径上可达**」。不可达的不报。

## 数据流分析

追踪：**数据从哪来 → 在哪变换 → 到哪去**。

在每个变换点问：
- 有信息**丢失**吗？（精度、字段、异常上下文被吞）
- 有信息**污染**吗？（未校验的外部输入进入信任区）
- 类型/单位**匹配**吗？（毫秒 vs 秒、分 vs 元、String 化的数字）
- `null` 是否被**安全传递**？谁负责判空——调用方还是被调方？契约明确吗？
- 跨边界（网络、DB、序列化）时格式是否一致？

**高价值发现点**：信任边界的错位。上游以为下游会校验，下游以为上游已校验。

---

## 控制流分析

- 所有分支都覆盖了吗？特别是 `else` 缺失的隐含分支
- 循环边界正确？**能终止吗**？（终止条件依赖可变外部状态时尤其危险）
- `switch` 的 fall-through 是有意的吗？有注释吗？
- **异常路径是否保持一致性**？——最常见的真 bug 藏在这里：
  - 抛异常时已修改的状态回滚了吗？
  - 资源在异常路径上释放了吗？
  - 部分成功的批量操作，调用方能知道哪些成功了吗？
- 早退（return/break/continue）跳过了必要的清理吗？

---

## 契约分析

对每个公开方法，显式化四件事，然后检查实现是否守约：

| 契约项 | 问题 |
|--------|------|
| **前置条件** | 调用者必须保证什么？代码检查了吗，还是默认相信？ |
| **后置条件** | 方法承诺返回什么？所有 return 路径都满足吗？ |
| **不变量** | 什么在整个生命周期恒成立？有路径能打破它吗？ |
| **异常契约** | 什么条件抛什么异常？调用方能区分并正确处理吗？ |

**契约变更是最隐蔽的破坏性变更**：签名没变，但"返回 null 表示不存在"改成了"返回空对象"，所有调用方的判空逻辑静默失效。

## 并发证伪

> 并发问题不能靠"看起来有共享状态"来判定。必须构造**具体的交错时序**。

### 报告的必要条件

必须能写出这样的时序表，否则不报：

```
T1: 线程A 执行 L42 (if (cache.get(k) == null))  → 判定为 null
T2: 线程B 执行 L58 (cache.put(k, v))            → 写入
T3: 线程A 执行 L43 (cache.put(k, compute()))    → 覆盖 B 的写入
后果：B 的写入丢失，且 B 认为写入成功
```

### 四类应报告的情形

> 直接吸收 alibaba/open-code-review 的判据。

1. **竞态条件**：存在"检查-then-执行"（check-then-act）模式，中间状态可被其他线程改变
2. **复合操作非原子**：需要原子性的多步操作缺少同步机制
3. **不安全的延迟初始化**：单例或缓存的双重检查锁定（DCL）缺陷（缺 volatile）
4. **并发写线程不安全集合**：多线程环境下修改 ArrayList / HashMap 等

### 六类**不应报告**的情形（降噪核心）

> 这是本文档最重要的部分。绝大多数并发误报来自忽略这六条。

1. **方法内局部变量** — 天生线程安全，每个线程有自己的副本
2. **单线程上下文** — 没有证据表明会被多线程调用（用 Grep 确认调用方后再判断）
3. **只读操作** — 即使是非线程安全的数据结构，若只读
4. **不可变对象** — final 字段指向不可变对象
5. **已有正确同步** — 已使用 synchronized / Lock / 原子类
6. **设计为单线程使用的组件** — 如 Builder 的构建阶段、临时 DTO

**判断顺序**：先用 Grep 确认调用上下文是否真的并发 → 再判断是否落入四类应报 → 最后排除六类不应报。跳过第一步的并发报告基本都是误报。

## 事务与一致性证伪（Java/Spring 常见）

- 事务边界与业务原子性边界一致吗？（跨越两个 `@Transactional` 方法的操作不是原子的）
- 事务内做了外部调用（HTTP、MQ）吗？→ 外部成功但事务回滚 = 不一致
- 消息发送与本地事务的顺序？→ 消息已发但事务失败
- 重试是幂等的吗？→ 重复扣款
- 分布式场景下"先写库后删缓存"vs"先删缓存后写库"的中间态

## 置信度自评

每条发现附置信度，Phase 4 会据此决定验证强度：

| 置信度 | 标准 |
|--------|------|
| **高** | 失败场景的每一步都在代码中可见，前置条件确认可达 |
| **中** | 失败场景成立，但某个前置条件依赖未读到的上游代码 |
| **低** | 模式可疑但无法构造完整场景 → **不要报告**（元原则 2） |

## 自我反驳清单（medium effort 无独立证伪者时自行执行）

对每条 Critical 候选，自问：

1. 这个失败场景真能发生？前置条件在**实际调用路径**上成立吗？
2. 上游是否已有校验/框架保证/类型约束阻止了它？（`@Valid`、非空约束、DB 约束、编译期类型）
3. 我是否误读了 API 语义？（去查文档/实现，别凭印象）
4. 我是否误读了执行顺序？（特别是注解、AOP、生命周期回调）
5. 它是否落入本文档列出的「不应报告」情形？

任一存疑 → 降级或丢弃。**推翻自己的发现不是失败，是审查质量的体现。**

# 设计视角判据

> design lens 加载。
>
> 设计问题的报告门槛比正确性更高：**设计缺陷必须落到"未来某个具体的改动会因此变困难"**，
> 否则就是主观偏好之争。本文档的作用是把模糊的设计直觉转化为可证伪的陈述。

---

## 设计发现的可证伪化

普通设计评论：「这个类职责太多，违反 SRP」→ 无法反驳也无法确认，作者只会防御。

可证伪的设计发现：

> 「`OrderService` 同时处理订单状态机和优惠计算。**当运营要新增一种优惠规则时**，
> 必须修改这个类，而修改它就要重新回归订单状态流转的全部用例——两个变化频率不同的
> 关注点被绑在一起。证据：本次 diff 中 L120-180 的优惠逻辑和 L20-60 的状态流转
> 没有任何数据共享。」

**模板**：`当 {具体的未来变更} 发生时，因为 {结构原因}，需要 {额外代价}。证据：{diff 中的事实}`

写不出「具体的未来变更」→ 降为 P3 或不报。

## 六个审查提问

### 1. 修改理由唯一吗？（SRP）

不要问"这个类做了几件事"（永远可以说做了很多事），要问：

- **列出所有会导致这个类被修改的外部原因**。超过一个，且这些原因的**变化频率不同** → 报告。
- 不同的调用方是否只用到这个类的不同部分？（分裂信号）

**不报告**：职责多但都源于同一个业务概念的内聚变化；DTO/配置类等天然的数据聚合。

### 2. 新增同类功能需要改几处？（OCP）

- 数一数：新增一个同类型的东西（新支付方式、新导出格式、新校验规则），要改几个文件？
- **理想是 1 处（新增文件）**。≥3 处散落修改 → 报告，并指出缺失的扩展点。
- 信号：`switch`/`if-else` 对类型做判断，且同样的判断在多处重复出现。

**不报告**：只有一个实现且无明确扩展需求时的"缺少抽象"——这是 YAGNI，过早抽象才是问题（见下文）。

### 3. 依赖方向正确吗？（DIP）

- 高层业务逻辑是否直接依赖具体技术实现（具体 DB 客户端、HTTP 客户端、第三方 SDK）？
- 依赖是否可在测试中替换？**不可测试 = 依赖方向错了**（可测试性是设计质量的探针，不是额外要求）
- 是否存在循环依赖？（包级、模块级）

**不报告**：项目整体不做依赖倒置且一致（一致性 > 局部教条）；简单 CRUD 的直接依赖。

### 4. 抽象层次一致吗？

同一个方法内是否混杂了不同抽象层次的操作？

```
// 层次混杂的信号
validateOrder(order);           // 业务层
conn.setAutoCommit(false);      // 基础设施层
calculateDiscount(order);       // 业务层
```

- 业务逻辑与基础设施（连接管理、序列化、日志、重试）交织 → 报告
- 抽象泄漏：上层需要知道下层的实现细节才能正确使用

### 5. 这个抽象有存在理由吗？（反过度工程）

> 与第 2 条方向相反。过早抽象和抽象不足同样是缺陷，而**过早抽象更难移除**。

应报告：
- 只有一个实现的接口，且无测试替换需求、无明确扩展计划
- 为不存在的需求预留的扩展点、配置开关、策略枚举
- 泛型/继承层次深到需要跳转 3 次才能找到实际逻辑
- 设计模式用在了简单问题上（单一逻辑套了工厂+策略+模板方法）
- 「以后可能会…」注释伴随的复杂结构

**判据**：删掉这层抽象，代码会变短且更易读吗？会 → 报告。

### 6. 知识只表达了一次吗？（DRY）

- 相同的**业务规则**在多处独立实现 → 报告（规则变更时会遗漏）
- 相同的**结构**但语义不同 → **不报告**（这是巧合重复，强行合并会造成错误耦合）

**关键区分**：DRY 针对知识，不针对代码形状。两段长得一样但会因不同原因而变化的代码，应当保持分离。

## 可扩展性专项

> 「可扩展性」容易变成空话。用以下三个具体探针替代。

| 探针 | 提问 | 报告门槛 |
|------|------|---------|
| **变化点识别** | 这个模块最可能变化的是什么？该变化被隔离了吗？ | 变化点与稳定部分耦合 |
| **扩展成本** | 新增一个同类实体/规则/渠道，改动面有多大？ | ≥3 处散落修改 |
| **契约稳定性** | 这个接口的下游变更会波及多少调用方？ | 内部实现细节泄漏到公开签名 |

**反向探针**（防过度）：这个扩展点在过去 N 次迭代中被用过吗？从未 → 它是负债不是资产。

## 命名（作为设计问题，而非风格问题）

命名错误往往是**设计错误的症状**，值得报告的是后者：

- 方法名与实际行为不符（`getX()` 有副作用、`validate()` 会修改状态）→ **最小惊讶原则破坏**，报 P1
- 同一概念在不同位置用不同名字 → 说明概念边界不清晰，报 P1
- 名字里含 `And`/`Or`（`saveAndNotify`）→ 职责信号，报 P2
- 名字需要注释才能理解 → 抽象错位
- 纯风格问题（缩写、大小写）→ P3，合并同类

## 不报告清单（design lens 降噪）

- 与项目既存一致风格不符但本身无害的写法
- 「可以用更时髦的语言特性」类建议
- 无具体未来变更支撑的「不够灵活」
- 测试代码、生成代码、迁移脚本的设计问题（生命周期短，标准不同）
- 本次 diff 未触及的历史遗留设计问题（除非本次变更明显加剧了它——此时报告并说明加剧关系）

> 最后一条特别重要：审查范围是**本次变更**。历史债务的罗列会淹没本次变更的真实风险。

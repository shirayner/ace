# 删除候选识别

> deletion lens 加载（max effort，或用户明确要求瘦身时）。
>
> **元原则 4：减法也是产出。**
> 「这段代码可以删掉」的价值常高于「这段代码可以优化」——删除消灭的是未来**所有**
> 维护成本、理解成本和 bug 面积。而且它是唯一能让系统变简单的操作。

---

## 为什么删除维度需要独立视角

正常的审查心态是"检查新增代码有没有问题"，这个心态天然看不见"什么本该消失"。
删除需要反向提问：**如果我要让这个模块变短一半，我会先动哪里？**

审查者不主动找，删除候选永远不会浮现——没人会主动汇报自己的代码是多余的。

---

## 七类删除候选

### 1. 死代码（最高置信度）

- 永远不可达的分支（条件恒为 false、`return` 之后的代码）
- 声明但从未读取的变量、字段
- 从未被调用的私有方法
- 大段注释掉的代码（且无保留意图说明）
- 未使用的 import、依赖

**确认方法**：Grep 全仓搜索标识符。注意反射、SPI、配置文件字符串引用、序列化字段——这些静态搜索抓不到。

### 2. 本次变更导致的遗留

> 最高价值类型，因为只有此刻的审查者能发现。

- 新实现已上线，**旧实现还在**（作者忘了删，或"先留着以防万一"）
- 新旧逻辑并存的兼容分支，而迁移已完成
- 被新代码取代但仍被少量调用点引用的旧方法
- 本次变更让某个参数/字段/配置项变得无意义

**探针**：本次 diff 新增了什么能力？搜一下：原来提供这个能力的东西还在吗？

### 3. 废弃的开关与配置

- 灰度开关已全量（配置固定为 true 已久）→ 开关与 false 分支都可删
- feature flag 对应功能已稳定
- 已无人使用的配置项（且有默认值）
- `@Deprecated` 标记超过一个版本周期且无调用方

### 4. 过早抽象的扩展点

- 只有一个实现的接口/抽象类，且无测试替换需求
- 为"以后可能"预留的策略枚举、工厂、注册表——从未新增第二项
- 从未被覆写的模板方法钩子
- 泛型参数实际只用过一种类型

**判据**：删掉这层，代码会变短且更易读吗？

### 5. 重复实现

- 同一业务规则的多处独立实现（保留一处，其余删除并改为调用）
- 项目内自实现的工具方法，而依赖库已提供（`StringUtils`、`Collections`）
- 多个功能重叠的工具类

### 6. 防御性冗余

> 需谨慎判断——防御性代码删错了会引入 bug。只在能证明不可达时报告。

- 上游已强制校验，下游重复校验（且上游校验不可绕过）
- 类型系统已保证的运行时检查（如对 `int` 判 null）
- 不可能触发的 catch 块
- 重复的判空（同一变量在同一路径上判了两次）

### 7. 测试与文档的僵尸

- 被 `@Ignore` / `@Disabled` 长期跳过的测试（要么修，要么删——留着是噪声）
- 断言被注释掉的测试（假绿灯，比没有测试更危险）
- 与代码已不符的注释/文档（误导性 > 无用）
- 重复覆盖同一路径的测试

## 安全性分级（必填）

每条删除候选必须给出分级和依据，**不允许只说"可以删"**：

| 分级 | 条件 | 必须提供的依据 |
|------|------|--------------|
| **现在删** | 静态可证无引用 | Grep 结果（含反射/配置/SPI 已排查的说明） |
| **计划删** | 有引用但可迁移 | 迁移步骤 + 影响的调用点清单 |
| **观察后删** | 无法静态确认（反射、外部调用、动态路由） | 建议的观察手段（埋点/日志/监控周期） |
| **不建议删** | 疑似冗余但有合理保留理由 | 说明为何保留（记录判断，防止下次重复讨论） |

---

## 反模式

| 反模式 | 危害 | 解药 |
|--------|------|------|
| **未验证就建议删** | 删掉反射/SPI 引用的代码 → 运行时炸 | 必须附 Grep 证据，并声明已考虑动态引用 |
| **删除防御性代码** | 上游校验哪天被绕过 → 无保护 | 只在能证明不可达时报告，否则归入「不建议删」 |
| **建议删测试** | 覆盖率下降，掩盖真问题 | 只删僵尸测试（已跳过/断言注释），不删"看起来重复"的测试 |
| **超出变更范围的大扫除** | 审查变成重构提案，PR 无法推进 | 优先报告与本次变更**相关**的删除候选；历史债务另立清单 |
| **只报不给依据** | 作者无法判断，条目被忽略 | 每条必填分级 + 依据 |

## 输出格式

```markdown
## 🗑 删除候选

| 位置 | 内容 | 分级 | 依据 |
|------|------|------|------|
| `OrderService.java:120-145` | 旧版优惠计算 `calcDiscountV1` | 现在删 | Grep 全仓无引用；已确认无反射/配置引用；本次 diff 的 V2 已取代 |
| `application.yml:34` | `feature.newFlow.enabled` | 计划删 | 已全量 3 个月；需先删代码中 2 处分支判断（`FlowRouter:56,89`） |
| `PaymentHandler.java:78` | `if (channel == null)` 判空 | 不建议删 | 上游有 `@NotNull` 但存在内部直调路径，保留防御 |

**可减少代码量**：约 N 行
```

统计"可减少代码量"是有意义的——它让减法的价值可见。

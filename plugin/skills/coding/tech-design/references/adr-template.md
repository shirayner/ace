# ADR 模板 — 架构决策记录

---

## 格式

```markdown
## ADR-[编号]: [决策标题（一句话摘要，可搜索）]

- **状态**: Draft / Adopted / Deprecated / Superseded by ADR-X
- **日期**: YYYY-MM-DD
- **决策者**: [人员/角色]

### 背景

[决策时面临的问题和约束。写清楚"为什么现在需要做这个决策"。]

### 约束

- [硬约束 1]
- [硬约束 2]
- [软约束 ...]

### 候选方案

#### 方案 A: [名称]
- **描述**: ...
- **优点**: ...
- **代价**: ...
- **适用条件**: ...

#### 方案 B: [名称]
- **描述**: ...
- **优点**: ...
- **代价**: ...
- **适用条件**: ...

#### 方案 C: [名称]（可选）
...

### 决定

选择 **方案 [X]**。

### 理由

[为什么选这个？直接关联到约束和优先级。]

关键考量：
1. [约束 A] 排除了方案 Y
2. [优先级 B] 使方案 X 的优势更突出
3. [风险 C] 在可接受范围内

### 代价与后果

**收益**：
- ...

**成本/技术债**：
- ...

**放弃的选项意味着**：
- ...

### 触发信号

当以下条件出现时，应重新评估此决策：
- [量化信号 1]
- [量化信号 2]
- [业务变化信号]

### 相关决策

- 依赖: ADR-Y
- 影响: ADR-Z
```

---

## 写好 ADR 的原则

1. **记录 WHY，不只是 WHAT** — 代码告诉你系统现在是什么样，ADR 告诉你为什么变成这样
2. **量化触发信号** — "当 QPS > 5000" 比 "当流量大了" 有用 100 倍
3. **诚实记录代价** — 只有优点的 ADR 是自欺欺人
4. **不怕写 Draft** — 半成品 ADR 比没有 ADR 好；先记录再完善
5. **及时更新状态** — 过时的 Adopted 比没有 ADR 更危险（误导后来者）

---

## 常见 ADR 主题

- 存储选型（数据库/缓存/消息队列）
- 服务拆分/合并决策
- 通信协议选择（HTTP/gRPC/消息）
- 一致性模型选择
- 部署架构决策
- 安全模型选择
- 第三方服务 vs 自建
- 数据模型设计取舍
- 缓存策略
- 错误处理/重试策略

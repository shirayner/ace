# 用户提问契约

> 本文件只规定“怎么问”。问什么、何时问由 `flow.md` 的 Frontier 与低价值过滤决定。

## 通道

环境提供 `AskUserQuestion` 时必须使用；不可用时降级为同语义 Markdown。不得因工具不可用而退化为开放式问题墙。

## 澄清模式

每轮提出 **1–4 个互不依赖的问题**，通常 2–4 个。只有一个高价值问题时只问一个；若后题依赖前题答案，留到下一轮。

每个问题包含：

1. 简短标题；
2. 为什么现在确认，以及答案会影响什么；
3. 1–3 个互斥、真实的候选项；
4. 推荐项及依据；
5. 自由补充入口。

`AskUserQuestion` 会自动提供 `Other`，不要在 options 中重复添加。选项标签简短，影响和推荐依据写在 question 或 description 中。

### 推荐规则

- 存在多个合理候选时：把推荐项放第一位，名称后标 `（推荐）`，说明推荐依据。
- 只有一个合理候选时：把它标为 `（待确认建议）`，并提供“暂不采纳，请说明原因”作为第二个真实选择；系统自动的 `Other` 仍用于补充、组合或纠正。不得为满足工具的最少选项数伪造另一套业务方案。
- 推荐只用于降低澄清成本，不代表用户已确认。

### Markdown 降级示例

```markdown
### Q1 · 删除的业务语义

“删除”存在多种解释，会影响数据保留、恢复、审计和验收。请选择本期语义：

A. 逻辑删除，可在 30 天内恢复（推荐）
   兼顾纠错、审计和实现成本。

B. 永久删除
   删除后不可恢复，适用于明确的合规清除场景。

C. 仅对当前用户隐藏
   数据仍参与后台处理，但不再向该用户展示。

Other：请补充其他语义或组合规则。
```

## 审批模式

完整需求对齐卡先用 Markdown 展示，再在同一轮单独调用 `AskUserQuestion`。审批问题和选项以 `alignment-gate.md` 为准，不与澄清问题混合。

处理结果：

- 选择“通过，需求已对齐”或明确表达完全等价语义：通过；
- 选择“拒绝，需要修正”：回到主流程；
- 选择 `Other`、补充内容、附带条件或提出修正：**不通过**。先更新理解、重做 Readiness，再展示新卡确认。

## 分组与节奏

- 互不依赖的问题可合并，单轮不超过 4 个。
- 答案会改变后题、选项或推荐时，必须串行。
- 高风险本身不强制单问；依赖关系决定串并行，认知负担决定本轮数量。
- 每轮回答后更新因果树并重新派生 Frontier，不沿用预设问卷。

## 禁止事项

- 只问开放题，要求用户从零作文；
- 为凑数量制造伪选项；
- 重复询问材料中已明确或执行者可查明的事实；
- 把有依赖的问题并列询问；
- 把澄清和审批混在一次调用；
- 把长篇背景塞入选项标签；
- 将 `Other` 或含条件同意视为审批通过。

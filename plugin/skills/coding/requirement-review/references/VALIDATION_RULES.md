# 输入验证规则

本文档定义 requirement-review skill 在各个步骤中的输入验证规则。

---

## 验证模式：Plan-Validate-Execute

所有关键步骤遵循以下验证模式：

```
Plan (规划)          → 明确验证点和通过标准
    ↓
Validate (验证)      → 执行验证规则，收集错误
    ↓
✅ Pass?
    ├─ 是 → Execute (执行) 进入下一步
    └─ 否 → Collect Errors (收集错误) → 返回用户修正 → 重新验证
```

**在以下关键步骤中应用此模式**：
- Step 1-2：输入来源验证（本地文件/链接/文本）
- Step 3：角色配置验证（roles.json 有效性、角色可用性）
- Step 6-7：报告结构验证（模板字段完整性、格式一致性）

---

## Step 1-2：输入来源验证

### 本地文件路径验证

**验证点**：

| 规则 | 说明 | 示例 |
|------|------|------|
| **路径格式** | 必须是绝对路径或相对路径（不支持波浪线） | ✅ `/Users/name/prd.md`<br>✅ `./prd.md`<br>❌ `~/prd.md` |
| **文件存在** | 文件必须存在且可读 | 若不存在 → 提示"文件不存在" |
| **文件大小** | 建议 ≤ 50KB（超过建议分模块输入） | 若 > 50KB → 警告"文件过大，建议分模块输入" |
| **文件编码** | 必须是 UTF-8 编码 | 若非 UTF-8 → 提示"请使用 UTF-8 编码保存文件" |
| **MIME 类型** | 支持 `.md`, `.txt`, `.pdf` | 若不支持 → 提示"不支持的文件格式" |

**验证流程**：

```
用户提供本地文件路径
    ↓ Plan
规划验证点：路径、文件存在、大小、编码、MIME类型
    ↓ Validate
1. 路径格式检查 → 是否为绝对/相对路径？
2. 文件存在性检查 → 文件是否存在？
3. 文件大小检查 → 是否 ≤ 50KB？
4. 文件编码检查 → 是否 UTF-8？
5. MIME 类型检查 → 是否支持的格式？
    ↓
✅ 所有检查通过？
    ├─ 是 → Execute（读取文件内容）
    └─ 否 → 收集所有错误 → 返回用户修正 → 重新验证
```

**错误消息示例**：

```
❌ 验证失败（共2处）：
  1. 路径格式错误：不支持波浪线展开 (~/)，请改用绝对路径或相对路径
  2. 文件编码错误：检测到 GBK 编码，请转换为 UTF-8 后重试

👉 请修正后重新提供文件路径
```

### Feishu 链接验证

**验证点**：

| 规则 | 说明 | 示例 |
|------|------|------|
| **URL 格式** | 必须以 `https://` 开头 | ✅ `https://...`<br>❌ `http://...` |
| **域名** | 必须是 Feishu 文档分享链接 | ✅ `https://xxx.feishu.cn/...`<br>❌ 其他域名 |
| **分享权限** | 链接必须可访问（非私有或过期） | 若链接失效 → 提示"链接无法访问" |
| **文档类型** | 支持 Doc、Wiki、Sheets 等文本类型 | 若无法解析内容 → 降级为文本输入 |

**验证流程**：

```
用户提供 Feishu 链接
    ↓ Plan
规划验证点：URL格式、域名、分享权限、文档类型
    ↓ Validate
1. URL 格式检查 → 是否以 https:// 开头？
2. 域名检查 → 是否 feishu.cn 域名？
3. 分享权限检查 → 链接是否可访问？
4. 文档类型检查 → 是否支持的文本类型？
    ↓
✅ 链接有效？
    ├─ 是 → Execute（解析 Feishu 内容）
    └─ 否 → 降级为文本输入 → 请求用户手动复制文档内容
```

**错误处理**：

```
⚠️  链接验证失败：
  - 原因：文档分享权限已过期或已取消分享

📋 降级方案：请手动复制 Feishu 文档内容并直接粘贴
```

### PRD 内容格式验证

**验证点**：

| 规则 | 说明 | 影响 |
|------|------|------|
| **内容非空** | PRD 内容不能为空 | 若空 → 提示"PRD 内容为空" |
| **包含标题** | 最好包含标题（markdown `#` 或文本开头） | 若无 → 自动生成临时标题 |
| **包含描述** | 最好包含基本描述或需求信息 | 若无 → 提示"内容过简，建议提供更多信息" |
| **字符编码** | 必须是有效的 UTF-8 | 若无效 → 提示"字符编码错误" |
| **内容长度** | 建议 50-50000 字符 | 若 < 50 → 警告"内容过少"<br>若 > 50KB → 建议分模块 |

**验证流程**：

```
加载 PRD 内容（本地文件、链接或直接粘贴）
    ↓ Plan
规划验证点：非空、标题、描述、编码、长度
    ↓ Validate
1. 内容非空检查 → 内容是否为空？
2. 编码检查 → 是否有效 UTF-8？
3. 内容长度检查 → 是否 50-50000 字符？
4. 标题提取 → 是否包含标题？
5. 描述识别 → 是否包含基本描述？
    ↓
✅ 内容有效？
    ├─ 是 → Execute（提取摘要，确认进行下一步）
    └─ 否 → 收集错误 → 返回用户修正 → 重新验证
```

**错误消息示例**：

```
⚠️  PRD 内容验证：
  ✅ 编码检查 - UTF-8 有效
  ⚠️  长度检查 - 135 字符（建议 50-50000）
  ⚠️  标题检查 - 未发现标题，将使用默认标题

📋 摘要：
  标题：（自动生成）
  内容概览：...

👉 确认继续？(y/n)
```

## Step 3：角色配置验证

### roles.json 有效性

**验证点**：

| 规则 | 说明 | 示例 |
|------|------|------|
| **文件存在** | 必须存在于 `resources/roles.json` | 若不存在 → 工作流停止 |
| **JSON 格式** | 必须是有效的 JSON | 若无效 → 提示格式错误 |
| **必需字段** | 每个角色必须有：`id`, `name`, `enabled` | 若缺失 → 标记为无效角色 |
| **至少一个角色** | 必须至少有一个 `enabled: true` 的角色 | 若无 → 工作流停止 |

**验证流程**：

```
Step 3：选择角色
    ↓ Plan
规划验证点：文件存在、JSON格式、必需字段、至少一个启用的角色
    ↓ Validate
1. 文件存在检查 → resources/roles.json 是否存在？
2. JSON 格式检查 → 是否有效 JSON？
3. 必需字段检查 → 每个角色是否有 id/name/enabled？
4. 启用角色检查 → 是否至少有一个 enabled: true？
    ↓
✅ 配置有效？
    ├─ 是 → Execute（显示角色列表，让用户选择）
    └─ 否 → 停止工作流 → 提示用户检查 resources/roles.json
```

**错误处理**：

```
❌ 角色配置验证失败：
  - 文件缺失：resources/roles.json 不存在
  - 建议：确保 resources/roles.json 存在并包含至少一个启用的角色

🛑 工作流停止。请修复上述问题后重试。
```

---

### 用户角色选择验证

**验证点**：

| 规则 | 说明 | 示例 |
|------|------|------|
| **角色存在** | 用户输入的角色必须存在于 roles.json | ✅ `backend_member`<br>❌ `unknown_role` |
| **角色启用** | 选择的角色必须是 `enabled: true` | 若为 false → 提示"角色已禁用" |
| **支持两种输入** | 支持编号（如 1）或角色 ID（如 backend_member） | 两种都有效 |
| **模板可加载** | 选定角色的 standard.md 和 template.md 必须存在 | 若缺失 → 提示"模板文件缺失" |

**验证流程**：

```
用户输入角色编号或 ID
    ↓ Plan
规划验证点：角色存在、角色启用、输入格式、模板可加载
    ↓ Validate
1. 输入格式检查 → 是否为有效的编号或 ID？
2. 角色存在检查 → 角色是否存在于 roles.json？
3. 角色启用检查 → 角色是否 enabled: true？
4. 模板加载检查 → standard.md 和 template.md 是否存在？
    ↓
✅ 角色有效？
    ├─ 是 → Execute（加载标准和模板）
    └─ 否 → 收集错误 → 提示用户选择有效角色 → 重新验证
```

**错误消息示例**：

```
❌ 角色选择无效：
  - 输入：unknown_role
  - 原因：此角色不存在或已禁用

📋 可用角色：
  [1] backend_member - 后端研发(会员)
  [2] ui - UI 设计

👉 请选择有效的角色编号或 ID
```

## Step 6-7：报告结构验证

### 模板字段完整性

**验证点**：

| 规则 | 说明 | 影响 |
|------|------|------|
| **必需字段** | 模板中标记为必需的字段必须填充 | 若缺失 → 返回 Step 5 |
| **字段映射** | 工作流输出的内容必须能映射到模板字段 | 若无法映射 → 跳过该内容 |
| **格式一致** | 填充内容的格式必须与模板一致（如表格格式） | 若格式不一致 → 调整格式 |

**验证流程**：

```
生成报告之前
    ↓ Plan
规划验证点：必需字段填充、字段映射、格式一致
    ↓ Validate
1. 必需字段检查 → 所有必需字段是否已填充？
2. 字段映射检查 → 内容是否成功映射到模板字段？
3. 格式一致性检查 → 填充的内容格式是否与模板一致？
    ↓
✅ 报告结构有效？
    ├─ 是 → Execute（生成最终报告）
    └─ 否 → 收集缺失信息 → 返回 Step 5 重新分析 → 重新验证
```

## 通用验证最佳实践

### 错误收集和展示

**规则**：
- ❌ 勿逐个检查、逐个报错（低效、用户体验差）
- ✅ 收集所有验证错误后统一展示（高效、清晰）

**示例**：

```
❌ 验证失败（共3处）：
  1. [关键] 文件不存在：/path/to/prd.md
  2. [警告] 文件大小超过建议值：120KB > 50KB
  3. [警告] 文件编码为 GBK，建议转换为 UTF-8

👉 请修正后重新提供
```

### 重试机制

**规则**：
- 验证失败后，允许用户修正并重新验证（最多 3 次）
- 第 3 次失败后，提示用户放弃或联系支持

**示例**：

```
❌ 验证失败（第 2/3 次）
[上次失败的错误信息]
👉 请修正后重新提供
```

### 降级方案

**规则**：
- 某些验证失败时，提供降级方案而非直接拒绝
- 如 Feishu 链接失效 → 降级为文本输入

**示例**：

```
⚠️  Feishu 链接无法访问

📋 降级方案：请手动复制文档内容并直接粘贴
```

## 参考：验证规则与 Hard-Gate 的关系

| 验证规则 | Hard-Gate | 说明 |
|---------|----------|------|
| 本地文件/链接/文本格式验证 | 门禁1 | Step 1-2 前置条件 |
| roles.json 有效性验证 | 门禁2 | Step 3 前置条件 |
| 用户角色选择验证 | 门禁3 | Step 3 完成条件 |
| 报告结构验证 | 门禁4 | Step 6 前置条件 |

验证规则定义了**如何检查**，Hard-Gate 定义了**什么时候检查**。

# 决策表穷举

> 命中信号：`RULE_DENSE` —— 规则数 ≥3 或存在条件组合。
> 更新：criteria。

## 为什么需要表

三条规则就有 8 种输入组合，五条有 32 种。自然语言描述规则时，人只会描述**他想到的那几种组合**，剩下的在执行期由 Agent 自行猜测——而猜测不会被记录，也不会被验证。

决策表的价值不是「更严谨」，而是**它会暴露空格**。空格就是未决决策。

## 方法

### 1. 列出条件维度与取值

```markdown
| 条件 | 取值 |
|---|---|
| 用户类型 | 新 / 老 |
| 订单金额 | <100 / ≥100 |
| 是否首单 | 是 / 否 |
```

### 2. 展开组合并逐格填结果

```markdown
| 用户类型 | 金额 | 首单 | 结果 | 来源 |
|---|---|---|---|---|
| 新 | <100 | 是 | 免运费 | 用户明确说明 |
| 新 | <100 | 否 | ? | **未决** |
| 新 | ≥100 | 是 | 免运费 | 推导 |
| ... | | | | |
```

**`来源` 列是关键**。它区分三种性质完全不同的格子：

- **用户明确说明** → 事实，可直接进 criteria；
- **推导** → 从已说明规则外推，需要确认或登记为假设；
- **未决** → Frontier 候选。

不加来源列的决策表会让推导值和事实混为一体，这正是「假设未被记录」的典型形态。

### 3. 半成功状态

组合表覆盖正常输入，但**中途失败的状态需要单独一列**：

```markdown
| 场景 | 已生效部分 | 期望行为 |
|---|---|---|
| 导入 1000 条时第 500 条失败 | 前 499 条已写入 | 整批回滚 / 保留并报告 / 断点续传 |
| 批量改名中途中断 | 部分文件已改 | ... |
```

这一列几乎总是暴露未决决策。它也直接决定 `PARTIAL` 与 `BLOCKED` 的分界：已交付部分**自身可用**才是 PARTIAL，半改坏是 BLOCKED + 回滚。

### 4. 正例 / 反例配对

对每条规则给出一个应通过和一个应拒绝的例子：

```markdown
| 规则 | 正例 | 反例 |
|---|---|---|
| <规则> | <应通过> | <应拒绝，及为什么> |
```

反例是规则边界的定义。只有正例的规则，边界由实现者随手决定。

## 输出到 criteria

每个非空格子成为判据的一部分，但**不是每格一条判据**——那会产生几十条冗余判据。正确做法：

```text
规则表本身作为一个 ARTIFACT_PROPERTY 或 BEHAVIOR 判据的验证依据
判据文本：「对 <表> 中全部 N 种组合，实际行为与表一致」
required_rung: E3（对读回结果做机械检验）
evidence: 覆盖全部组合的检验结果
```

这样判据数量可控，同时验证覆盖面明确。注意判据必须说明**组合数 N**，否则「与表一致」可以靠只测两种组合蒙过。

## 收敛信号

决策表可以停止扩展，当：

- 所有格子有来源，且「未决」格已进入 Frontier 或登记为假设；
- 新增维度不改变任何已填结果（该维度与本目标无关）；
- 剩余组合在现实中不可能出现（**显式记录为不可能，而非留空**）。

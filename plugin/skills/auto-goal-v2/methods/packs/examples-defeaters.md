# 承重假设与 Defeater

> 命中信号：`LOAD_BEARING_ASSUMPTION`。
> 更新：assumption status。

## 假设不是问题，未记录的假设才是

不可能把所有槽位都问清楚。假设很便宜——**没有 defeat 条件的假设**才是事故源：它无法被证伪，因此永远不会被发现是错的。

```text
坏：假设用户量不大
好：假设并发峰值 <100 QPS —— defeat 条件：监控出现 429 或 P99 >1s
```

右侧可以被现实推翻，左侧只能在事故后被追认。

## 登记格式

```markdown
| 假设 | 承重程度 | defeat 条件 | 状态 |
|---|---|---|---|
| <假设内容> | 高/中/低 | <什么现象出现说明它不成立> | 未验证/已验证/已被推翻 |
```

**承重程度** = 它错了会推翻多少已做工作。高承重假设应优先验证或转为 Frontier 问题。

## Steel-man → Attack

对承重假设做两步，顺序不可交换：

### 1. Steel-man：把它建成最强形态

```markdown
这个假设最有可能成立的理由是：<最强论证>
支持它的证据：<有什么>
```

先建强再攻，避免打稻草人。直接攻击一个弱化版本，得到的「已经考虑过风险」是虚假的。

### 2. Attack：找它失效的具体场景

```markdown
它会在什么情况下失效？<具体场景，不是"可能有意外">
失效的早期信号是什么？→ 这就是 defeat 条件
失效后代价多大？→ 这决定承重程度
```

Attack 的产物**就是 defeat 条件**。写不出具体失效场景，说明还没真正检验这个假设。

## Defeater 的三种结局

| 结局 | 处理 |
|---|---|
| 找到可查证的失效场景 | 派 discovery worker 查证（不问用户） |
| 找到只有 principal 知道的失效条件 | 进入 Frontier |
| 找不到具体失效场景 | 假设保留，记录已做过 attack |

第三种也是有效结果：它把「没想过」变成「想过且没找到反例」，这两者在事后复盘时性质完全不同。

## 假设被推翻时

```text
ASSUMPTION_DEFEATED 事件 → 重新评估依赖它的判据与计划
```

若当前计划因此失效：

- 已能确定合法替代计划 → 回 `PLANNING`，**不是** BLOCKED；
- 无替代计划 → `BLOCKED(reason=PLAN_CHANGE_REQUIRED)`。

误用 BLOCKED 是常见错误：假设被推翻本身不构成阻塞，只有「没有任何可行替代」才构成。

## 为什么必须主动找反证

模型倾向给出貌似可行的计划，而不是承认做不到——在不可解问题上，有实测显示 54% 的情况会给出自信但错误的计划，只有 27% 被正确判定为不可解。

这意味着：**「我没发现问题」几乎不携带信息**。只有主动 attack 之后仍未发现问题，才略微提高置信度。复杂度是负债，未经检验的假设是隐藏负债。

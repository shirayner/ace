# 判定型取样

> 命中信号：`JUDGMENT_CRITERION` —— 存在 `JUDGMENT` 或 `KNOWLEDGE` 判据。
> 更新：evidence contract。

## 核心问题

判定型判据的判定权**不在 Agent**。这不是能力问题而是权限问题：即使 Agent 的判断恰好正确，它也没有资格宣布「这封信足够动人」。

由此产生两种失效：

1. **自造 rubric 自评**——编一套评分标准给自己打分，报 DONE。调研与写作类目标的头号病。
2. **整篇做完再问**——耗尽预算产出一个方向就错的成品。

第一种是权限越界，第二种是流程浪费。取样同时解决两者。

## 方法：尽早取样

```text
1. 识别判定维度（风格？深度？立场？格式？）
2. 产出最小样本（一段、一个章节、一个示例，不是完整产物）
3. 交给 acceptor 取判定
4. 用判定结果校准剩余工作
5. 完整产出后仍需 acceptor 最终确认（E4）
```

**样本要小到可以被丢弃**。如果样本大到「重做太可惜」，取样就失去了意义——它会变成为已做工作寻求背书。

### 样本形式

| 目标类型 | 有效样本 | 无效样本 |
|---|---|---|
| 写一封信 | 开头两段 + 结尾 | 全文初稿 |
| 市场调研 | 一家竞品的完整分析 | 全部竞品的浅层列表 |
| 学习材料 | 一个概念的讲解 | 完整大纲 |
| 设计方案 | 一个关键界面 | 全部界面的线框 |

有效样本的判据：它展示了**风格与深度**，而不是覆盖面。覆盖面可以后补，风格错了要全部重做。

## 向 acceptor 提问的形式

不要问「这样行吗」——这会得到礼貌的「可以」。要给出可对比的选项：

```markdown
这是 <维度> 的两种处理：

A. <样本 A> —— 特点：<X>，代价：<Y>
B. <样本 B> —— 特点：<Z>，代价：<W>

我倾向 A，因为 <理由>。你觉得哪个方向对？
```

两个样本的对比会暴露 acceptor 自己也未明说的偏好。单个样本只能得到通过/不通过，得不到方向。

## 代理 rubric 的边界

**允许**：把可明文核查的属性抽出来做 `ARTIFACT_PROPERTY` 判据，由 Agent 验到 E3。

```text
「覆盖 5 家竞品且每条结论有出处」  → ARTIFACT_PROPERTY，Agent 可验 E3
「建议对决策有帮助」              → JUDGMENT，仅 acceptor 可判 E4
```

**禁止**：用 rubric 替代最终判定。V2 明确不允许通过「用户预授权的代理 rubric」把 `JUDGMENT/KNOWLEDGE` 转成 Agent 自验。rubric 验证产物属性，不验证价值。

这个边界是刻意画在这里的：产物属性可以穷举并机械检验，价值判断不能。把后者伪装成前者，就是把「我按标准做了」偷换成「它是好的」。

## acceptor 不可触达时

```text
acceptor 存在但本轮无法触达 → 终态 UNVERIFIABLE
                             不是 DONE，也不是 BLOCKED
```

交接物必须写明：已达最高等级（通常 E3 的产物属性）、为何无法更高、**谁能最终判定**。

Agent 不得自封 acceptor：`acceptor_ref` 为 `agent`、`self`、`controller`、`worker:*` 均被 `gateCriterion()` 拒绝（不变量 I9）。

## KNOWLEDGE 类的特殊性

学习类目标的判定权在**用户脑内**，Agent 连观测通路都没有：

```text
交付材料 ≠ 用户学会了
```

可行的证据形式（均需用户参与）：用户自评、用户复述、用户完成练习、用户独立应用到新场景。没有其中任一，终态是 `UNVERIFIABLE`。

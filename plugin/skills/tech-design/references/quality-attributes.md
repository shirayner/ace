# 质量属性框架

---

## 七大核心质量属性

### 1. 性能

| 维度 | 度量 | 典型目标 |
|------|------|----------|
| 延迟 | P50/P95/P99 | API: P99 < 200ms |
| 吞吐量 | RPS/TPS | 取决于业务规模 |
| 感知延迟 | 用户感知的响应时间 | < 1s 感觉即时 |

**关键洞察**：
- 感知延迟往往比实际延迟更重要（进度条、骨架屏）
- P99 比 P50 更有价值——异常值揭示系统脆弱点
- 慢比宕机更危险——慢调用缓慢消耗资源

**常见取舍**：
- 缓存 → 牺牲数据新鲜度
- 异步化 → 牺牲即时反馈
- 预计算 → 牺牲存储空间

---

### 2. 可用性

| 级别 | 年停机 | 月停机 | 适用场景 |
|------|--------|--------|----------|
| 99% | 3.65 天 | 7.3 小时 | 内部工具 |
| 99.9% | 8.76 小时 | 43 分钟 | 普通 B 端 |
| 99.95% | 4.38 小时 | 22 分钟 | 重要 B 端 |
| 99.99% | 52.6 分钟 | 4.3 分钟 | 支付/核心交易 |
| 99.999% | 5.26 分钟 | 26 秒 | 生命安全系统 |

**关键洞察**：
- 每多一个 9，成本指数级增长
- 可用性 = min(所有串行依赖的可用性)
- 依赖越多，可用性越低

**实现模式**：
- 冗余（多副本、多可用区）
- 故障转移（主备切换）
- 优雅降级（核心功能保活）

---

### 3. 可扩展性

**核心原则**：
- 无状态系统扩展好；有状态系统扩展差
- 垂直扩展有上限；水平扩展有复杂度
- 扩展策略取决于瓶颈类型（计算/存储/网络）

**扩展模式**：

| 模式 | 适用场景 | 代价 |
|------|----------|------|
| 垂直扩展 | 初期、热点明确 | 有硬上限 |
| 水平扩展（无状态） | Web/API 层 | 需要负载均衡 |
| 分片 | 数据层 | 跨片查询复杂 |
| 读写分离 | 读多写少 | 一致性延迟 |
| CQRS | 读写模型差异大 | 复杂度翻倍 |

---

### 4. 一致性

**一致性光谱（非二元选择）**：

```
强一致性 ←→ 线性化 → 顺序一致 → 因果一致 → 最终一致 ←→ 无保证
```

**判断标准**：这份数据值得什么级别的一致性？

| 数据类型 | 推荐一致性 | 理由 |
|----------|-----------|------|
| 账户余额 | 强一致 | 错误直接导致资金问题 |
| 订单状态 | 强一致 | 影响用户决策 |
| 浏览计数 | 最终一致 | 短暂不准确可接受 |
| 缓存内容 | 最终一致 | TTL 过期即可 |
| 搜索索引 | 最终一致 | 秒级延迟可接受 |

---

### 5. 安全性

**纵深防御层次**：
1. 网络层（防火墙、VPN、WAF）
2. 应用层（认证、授权、输入校验）
3. 数据层（加密、脱敏、访问控制）
4. 审计层（日志、溯源、告警）

**关键权衡**：
- 安全 vs 性能（加密开销）
- 安全 vs 易用性（多因素认证）
- 安全 vs 开发效率（严格的代码审查）

---

### 6. 可维护性 / 可演进性

**度量维度**：
- 模块耦合度
- 变更影响范围
- 新人上手时间
- 部署频率和风险

**关键实践**：
- ADR 记录决策推理
- 清晰的模块边界
- 自动化测试覆盖
- 渐进式迁移能力

---

### 7. 成本

**成本维度**：
- 云资源（计算、存储、网络）
- 第三方服务（API 调用、SaaS）
- 人力（开发、运维）
- Token 消耗（AI 系统特有）

**关键洞察**：
- "最被忽视但往往是真正的约束"
- 成本常与性能/可用性冲突
- AI 系统成本可能随使用量线性增长（无规模效应）

---

## 冲突矩阵

不可同时最大化的属性对：

| 属性 A | 属性 B | 冲突本质 |
|--------|--------|----------|
| 一致性 | 可用性 | CAP 定理 |
| 一致性 | 性能 | 同步等待 vs 异步快速 |
| 性能 | 成本 | 更多资源 = 更好性能 = 更高成本 |
| 安全性 | 易用性 | 更多验证 = 更多摩擦 |
| 安全性 | 性能 | 加密/校验有开销 |
| 灵活性 | 简单性 | 更多扩展点 = 更多代码/配置 |
| 可用性 | 一致性 | 网络分区时只能选一个 |

## 用业务语言翻译权衡

技术权衡需要用三种货币向业务方解释：

| 货币 | 说法 |
|------|------|
| **金钱** | "选方案 A 每月多花 X 元，但避免了 Y 问题" |
| **风险** | "选方案 B 有 Z% 概率出现 W 问题，影响 N 用户" |
| **时间** | "方案 C 多花 2 周开发，但上线后运维成本降低 50%" |

**呈现方式**：
> "方案 A + 它的代价" — 而非宣布"最佳方案"

让决策者看到完整图景后自行权衡，而非替决策者决策。

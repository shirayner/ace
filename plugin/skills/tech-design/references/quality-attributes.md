# 质量属性框架

---

## 七大核心质量属性

### 1. 性能

**关键洞察**：
- 感知延迟往往比实际延迟更重要（进度条、骨架屏）
- P99 比 P50 更有价值——异常值揭示系统脆弱点
- 慢比宕机更危险——慢调用缓慢消耗资源

**常见取舍**：
- 缓存 → 牺牲数据新鲜度
- 异步化 → 牺牲即时反馈
- 预计算 → 牺牲存储空间

---

### 2. 可用性

**关键洞察**：
- 每多一个 9，成本指数级增长
- 可用性 = min(所有串行依赖的可用性)
- 依赖越多，可用性越低

**常见取舍**：
- 冗余 → 牺牲成本和一致性复杂度
- 优雅降级 → 牺牲功能完整性
- 多可用区部署 → 牺牲延迟和运维简单性

---

### 3. 可扩展性

**关键洞察**：
- 无状态系统扩展好；有状态系统扩展差
- 垂直扩展有上限；水平扩展有复杂度
- 扩展策略取决于瓶颈类型（计算/存储/网络）

**常见取舍**：
- 分片 → 牺牲跨片查询能力
- CQRS → 牺牲一致性和复杂度
- 读写分离 → 牺牲写后即读一致性

---

### 4. 一致性

**关键洞察**：
- 一致性是光谱而非二元：强一致 → 线性化 → 顺序 → 因果 → 最终 → 无保证
- 核心问题："这份数据值得什么级别的一致性？"
- 越靠近钱的数据越需要强一致，越靠近展示的数据越能容忍最终一致

**常见取舍**：
- 强一致 → 牺牲可用性和延迟
- 最终一致 → 牺牲用户体验（短暂脏读）
- 补偿事务 → 牺牲实现简洁性

---

### 5. 安全性

**关键洞察**：
- 安全是纵深防御——任何单层都可能被突破
- 最常被忽视的是审计层（没有日志 = 事后无法溯源）

**常见取舍**：
- 安全 vs 性能（加密开销）
- 安全 vs 易用性（多因素认证）
- 安全 vs 开发效率（严格的代码审查）

---

### 6. 可维护性 / 可演进性

**关键洞察**：
- 最终决定系统寿命的不是性能，而是团队能否继续理解和修改它
- ADR 记录"为什么不选 B"比记录"为什么选 A"更有价值

**常见取舍**：
- 模块化 → 牺牲短期开发速度
- 抽象层 → 牺牲直接性和调试便利
- 微服务 → 牺牲部署和运维简单性

---

### 7. 成本

**关键洞察**：
- "最被忽视但往往是真正的约束"
- 成本常与性能/可用性冲突
- AI 系统成本可能随使用量线性增长（无规模效应）

**常见取舍**：
- 省钱 → 牺牲性能或可用性
- 自建 → 牺牲人力和时间
- 用更便宜的小模型 → 牺牲输出质量

---

## 冲突矩阵

不可同时最大化的属性对：

| 属性 A | 属性 B | 冲突本质 |
|--------|--------|----------|
| 一致性 | 可用性 | CAP 定理 |
| 一致性 | 性能 | 同步等待 vs 异步快速 |
| 性能 | 成本 | 更多资源 = 更好性能 = 更高成本 |
| 安全性 | 易用性 | 更多验证 = 更多摩擦 |
| 安全性 | 性能 | 加密/校验有开销 |
| 灵活性 | 简单性 | 更多扩展点 = 更多代码/配置 |
| 可用性 | 一致性 | 网络分区时只能选一个 |

## 用业务语言翻译权衡

技术权衡需要用三种货币向业务方解释：

| 货币 | 说法 |
|------|------|
| **金钱** | "选方案 A 每月多花 X 元，但避免了 Y 问题" |
| **风险** | "选方案 B 有 Z% 概率出现 W 问题，影响 N 用户" |
| **时间** | "方案 C 多花 2 周开发，但上线后运维成本降低 50%" |

**呈现方式**：
> "方案 A + 它的代价" — 而非宣布"最佳方案"

让决策者看到完整图景后自行权衡，而非替决策者决策。

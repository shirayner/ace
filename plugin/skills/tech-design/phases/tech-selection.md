# 技术选型 — 决策分析流程

面对具体技术选择时的结构化决策框架。

---

## 选型流程

```
明确决策点 → 约束收集 → 候选方案 → 多维评估 → 决策记录
```

---

## Step 1：明确决策点

**提问**：
- 具体要决定什么？（存储、框架、中间件、协议、模式...）
- 决策的上下文是什么？（在什么系统里、什么阶段）
- 这个决策的生命周期？（多久会被重新评估）
- 可逆性如何？（换掉的成本有多大）

---

## Step 2：约束收集

**硬约束（不可协商）**：
- 团队技术栈（已有什么能力）
- 已有基础设施（公司/部门统一的中间件）
- 合规要求（数据主权、安全认证）
- 预算上限
- 时间线

**软约束（可权衡）**：
- 性能要求
- 扩展性预期
- 运维复杂度容忍度
- 社区活跃度偏好
- 学习曲线

---

## Step 3：候选方案

**生成原则**：
- 至少 2 个，最多 4 个候选
- 包含一个"保守选择"（最熟悉/最成熟）
- 包含一个"最佳匹配"（最符合需求）
- 可选：一个"激进选择"（最新/最强但风险大）

**每个候选必须说明**：
- 一句话定位
- 核心优势
- 核心劣势/风险
- 适用场景

---

## Step 4：多维评估

### 评估矩阵

| 维度 | 权重 | 候选 A | 候选 B | 候选 C |
|------|------|--------|--------|--------|
| 功能匹配度 | | | | |
| 性能/扩展性 | | | | |
| 运维复杂度 | | | | |
| 团队熟悉度 | | | | |
| 社区/生态 | | | | |
| 成本 | | | | |
| 风险 | | | | |

**权重由用户约束决定**（不是固定的）。

### 关键差异化问题

选型的核心不是"哪个最好"，而是：
> "在你的约束下，哪个最合适？你愿意为了 A 优势付出 B 代价吗？"

### 常见陷阱

- **过度关注功能对比** → 忽略运维、团队能力、迁移成本
- **只看 benchmark** → 忽略实际场景的访问模式差异
- **追新技术** → 忽略团队学习曲线和生态成熟度
- **过度设计** → 当前规模根本不需要这个能力

---

## Step 5：决策记录

输出 ADR 格式（Read `references/adr-template.md`）：

```markdown
## ADR-XXX: [选型标题]

- **状态**: Adopted
- **背景**: [为什么需要做这个选型]
- **约束**: [硬约束列表]
- **候选项**:
  - A: [描述] — 优点... 代价...
  - B: [描述] — 优点... 代价...
  - C: [描述] — 优点... 代价...
- **决定**: 选择 [X]
- **理由**: 因为 [约束/优先级]，[X] 在 [关键维度] 上最匹配
- **代价**: 放弃了 [Y 的优势]，意味着 [具体影响]
- **触发信号**: 当 [条件] 出现时，重新评估此决策
```

## 常见选型场景速查

### 存储选型

| 数据特征 | 推荐方向 | 关键考量 |
|----------|----------|----------|
| 强关系、事务 | 关系型数据库 | ACID 保证 |
| 灵活 Schema | 文档数据库 | 查询模式变化 |
| 高速读取、简单 Key | KV 存储/缓存 | 持久化需求 |
| 全文搜索 | 搜索引擎 | 实时性 vs 批量 |
| 语义相似度 | 向量数据库 | 召回率 vs 延迟 |
| 时间序列 | 时序数据库 | 聚合粒度、保留策略 |
| 大文件 | 对象存储 | 访问频率 |

### 通信模式选型

| 场景 | 推荐方向 | 关键考量 |
|------|----------|----------|
| 同步请求-响应 | HTTP/gRPC | 延迟要求、IDL 需求 |
| 异步解耦 | 消息队列 | 可靠性、顺序性 |
| 实时推送 | WebSocket/SSE | 连接数、单向/双向 |
| 事件广播 | Pub/Sub | 消费者独立性 |
| 批量处理 | 调度/流处理 | 延迟容忍度 |

### 架构模式选型

| 因素 | 倾向单体 | 倾向微服务 |
|------|----------|-----------|
| 团队规模 | < 10 人 | > 20 人多团队 |
| 部署频率 | 整体部署可接受 | 需独立部署 |
| 规模需求 | 均匀扩展 | 热点模块差异大 |
| 数据一致性 | 强事务需求 | 可接受最终一致 |
| 运维能力 | 有限 | 有平台支撑 |

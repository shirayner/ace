# 正向设计 — 七阶段流程

从模糊需求到完整技术方案的引导式设计流程。

---

## 阶段总览

```
阶段 0: 开场定位
    ↓
阶段 1: 业务本质与范围
    ↓
阶段 2: 灵魂六问（约束收窄）
    ↓
阶段 3: 信封估算
    ↓
阶段 4: 质量属性取舍
    ↓
阶段 5: 关键决策
    ↓
阶段 6: 收敛产出
    ↓
阶段 7: 挑战验证
```

支持循环回溯——发现前阶段不清则回退。

---

## 阶段 0：开场定位

**目标**：一句话锁定系统本质。

**开场问题**：
> "用一两句话告诉我：你想做的是个什么东西？它最像你心目中的哪个已有产品？"

**收敛条件**：能用一句话描述系统定位。

**产出**：一句话定位 + 最近似的已知系统类型。

**动作**：定位完成后，检查 `references/knowledge-anchors.md` 中是否有匹配模板。若有，加载其"必须追问的关键决策"作为后续阶段的引导。

---

## 阶段 1：业务本质与范围

**目标**：明确做什么、不做什么。

**逐步探索（每轮 1-2 问）**：
- 为谁解决什么问题？价值/收入从何而来？
- MVP 范围：做什么 vs **明确不做什么**
- 需求分类：功能性需求 vs 质量属性 vs 硬约束
- 现有系统上下文：有哪些已存在的系统/接口需要对接？

**做减法引导**：
> "这个不做行不行？不做会怎样？"
> "范围每砍一块，架构就简单一个量级。"

**收敛条件**：
- [ ] 核心用户和核心价值明确
- [ ] "做/不做" 清单确认
- [ ] 已知外部依赖/集成点列出

**产出**：定位 + "做/不做" 清单 + 外部依赖列表

---

## 阶段 2：灵魂六问

**目标**：用六个关键问题收窄架构解空间。

| # | 问题 | 架构影响 |
|---|------|----------|
| 1 | **规模多大？** 当前/峰值用户或数据量 | 决定何时需要扩展准备 |
| 2 | **读写比？** 读密集还是写密集 | 优化方向（读路径 vs 写路径） |
| 3 | **一致性要求？** 写完立即可读还是容忍最终一致 | 一致性 vs 性能/可用性取舍 |
| 4 | **增长预期？** 年增长轨迹——渐进还是爆发 | 是否需要预留扩展能力 |
| 5 | **失败代价？** 宕机/数据丢失/计费错误的后果 | 可靠性/可用性/审计投入 |
| 6 | **约束条件？** 团队规模、时间线、预算、合规、现有系统 | 排除不可行方案 |

**交互策略**：
- 不要一次甩出全部六问
- 根据前面的回答决定哪些问题需要深挖
- 用户不确定时提供锚点数字帮助估算

**收敛条件**：六问全部有答案（哪怕是"不确定，假设为X"）。

**产出**：六问答案 + 约束收窄后的候选空间描述

---

## 阶段 3：信封估算

**目标**：用数量级数字锚定设计边界。

**核心公式**：
```
写 QPS ≈ 日写入量 ÷ 100,000（86400 ≈ 10^5）
读 QPS = 读写比 × 写 QPS
峰值 ≈ 均值 × 3（或特定业务的峰谷比）
年存储 ≈ 单条记录大小 × 日增长 × 365
带宽 = 请求大小 × QPS
```

**AI/LLM 系统额外估算维度**：
- 每请求 Token 数 × 并发 → 推理成本
- 上下文窗口 × 请求数 → KV Cache 内存
- 流式首 Token 延迟 vs 完整响应延迟
- Agent 工具调用步数 × 循环上限

**判断**：估算完成后回答——
> "什么最先杀死这个系统？"（读、写、存储、带宽、GPU、成本、还是人工审核？）

**收敛条件**：
- [ ] 关键路径的 QPS/存储有数量级数字
- [ ] 瓶颈方向初步识别

**产出**：估算数字表 + "第一瓶颈"判断

---

## 阶段 4：质量属性取舍

**目标**：显式暴露质量属性冲突，让用户做优先级排序。

**逐项过清单**（Read `references/quality-attributes.md` 获取详细框架）：
> "对你这个系统，[属性X] 重要吗？目标是多少？"

**核心属性**：
性能 / 可用性 / 持久性 / 可扩展性 / 一致性 / 安全性 / 成本 / 可维护性 / 可观测性 / 可演进性

**关键动作**：
1. 识别冲突对（如：一致性 vs 可用性，性能 vs 成本）
2. 让用户排优先级——"不可能全要"
3. 用业务语言翻译权衡：**金钱、风险、时间**

**收敛条件**：
- [ ] Top 3 优先质量属性确认
- [ ] 已知冲突的取舍方向明确

**产出**：质量属性表（属性 | 目标 | 重要性理由 | 可接受的取舍）

---

## 阶段 5：关键决策

**目标**：在架构岔路口做出显式选择并记录推理。

**对话模板**：
> "这里有个岔路口：**选项 A**（优点...，代价...）vs **选项 B**（优点...，代价...）。
> 结合你前面说的〔某约束〕，你倾向哪个？为什么？"

**通用决策维度**：
- 存储选型（按访问模式）
- 同步 vs 异步
- 单体 vs 拆分
- 缓存策略
- 状态放置（客户端/服务端/外部）
- 扩展方式（垂直/水平）
- 数据一致性模型
- 错误处理策略

**每个决策必须记录**：
```
决策：选了 X
放弃：Y
原因：因为约束 Z
代价：W
触发信号：当 [条件] 出现时重新评估
```

**收敛条件**：所有关键岔路口都有决策 + 推理。

**产出**：决策列表（ADR 格式）

---

## 阶段 6：收敛产出

**目标**：将前面所有阶段的产出整合为结构化文档。

**根据复杂度选择模板**：
- 完整系统设计 → `references/full-design-template.md`
- 单功能/小模块 → `references/light-design-template.md`

**核心产出物**：
1. 一句话定位 + 核心需求与约束表
2. 架构全景图（Mermaid）— Context → Container
3. 关键数据流 — 1-2 个主航道场景，步骤编号
4. 数据模型与存储选型表
5. ADR 决策记录
6. 规模化与瓶颈分析
7. 演进路线 — MVP → 成长期 → 成熟期
8. 风险与未决问题

**制图规则**：
- 单张图一个抽象层级
- 用 Mermaid graph/sequenceDiagram/classDiagram
- 箭头标方向与含义
- Component 仅在"灵魂部件"需深挖时绘制

**产出**：完整技术方案文档

---

## 阶段 7：挑战验证

**目标**：主动质疑自己的设计，暴露盲点。

**五大挑战维度**：

### 1. 一致性/幂等
- 重复写入会怎样？
- 重试是否安全？
- 是否存在重复扣费风险？
- 不确定状态如何处理？

### 2. 韧性
- 依赖方故障时如何降级？
- 超时设置是否合理？
- 是否有熔断机制？
- 错误预算如何分配？

### 3. 热点/规模
- 扇出爆炸点在哪？
- P99 尾部延迟可接受吗？
- 队列积压时如何处理？
- 存在单点瓶颈吗？

### 4. 安全/多租户
- 权限边界是否清晰？
- 是否存在越权路径？
- 数据隔离是否完整？
- 审计日志是否充分？

### 5. AI 专项（仅 AI 系统适用）
- 模型幻觉如何防护？
- Prompt 注入如何防御？
- 成本是否有硬上限？
- 质量退化如何检测？

### 6. 演进
- 哪些假设失效最致命？
- 什么信号触发架构升级？
- 最难迁移的决策是哪个？

**挑战完成后**：
- 将发现的问题补充到方案的"风险与未决问题"中
- 对严重问题回溯修改方案

**收敛条件**：所有维度过一遍，新发现的风险已记录或已修复。

**产出**：更新后的方案 + 挑战验证通过的确认

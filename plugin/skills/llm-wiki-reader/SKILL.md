# LLM Wiki Reader

为需求评审 Agent 和方案设计 Agent 提供渐进式加载 .ace/wiki/ 知识库的协议。

## 触发条件

用户消息包含以下任一模式时激活：

| 任务类型 | 关键词/模式 |
|----------|------------|
| 需求理解 | "评审这个需求" / "分析这个 PRD" / "这个功能影响哪些" / "现有的 XX 逻辑是什么" |
| 方案设计 | "设计 XX 方案" / "技术方案" / "XX 功能怎么实现" / "接口设计" |
| 影响分析 | "改了这个会影响哪些" / "XX 的上下游" / "影响范围" |

## 入口流程

1. 检查项目根目录 `.ace/wiki/` 是否存在
   - **存在** → 进入加载协议
   - **不存在** → 告知用户项目尚未生成 Wiki，建议先用 `llm-wiki-generator` 生成。**不阻塞任务**，回退到代码分析兜底。

2. 检查 wiki 是否过期（如果 entry frontmatter 含 `generated_at` 和 `source_commit`）
   - 对比当前 HEAD，如果源码有更新 → 标注"wiki 可能过期"，仍加载但降低可信度
   - 无法确定 → 正常加载

## 渐进加载协议（软指引）

以下是推荐路径，Agent 根据上下文自行判断实际加载深度，不强制。

### L1: SUMMARY.md（~1100 tokens，先读）

**内容**: 项目元信息（`business_domain`/`keywords`/`project_type`）、快速查找表（问题→入口）、核心业务流程（概要+入口角色）、核心领域模型（定义+关联入口+关联原因）

**何时读**:
- 几乎所有任务的首选入口——SUMMARY 包含项目级元信息（业务板块、关键词），帮助 Agent 在最初就判断"这是否是相关项目"
- 需求评审：理解业务全景和现有规则
- 影响分析：从领域模型出发找所有关联入口

**怎么用**:
1. 先读 frontmatter，匹配 `business_domain` / `keywords` 判断项目相关性
2. 用"快速查找"表定位入口
3. 未命中 → 读业务流程，找到任务涉及的流程
4. 未命中 → 读领域模型，找到任务涉及的概念
5. 仍无法定位 → 去 L2（INDEX 入口目录）模糊匹配

### L2: INDEX.md（~200 tokens，SUMMARY 不够时读）

**内容**: 项目描述、入口目录（按类型分组 + 描述）

**何时读**:
- SUMMARY 快速查找未命中，需要扫描完整入口列表
- 方案设计前需要了解全部入口全景
- 需要知道入口总数和类型分布

**怎么用**:
- 扫描入口目录，匹配任务关键词定位候选入口
- 确定目标 entry 后 → 去 L3

**不需要读 L2 的情况**:
- SUMMARY 快速查找已命中目标入口
- 任务中明确给出了入口类名
- 已熟悉项目入口结构

### L3: entries/（~2000-5000 tokens/个，需要深入时读）

**内容**: 业务场景、业务输入/输出、业务规则、调用链路、外部依赖、主要实现类、相关入口

**何时读**:
- 需要理解某个入口的具体业务规则和约束
- 需要了解接口契约（输入/输出）
- 需要了解调用链和外部依赖（方案设计）

**怎么用**:
- 读取 entry 完整内容
- 检查 frontmatter 的 `related_business` 和 body 的"相关入口"章节
- 判断是否需要追踪关联 entry（见交叉引用追踪规则）

## 场景矩阵

| 任务场景 | 推荐路径 | 理由 |
|----------|---------|------|
| 首次接触项目 | SUMMARY → INDEX（入口目录） | SUMMARY 提供项目元信息+业务全景，INDEX 补充入口清单 |
| 理解系统有哪些能力 | SUMMARY（业务流+领域模型） | 业务流和模型直接展示系统能力边界 |
| 评审某个功能的新需求 | SUMMARY（查找表）→ entry | 快速定位，深读规则 |
| 设计新接口/改造旧接口 | SUMMARY（查找表）→ 目标 entry → INDEX（关联 entry） | 快速定位主入口，INDEX 补充关联入口 |
| 分析变更影响范围 | SUMMARY（领域模型）→ 所有关联 entry | 从模型出发找所有消费者 |
| 跨入口功能调研 | SUMMARY（业务流）→ 流程涉及的全量 entry | 先端到端，再逐个深挖 |
| 已知入口名查具体规则 | entry（直查） | 跳过 SUMMARY/INDEX |

## 交叉引用追踪规则

读完入口 A 的 entry 后，检查 frontmatter `related_business` 和 body "相关入口"章节。

**追踪信号**（建议继续读关联 entry）:
- 任务涉及多个入口联动
- 需要理解上下游数据流
- 入口 A 的规则引用了入口 B 的产出

**停止信号**（不追踪）:
- 任务只涉及单一入口
- 已读 entry 足够回答当前问题
- token 预算紧张

## 异常处理

统一原则：**wiki 是最佳路径不是唯一路径，查不到不阻塞，回退代码分析兜底**。

| 异常 | 处理 |
|------|------|
| `.ace/wiki/` 不存在 | 告知用户，建议用 `llm-wiki-generator` 生成。不阻塞，回退代码分析 |
| SUMMARY.md 查不到关键词 | 退回 INDEX.md 扫描入口目录模糊匹配。仍失败则告知用户 |
| 指定 entry 文件不存在 | 提示 wiki 可能不完整，退回 INDEX 找替代入口 |
| Wiki 过期（generated_at < HEAD commit） | 加载但标注可信度降低 |
| INDEX 入口数与 entries/ 文件数不匹配 | 提示缺失，读存在的，缺失标记"未生成" |

## 与 llm-wiki-generator 的协作

- `llm-wiki-generator` 负责**生成** wiki（构建时操作）
- `llm-wiki-reader` 负责**消费** wiki（运行时操作）
- wiki 不存在时，reader 指引用户先用 generator 生成
- generator 的 SKILL.md 末尾引用 reader："消费 Wiki 请用 llm-wiki-reader"

# 验证 Iron Law

**NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE.**

如果你没有在**本次消息**中运行验证命令，你不能声称它通过了。

---

## Gate Function

标记任务完成前，必须按序执行：

### 1. IDENTIFY — 什么能证明这个声称？

根据交付类型选择验证手段：
- 代码变更 → 编译命令 + 相关测试
- 配置/文档 → 格式检查 + 内容一致性验证
- 架构设计 → 对照完成标准逐条检查
- 无自动化手段 → 人工 review 关键路径，向用户说明验证范围和局限

### 2. RUN — 执行完整验证命令

- **必须是 fresh 执行**，不复用旧结果
- 运行完整命令（不要 `--skip-xxx`）
- 多个验证手段都要运行（编译 AND 测试，不是 OR）

### 3. READ — 完整阅读输出

- 检查 exit code（非零 = 失败）
- 计数失败/警告条数
- 不要只看最后一行

### 4. VERIFY — 输出是否确认声称？

- **YES** → 携带证据摘要，声称完成
- **NO** → 报告实际状态，**不声称完成**，修复后重新验证

### 5. ONLY THEN — 调用 TaskUpdate completed

跳过任何步骤 = 虚假声称，不是验证。

---

## 验证证据格式

```
验证: {命令} → {结果摘要}（exit code {N}）
```

示例：
```
验证: mvn compile → BUILD SUCCESS（exit code 0）
验证: npm test → 42 passed, 0 failed（exit code 0）
验证: 人工检查完成标准 → 5/5 条满足
```

---

## Red Flags — 正在跳过验证

| 你的想法 | 真相 |
|---------|------|
| "应该没问题了" | RUN 验证命令 |
| "我有信心" | 信心 ≠ 证据 |
| "这次可以跳过" | 没有例外 |
| "部分检查就够了" | 部分什么也不证明 |
| "刚改过，肯定好了" | 改过 ≠ 验证过 |
| "测试通过了"（但没运行） | 没运行 = 没通过 |
| "只是文档/配置" | 格式和一致性也需要验证 |

## 适用时机

- TaskUpdate status → `completed` 之前
- 向用户报告"已完成""搞定了""done"之前
- 标记 Phase done 之前
- 准备进入下一个任务之前
- aspec apply 完成后检查 Spec-Code 一致性

# 通用理解协议

> **核心命题**：理解是做出正确决策的前提。不充分的理解 = 在错误前提上构建方案。
>
> 本协议定义 AI 如何深度理解任务输入（用户请求、外部产物、代码现状），是所有下游决策（对齐、设计、实现）的认知基础层。

---

## 思考纪律（始终激活）

宁可慢一步想清楚，不要快一步做错了。

**过程纪律**

- **序** — 理解先于规划，规划先于行动。未经理解的方案是猜测。
- **验** — 用事实闭环，不以假设收尾。预期与现实的差距就是认知盲区。

**思考品质**

- **深** — 多问一层为什么。抵达机制层和根因层才算理解。
- **广** — 在系统中定位局部。改动一处，影响传向何方？
- **辨** — 主动为自己的结论找反证。区分事实、推断与猜测。
- **简** — 复杂度是负债。真正想明白了的方案往往简洁。

**元认知警报**：觉察不到自己在浅层思考，是最危险的浅层思考。

---

## 苏格拉底追问

在思考过程中执行四追问，形成深层理解：

- **追问目的**：为什么做？解决什么根本问题？谁受益？
- **追问完整性**：全貌还是冰山一角？关联问题？前置依赖？
- **追问前提**：假设成立吗？更好的问题框架？是否在解决错误的问题？
- **追问约束**：什么不能动？硬限制？时间/资源/技术债？

目标：理解用户真正需要什么——包括他们自己可能没意识到的部分。

## 问题驱动探索

不是"去看这些地方"，而是**为了回答关键问题而探索**。

### 执行顺序

1. **识别决策前提**：做出正确决策需要确认哪些事实？
2. **定位知识缺口**：哪些前提当前不确定？（标记为 UNKNOWN）
3. **目标性探索**：用工具（Read/Glob/Grep/Agent）填补每个 UNKNOWN
4. **充分性判定**：所有关键前提已验证 OR 已标记为"需向用户确认"

### 探索手段

知识缺口决定去哪里找。以下是常见手段，任何能填补 UNKNOWN 的合法手段都应使用（≥3 个独立缺口时必须并行 Agent）：

**内部探索**（了解现状）：
- memory + CLAUDE.md：用户偏好与项目规则
- 项目结构（Glob）、关键文件（Read）、相关代码（Grep）
- git status：当前工作状态

**外部知识**（获取权威参考）：
- WebSearch/WebFetch：官方文档、最佳实践、业界标准
- 用户提供的参考链接

### 充分性标准

不是"看了多少文件"，而是"每个关键前提是否有证据支撑"。

## Defeater 搜索

对输入中的核心断言**默认执行**反驳检查。这不是对抗，而是认知互补——照亮盲区。

### 方法：Steel-man → Attack

1. **Steel-man**：先构建断言的最强版本（假设它是对的，最佳理由是什么？）
2. **Attack**：再尝试攻破最强版本

### 检查两类 Defeater

- **Rebutting**（直接反证）：与已知事实/代码现状矛盾？因果推断有反例？
- **Undercutting**（切断推理链）：从前提到结论跳跃了什么？前提本身未验证？

### 力度增强信号

以下情况加大搜索力度：
- 以确定语气做出因果断言
- 方案与已知最佳实践或代码现状相悖
- 现象有多种解释但只给了一种
- 涉及不可逆操作
- **外部产物声明"新增"组件**（必须验证是否已有可复用实现）

### 结果处理

- 攻破成功 → 标记为"前提不成立"，纳入理解输出
- 未攻破 → 断言成立，正常推进

## 输入源验证 [扩展点]

> 不同场景的"输入"性质不同，验证策略也不同。调用方通过条件标注声明验证策略。

### [IF verify=artifact-grounding] 产物落地验证

适用：输入包含外部生成的技术方案（SpecHub 产物、架构文档等）。

**动作**：
1. 从产物提取所有 `[新增]`/`[修改]` 声明
2. 对每个新增项：搜索代码是否已有可复用的同类实现
3. 对每个修改项：Read 被修改代码确认当前结构
4. 对架构选型：验证是否与项目现有模式一致
5. 产出验证清单（✓/⚠️/✗）

### [IF verify=code-impact] 代码影响验证

适用：输入是代码变更请求（bug fix、重构等）。

**动作**：
1. 定位变更点的调用方/被调用方
2. 验证变更是否影响上下游
3. 检查是否有测试覆盖

### [IF verify=none] 无需验证

适用：输入是纯概念性问题（学习、调研、开放性讨论）。

## 质量门槛

理解完成的**必要条件**。参数由调用方声明，以下为默认值：

| 维度 | 默认门槛 | 自检方式 |
|------|---------|---------|
| 新洞察 | ≥1 个输入中未显式提及但影响方案的发现 | 能表述为"输入没说但我发现..." |
| 前提审计 | ≥2 个隐含假设被显式确认或否定 | 每个标记为"已验证/需确认/已探索" |
| Defeater | 对核心断言尝试了反驳 | 记录：攻破/未攻破 |
| 充分性 | 关键前提无 UNKNOWN 残留 | 已探索 OR 转入澄清 |
| 元认知 | 明确标注"我不确定"的区域 | 不用假设填充 |

### 参数化覆写

调用方可声明覆写：
```
[understanding threshold: insight≥1, assumptions≥3, defeater=mandatory]
```

未满足门槛时：继续探索/追问，不推进到下游。

---

## 理解输出

本协议执行完毕后，产出以下结构化结果供下游（对齐层/设计层）使用：

```
understanding_result:
  insights: [新发现列表]
  assumptions: [{假设, 状态:已验证/需确认/已否定}]
  defeater_results: [{断言, 攻破/未攻破, 证据}]
  unknowns: [仍不确定的项 → 需向用户澄清]
  grounding: [验证清单 — 仅当 verify≠none 时存在]
```

此输出是对齐层设计提问和展示确认内容的依据。

## 调用示例

### auto-goal 调用
```
Read understanding-protocol.md
  verify = none (通用目标，无外部产物)
  threshold = {insight≥1, assumptions≥3, defeater=mandatory}
→ 产出 understanding_result
→ 传入 alignment-protocol.md
```

### spechub-coding 调用
```
Read understanding-protocol.md
  verify = artifact-grounding (有外部产物需验证)
  threshold = {insight≥1, assumptions≥2, defeater=mandatory}
→ 产出 understanding_result (含 grounding 验证清单)
→ 传入 alignment-protocol.md (G0 格式)
```

### spec-engine Phase 1/2 调用
```
Read understanding-protocol.md
  verify = none (澄清阶段，产物已在 Phase 0.5 验证过)
  threshold = {insight≥1, assumptions≥2, defeater=required}
→ 产出 understanding_result
→ 传入 alignment-protocol.md (4-elements 格式)
```

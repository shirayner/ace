# 对齐协议

在修改性操作前确保 AI 正确理解用户意图。

---

## 三步流程

### Step 1: 深度分析（内部推理，不展示给用户）

结合已有上下文 + 探索性工具（Read/Glob/Grep/Agent），在内部执行四追问：

- **追问目的**：为什么做？解决什么根本问题？谁受益？
- **追问完整性**：全貌还是冰山一角？关联问题？前置依赖？
- **追问前提**：假设成立吗？更好的问题框架？是否在解决错误的问题？
- **追问约束**：什么不能动？硬限制？时间/资源/技术债？

**输入源**（由调用方上下文决定）：
- auto-goal 场景：memory、CLAUDE.md、git status、会话历史
- aspec proposal 场景：Read `dimensions.md` 需求维度 + 盲区表
- aspec design 场景：Read `dimensions.md` 设计维度 + 盲区表 + ADR
- 通用：项目结构（Glob）、关键文件（Read）、相关代码（Grep）

**输出**：识别出的不确定性列表 + 隐含决策点（用于 Step 2 的提问设计）。

---

### Step 2: 引导性澄清

基于 Step 1 结论，设计面向用户的具体问题，调用 **AskUserQuestion** 批量澄清。

**设计原则**：
- 具体、可行动、关联用户业务场景
- 主动指出关联："我注意到 X 还涉及 Y——是否在范围内？"
- 暴露取舍："方案 A 更简单但有 X 风险，方案 B 更复杂但更全——优先级？"

**跳过条件**（必须**同时满足全部**）：
- 同一会话中已明确表达完整意图
- Step 1 未发现隐含决策点
- 不存在"用户可能惊讶"的假设
- 延续性修复（而非新目标）

**如不确定是否需要澄清 → 澄清。** 默认执行，跳过是例外。

**Terminal state = AskUserQuestion 工具调用。** 没有调用 = 此步骤未完成。

---

### Step 3: 对齐确认（不可跳过）

**先**用 markdown 展示四要素（每要素标题独占一行，内容换行后写）：

```
**我的理解**
（1-2 句核心意图 + 关联问题）

**计划方向**
（1-2 句高层策略）

**关键假设**
- 假设 1
- 假设 2

**完成标准**
- 可测试条件 1
- 可测试条件 2
```

格式禁忌：标题和内容同行（~~"我的理解 — xxx"~~）；把内容放入 AskUserQuestion（显示异常）。

**然后**在同一 response 中调用 **AskUserQuestion** 确认。

**Terminal state = AskUserQuestion 工具调用。** 写了对齐内容但没调用 = 未完成。

---

## 惊讶测试

**一句话判断**：如果用户此刻看到我的决策会惊讶 → 暂停询问。

触发条件：
- 多个可行方案且各有取舍
- 决策依赖用户偏好
- 范围超出原始目标
- 不可逆操作
- 正在填补用户未说明的部分

---

## Red Flags — 正在跳过对齐

以下想法 = 正在合理化，**立即停止当前动作**：

| 你的想法 | 真相 |
|---------|------|
| "这个任务很简单" | 简单 = 隐含决策被忽略，恰恰最需要对齐 |
| "用户已经说清楚了" | 说清楚 ≠ 你理解 100% 正确 |
| "auto mode 要求立即执行" | auto mode 不覆盖对齐门禁 |
| "先探索再对齐" | 对齐在任何操作之前 |
| "对齐会让用户等太久" | 做错让用户等更久 |
| "上一轮已经对齐过了" | 新目标 = 新对齐 |
| "读文件就知道怎么做" | 读文件是探索，不是对齐 |
| "先出初版再迭代" | 先对齐再出初版 |
| "这只是延续性修复" | 延续性需同时满足全部跳过条件 |
| "我理解用户要什么" | 理解 ≠ 验证，调用 AskUserQuestion 确认 |
| "我已经写了对齐内容" | 写了 ≠ 调用了工具，缺工具调用无效 |

**如果正在想上述任何一条 → 回到 Step 1。**

**违反形式 = 违反精神。** 对齐的形式（AskUserQuestion 工具调用）就是对齐的实质。

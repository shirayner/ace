# ACE 解决的问题

深入分析 AI 辅助开发中的痛点，以及 ACE 的解决方案

---

## 问题一：AI 输出质量不稳定

### 症状

```
同样的提示词，今天生成的代码很优雅，明天就很糟糕
复杂任务做到一半就偏离方向
代码风格不一致，需要反复调整
```

### 根因分析

| 层面 | 问题 |
|------|------|
| **上下文** | Claude 没有记住你的编码偏好 |
| **约束** | 缺乏明确的质量标准和检查点 |
| **深度** | 简单任务直接响应，复杂任务缺乏分析框架 |

### ACE 解决

**1. 记忆系统**
```markdown
~/.claude/memory/user_profile.md
---
- 主要语言：Java
- 框架：Spring Boot
- 代码风格：显式优于隐式，强调可读性
- 测试要求：单元测试覆盖率 >= 80%
```

每次对话自动加载，Claude 了解你的背景。

**2. 质量规则**
```markdown
# clean-code.md 强制要求：
- 单一职责：函数 < 30 行
- 意图清晰：命名即文档
- 显性错误：不吞异常
```

代码生成时自动应用这些约束。

**3. 复杂度适配**
```
简单任务 → 快速响应
复杂任务 → OODA 循环分析
  - 观察：理解需求
  - 定向：评估方案
  - 决策：选择策略
  - 行动：执行并验证
```

## 问题二：复杂任务难以驾驭

### 症状

```
"帮我重构这个模块" → 改了 20 个文件 → 编译失败 → 不知道怎么回退
需求理解有偏差，做到一半才发现方向错了
任务中断后，重新进入上下文很困难
```

### 根因分析

1. **缺乏规划**：直接动手，边做边想
2. **缺少验证**：大量修改后统一检查，错误累积
3. **上下文丢失**：任务状态只在对话中，中断了就丢失

### ACE 解决

**1. Plan Mode（规划优先）**
```
用户：重构用户模块
Claude：进入 Plan Mode
  ├─ 探索：分析当前代码结构
  ├─ 规划：提出重构方案
  ├─ 确认：用户审查方案
  └─ 执行：按规划逐步实施
```

**2. 验证内建**
```
每个变更后立即验证：
  ✓ 编译通过？
  ✓ 测试通过？
  ✓ 满足约束？
失败即停止，防止错误扩散
```

**3. 状态外化**
```
.tasks/auto-goal-{id}/
├── state.md         # 当前进度
├── decisions.md     # 关键决策
└── reflections.md   # 经验教训
```

任务状态写入文件，随时可恢复。

## 问题三：安全风险

### 症状

```
Claude 执行了 rm -rf /（幸亏有权限限制）
不小心提交了 .env 文件到 Git
生产环境被错误修改
```

### 根因分析

- AI 没有危险感知
- 缺乏操作确认机制
- 敏感文件保护不足

### ACE 解决

**1. Hookify 守卫**

| 守卫 | 功能 | 示例 |
|------|------|------|
| block-dangerous-ops | 拦截危险命令 | rm -rf, git push --force |
| protect-secrets | 保护敏感文件 | 编辑 .env 时警告 |
| require-verification | 要求验证 | 提交前编译+测试 |

**2. 分级确认策略**
```
低风险操作 → 直接执行
中风险操作 → 执行后简报
高风险操作 → 执行前确认
不可逆操作 → 多重确认
```

## 问题四：需求管理混乱

### 症状

```
需求在对话中口头描述，后来忘记了
设计决策没有记录，新成员不了解背景
代码和需求对不上，找不到原始文档
```

### 根因分析

- 需求分散在对话中
- 决策过程不可追溯
- 缺乏结构化存储

### ACE 解决

**OpenSpec 规范驱动**

```
openspec/
├── taxonomy/        # 问题分类学
│   ├── requirement-issue-taxonomy.md   # 需求问题分类学
│   └── design-issue-taxonomy.md        # 技术设计问题分类学
├── issues/          # 问题跟踪
│   ├── requirements/# 需求文档
│   └── designs/     # 设计文档
├── procedures/      # 流程规范
└── evolution/       # 演进记录
    ├── adr/         # 架构决策
    └── glossary.md  # 术语表
```

**需求-代码可追溯**
```
需求文档 → 设计决策 → 代码实现
     ↑                    ↓
     └────── 变更影响 ────┘
```

## 问题五：团队协作困难

### 症状

```
每个人用不同的提示词风格
代码审查标准不一致
新来的成员不知道怎么用 Claude
```

### 根因分析

- 缺乏统一的 AI 使用规范
- 最佳实践没有沉淀
- 个人偏好差异大

### ACE 解决

**1. 统一规则**
```
~/.claude/rules/ace/     # 团队共享规则
├── thinking.md          # 统一思考方式
├── clean-code.md        # 统一代码标准
└── code-quality.md      # 统一质量要求
```

**2. 角色模板**
```
Backend Developer 画像
- 统一技术栈
- 统一工具链
- 统一编码风格
```

**3. 知识沉淀**
```
好的提示词 → 提炼为 Skill
常见任务 → 标准化流程
经验教训 → 写入 Rules
```

---

## 汇总：ACE 的解决矩阵

| 问题 | ACE 组件 | 原理 |
|------|---------|------|
| 质量不稳定 | Rules + Memory | 约束 + 上下文 |
| 复杂任务难驾驭 | auto-goal skill | OODA + 状态外化 |
| 安全风险 | Hookify + Hooks | 多层防护 |
| 需求管理混乱 | Spec 工作流 | 结构化存储 |
| 团队协作困难 | 统一规则 + 角色 | 标准化 |

# aspec 深度优化分析：从补偿型脚手架到共生型增强

> 分析日期: 2026-04-23
> 分析主题: aspec (ace-spec) v5.0.3 全面优化空间分析
> 分析方法: 多学科理论驱动 + "去掉它会怎样"反向论证
> 硬约束: 寄生模式不可破坏——只增强 OpenSpec，不修改其 schema

---

## 1. 诊断总论：存在理由审查

### 1.1 核心问题

aspec v5 的设计诞生于一个关键洞察：**跳过澄清 = AI 基于假设实施 = 大概率返工**。这在 2024-2025 年的弱模型时代完全正确。但进入 2026 年 frontier model 时代，必须追问一个更根本的问题：

> **aspec 的每一个组件，是在帮助模型做它做不到的事，还是在替代模型做它已经能做好的事？**

这不是否定 aspec 的价值——而是将其从"补偿型脚手架"进化为"共生型增强"。补偿型脚手架在模型变强时成为负债；共生型增强随模型变强而释放更大价值。

### 1.2 审查标准："去掉它会怎样"测试

对 aspec 的每个组件执行以下测试：

```
┌─────────────────────────────────────────────────────────┐
│              "去掉它会怎样"决策树                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  去掉这个组件后，frontier model 会...                   │
│                                                         │
│  ├─ 一致性地犯同类错误？ → 保留（真防护栏）             │
│  │                                                      │
│  ├─ 偶尔犯错但能自行修正？ → 简化为验证点（闭环）       │
│  │                                                      │
│  ├─ 基本不犯错？ → 删除（过时的补偿）                   │
│  │                                                      │
│  └─ 表现反而更好？ → 立即删除（活跃的负债）             │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 1.3 成本模型：每个 token 的机会成本

aspec v5 的 token 预算消耗估算：

| 组件类别 | 文件数 | 估算 Token 数 | 加载时机 |
|----------|--------|--------------|----------|
| config.yaml (context + rules) | 1 | ~2,500 | 始终（注入 OpenSpec 工作流） |
| 问题分类学 (taxonomy) | 2 | ~4,000 | 每次澄清流程 |
| 问题清单模板 (issues) | 3 | ~5,500 | 每次澄清创建实例 |
| 流程规范 (procedures) | 4 | ~3,000 | 每次澄清执行 |
| 知识进化模板 (evolution) | 3 | ~1,200 | 每次 archive |
| 复盘模板 | 1 | ~1,000 | 每次 archive |
| **总计** | **14** | **~17,200** | — |

关键洞察：**这 17,200 tokens 中，多少在传递模型不知道的信息（知识），多少在告诉模型它已经知道怎么做的事（过程）？**

研究表明（2025 EMNLP）：原始输入长度本身就会降低 LLM 推理能力，即使所有相关信息都可获取。这意味着 **aspec 中每一个不直接服务于防错的 token，都在消耗模型的推理预算**。

### 1.4 分类框架

将 aspec 的 14 个文件按"知识型 vs 过程型"分类：

```
知识型（高 token 价值）               过程型（随模型增强而贬值）
────────────────────                 ────────────────────
ADR 技术决策账本                      需求澄清流程（6 步骤）
领域词汇表                            设计澄清流程（6 步骤）
风险图谱                              交互式澄清协议
问题分类学（部分）                     进化体系操作步骤
                                      问题清单模板格式
                                      复盘报告模板格式
                                      config.yaml 过程描述
```

**知识型**组件携带项目特有信息，模型无法自行推导——这是 aspec 的核心价值。
**过程型**组件告诉模型"怎么做"——这正是 frontier model 越来越不需要的。

## 2. 组件级诊断：14 个文件的逐一审查

### 2.1 config.yaml — 控制中枢

**当前状态**：151 行，承载 context（工作模式 + 门禁 + 状态机 + 知识库索引 + 进化体系描述）+ rules（5 个阶段的规则注入）。

**"去掉它会怎样"**：
- **context 中的门禁条件**：去掉后模型会跳过澄清直接出方案 → **真防护栏，保留**
- **context 中的状态机描述**：模型能理解简单状态流转 → **可极度精简**
- **context 中的知识库消费速查**：告诉模型在每个阶段读什么文件 → **保留但可压缩为 3 行索引**
- **context 中的进化体系描述**：20+ 行详细说明 → **改为指针引用，按需加载**
- **rules 中的过程指令**：逐步骤告诉模型怎么做 → **大量可精简为声明式约束**

**诊断结论**：context 部分存在大量过程性描述，可压缩 60%+。rules 部分从"步骤指令"转为"声明式约束"可压缩 50%+。

### 2.2 需求问题分类学 (requirement-issue-taxonomy.md)

**当前状态**：~180 行，6 维度 × 3 子类，每个子类含"症状"和"检查点"。

**"去掉它会怎样"**：
- Frontier model 对"功能完整性""数据一致性""边界条件"等通用维度有强原生能力
- 但对**项目特定的**检查盲区（如团队历史上反复踩坑的模式）缺乏认知
- 实测观察：模型对通用维度（1-4）的覆盖率 >90%，但对"集成与依赖""优先级与范围"（5-6）偶有遗漏

**诊断结论**：通用维度描述是"教模型它已经知道的事"。价值集中在：
1. **维度枚举本身**（提醒模型不要遗漏某个大类）— 保留但可精简为一行清单
2. **项目特有的检查盲区**（通过 Layer B 进化积累）— 这才是核心价值

### 2.3 设计问题分类学 (design-issue-taxonomy.md)

**当前状态**：~200 行，7 维度 × 3 子类，结构同上。

**诊断结论**：同 2.2。对后端开发者（用户画像），模型在架构决策、技术选型、接口设计等维度的能力极强。价值在于维度枚举而非详细检查点。

### 2.4 需求问题清单模板 (requirement-issues.md)

**当前状态**：~200 行，完整的表格结构 + 详细说明格式 + 状态流转说明 + 关联文档。

**"去掉它会怎样"**：模型会自行创建某种结构来记录问题，但格式不一致。

**诊断结论**：**格式过重**。一个 200 行的模板中，大部分是"占位符"和"格式说明"，真正的信息密度极低。模板的价值在于定义**必要字段**（ID、描述、严重度、状态、决策结果），不在于预定义每个可能的章节。

### 2.5 设计问题清单模板 (design-issues.md)

**诊断结论**：同 2.4。~200 行中信息密度 <10%。

### 2.6 实施观察笔记 (retrospective-notes.md)

**当前状态**：~30 行，4 个分类的简单模板。

**诊断结论**：轻量且有价值。**保留，微调**。

### 2.7 需求澄清流程 (requirement-clarification-flow.md)

**当前状态**：~60 行，6 个步骤的详细操作指南。

**"去掉它会怎样"**：模型不会自发地按 6 步骤执行，但模型知道如何分析需求、识别问题、提问澄清。

**诊断结论**：步骤 1-3（读分类学 → 识别功能点 → 检查维度）是模型的**原生能力**。步骤 4（创建 issues 文件）和步骤 5-6（交互澄清 + 状态更新）才是需要指导的行为。可压缩 70%。

### 2.8 设计澄清流程 (design-clarification-flow.md)

**诊断结论**：同 2.7。其中"强制用户确认"（步骤 4）是真防护栏，其余是过程指令。

### 2.9 交互式澄清协议 (interactive-clarification-protocol.md)

**当前状态**：~50 行，定义批量提问格式和回答处理规则。

**"去掉它会怎样"**：模型会逐题提问而非批量提问，降低用户体验。

**诊断结论**："批量提问"和"断点续传"是模型不会自发做的事 → **真防护栏**。但格式说明过详。可压缩 60%。

### 2.10 进化体系 (evolution-system.md)

**当前状态**：~150 行，三层架构 + 详细操作步骤 + 进化分析逻辑 + 用户交互提案格式。

**"去掉它会怎样"**：模型完全不会自发地执行知识累积和进化分析。

**诊断结论**：**这是 aspec 最独特的价值**——它做的是模型绝对不会自发做的事。但操作步骤过于冗长。核心价值是"什么时候更新什么"的映射关系（~20 行），而非"怎么更新"的详细步骤（~130 行）。

### 2.11 知识进化模板 (adr.md / glossary.md / risk-map.md)

**当前状态**：3 个文件各 ~30 行，定义格式和用途。

**诊断结论**：轻量、有效。**保留，可微调**。

### 2.12 复盘模板 (retrospective-template.md)

**当前状态**：~90 行，9 个章节的完整模板。

**"去掉它会怎样"**：模型会生成某种复盘，但可能遗漏"漏检问题"和"效率信号"等反直觉章节。

**诊断结论**：章节枚举有价值（防遗漏），但详细表头和格式说明是过程性开销。

## 3. 多学科理论框架

### 3.1 认知负荷理论 (Cognitive Load Theory — Sweller, 1988)

**核心概念**：工作记忆容量有限，认知负荷分三类：
- **内在负荷** (Intrinsic)：任务本身的复杂度——不可压缩
- **外在负荷** (Extraneous)：不良呈现方式导致的额外负荷——应消除
- **关联负荷** (Germane)：构建 schema 的有效认知投入——应最大化

**映射到 aspec**：

| 负荷类型 | aspec 中的对应 | 当前状态 |
|----------|---------------|----------|
| 内在负荷 | 需求/设计本身的不确定性 | 不可压缩，aspec 核心要处理的 |
| 外在负荷 | 模板格式、过程步骤、状态机描述 | **过重**——占 token 预算的 60%+ |
| 关联负荷 | 知识累积（ADR、术语表、风险图谱） | **不足**——被外在负荷挤压 |

**优化原则 T1**：**最小化外在负荷，最大化关联负荷**。具体而言：把 token 预算从过程描述（外在）转移到项目知识（关联）。模型的"工作记忆"（上下文窗口）是固定的——过程指令每多占一个 token，就少了一个 token 用于理解实际需求。

**认知负荷理论的"分离注意力效应"**（Split-Attention Effect）也直接适用：当模型必须同时参照分类学文件 + 过程指令 + 实际需求时，注意力在多个信息源间切换，推理效率下降。**整合信息源、减少引用跳转**是关键优化方向。

### 3.2 控制论 (Cybernetics — Wiener, 1948; Ashby, 1956)

**核心概念**：
- **开环控制**：预设指令，不根据反馈调整（如恒温器没有温度传感器）
- **闭环控制**：基于反馈调整行为（如有温度传感器的恒温器）
- **必要多样性定律** (Ashby)：控制器的多样性必须匹配被控系统的多样性

**映射到 aspec**：

aspec 当前的分类学是典型的**开环控制**——预设 6×3 / 7×3 的检查维度，静态不变，不随项目经验调整。但 aspec 同时拥有**闭环**的门禁机制（"状态不对就不让过"）和进化体系（复盘反馈）。问题在于这两个闭环的反馈速度不匹配：

```
                    反馈速度
门禁（实时闭环）    ████████████  每次 proposal 前检查
进化（慢速闭环）    ██            累积 3+ 复盘才触发
分类学（开环）      ─             从不根据反馈调整
```

分类学是系统中**唯一的开环组件**，也是 token 消耗最大的组件。

**优化原则 T2**：**让分类学从开环升级为闭环**。分类学不应是静态的预设清单，而应是由进化体系驱动的**动态知识**——初始轻量（仅维度枚举），随项目复盘积累"已知盲区"而逐渐充实。这样分类学的信息密度持续增长，而非随时间稀释。门禁保持实时闭环不变。

### 3.3 Spec Coding 理论：Spec 作为跨会话认知锚点

**核心概念**：Spec-Driven Development (SDD) 的核心洞见是——**Spec 不是文档，是持久化的共享认知**。Spec 是跨会话的状态锚点、跨上下文压缩的决策记忆、代码实现的验证基准。

SDD 解决的根本问题是 AI 编码中的**认知断裂**：
- 会话内：上下文窗口有限，长任务中前期决策被压缩丢失
- 会话间：新会话无法继承旧会话的推理和决策
- 人机间：用户的意图和 AI 的理解之间存在漂移

Spec 文件通过**外化决策**解决这三个断裂——但前提是 Spec 本身必须是**高密度、自包含、面向恢复设计**的。

**映射到 aspec**：

aspec 的 issues 文件（requirement-issues.md / design-issues.md）承担了"跨会话认知锚点"的角色，但存在三个结构性问题：

| 问题 | 表现 | 后果 |
|------|------|------|
| **Spec 产出物质量标准缺失** | aspec 定义了 issues 的格式，但对 proposal.md / design.md / tasks.md 几乎无质量约束 | 核心 Spec 产出物质量不稳定 |
| **Spec 消费路径不明** | config.yaml 有"知识库消费速查"，但没有"Spec 消费速查" | apply 阶段不清楚如何将 Spec 决策映射到代码变更 |
| **Spec 变更协议缺失** | 实施中发现需求变更只有"暂停→更新问题清单→继续" | 无法区分"小调整"与"需要 re-spec 的重大变更" |

**优化原则 T3**：**Spec 产出物是第一公民，过程工件是第二公民**。aspec 的 token 预算应优先保障 proposal / design / tasks 这些核心 Spec 的质量标准和消费路径定义，而非 issues 模板的格式完美。issues 是达成 Spec 质量的手段，不是目的本身。

### 3.4 延展心灵 (Extended Mind — Clark & Chalmers, 1998)

**核心概念**：认知过程不局限于头脑内部，外部工具（笔记本、计算器、文件系统）可以成为认知系统的一部分。判断标准：如果外部资源以一种**可靠、可信、随时可取**的方式参与认知过程，它就是心灵的延展。

**映射到 aspec**：

文件系统就是模型的延展心灵。aspec 的知识进化体系（ADR、术语表、风险图谱）完美符合 Clark & Chalmers 的判断标准：

| 标准 | aspec 知识库的表现 |
|------|-------------------|
| 可靠性 | 文件系统上的持久化存储 ✓ |
| 可信性 | 来自项目真实决策记录 ✓ |
| 随时可取 | 可在任何阶段读取 ✓ |
| 因果角色 | 影响后续决策（ADR 防止重复讨论） ✓ |

**但过程型文件不符合延展心灵的标准**——它们不携带信息，而是携带指令。一个恒温器的说明书不是恒温器的一部分。

**优化原则 T4**：**将 aspec 的重心从"指令集"转向"外化认知"**。aspec 的持久价值不在于告诉模型怎么做（说明书），而在于为模型提供它不具备的项目特有知识（延展心灵）。每次 archive 积累的知识让模型的认知能力随项目历史增长。

### 3.5 信息论 (Information Theory — Shannon, 1948)

**核心概念**：
- **信息量 = 消除的不确定性**。一条消息的信息量与其"意外程度"成正比
- **冗余** (Redundancy)：重复已知信息，不消除新的不确定性
- **信噪比** (SNR)：有效信号与噪声的比率

**映射到 aspec**：

对 frontier model 而言，aspec 中不同组件的信息量差异巨大：

| 组件 | 对模型的"意外程度" | 信息量 |
|------|-------------------|--------|
| "检查功能完整性" | 极低——模型原生就做 | ≈ 0 bits |
| "检查数据一致性策略" | 低——常规分析维度 | 低 |
| "项目 ADR：选择 Redis 而非 Memcached 因为..." | 高——项目特有决策 | 高 |
| "去年 Q3 该模块出过并发 bug" | 极高——模型无法推导 | 极高 |
| "批量提问，不逐题单独提交" | 中——反直觉行为 | 中 |

**优化原则 T5**：**最大化信噪比**。每个保留在 aspec 中的 token 都应该传递高信息量的内容。具体策略：
- 删除模型已知的通用知识（"检查边界条件""考虑异常处理"）
- 保留和强化项目特有知识（ADR、风险图谱、历史教训）
- 将反直觉行为提升为显式规则（"批量提问""强制设计确认"）

### 3.6 元认知 (Metacognition — Flavell, 1979)

**核心概念**：对自己认知过程的认知——知道自己知道什么、不知道什么、什么时候需要帮助。

**映射到 aspec**：

aspec 当前的方式是**外部驱动的元认知**——由分类学告诉模型"你应该检查这些维度"，而非让模型自己判断"我在哪些方面不确定"。

Frontier model 已具备相当的元认知能力：
- 能识别自己信息不足的领域
- 能主动请求澄清（ask_user_question 是原生工具）
- 能评估自己方案的信心水平

**优化原则 T6**：**从外部驱动转向元认知引导**。不告诉模型"检查这 18 个子类"，而是提示模型"评估你对这个需求的确信度，识别你不确定的部分"。用**自我评估**替代**检查清单**。保留分类学作为"后备"——当模型的自我评估遗漏了关键维度时，才触发维度提醒。

### 3.7 社会学：制度化与官僚化 (Weber, 1922; DiMaggio & Powell, 1983)

**核心概念**：
- **制度化** (Institutionalization)：有效实践固化为制度
- **官僚化** (Bureaucratization)：制度脱离原始目的，过程本身成为目的
- **制度同构** (Institutional Isomorphism)：组织趋于采用相同结构，不论是否适合

**映射到 aspec**：

aspec 有官僚化风险：
- 最初目的：**防止基于假设的返工**
- 官僚化表现：200 行的 issue 模板中 90% 是格式和占位符，实际信息 <10%
- 更深的症状：**过程工件（issue 格式）获得的 token 投资远超 Spec 产出物（proposal/design 质量标准）**

制度同构风险：issue 模板的格式来自人类项目管理实践（JIRA / Linear 风格），但 AI 工作流不需要相同的结构——模型不需要"表格"来组织思维。

**优化原则 T7**：**制度要服务于目的，而非自我维持**。定期评估每个流程步骤是否还在服务于"防止假设返工"的核心目的。允许约束退化——当项目知识库足够丰富时，某些提醒可以自动降级。

### 3.8 Spec Coding 理论：Spec-Code 闭环与验证基准

**核心概念**：Spec Coding 的完整闭环是 **Specify → Implement → Verify against Spec → Archive learnings**。验证（Verify）不是可选的附加步骤，而是闭环的关键一环——没有验证，Spec 退化为"写完就扔"的一次性文档。

**映射到 aspec**：

aspec 的闭环在**前半段很强，后半段缺失**：

```
Specify（强）         Implement（中）       Verify（弱）         Archive（强）
澄清门禁 ✓           遵循决策 ✓           ← 缺口 →            进化体系 ✓
问题追踪 ✓           观察笔记 △                                复盘报告 ✓
```

具体缺口：

1. **无 Spec-Code 一致性验证**：apply 阶段要求"遵循澄清决策"，但没有结构化手段验证实现是否真的符合 Spec。全靠模型自觉。
2. **无 Spec 完成标准**：门禁只检查 issues 的 status (clarified)，不检查 Spec 产出物本身的完整性——proposal 可能缺少 Capabilities 定义，design 可能遗漏已知风险区域。
3. **无 Spec 变更阈值**：实施中发现偏差时，"暂停→更新问题清单→继续"是唯一路径。缺少"偏差超过阈值则必须 re-spec"的判断机制。

**优化原则 T8**：**Spec 是验证基准，不仅是实施指南**。aspec 应在 apply 和 archive 阶段补全验证闭环：实施完成后，显式检查代码变更是否覆盖了所有 Spec 中的决策和约束。这不需要逐行对照——声明式地要求"验证 Spec-Code 一致性"即可，模型有能力自行执行。

## 4. 核心优化原则：从理论到实践的收敛

将第 3 章的 8 个理论原则收敛为 5 条可直接指导优化的元原则。

### 原则 P1：声明式约束优于过程式指令

> 告诉模型"什么是好的结果"，而非"每一步怎么做"。
> — 源自 T1 (认知负荷)、T6 (元认知)、Claude Code "Less Scaffolding"

**理论依据**：过程式指令增加外在认知负荷（T1），剥夺模型的元认知自主性（T6），且随模型能力增强而贬值。声明式约束只定义边界，模型在边界内自主推理——推理能力越强，效果越好。

**实践判据**：如果一条指令能改写为"确保 X 状态达成"的形式，就不应该写成"第一步做 A，第二步做 B，第三步做 C"的形式。

**示例变换**：

```
# Before（过程式，~60 行）
步骤 1：读取需求问题分类学
步骤 2：分析需求，识别功能点
步骤 3：按 6 个维度检查每个功能点
步骤 4：创建 spec/requirement-issues.md
步骤 5：启动交互式澄清
步骤 6：确认澄清完成，更新状态

# After（声明式，~10 行）
创建 proposal 前，必须满足：
- spec/requirement-issues.md 存在且状态为 clarified
- 所有 High 问题有明确答案
- 使用批量提问方式（非逐题）澄清
产出物参考 openspec/templates/issues/requirement-issues.md 的 schema
```

### 原则 P2：知识优于过程——token 预算分配倒置

> 将 token 预算从"告诉模型怎么做"转向"给模型它不知道的信息"。
> — 源自 T4 (延展心灵)、T5 (信噪比)

**理论依据**：模型的"怎么做"能力在持续增强（会自然贬值），但项目特有知识（ADR、风险、术语）是模型无论多强都无法自行推导的（永不贬值）。

**当前 token 分配**：

```
过程型 token（~11,500 ≈ 67%）  >>>>  知识型 token（~5,700 ≈ 33%）
```

**目标 token 分配**：

```
过程型 token（~2,500 ≈ 36%）  <<<<  知识型 token（~4,400 ≈ 64%）
```

**关键行动**：知识进化体系（evolution）是 aspec 最核心的价值——它让模型的"延展心灵"随项目历史成长。应将优化省下的 token 预算让渡给更丰富的项目知识。

### 原则 P3：Spec 产出物优先——过程为 Spec 服务

> 澄清过程是手段，高质量的 Spec 产出物才是目的。Token 预算应向 Spec 质量标准倾斜。
> — 源自 T3 (Spec 作为认知锚点)、T7 (反官僚化)

**理论依据**：aspec 当前 90% 的 token 投资在过程工件（issues 格式、澄清步骤、分类学检查点）上，而对核心 Spec 产出物（proposal / design / tasks）的质量标准几乎没有定义。这是本末倒置——issues 是达成高质量 Spec 的手段，不应获得比 Spec 本身更多的关注。

**实践方式**：

```
# aspec 应该定义的（当前缺失）
proposal 完成标准：
- 包含 Why（问题陈述）、Capabilities（功能定义）、Impact（影响评估）
- Capabilities 中每个功能点有唯一 ID，与 requirement-issues 可追溯

design 完成标准：
- 每个技术决策包含四要素
- 已知风险区域（来自 risk-map）已标注应对策略
- 与 design-issues 中所有 High 决策一致

tasks 完成标准：
- 每个任务可追溯到 design 中的具体决策
- 任务粒度支持原子验证
```

**关键洞察**：aspec 定义了 200 行的 issue 模板格式，但对 proposal / design / tasks 的质量标准是零行。这个失衡是最大的优化机会。

### 原则 P4：分离"模板 schema"与"模板格式"

> 定义必要字段（schema），不定义呈现格式（format）。
> — 源自 T1 (最小化外在负荷)、T7 (反官僚化)

**理论依据**：一个 200 行的 issue 模板中，schema 信息（字段名、类型、约束）约 20 行，格式信息（表头、占位符、示例、说明）约 180 行。格式信息是纯外在负荷。

**实践方式**：

```
# Before（200 行模板）
完整的 Markdown 表格 + 每个字段的格式说明 + 占位符 + 示例

# After（最小 schema，~20 行）
issue 必须包含：
- id: R{功能点序号}-{序号}
- description: 一句话描述
- severity: High | Medium | Low
- status: open | clarifying | clarified
- answer: 澄清后的决策（状态为 clarified 时必填）
组织方式和呈现格式由模型根据问题数量和复杂度自行决定。
```

### 原则 P5：面向退化设计——每个约束都有"日落条件"

> 约束应随模型能力增强而可退化，而非永久固化。
> — 源自 Claude Code "面向模型进化设计"、T7 (反官僚化)

**理论依据**：今天必要的约束，明天可能成为负债。aspec 应内建"约束有效性评估"机制。

**实践方式**：每个约束附带"日落条件"——当满足什么条件时可以移除这个约束。

```yaml
# 示例：分类学维度提醒
constraint: 澄清时提醒模型检查 6 个维度
sunset-condition: 当连续 5 个 change 的复盘显示模型自主覆盖了所有维度时，移除此提醒
```

这与进化体系（Layer B）天然契合：Layer B 的"进化分析"不仅应该新增检查维度，还应该评估是否可以移除过时维度。

## 5. 架构级优化方向

### 5.1 方向 A1：config.yaml 重构——从"百科全书"到"索引 + 约束"

**当前问题**：config.yaml 同时承载了工作模式描述、门禁条件、状态机、知识库索引、进化体系描述、各阶段规则。151 行中大量是过程性描述。

**优化方向**：

```
config.yaml v5（当前）          config.yaml v6（目标）
├─ context（66 行）             ├─ constraints（~15 行）
│   ├─ 工作模式描述             │   ├─ 门禁条件（声明式）
│   ├─ 门禁条件表格             │   └─ 行为约束（批量提问等）
│   ├─ 状态机描述               │
│   ├─ 严重程度说明             ├─ knowledge-index（~8 行）
│   ├─ 知识库索引               │   └─ 阶段 → 读取文件映射
│   └─ 进化体系描述             │
│                               └─ rules（~20 行，声明式）
├─ rules（80 行）                   ├─ proposal: 约束 + 产出物
│   ├─ proposal（步骤描述）         ├─ design: 约束 + 产出物
│   ├─ specs（步骤描述）            ├─ tasks: 约束
│   ├─ design（步骤描述）           ├─ apply: 约束
│   ├─ tasks（步骤描述）            └─ archive: 约束 + 指针
│   ├─ apply（步骤描述）
│   └─ archive（步骤描述）
│
总计：~151 行 / ~2,500 tokens    总计：~43 行 / ~700 tokens
```

**示例——rules.proposal 的声明式重写**：

```yaml
# Before (~7 行过程描述)
proposal:
  - |
    BEFORE creating proposal：
    1. 检查 spec/requirement-issues.md 是否存在且状态为 clarified
    2. 不满足 → 执行 openspec/templates/procedures/requirement-clarification-flow.md 中的完整流程
    3. 通过后创建 proposal，在 Why / Capabilities / Impact 中引用澄清决策
  - "🚫 禁止跳过..."

# After (~3 行声明式约束)
proposal:
  gate: spec/requirement-issues.md 状态为 clarified
  constraint: proposal 必须引用 requirement-issues.md 中的澄清决策
  on-fail: 识别需求不确定性，批量向用户澄清，更新 requirement-issues.md
```

**寄生模式兼容性**：完全兼容——只改变 aspec 注入的内容格式，不改变 OpenSpec schema。

### 5.2 方向 A2：分类学重构——从"详尽检查清单"到"维度枚举 + 进化盲区"

**当前问题**：两个分类学文件合计 ~380 行 / ~4,000 tokens。大部分内容（症状描述、检查点问题）是模型原生就知道的通用知识。

**优化方向**：

```
分类学 v5（当前）               分类学 v6（目标）
├─ 6 维度详细展开               ├─ 维度枚举（一行清单）
│   ├─ 每维度 3 子类            ├─ 已知盲区（来自进化体系）
│   ├─ 每子类症状描述           └─ 日落清单（待退化的维度）
│   └─ 每子类 3 个检查点
│
~180 行 / ~2,000 tokens        ~30 行 / ~400 tokens
```

**示例——需求分类学重构**：

```markdown
# 需求澄清维度

检查不确定性时参考以下维度（不要逐条遍历，聚焦于当前需求中不确定的部分）：

维度：功能完整性 | 数据关切 | 用户体验 | 边界异常 | 集成依赖 | 优先级范围

## 项目已知盲区（来自进化体系，优先检查）

*暂无。首次 archive 后自动填充。*

## 待退化维度

*暂无。连续 5 次复盘该维度无新发现时自动添加。*
```

**关键设计**："项目已知盲区"段是 aspec 真正的差异化价值——它携带模型无法自行推导的项目特有信息。随着使用，盲区积累越来越多，分类学变得越来越有价值（而非一开始就很重但价值递减）。

### 5.3 方向 A3：模板体系重构——"最小 schema + 自由格式"

**当前问题**：issues 模板合计 ~400 行 / ~5,500 tokens，信息密度 <10%。模板预设了所有可能的章节和格式，但实际使用时大部分章节为空。

**优化方向**：

```
模板 v5（当前）                 模板 v6（目标）
├─ 完整表格结构                 ├─ 必要字段 schema（~10 行）
├─ 每个字段详细说明             ├─ 状态流转规则（~5 行）
├─ 占位符和示例                 └─ 组织方式由模型自行决定
├─ 状态流转完整说明
├─ 关联文档列表
└─ 备注区域

~200 行 / ~2,800 tokens        ~20 行 / ~300 tokens
```

**requirement-issues.md 最小 schema 示例**：

```markdown
# 需求问题清单
状态: discovering | clarifying | clarified | superseded

## 字段定义
每个问题必须包含：id, description, severity (High/Medium/Low), status, answer（clarified 时必填）

## 组织方式
按功能点分组，格式自行决定。确保可追溯到对应 spec。
```

**寄生模式兼容性**：完全兼容——只改变模板的详细程度，不改变 OpenSpec 的文件结构和路径约定。

### 5.4 方向 A4：过程文件合并——从"四个独立文档"到"嵌入式约束"

**当前问题**：4 个 procedure 文件合计 ~260 行 / ~3,800 tokens，大量是模型原生能力的重复描述。

**优化方向**：

```
procedures v5（当前）                procedures v6（目标）
├─ requirement-clarification-flow.md   ├─ clarification-protocol.md（合并）
├─ design-clarification-flow.md        │   ├─ 行为约束（批量提问等）
├─ interactive-clarification-protocol  │   └─ 设计澄清强制确认规则
└─ evolution-system.md                 │
                                       └─ evolution-system.md（精简）
                                           └─ 更新映射 + 进化触发条件

4 个文件 / ~260 行 / ~3,800 tokens    2 个文件 / ~60 行 / ~900 tokens
```

**合并逻辑**：
- 需求澄清流程和设计澄清流程的 80% 内容是相同的（分析 → 发现问题 → 澄清 → 更新状态）——差异只在"设计澄清强制确认"
- 交互协议的核心规则（批量提问、断点续传）可嵌入合并后的文件
- 进化体系保留但精简——核心是"什么时候更新什么"的映射表

### 5.5 方向 A5：进化体系增强——双向进化（新增 + 退化）

**当前问题**：进化体系只支持"新增"（发现新盲区 → 增加检查维度），不支持"退化"（某维度持续无新发现 → 移除提醒）。长期运行后分类学只会膨胀。

**优化方向**：

```
进化 v5（单向）                  进化 v6（双向）
Layer B 触发时：                 Layer B 触发时：
- 分析漏检 → 新增维度           - 分析漏检 → 新增维度/盲区
- 分析噪音 → 删除维度           - 分析噪音 → 删除维度
                                 - 分析覆盖率 → 退化维度提醒
                                 - 评估约束有效性 → 建议移除过时约束
```

**"退化"机制设计**：

```markdown
## 维度退化规则

当一个分类学维度满足以下条件时，标记为"待退化"：
- 连续 N 次（建议 N=5）复盘中，该维度零漏检、零命中
- 说明模型已能自主覆盖此维度，提醒不再必要

待退化维度在下次 Layer B 分析时展示给用户：
"维度 X 已连续 5 次无新发现，建议退化为隐式（不再主动提醒）。确认？"

退化不是删除——维度仍在清单中，但标记为"隐式"，不占用 token。
```

这让 aspec 随时间变得更精简而非更臃肿——这才是健康的进化方向。

### 5.6 方向 A6：补全 Spec-Code 验证闭环

**当前问题**：aspec 在 Specify 阶段（前半段闭环）很强，但在 Verify 阶段（后半段闭环）几乎为零。apply 阶段只有"遵循决策"的笼统要求和可选的观察笔记，没有结构化的 Spec-Code 一致性验证。

**优化方向**：在 apply 和 archive 阶段补全验证闭环。

```yaml
# config.yaml — 新增验证约束
rules:
  apply:
    - "实施完成后，验证代码变更覆盖了所有 Spec 决策"
    - "验证方式：逐条检查 tasks.md 中的任务是否完成 + design.md 中的决策是否体现在代码中"
  archive:
    - "复盘报告增加：Spec-Code 一致性评估段"
```

**验证不是微管理**——不需要告诉模型如何验证，只需要声明"验证必须发生"。模型有能力对照 Spec 文件检查实现。

### 5.7 方向 A7：定义 Spec 产出物完成标准

**当前问题**：门禁只检查 issues 的 status，不检查核心 Spec 产出物（proposal / design / tasks）的完整性。一个缺少 Capabilities 定义的 proposal 也能通过门禁。

**优化方向**：为 Spec 产出物添加声明式完成标准。

```yaml
# config.yaml — Spec 完成标准（声明式）
rules:
  proposal:
    gate: spec/requirement-issues.md 状态为 clarified
    spec-quality:
      - "proposal 包含 Why / Capabilities / Impact"
      - "每个 Capability 有唯一 ID，与 requirement-issues 可追溯"
  design:
    gate: spec/design-issues.md 状态为 clarified 或 resolved
    spec-quality:
      - "每个技术决策包含四要素"
      - "已知风险区域（risk-map）有应对策略"
  tasks:
    spec-quality:
      - "每个任务可追溯到 design 决策"
      - "任务粒度支持原子验证"
```

**寄生模式兼容性**：完全兼容——这是通过 rules 注入的声明式约束，不改变 OpenSpec schema。

### 5.8 方向 A8：Spec 变更协议——区分"微调"与"re-spec"

**当前问题**：实施中发现偏差时，唯一路径是"暂停→更新问题清单→继续"。大型复杂项目中，某些发现可能颠覆原设计假设，需要回退到 Spec 阶段重新设计。当前没有判断机制。

**优化方向**：

```yaml
# config.yaml — Spec 变更协议
rules:
  apply:
    - |
      实施中发现偏差时的处理：
      - 微调（不影响设计决策）：更新问题清单，继续
      - 重大偏差（影响 High 级设计决策或新增 High 级需求问题）：
        暂停实施 → 回退到 proposal/design 阶段 → 重新澄清 → 更新 Spec → 继续
      判断标准：是否需要修改 design.md 中的核心技术决策
```

**为什么这对大型项目关键**：大型项目的 apply 阶段可能跨多个会话、多天时间。没有变更协议，"小修小补"会逐渐累积偏离原 Spec，最终发现实现与设计严重不一致。变更协议是 Spec 作为 Source of Truth 的守护机制。

### 6.1 config.yaml v6 骨架

基于 A1 方向的具体重写骨架：

```yaml

context: |
  ## aspec 约束（强制）

  | 门禁 | 条件 | 失败动作 |
  |------|------|----------|
  | proposal 前 | spec/requirement-issues.md 状态 clarified | 识别不确定性 → 批量澄清 |
  | tasks 前 | spec/design-issues.md 状态 clarified/resolved | 识别设计风险 → 批量澄清 |

  ## 行为约束
  - 澄清使用批量提问（非逐题），支持断点续传
  - 设计澄清即使无问题也必须向用户确认决策摘要
  - 技术决策必须记录：选择 + 理由 + 备选 + 排除原因

  ## Spec 产出物完成标准
  - proposal: 包含 Why / Capabilities（每个有唯一 ID）/ Impact，引用 requirement-issues 澄清决策
  - design: 每个技术决策四要素，已知风险区域（risk-map）有应对策略
  - tasks: 每个任务追溯到 design 决策，粒度支持原子验证

  ## Spec 变更协议（apply 阶段）
  - 微调（不影响设计决策）：更新问题清单，继续
  - 重大偏差（影响 High 级决策）：暂停 → 回退 proposal/design → 重新澄清

  ## 知识库（按阶段按需读取）
  explore/propose: ADR + Glossary
  design: ADR + Risk Map + 分类学盲区
  tasks: Risk Map
  apply: ADR + Risk Map + Spec 决策
  archive: 全部 → 更新 → 进化分析

rules:
  proposal:
    - "gate: spec/requirement-issues.md 状态为 clarified"
    - "产出符合 Spec 完成标准，引用 requirement-issues.md 中的澄清决策"
  specs:
    - "与 requirement-issues.md 的功能点定义保持一致"
  design:
    - "gate: spec/design-issues.md 状态为 clarified 或 resolved"
    - "产出符合 Spec 完成标准"
  tasks:
    - "覆盖 design-issues.md 中所有 High 决策"
    - "任务描述引用相关设计决策"
  apply:
    - "实施前读取所有 Spec 文件（proposal + design + issues）的决策"
    - "发现偏差：按 Spec 变更协议处理（微调 vs 回退 re-spec）"
    - "实施完成后验证 Spec-Code 一致性"
    - "观察记录到 spec/retrospective-notes.md"
  archive:
    - "生成复盘报告到 openspec/retrospectives/（含 Spec-Code 一致性评估）"
    - "执行进化更新：详见 openspec/templates/procedures/evolution-system.md"
```

**对比**：151 行 → ~45 行，token 开销从 ~2,500 降至 ~750。门禁和核心约束完整保留。

## 7. 实施路线图与风险

### 7.1 分阶段实施策略

```
Phase 1（低风险，高收益）— 压缩过程，保留结构
├─ config.yaml 声明式重写（A1）
├─ 分类学精简为维度枚举 + 盲区（A2）
├─ 问题清单模板最小化（A3）
└─ 验证：对比现有项目的澄清质量

Phase 2（中风险，结构性改进）— 合并文件，补全闭环
├─ 过程文件合并为 2 个（A4）
├─ 复盘模板精简（6.8）
├─ 进化体系增加退化机制（A5）
├─ 新增 Spec 产出物完成标准（A7）
└─ 验证：完整 change 周期端到端测试

Phase 3（Spec Coding 增强）— 验证闭环 + 变更协议
├─ Spec-Code 验证闭环（A6）
├─ Spec 变更协议（A8）
├─ 约束日落机制（P5 的具体实现）
└─ 验证：大型项目跨会话 change 端到端测试
```

### 7.2 风险与缓解

| 风险 | 可能性 | 影响 | 缓解策略 |
|------|--------|------|----------|
| 精简过度导致澄清质量下降 | 中 | 高 | 保留门禁不变；A/B 对比测试 |
| 模型在简短指令下不执行批量提问 | 低 | 中 | "批量提问"是明确的行为约束，非过程描述 |
| OpenSpec 升级不兼容 | 低 | 中 | 所有优化在 aspec 注入层完成，不触及 OpenSpec schema |
| 退化机制误删重要维度 | 低 | 中 | 退化需用户确认；维度不删除只标记"隐式" |
| 知识库格式变化影响进化体系 | 低 | 低 | 知识模板变化极小（6.11 只微调） |

### 7.3 验证策略

**核心验证问题**："精简后的 aspec 是否保持了相同的防错能力？"

**验证方法**：

1. **回归测试**：用现有项目的历史 change 重新跑 v6 流程，对比：
   - 澄清问题的覆盖率（是否遗漏了 v5 能发现的问题）
   - 用户交互轮数（是否反而增加了）
   - token 消耗（预期下降 60%+）

2. **消融实验**：逐一去除优化项，观察哪些去除后质量明显下降

3. **长期观察**：进化体系的退化机制需要跨多个 change 观察

### 7.4 寄生模式合规性检查

| 优化方向 | 是否修改 OpenSpec schema | 寄生模式合规 |
|----------|------------------------|-------------|
| A1 config.yaml 重写 | 否（改的是 aspec 注入内容） | ✓ |
| A2 分类学重构 | 否（aspec 自有模板） | ✓ |
| A3 模板体系重构 | 否（aspec 自有模板） | ✓ |
| A4 过程文件合并 | 否（aspec 自有流程） | ✓ |
| A5 双向进化 | 否（增强进化逻辑，不改结构） | ✓ |
| A6 Spec-Code 验证闭环 | 否（通过 rules 注入约束） | ✓ |
| A7 Spec 完成标准 | 否（通过 rules 注入约束） | ✓ |
| A8 Spec 变更协议 | 否（通过 rules 注入约束） | ✓ |

**结论**：所有优化方向均可在寄生模式约束内实施。A6-A8 是纯粹的 rules 注入，与 OpenSpec schema 零耦合。

## 8. 总结

### 核心发现

aspec v5 是一个为弱模型时代设计的**补偿型脚手架**。它的核心价值——门禁机制和知识进化体系——在强模型时代依然成立。但它的实现方式——详尽的检查清单、冗长的过程指令、重格式的模板——在 frontier model 时代成为活跃负债。

### 优化方程

```
aspec v6 = aspec v5 的核心价值（门禁 + 进化） 
         - 过程性脚手架（步骤指令 + 格式教程 + 详细检查点）
         + 声明式约束（告诉模型什么是好的结果）
         + Spec 质量标准（定义 proposal/design/tasks 的完成标准）
         + Spec-Code 验证闭环（实施后验证一致性）
         + Spec 变更协议（区分微调与 re-spec）
         + 双向进化（新增盲区 + 退化过时维度）
```

### 五条元原则回顾

| # | 原则 | 一句话 |
|---|------|--------|
| P1 | 声明式优于过程式 | 告诉模型"什么是好的"，不告诉"每步怎么做" |
| P2 | 知识优于过程 | token 预算给项目知识，不给操作指南 |
| P3 | Spec 产出物优先 | 过程为 Spec 服务，不是反过来 |
| P4 | schema 与 format 分离 | 定义字段，不定义格式 |
| P5 | 面向退化设计 | 每个约束都有日落条件 |

### 预期效果

- Token 开销：~17,200 → ~3,500（-80%）
- 门禁能力：不变
- Spec 质量标准：**新增**（proposal / design / tasks 完成标准）
- Spec-Code 验证：**新增**（apply/archive 阶段闭环）
- Spec 变更协议：**新增**（大型项目守护机制）
- 进化能力：增强（双向）
- 知识占比：33% → 55%+
- 可维护性：14 个文件 → 10 个文件，每个文件更短更聚焦

### 哲学总结

> aspec 的终极形态不是一个更完善的检查清单，而是一个越用越聪明的**项目记忆体**。
> 它不替代模型思考，而是给模型提供它无法自己获取的知识。
> 它不限制模型行动，而是在关键节点确保人类参与决策。
> 它不只管"想清楚"（Specify），还管"做对了"（Verify）——Spec 是起点也是验证基准。
> 它随模型能力增强而自然精简，而非随时间堆积而臃肿。

## 一、灵魂之问：aspec 到底是什么？

在探讨优化之前，必须先回答一个根本性问题：**aspec 的本质是什么？**

### 1.1 三种可能的身份

| 身份 | 定义 | 随模型增强的命运 |
|------|------|------------------|
| **流程脚手架** | 补偿模型能力不足的过程指令 | 逐渐过时，终将被淘汰 |
| **通信协议** | 定义人机对齐的信息交换格式 | 永远需要，模型越强协议越精炼 |
| **认知外化体** | 跨会话的项目记忆与经验载体 | 越来越有价值，是模型唯一缺失的能力 |

**诊断**：当前 config.yaml 中，约 **65% 是流程脚手架**（如何澄清、如何对齐的详细步骤），**20% 是通信协议**（门禁、文件约定），**15% 是认知外化体**（经验进化系统）。

**结论**：aspec 的"灵魂"应该是 **通信协议 + 认知外化体**。流程脚手架是历史包袱。

### 1.2 存在性验证：如果删除 aspec 会怎样？

逐条对 config.yaml 的核心行为做"删除测试"：

| 行为 | 删除后模型会怎样？ | 结论 |
|------|---------------------|------|
| 需求澄清 | 模型本身就会澄清需求 | ❌ 删除 |
| 批量通过 AskUserQuestion 提问 | 模型可能逐个问或不用该工具 | ⚠️ 保留提示 |
| 写入 issues/ 文件 | 模型不会自发写到特定路径 | ✅ 保留约定 |
| 展示对齐摘要再确认 | 模型可能直接开始做 | ✅ 保留门禁 |
| 门禁拦截（无 clarified 不能 proposal） | 模型不会自设硬门禁 | ✅ 保留 |
| 4 要素技术决策 | 模型做决策时自然覆盖大部分 | ⚠️ 精简为提示 |
| 经验读取（proposal/design 前） | 模型绝不会自发读历史经验 | ✅ 保留（核心价值） |
| 经验写入（apply 后复盘） | 模型不会自发做跨会话持久化 | ✅ 保留（核心价值） |
| 惊讶测试 | 模型有时会自信地做错决策 | ✅ 保留（元规则） |
| 深度探索思考 | 模型可能浮于表面 | ⚠️ 需要更好的触发方式 |
| 严重度定义（High/Medium/Low） | 模型原生理解 | ❌ 删除 |
| 状态机（discovering→clarifying→...） | 模型不需要显式状态机 | ❌ 删除 |
| Issue Schema 格式 | 模型可以自组织 | ⚠️ 只保留必填字段 |
| 贪吃蛇示例 | 上下文噪声 | ❌ 删除 |

**量化**：281 行中，约 70 行属于 ✅ 保留，50 行属于 ⚠️ 精简，160 行属于 ❌ 删除。

## 二、根因诊断：为什么 config.yaml 既臃肿又有时不被遵循？

### 2.1 根因一：混淆了"约束"与"教学"

**现象**：config.yaml 同时在做两件事——（a）告诉模型必须遵守的规则，（b）教模型如何执行任务。

**例证**：需求澄清部分（lines 50-87）用了约 40 行来描述"怎么澄清"（功能清单、功能细节、边界排除、优先级——还有贪吃蛇的具体示例）。但这些是**通识能力**，模型已经知道如何结构化需求分析。真正需要的约束只有："必须澄清并获得确认后才能创建 proposal。"

**认知科学视角（Cognitive Load Theory）**：教学内容构成**外在认知负荷**——它不帮助完成当前任务，反而挤占处理实际需求的认知资源。EMNLP 2025 的研究证实：原始输入长度本身就会降低 LLM 推理质量，即使所有信息都是相关的。

**控制论视角**：一个恒温器只需要"目标温度"和"当前温度"就能工作。你不需要教它"热力学原理"——那是它的内在能力。aspec 当前在做的，就是给恒温器配了一本热力学教科书。

### 2.2 根因二：指令密度过低导致"注意力稀释"

**现象**：281 行中，真正的"不可违反的硬约束"约 15 条，散布在大量上下文描述、格式说明和示例中。模型需要在噪声中捕捉信号。

**信息论视角**：如果 config.yaml 的信息熵为 H，有效信号为 S，则信噪比 SNR = S/H。当前 SNR ≈ 15条硬约束 / 281行总量 ≈ 0.05，即 95% 是噪声。

**心理学视角（Weber-Fechner 定律的类比）**：人类感知阈值随背景强度的增加而提高——要注意到一个信号，信号强度必须与背景噪声保持一定比例。对 LLM 而言同理：当 context 充满了描述性文本时，关键约束的"感知强度"下降。

**直接后果**：这就是为什么门禁有时不被遵循——不是模型不理解门禁，而是门禁淹没在了冗长的上下文中。**更少的指令 = 更高的每条指令遵循率。** 这是反直觉但有实证支持的。

### 2.3 根因三：过程描述与模型原生能力重叠

**现象**：config.yaml 详细描述了"如何做需求分析"、"如何做设计决策"——这些是 frontier 模型的核心能力。

**延展心灵理论（Clark & Chalmers, 1998）** 的判断标准：一个外部元素是否构成认知的一部分？条件之一是"它必须提供主体自身认知所不具备的东西"。如果模型已经具备需求分析能力，那么描述如何做需求分析的文本就不是"延展心灵"，而是"认知冗余"。

**Anthropic 的原话**："For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it."

### 2.4 根因四：context 和 rules 的职责重叠

**现象**：澄清协议在 context 中描述了一遍（lines 49-89），又在 rules 的 proposal/design PRE 规则中重复了一遍（lines 153-188, 198-232）。这不仅浪费 token，还造成两个问题：

1. **一致性风险**：两处描述可能随版本迭代逐渐分化
2. **认知干扰**：模型需要合并两处描述来理解完整行为——这是认知心理学中的"分裂注意力效应"（Split-Attention Effect）

### 2.5 根因五："深度探索"不能靠过程指令实现

**用户关注**："探索思考问题要深入全面不能停在表面，要触及根因和灵魂。"

**认知科学诊断**：深度思考是**元认知能力**（Flavell, 1979）——对自身认知过程的监控和调节。这种能力不能通过"请深入思考"的指令来注入，就像你不能通过告诉一个人"请有创意"来让他变有创意。

**什么能真正促进深度探索？**

1. **元认知触发器** — 不是描述如何深度思考，而是设置触发自检的检查点。例如："在标记任何问题为 Low 之前，自问：如果这个问题在实施阶段暴露，返工成本有多高？"
2. **经验系统的盲区注入** — 来自 `dimensions.md` 的已知盲区迫使模型关注它通常会忽略的维度。这是**真正起作用**的机制——它不靠过程指令，靠的是**信息注入**。
3. **验证标准** — 不描述"深入分析"的过程，而是定义"深入"的标准。例如："每个 High 问题必须包含 root cause（为什么这是不确定的）和 impact scope（如果错了会影响什么）。"

## 三、核心框架：协议-约定-引导 三层模型

基于以上根因分析，提出 aspec 的新架构模型：

```
┌─────────────────────────────────────────────────┐
│  Layer 1: 协议（Protocol）                       │
│  不可违反的硬约束。删除任何一条 = 工作流崩溃      │
│  ·门禁条件  ·经验读写钩子  ·惊讶测试元规则        │
│  占比目标：40% token                              │
├─────────────────────────────────────────────────┤
│  Layer 2: 约定（Convention）                      │
│  文件系统位置和输出格式。保证跨会话一致性          │
│  ·文件路径约定  ·Issue 必填字段  ·工具使用约定     │
│  占比目标：30% token                              │
├─────────────────────────────────────────────────┤
│  Layer 3: 引导（Guidance）                        │
│  可选的质量增强。模型能力增强时首先退化的层        │
│  ·维度提示  ·元认知触发器  ·质量标准              │
│  占比目标：30% token                              │
└─────────────────────────────────────────────────┘
```

**当前状态 vs 目标状态**：

| 层 | 当前 token 占比 | 目标 token 占比 |
|----|-----------------|-----------------|
| Protocol | ~15% | ~40% |
| Convention | ~20% | ~30% |
| Guidance | ~65%（大量过程描述） | ~30%（精选元认知触发） |

关键翻转：**协议层占比从 15% 提升到 40%**——不是因为协议变多了，而是因为噪声减少了，信号浓度提高了。

## 四、十个优化方向

### 方向 1：从"过程手册"到"通信协议"

**根因对应**：根因一（混淆约束与教学）

**当前问题**：config.yaml 读起来像一本"操作手册"——详细描述每个步骤如何执行。但操作手册的适用对象是能力不足的执行者。对 frontier 模型，它应该读起来像一份"协议规范"——只定义接口契约。

**优化方向**：

将 context 重构为协议格式：

```
# 当前（过程描述，~40 行）
需求澄清和设计澄清分两个独立步骤...
步骤一：澄清...通过 AskUserQuestion 工具批量提问...
步骤二：对齐确认...用 markdown 文本向用户呈现对齐内容...
（然后是功能清单/功能细节/边界排除/优先级的详细描述和贪吃蛇示例）

# 目标（协议声明，~5 行）
## 协议
- 每个阶段转换前：澄清不确定性 → 展示理解 → AskUserQuestion 确认
- 对齐内容用 markdown 文本输出（大段内容在 AskUserQuestion 中显示异常）
- 门禁拦截：前置条件未满足时，禁止创建下阶段产物
```

**理论支撑**：
- **Cybernetics（控制论）**：有效控制器只需目标函数和反馈回路，不需要执行路径描述
- **Anthropic 设计哲学**："General guidance over prescriptive steps" — 模型用通用引导获得的推理质量，往往优于人类预设的详细步骤

**精简预估**：~40 行 → ~5 行

### 方向 2：门禁结构化——从叙述到声明

**根因对应**：根因二（注意力稀释）

**当前问题**：门禁条件分散在 context 的表格、叙述文本和 rules 的 `🚫` 标记中。模型需要从多处提取和合并信息才能理解完整的门禁图。

**优化方向**：

将所有门禁集中为一个结构化声明，放在 config.yaml 的最高优先位置：

```yaml
gates:
  proposal:
    requires: issues/requirement-issues.md 存在且状态为 clarified
    alignment: 必须展示需求理解摘要并通过 AskUserQuestion 确认
  design:
    requires: issues/design-issues.md 存在且状态为 clarified
    alignment: 必须展示技术方案摘要并通过 AskUserQuestion 确认
  tasks:
    requires: design.md 已通过用户审批
  apply:
    reads: issues/requirement-issues.md, issues/design-issues.md
```

**为什么这会提高合规率**：

1. **信息论**：集中 = 高信噪比。模型一次扫描就能获取所有门禁信息
2. **Poka-yoke（防错设计）**：结构化声明消除了歧义——门禁条件是 unambiguous 的
3. **认知负荷**：消除了"分裂注意力效应"——不再需要从多处合并信息

**精简预估**：散布在 context（~15 行）+ rules（~10 行） → 集中声明 ~8 行

### 方向 3：经验系统的"钩子化"——精简触发，丰富载体

**根因对应**：经验进化是 aspec 的核心价值

**当前问题**：经验系统的描述在 context 中占约 50 行（生命周期、应用时机、提取、验证、收敛），在 rules 中又重复了操作步骤。但经验系统的实质只有 4 个钩子：

1. **proposal PRE**：读取需求相关经验
2. **design PRE**：读取技术相关经验
3. **apply POST**：提取本次经验，验证已有经验
4. **archive POST**：收敛/淘汰

**优化方向**：

将经验系统重构为"钩子 + 载体"模式：
- **钩子**（在 rules 中，~8 行）：只声明何时读/写 experience.md
- **载体**（experience-template.md，已有）：定义经验的结构
- **行为**（模型原生能力）：如何提取、如何判断有效/无效——模型已经知道

```yaml
# 经验钩子（全部）
proposal: [PRE] 读取 experience.md 中需求相关经验，告知用户
design: [PRE] 读取 experience.md 中技术相关经验，告知用户
apply: [POST] 复盘提取经验到 experience.md，验证本次应用的经验（✓/✗/—）
archive: [POST] 条目>20 时提议合并/淘汰
```

**理论支撑**：
- **延展心灵**：experience.md 是模型的"外化记忆"——真正构成认知延展的部分。config.yaml 中描述如何使用这个记忆的文本不是延展心灵，是"使用说明"
- **知识 vs 过程**：经验系统的价值在于**知识积累**（experience.md 的内容），不在于**过程描述**（config.yaml 中如何操作的步骤）

**精简预估**：context ~50 行 + rules ~15 行 → rules ~8 行

### 方向 4：深度探索的"元认知触发"替代"过程描述"

**根因对应**：根因五（深度不靠过程指令实现）

**当前问题**：config.yaml 描述了探索的维度（dimensions.md 引用）和质量标准，但缺少**触发深度思考的元认知机制**。模型可能按部就班地遍历维度列表，但这恰恰是"表面深度"——看起来全面，实际是机械式检查。

**优化方向**：

用元认知触发器替代维度遍历：

```yaml
context: |
  ## 深度探索协议
  不要遍历维度清单做表面扫描。聚焦于：
  - 这个需求/设计中，哪些部分让你最不确定？为什么？
  - 如果实施阶段才发现理解有误，哪些误解的返工成本最高？
  - dimensions.md 中的已知盲区是否与本次 change 相关？
```

**为什么这比维度列表更有效**：

1. **元认知（Flavell）**：触发自我监控（"我不确定什么？"）比外部检查清单更能激活深度思考
2. **Pragmatism（Dewey）**：问题定义比问题求解更重要——"这里有什么让我困惑的？"比"检查这 6 个维度"更能引导到真正的不确定性
3. **Flow 理论（Csikszentmihalyi）**：深度思考需要**挑战与能力匹配**——机械遍历太简单，无法进入 flow 状态；"在不确定性中找到最高风险的部分"是适当挑战

**补充机制**：dimensions.md 的已知盲区保留——这是经验系统积累的**信息**，是模型不可能自己推导出的。但它的定位从"必须遍历的清单"变为"历史经验的提示"。

**精简预估**：间接效果——允许删除大段维度遍历相关的描述

### 方向 5：context 与 rules 的职责边界重新划分

**根因对应**：根因四（context 和 rules 重叠）

**当前问题**：context 描述"做什么"，rules 描述"具体怎么做"，两者高度重叠。

**优化方向**：

严格划分职责：

| 字段 | 职责 | 内容类型 |
|------|------|----------|
| **context** | 世界观（不变的背景知识） | 工作模式、协议、元规则、文件约定 |
| **rules** | 行为约束（每阶段的具体指令） | 门禁、钩子、不可违反的约束 |

**具体策略**：

- context **只包含**：语言指令、寄生模式声明、流程概览（一行）、门禁声明、惊讶测试、文件约定、深度探索协议
- rules **只包含**：每阶段的 [PRE]/[POST]/[CONSTRAINT] 指令，每条指令 ≤ 3 行
- **删除**所有 context 中重复的过程描述

**理论支撑**：
- **信息论（Shannon）**：冗余降低有效信道容量。context 和 rules 的重叠是信息论中的"编码冗余"
- **单一职责原则**：每个字段只承担一个职责

**精简预估**：消除重叠约 40-50 行

### 方向 6：规则的"语义压缩"——用意图替代步骤

**根因对应**：根因一（混淆约束与教学）+ 根因三（与模型能力重叠）

**当前问题**：rules 中的每条规则平均约 8-15 行，包含详细的步骤说明。

**优化方向**：

每条规则压缩为 1-3 行，只保留**意图**和**不可推导的约束**：

```yaml
# 当前（~15 行）
- |
  [PRE] **需求澄清 - 步骤1: 分析并写入问题清单**
  1. 读取 dimensions.md 作为参考维度和已知盲区，自主探索需求不确定性
  2. **必须写入文件**：将识别出的所有 High/Medium 问题写入 issues/requirement-issues.md
     - 格式：id, description, severity, status=clarifying, answer=(待填写)
     - 末尾添加统计：总数、High/Medium/Low 分布
  3. 向用户展示："已识别 X 个 High 问题、Y 个 Medium 问题，准备批量澄清"

# 目标（~2 行）
- |
  [PRE] 自主分析不确定性（参考 dimensions.md 盲区），写入 issues/requirement-issues.md
```

模型不需要被告知：
- 如何分析不确定性（原生能力）
- issue 的精确格式（可自组织，或由 template 定义）
- 如何展示统计（自然行为）

模型需要被告知：
- 写到哪个文件（约定）
- 参考什么（dimensions.md 的盲区）

**理论支撑**：
- **Anthropic ACI 设计原则**：工具文档写意图，不写步骤。"See from the model's perspective"
- **信息论**："写入 issues/requirement-issues.md" 信息量 ≈ 1.0（模型无法推导）。"读取 dimensions.md 作为参考维度" 信息量 ≈ 0.3（模型大概会参考）。"格式：id, description, severity..." 信息量 ≈ 0.1（模型能自组织）

**精简预估**：rules 从 ~130 行 → ~40 行

### 方向 7：寄生模式的"最小注入"原则

**根因对应**：寄生模式约束

**当前问题**：aspec 通过 context 和 rules 注入 OpenSpec——但注入量越大，与 OpenSpec 自身行为的冲突风险越高。

**优化方向**：

定义"最小注入原则"：**只注入 OpenSpec 不会自发产生的行为。**

OpenSpec 本身已经有的能力（无需注入）：
- 阶段流程管理（proposal → specs → design → tasks → apply → archive）
- 基本的 spec 生成能力
- 文件组织（openspec/ 目录结构）

aspec 需要注入的（OpenSpec 不做的事）：
- 强制人机对齐门禁
- 经验进化钩子
- 深度探索元认知触发
- 惊讶测试元规则
- 中文语言指令

**理论支撑**：
- **寄生生物学**：成功的共生关系中，寄生体提供宿主缺失的能力，而非试图控制宿主的所有行为
- **Ashby 的必要多样性法则**：控制器的复杂度不应超过被控系统所需——过度控制反而降低系统适应性

### 方向 8：面向模型进化的"日落架构"

**根因对应**：未来模型能力增强

**当前问题**：config.yaml 没有自我退化的机制。随着模型能力增强，越来越多的指令变成冗余，但没有信号触发删除。

**优化方向**：

为每条 Guidance 层规则标注"日落条件"：

```yaml
# 示例
- rule: 对齐内容用 markdown 文本输出，不放在 AskUserQuestion 中
  sunset: 当 AskUserQuestion 支持大段内容渲染时删除
  
- rule: 参考 dimensions.md 已知盲区
  sunset: 当经验系统稳定运行 10+ change 后，盲区自然丰富，可降级为可选
```

**实践策略**：不需要在 config.yaml 中显式标注（增加 token），但在经验进化的**收敛阶段**（archive POST）加入一个检查：

> "回顾当前 config.yaml 中的 Guidance 规则，是否有规则在最近 5 次 change 中从未被触发或从未影响输出？如果有，标记为退化候选。"

**理论支撑**：
- **Cybernetics（负反馈回路）**：系统需要减弱机制，不仅仅是增强机制。没有负反馈的系统会无限膨胀
- **Institutional Theory（制度退化）**：Weber 的官僚化理论——制度一旦建立就倾向于自我维护。主动的退化机制是对抗官僚化的唯一方法
- **Complex Adaptive Systems**：边缘自组织——系统在秩序和混沌的边缘最具适应力。过度规则化推向僵化的秩序

### 方向 9："验证标准"替代"过程指令"——让输出定义质量

**根因对应**：根因一 + 根因五

**当前问题**：config.yaml 描述了很多"如何做"，但很少描述"做到什么标准算完成"。例如，详细描述了设计澄清的 3 个步骤，但没有说"设计澄清完成的标准是什么"。

**优化方向**：

用输出标准替代过程步骤：

```yaml
# 当前：描述过程（how）
[PRE] 设计澄清 - 步骤1: 分析...
[PRE] 设计澄清 - 步骤2: 提问...
[PRE] 设计澄清 - 步骤3: 更新...

# 目标：声明标准（what good looks like）
[PRE] 设计澄清完成标准：
  - 所有 High 不确定性已有决策且记录在 issues/design-issues.md
  - 每个决策包含选择、理由、备选方案
  - 用户通过 AskUserQuestion 确认技术方案
```

**为什么标准比步骤更有效**：

1. **Goal Setting Theory（Locke & Latham）**：明确的目标标准比详细的过程指令更能驱动高绩效——因为目标给予执行者选择最优路径的自由
2. **TOTE 模型**：Test-Operate-Test-Exit——验证标准提供了 Test 环节。没有标准，就没有"完成"的信号
3. **Anthropic 最佳实践**："Verification is the highest-leverage intervention" — 验证是最高杠杆的干预

### 方向 10：Spec 质量标准——填补"输出物缺失"

**根因对应**：现有分析已识别但未展开

**当前问题**：config.yaml 对**过程**（如何澄清、如何对齐）投入了大量 token，但对**产出物**（proposal/design/tasks 应该是什么质量）投入为零。这是严重的本末倒置。

**优化方向**：

将 token 预算从"过程描述"转移到"输出质量标准"：

```yaml
# Spec 质量标准（新增）
spec_quality:
  proposal:
    - 每个 Capability 有明确边界和可测试的验收条件
    - Why（为什么做）与 What（做什么）分离
  design:
    - 每个 High 决策包含：选择、理由、备选方案、排除原因
    - 组件间依赖关系显式化
  tasks:
    - 每个任务可独立验证
    - 可追溯到 design 中的具体决策
```

**理论支撑**：
- **Spec Coding 规范**：Spec 的价值在于它是"可执行的规格"——质量标准确保这个"规格"是可靠的
- **Harness Engineering（Hashimoto）**：每次错误工程化一个永久修复到环境中——质量标准就是这个"永久修复"

## 五、整体优化蓝图

### 5.1 config.yaml 目标结构（~60-70 行）

```
context: (~30 行)
  ├── 语言与工作模式 (2 行)
  ├── 流程概览 (1 行)
  ├── 门禁声明 (8 行，结构化)
  ├── 惊讶测试 (1 行)
  ├── 文件约定 (5 行)
  ├── 深度探索协议 (5 行，元认知触发)
  ├── Spec 质量标准 (8 行)
  └── 经验系统概述 (2 行，仅声明目的)

rules: (~30-40 行)
  ├── proposal (8 行)
  │   ├── [PRE] 经验读取钩子
  │   ├── [PRE] 需求澄清（意图，非步骤）
  │   └── 🚫 门禁
  ├── specs (2 行)
  ├── design (8 行)
  │   ├── [PRE] 经验读取钩子
  │   ├── [PRE] 设计澄清（意图，非步骤）
  │   └── 🚫 门禁
  ├── tasks (4 行)
  ├── apply (8 行)
  │   ├── [PRE] 读取决策
  │   ├── [CONSTRAINT] spec-code 一致性
  │   └── [POST] 经验提取与验证
  └── archive (2 行)
```

### 5.2 精简效果预估

| 维度 | 当前 | 目标 | 变化 |
|------|------|------|------|
| 总行数 | 281 | ~65 | **-77%** |
| 估算 token | ~4,500 | ~1,000 | **-78%** |
| 协议/约束占比 | ~15% | ~45% | +200% |
| 过程描述占比 | ~65% | ~15% | -77% |
| 知识/标准占比 | ~20% | ~40% | +100% |
| 门禁集中度 | 分散 3+ 处 | 集中 1 处 | 结构化 |

### 5.3 合规率预测

**假设**：门禁遵循率与信噪比正相关（有理论和实证支持）

- 当前：281 行中 15 条硬约束 → SNR ≈ 0.05 → 预测合规率 ~70-80%
- 优化后：65 行中 15 条硬约束 → SNR ≈ 0.23 → 预测合规率 ~90-95%

**关键洞察**：**合规率的提升不是来自增加更多约束，而是来自减少噪声。** 这是最反直觉但也最重要的优化方向。

## 六、跨学科理论整合

### 汇总：每个优化方向的理论根基

| 方向 | 核心理论 | 一句话逻辑 |
|------|----------|------------|
| 1. 过程→协议 | 控制论 + Anthropic 哲学 | 恒温器不需要热力学教科书 |
| 2. 门禁结构化 | 信息论 + Poka-yoke | 集中信号，消除歧义 |
| 3. 经验钩子化 | 延展心灵 | 知识是延展，使用说明不是 |
| 4. 元认知触发 | Flavell 元认知 + Flow | 触发自检比描述过程更有效 |
| 5. 职责边界 | 单一职责 + Shannon | 消除编码冗余 |
| 6. 语义压缩 | 信息论 + ACI 设计 | 传达意图，不传达步骤 |
| 7. 最小注入 | 共生理论 + Ashby | 寄生体提供缺失能力，不控制宿主 |
| 8. 日落架构 | 负反馈 + 制度退化理论 | 没有减弱机制的系统会无限膨胀 |
| 9. 验证替代指令 | Goal Setting + TOTE | 标准比步骤更驱动绩效 |
| 10. Spec 质量标准 | Spec Coding + Harness | Token 应投资在产出物，不在过程 |

### 底层逻辑链

```
模型能力增强（前提）
    ↓
过程描述的价值递减（推论）
    ↓
信噪比恶化 → 合规率下降（后果）
    ↓
删除过程，保留协议（策略）
    ↓
更少指令 + 更高合规 + 更深思考（结果）
```

这个逻辑链可以用一句话表达：

> **aspec 的优化方向不是写得更好，而是写得更少。每删除一行不必要的指令，都在提高剩余指令的遵循率。**

## 八、下一步建议

1. **最高优先级**：方向 1（协议化）+ 方向 2（门禁结构化）+ 方向 6（语义压缩）— 这三个方向组合实施可实现 ~70% 的精简

4. **实施后验证**：在 3-5 个实际 change 中对比 v9.4 和 v10 的门禁遵循率、探索深度、经验积累质量

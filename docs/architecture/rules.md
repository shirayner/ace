## 1. thinking.md — 深度思考原则

### 设计理念

基于认知科学和东方智慧的六字原则，建立系统性的思考框架。

### 六字原则

| 字 | 含义 | 自检问题 | 理论来源 |
|---|------|---------|---------|
| **序** | 顺序、秩序 | 理解够启动下一步吗？ | 实用主义 |
| **验** | 验证、检验 | 什么条件下结论不成立？ | 证伪主义 |
| **深** | 深度、深入 | 到根因层了吗？ | 第一性原理 |
| **广** | 广度、系统 | 改动影响传向何方？ | 系统论 |
| **辨** | 辨别、辨析 | FACT/INFER/ASSUME？ | 批判性思维 |
| **简** | 简洁、简化 | 能更简单吗？ | 奥卡姆剃刀 |

### 过程纪律

**序** — 理解先于规划，规划先于行动
```
未经理解的方案是猜测
未经规划的执行是冲动
```

**验** — 用事实闭环，不以假设收尾
```
预期与现实的差距 = 认知盲区
验证不通过 → 回到"序"重新来
```

### 使用场景

适用于所有复杂任务，特别是：
- 架构设计
- 问题诊断
- 方案评估
- 代码审查

## 2. clean-code.md — Clean Code 核心原则

### 设计理念

基于 Robert C. Martin 的《Clean Code》，建立代码质量的价值观。

### 六条原则

| 原则 | 核心 | 反面示例 |
|------|------|---------|
| **意图清晰** | 命名即意图 | `data` → `userProfile` |
| **单一职责** | 一个模块只做一件事 | 上帝类 |
| **最小 Surprise** | 做读者期望的事 | 命名与行为不一致 |
| **DRY** | 每处知识只表达一次 | 重复代码 |
| **简洁胜于复杂** | KISS, YAGNI | 过度工程 |
| **渐进改进** | 离开时比发现时更干净 | 破窗效应 |

### 执行优先级

当原则冲突时：

```
正确性 > 性能
可读性 > 简洁
清晰 > clever
简单 > 通用
显式 > 隐式
```

### 反模式速查

| 反模式 | 症状 | 解药 |
|--------|------|------|
| 上帝类 | 类做太多事 | 拆分职责 |
| 重复代码 | 相似代码多处 | 提取公共逻辑 |
| 过度工程 | 为假设的未来设计 | YAGNI |
| 紧耦合 | 修改一处影响多处 | 引入抽象层 |
| 静默失败 | 错误被吞掉 | 显性错误处理 |

## 3. code-quality.md — 代码质量标准

### 设计理念

将 clean-code 原则转化为可操作的检查清单，自动应用于代码编辑场景。

### 函数/方法质量检查

| 检查项 | 标准 | 未通过处理 |
|--------|------|-----------|
| 职责单一 | 能用"动词+名词"一句话描述 | 拆分函数 |
| 长度适中 | 理想 20 行内，最多 30 行 | 提取子函数 |
| 参数数量 | 3 个以内 | 封装为对象 |
| 嵌套深度 | 3 层以内 | 卫语句/早期返回 |
| 可测试性 | 不依赖全局状态 | 注入依赖 |

### 命名质量检查

| 检查项 | 标准 | 反面示例 |
|--------|------|---------|
| 表达意图 | 看到名字知用途 | `data` → `userProfile` |
| 避免歧义 | 同一概念同一词汇 | 混用 get/fetch/retrieve |
| 避免缩写 | 除非是行业通用 | `usrCnt` → `userCount` |
| 区分状态 | 布尔值用 is/has/should | `valid` → `isValid` |
| 体现副作用 | 修改操作动词明确 | `fetchAndSaveUser()` |

### SOLID 原则检查

- **S** — 描述职责时是否用了"和"/"或"？
- **O** — 新功能通过添加代码实现？
- **L** — 子类能替换父类？
- **I** — 客户端不依赖不需要的接口？
- **D** — 依赖抽象而非具体实现？

## 4. reporting.md — 报告输出规则

### 设计理念

将分析结果、总结或报告自动输出到 markdown 文件，便于查阅和共享。

### 触发条件

以下场景自动触发报告输出：
- 要求将分析结果输出到文件
- "写到文件"、"输出到文档"、"生成报告"
- 指定了输出文件路径且内容为分析性质

### 输出规范

```markdown
# {报告标题}

## 执行摘要
{核心结论，3-5 句话}

## 详细分析
{分章节详细说明}

## 结论与建议
{ actionable 的建议 }

---
生成时间: {timestamp}
```

### 使用场景

- 代码审查报告
- 架构分析
- 问题诊断
- 性能分析

## 5. task-recovery.md — 任务恢复规则

### 设计理念

长任务可能跨会话执行，需要机制恢复上下文。

### 恢复流程

```
用户说"继续"
    ↓
搜索 .tasks/*/state.md
    ↓
读取状态文件
    ↓
验证已完成产出
    ↓
从断点继续
```

### 状态文件结构

```markdown
# {任务标题}
Type: {auto-goal | coding}
Status: {pending | in-progress | completed}

## Goal
{目标 + 验收标准}

## Mental Model
{当前理解}

## Progress
### Phase N: {标题}
- Status: {状态}
- Steps: [x] done / [ ] todo
- Verification: {验证标准}

## Files Modified
- {path}: {变更说明}
```

### 信任但验证

恢复时必须验证：
```
state.md 声称的产出
    ↓
Glob/Read 轻量确认
    ↓
真实存在？→ 继续
不存在？→ 标记为待完成
```

## 6. context-hygiene.md — 上下文卫生规则

### 设计理念

上下文窗口是工作记忆，主动管理而非被动耗尽。

### Compaction 保护

上下文被压缩时，**必须保留**：

```markdown
1. 当前任务状态
2. 关键决策及理由
3. 已修改的文件列表
4. 未完成的待办项
5. 验证结果
```

### 上下文工程策略

| 策略 | 做法 | 时机 |
|------|------|------|
| **隔离** | 探索性工作用 sub-agent | 搜索、读大文件 |
| **压缩** | 已完成阶段摘要化 | 大阶段完成后 |
| **外化** | 关键结果写入文件 | 重要决策时 |
| **按需加载** | 根据阶段拉入上下文 | 每步开始前 |

### 信息节奏

```
前期宽探索 (广度优先)
    ↓
中期深执行 (深度优先)
    ↓
后期纯验证
```

## 7. memory-policy.md — 记忆质量策略

### 设计理念

全局 memory 是跨项目共享的稀缺资源，需要严格筛选。

### 保存门槛

**必须同时满足** (AND)：
1. 跨会话复用
2. 不可推导

**至少满足一项** (OR)：
3. 反直觉
4. 高复用
5. 纠错信号

### 绝不保存

- 项目特定的构建命令
- 临时状态
- 代码模式
- Git 历史
- 已在 CLAUDE.md 中的内容

### 写入纪律

```markdown
---
name: {memory name}
description: {one-line}
type: {user | feedback | project | reference}
---

{内容}

**Why:** {原因}

**How to apply:** {应用方法}
```

## 8. interactive-clarify.md — 交互式澄清规则

### 设计理念

不确定性分级，"必须澄清"级必须通过交互工具向用户提问。

### 不确定性分级

| 级别 | 处理方式 |
|------|---------|
| **必须澄清** | 通过 AskUserQuestion 提问 |
| **可合理假设** | 标注后继续使用 |
| **无关紧要** | 内部决定 |

### 提问原则

- 批量组织问题（1-4 个），减少打断
- 提供明确选项 + "Other" 自由输入
- 涉及方案选择时，用 preview 展示差异

## 自定义规则

可以在 `~/.claude/rules/custom/` 添加自己的规则：

```bash
mkdir -p ~/.claude/rules/custom
echo "# 我的团队规则" > ~/.claude/rules/custom/team-style.md
```

然后在 `~/.claude/CLAUDE.md` 中引用：

```markdown
## 团队规则
- @~/.claude/rules/custom/team-style.md
```

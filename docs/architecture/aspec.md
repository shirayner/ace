# aspec — 寄生模式增强型 OpenSpec

> **ace-spec** (简称 aspec) 是 ACE 的规范驱动开发工作流，采用"寄生模式"在 OpenSpec 基础上增强需求澄清和设计决策机制。

---

## 设计理念与哲学

### 核心洞察

```
跳过澄清 = AI 基于假设实施 = 大概率返工
```

传统开发流程中，AI 在需求不明确时往往基于假设直接编码，导致：

- 需求理解偏差 → 代码与预期不符
- 设计决策未经确认 → 返工修改成本高
- 隐性约束未显式化 → 边界条件遗漏

aspec 通过在关键阶段注入**前置检查**和**交互式澄清**，强制将不确定性显式化，避免基于假设的实施。

### 寄生模式 (Parasitic Pattern)

```
┌─────────────────────────────────────────────────────────────┐
│                    寄生模式架构                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   OpenSpec 核心工件                                          │
│   ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐ │
│   │taxonomy │    │ issues  │    │evolution│    │procedur │ │
│   │问题分类学│    │问题跟踪 │    │知识进化 │    │流程规范 │ │
│   └─────────┘    └─────────┘    └─────────┘    └─────────┘ │
│        │              │              │              │       │
│        ▼              ▼              ▼              ▼       │
│   ┌─────────────────────────────────────────────────────┐  │
│   │              aspec 增强注入                          │  │
│   │  ┌─────────────────┐    ┌─────────────────┐         │  │
│   │  │ 需求澄清门禁    │    │ 设计澄清门禁    │         │  │
│   │  │ (proposal 阶段) │    │ (proposal 阶段) │         │  │
│   │  └─────────────────┘    └─────────────────┘         │  │
│   └─────────────────────────────────────────────────────┘  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**寄生模式特点**：

- **不改变底层 schema**：OpenSpec 的文件结构和规范保持不变
- **在关键阶段注入**：在 proposal 流程中强制检查澄清状态
- **渐进式累积**：每次 archive 后自动积累知识，流程越用越精准

### 核心原则

| 原则                     | 说明                                        |
| ------------------------ | ------------------------------------------- |
| **不确定性显式化** | 所有需求/设计问题必须显式记录，禁止隐性假设 |
| **门禁机制**       | 不满足澄清条件时强制阻断，禁止跳过          |
| **知识累积**       | 每次开发迭代自动沉淀决策、术语、风险        |
| **可追溯性**       | 从需求 → 设计 → 代码的完整链路追踪        |

## OpenSpec 基础

aspec 构建在 OpenSpec 框架之上。理解 OpenSpec 的设计理念和核心工件是使用 aspec 的基础。

### OpenSpec 设计理念

OpenSpec 是**规范驱动开发框架**，核心理念是：

- **可追溯性**：从需求到设计到代码的完整链路追踪
- **知识沉淀**：开发过程中的决策、术语、风险自动积累为可复用知识
- **结构化管理**：需求、设计、决策以统一格式管理，消除信息孤岛

### OpenSpec 核心工件

```
openspec/
├── config.yaml                          # 配置文件（门禁规则、状态机、知识库索引）
├── taxonomy/                            # 问题分类学
│   ├── requirement-issue-taxonomy.md    #   需求问题分类学（6 维度 × 3 子类）
│   └── design-issue-taxonomy.md         #   技术设计问题分类学（7 维度 × 3 子类）
├── issues/                              # 问题跟踪模板
│   ├── requirement-issues.md            #   需求澄清问题记录
│   ├── design-issues.md                 #   设计澄清问题记录
│   └── retrospective-notes.md           #   实施观察笔记
├── procedures/                          # 流程规范
│   ├── requirement-clarification-flow.md    #   需求澄清流程
│   ├── design-clarification-flow.md         #   设计澄清流程
│   ├── interactive-clarification-protocol.md #  交互式澄清协议
│   └── evolution-system.md                  #   知识进化体系
└── evolution/                           # 知识进化
    ├── adr.md                           #   架构决策记录 (ADR)
    ├── glossary.md                      #   领域术语表
    └── risk-map.md                      #   风险图谱
```

**问题分类学** 是 aspec 澄清机制的核心驱动力：

- **需求问题分类学**（6 维度）：功能完整性、数据关切、用户体验、边界与异常、集成与依赖、优先级与范围
- **技术设计问题分类学**（7 维度）：架构决策、技术选型、接口设计、数据与状态、安全合规、性能可靠性、部署运维

每个维度下设 3 个子类，配有"症状"（识别信号）和"检查点"（具体追问），确保问题识别的系统性和完整性。

**知识进化** 是三层累积体系：

- **Layer A**（每次 archive 立即更新）：ADR 决策账本、领域术语表、风险图谱
- **Layer B**（累积 3+ 复盘后触发）：问题分类学优化、任务模板优化
- **Layer C**（长期积累）：跨项目模式识别

## 开发流程

对用户而言，aspec 的完整开发流程只有**三个命令**：

```
/opsx:proposal  ──→  /opsx:apply  ──→  /opsx:archive
  创建提案              代码实现            归档复盘
```

### `/opsx:proposal` — 创建提案

**输入**：需求文档、可选调研文档

**输出**：

- `spec/requirement-issues.md` — 需求澄清文档
- `spec/proposal.md` — 需求提案
- `spec/design-issues.md` — 技术澄清文档
- `spec/design.md` — 技术设计
- `spec/tasks.md` — 实施任务计划

**执行流程**（包含两类澄清）：

```
┌─────────────────────────────────────────────────────────────────────┐
│                     /opsx:proposal 执行流程                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ┌─────────────────┐                                                │
│  │ 1. 需求澄清      │  基于需求问题分类学（6 维度）扫描需求          │
│  │    门禁 ⚡        │  识别 High/Medium 问题 → 批量交互式提问        │
│  └────────┬────────┘  产出: requirement-issues.md (状态: clarified) │
│           │                                                         │
│           ▼                                                         │
│  ┌─────────────────┐                                                │
│  │ 2. 创建提案      │  基于澄清后的需求理解                         │
│  │                  │  产出: proposal.md (Why / Capabilities / Impact)│
│  └────────┬────────┘                                                │
│           │                                                         │
│           ▼                                                         │
│  ┌─────────────────┐                                                │
│  │ 3. 技术澄清      │  基于技术设计问题分类学（7 维度）扫描设计       │
│  │    门禁 ⚡        │  识别设计不确定性 → 批量交互式提问              │
│  └────────┬────────┘  产出: design-issues.md (状态: clarified)      │
│           │                                                         │
│           ▼                                                         │
│  ┌─────────────────┐                                                │
│  │ 4. 确定技术方案   │  基于澄清后的设计决策                         │
│  │    和 task       │  产出: design.md + tasks.md                    │
│  └─────────────────┘                                                │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**门禁机制**：

- **需求澄清门禁**：`requirement-issues.md` 状态必须为 `clarified` 后才能创建提案
- **设计澄清门禁**：`design-issues.md` 状态必须为 `clarified` 或 `resolved` 后才能生成任务

**交互式澄清协议**：

- 所有 High/Medium 问题一次性批量提出（2-4 选项 + 自由输入）
- 支持断点恢复（用户可中途退出，下次自动续接）
- 设计澄清即使无 High/Medium 问题也会展示决策摘要请求确认

---

### `/opsx:apply` — 代码实现

**输入**：`spec/design.md` + `spec/tasks.md`

**执行方式**：

- 严格遵循 proposal 阶段的澄清决策
- 按 `tasks.md` 中的任务列表逐项执行
- 原子变更，改一步验一步
- 每完成一个任务立即标记 `- [x]`
- 记录实施观察到 `spec/retrospective-notes.md`（意外问题、好的实践、风险事件）

**产出**：

- 可运行的代码
- 更新的 `spec/tasks.md`（任务完成标记）
- 可选的 `spec/retrospective-notes.md`

---

### `/opsx:archive` — Spec 归档

**目标**：开发完成后进行 Spec 归档，复盘并推动知识库进化。

**执行流程**：

1. **生成复盘报告**：

   - 读取所有 spec 文档
   - 生成 `openspec/retrospectives/{YYYY-MM-DD}-{change-name}.md`
   - 向用户展示复盘摘要（5-8 行）
2. **Layer A — 立即更新**（每次 archive 触发）：

   - ADR 技术决策账本
   - 领域词汇表
   - 风险图谱
   - 规格演化日志
   - 效率指标
3. **Layer B — 条件触发**（累积 3+ 复盘后）：

   - 问题分类学优化（需求/设计维度演进）
   - 任务模板优化
   - 用户偏好记录

## 常见问题场景

### 场景一：新功能开发

```
/opsx:proposal 帮我实现用户积分系统
├── 需求澄清：积分获取规则？消费规则？过期策略？
├── 创建提案：proposal.md
├── 技术澄清：并发扣减方案？积分流水存储？
└── 确定方案：design.md + tasks.md

/opsx:apply
└── 按 tasks.md 逐项实现，每步验证

/opsx:archive
└── 复盘，更新 ADR、术语表、风险图谱
```

### 场景二：Bug 修复

```
/opsx:proposal  修复订单金额计算错误的 bug（轻量版，bug 修复通常问题较少）
├── 需求澄清：复现条件？影响范围？
├── 提案：修复方案
├── 技术澄清：根因分析确认
└── tasks.md（通常 1-2 个任务）

/opsx:apply
└── 修复 + 回归测试

/opsx:archive
└── 轻量复盘，更新 risk-map.md
```

### 场景三：架构重构

```
/opsx:proposal  将单体架构拆分为微服务（完整版，大量澄清）
├── 需求澄清：服务边界？数据一致性策略？迁移策略？
├── 提案：拆分方案
├── 技术澄清：通信协议？分布式事务？降级策略？
└── 分阶段 tasks.md

/opsx:apply
└── 分阶段实施，每阶段验证

/opsx:archive
└── 深度复盘，大量知识库更新
```

## 最佳实践

### 应该做的

1. **严格遵守门禁**：不跳过澄清阶段，不满足条件时强制阻断
2. **显式记录决策**：所有技术决策记录四要素（选什么、为什么、备选、为何放弃）
3. **及时标记完成**：每完成一个任务立即用 `- [x]` 标记
4. **轻量观察记录**：实施中遇到的问题随手记录到 retrospective-notes.md
5. **定期复盘**：archive 时认真完成复盘，推动知识库进化

### 避免的

1. **跳过澄清**："先做了再说" → 大概率返工
2. **隐性假设**：不明确记录问题 → 后续争议
3. **一次性大改**：多个任务攒到最后一起验证 → 难以定位问题
4. **不复盘**：archive 只归档不复盘 → 知识无法累积

## 快速开始

```bash
# 1. 进入项目目录
mkdir my-project && cd my-project

# 2. 初始化 aspec 工作流
ace spec init

# 3. 启动 Claude Code，使用三个命令驱动开发
/opsx:proposal    # 创建提案（含需求澄清 + 技术澄清）
/opsx:apply       # 按方案实施代码
/opsx:archive     # 归档复盘，沉淀知识
```

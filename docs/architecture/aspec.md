# aspec — 寄生模式增强型 OpenSpec

> **ace-spec** (简称 aspec) 是 ACE 的规范驱动开发工作流，采用"寄生模式"在 OpenSpec 基础上增强需求澄清和设计决策机制。

---

## 设计理念与哲学

### 核心洞察

```
跳过澄清 = AI 基于假设实施 = 大概率返工
```

传统开发流程中，AI 在需求不明确时往往基于假设直接编码，导致：

- 需求理解偏差 → 代码与预期不符
- 设计决策未经确认 → 返工修改成本高
- 隐性约束未显式化 → 边界条件遗漏

aspec 通过在关键阶段注入**前置检查**和**交互式澄清**，强制将不确定性显式化，避免基于假设的实施。

### 寄生模式 (Parasitic Pattern)

```
┌──────────────────────────────────────────────┐
│              寄生模式架构                      │
├──────────────────────────────────────────────┤
│                                              │
│   OpenSpec CLI（schema + templates）          │
│        ↕ context / rules 注入                │
│   aspec 增强（config.yaml）                   │
│   ┌────────────┐  ┌────────────┐             │
│   │ 需求澄清    │  │ 设计澄清    │             │
│   │ + 对齐确认  │  │ + 对齐确认  │             │
│   └────────────┘  └────────────┘             │
│   ┌────────────┐  ┌────────────┐             │
│   │ 惊讶测试    │  │ 知识进化    │             │
│   └────────────┘  └────────────┘             │
│                                              │
└──────────────────────────────────────────────┘
```

**寄生模式特点**：

- **不改变底层 schema**：通过 config.yaml 的 context 和 rules 字段注入，不修改 OpenSpec 本身
- **门禁机制**：需求澄清 + 对齐确认 → proposal；设计澄清 + 对齐确认 → design；用户审批 → tasks
- **知识累积**：每次 apply 完成后自动复盘，沉淀经验到 experience.md

### 核心原则

| 原则                     | 说明                                        |
| ------------------------ | ------------------------------------------- |
| **不确定性显式化** | 所有需求/设计问题必须显式记录，禁止隐性假设 |
| **门禁机制**       | 不满足澄清条件时强制阻断，禁止跳过          |
| **知识累积**       | 每次开发迭代自动沉淀决策、术语、风险        |
| **可追溯性**       | 从需求 → 设计 → 代码的完整链路追踪        |

## OpenSpec 基础

aspec 构建在 OpenSpec 框架之上。理解 OpenSpec 的设计理念和核心工件是使用 aspec 的基础。

### OpenSpec 设计理念

OpenSpec 是**规范驱动开发框架**，核心理念是：

- **可追溯性**：从需求到设计到代码的完整链路追踪
- **知识沉淀**：开发过程中的决策、术语、风险自动积累为可复用知识
- **结构化管理**：需求、设计、决策以统一格式管理，消除信息孤岛

### aspec 模板文件（3 文件，0 子目录）

```
openspec/
├── config.yaml              # 中枢配置（context 注入流程/约束/协议，rules 注入阶段门禁）
├── dimensions.md            # 澄清维度（需求 6 维 + 设计 7 维 + 项目已知盲区）
└── experience-template.md   # 项目经验库（技术决策/领域词汇/风险图谱/复盘记录）
```

**澄清维度**（dimensions.md）：

- **需求维度**：功能完整性 | 数据关切 | 用户体验 | 边界异常 | 集成依赖 | 优先级范围
- **设计维度**：架构决策 | 技术选型 | 接口设计 | 数据状态 | 安全合规 | 性能可靠性 | 部署运维
- 维度作为参考而非约束，AI 可自主探索新的不确定性
- **项目已知盲区**：由知识进化自动维护，澄清时优先检查

**知识进化**（experience-template.md）：

- **技术决策 (ADR)**：选择 + 理由 + 备选方案 + 状态
- **领域词汇**：定义 + 首次出现
- **风险图谱**：代码热点 + 问题模式
- **复盘记录**：每次 apply 完成后追加
- **生命周期**：提取 → 存储 → 主动应用 → 验证 → 收敛

## 开发流程

对用户而言，aspec 的完整开发流程只有**三个命令**：

```
/opsx:proposal  ──→  /opsx:apply  ──→  /opsx:archive
  创建提案              代码实现            归档收敛
```

### `/opsx:proposal` — 创建提案

**流程**：
```
explore → [需求澄清 → 对齐确认] → proposal → specs
       → [设计澄清 → 对齐确认] → design.md → [用户审批] → tasks
```

**澄清与对齐协议**（需求和设计阶段共用）：

1. **步骤一：澄清** — 读取 dimensions.md 参考维度和盲区，自主探索不确定性，通过 AskUserQuestion 批量提问
2. **步骤二：对齐确认** — AI 用 markdown 呈现 4 要素（我的理解/计划方向/关键假设/完成标准），再通过 AskUserQuestion 让用户确认

**门禁条件**：

| 阶段 | 前置条件 |
|------|----------|
| proposal | 需求澄清完成 + 对齐确认通过 |
| design.md | 设计澄清完成 + 对齐确认通过 |
| tasks | 用户审批 design.md |

**通用原则：惊讶测试** — 替用户做选择时，如果用户此刻看到该决策会惊讶 → 暂停，展示选项等待确认。

---

### `/opsx:apply` — 代码实现

**执行方式**：
- 实施前读取所有澄清决策（requirement-issues.md、design-issues.md）
- 按 `tasks.md` 逐项执行，原子变更，改一步验一步
- 新问题暂停评估，记录到 `spec/notes.md`
- Spec-Code 一致性：偏差须记录理由

**apply 完成后 — 复盘与知识进化**：
1. 回顾实施过程，按 experience-template.md 结构追加复盘
2. 提取知识更新 experience.md（技术决策/术语/风险）
3. 漏检问题更新 dimensions.md 盲区段
4. 展示摘要供用户确认

---

### `/opsx:archive` — Spec 归档

**目标**：归档 spec 并执行知识收敛检查。

**执行流程**：
1. 执行 OpenSpec 标准归档
2. **收敛检查**：experience.md 条目超阈值时提议合并/淘汰（需用户确认）

> 注：复盘和知识提取已在 apply 阶段完成，archive 专注于归档和收敛。

## 常见问题场景

### 场景一：新功能开发

```
/opsx:proposal 帮我实现用户积分系统
├── 需求澄清：积分获取规则？消费规则？过期策略？
├── 创建提案：proposal.md
├── 技术澄清：并发扣减方案？积分流水存储？
└── 确定方案：design.md + tasks.md

/opsx:apply
└── 按 tasks.md 逐项实现，每步验证

/opsx:archive
└── 复盘（apply 阶段已完成），archive 执行收敛检查
```

### 场景二：Bug 修复

```
/opsx:proposal  修复订单金额计算错误的 bug（轻量版，bug 修复通常问题较少）
├── 需求澄清：复现条件？影响范围？
├── 提案：修复方案
├── 技术澄清：根因分析确认
└── tasks.md（通常 1-2 个任务）

/opsx:apply
└── 修复 + 回归测试

/opsx:archive
└── 轻量复盘，更新 experience.md
```

### 场景三：架构重构

```
/opsx:proposal  将单体架构拆分为微服务（完整版，大量澄清）
├── 需求澄清：服务边界？数据一致性策略？迁移策略？
├── 提案：拆分方案
├── 技术澄清：通信协议？分布式事务？降级策略？
└── 分阶段 tasks.md

/opsx:apply
└── 分阶段实施，每阶段验证

/opsx:archive
└── 深度复盘，大量经验库更新
```

## 最佳实践

### 应该做的

1. **严格遵守门禁**：不跳过澄清阶段，不满足条件时强制阻断
2. **显式记录决策**：所有技术决策记录四要素（选什么、为什么、备选、为何放弃）
3. **及时标记完成**：每完成一个任务立即用 `- [x]` 标记
4. **轻量观察记录**：实施中遇到的问题随手记录到 spec/notes.md
5. **定期复盘**：archive 时认真完成复盘，推动知识库进化

### 避免的

1. **跳过澄清**："先做了再说" → 大概率返工
2. **隐性假设**：不明确记录问题 → 后续争议
3. **一次性大改**：多个任务攒到最后一起验证 → 难以定位问题
4. **不复盘**：archive 只归档不复盘 → 知识无法累积

## 快速开始

```bash
# 1. 进入项目目录
mkdir my-project && cd my-project

# 2. 初始化 aspec 工作流
ace spec init

# 3. 启动 Claude Code，使用三个命令驱动开发
/opsx:proposal    # 创建提案（含需求澄清 + 技术澄清）
/opsx:apply       # 按方案实施代码
/opsx:archive     # 归档复盘，沉淀知识
```

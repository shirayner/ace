# 变异复验方法论：并发编辑期的可归因判据

**用途**：任何 Agent 在本仓做变异验证（mutation testing）前先读本文。并发编辑期间，基于全仓快照的变异复验默认**不可归因**——本文给出使其可归因的最小前置条件与实现。

**来源**：本任务中同一缺陷连续发作二十五次（§0）。前三次是我自己的变异复验把并发编辑的中间状态当成了变异效果；第 4–7 次来自其他 Agent 的实测。前五次根因相同——**单次观测直接当结论**；第六次的现象为真而**归因为假**；第七次发生在**忠实执行本文判据的过程中**，证明执行判据不能保证判据前提成立。**第 8–17 次不是使用者用错，是判据自身的缺陷**——判据集合漏了一项竞争解释、判据实现有恒绿盲区、验证判据所用的度量自己未被验证、验证只覆盖了一个方向、证据本身会随时间消失、度量分辨力与变异族不匹配、自证探针从未执行、门禁自身空转、判据作用域小于使用者的实际动作、观测方不在自己的观测模型里；它们只能由审判据本身发现，且**十次全部以成功退出**。第 18 次归第六次那一族（归因为假），但形态是新的：**扫描本身完整有效，扫的却不是那根轴**。第 19 次是**测量装置自己的动静与被测现象落在同一个聚合数字上**；第 20 次是**同一个竞态在一处自曝为红、在另一处静默空转**；第 21 次是**修复正确而修复所依据的归因是错的**。**第 22–25 次是同一次调查的四段，演示一个正确的机制发现如何被自己的实现连续四次几乎毁掉**：解析器把「读不懂」印成 `false`（且方向朝着已有结论）、我把「不在快照里」写成「原理上取不到」、归属键的作用域比证据窄、归属键的时刻比证据晚。**四段里只有一段是关于世界的，其余三段都是关于实现的，而它们全部以「看起来是结论」的形式输出。** 没有一次是「变异做错了」。

## 核心命题：杀死与存活是不对称的证据

> **杀死**是**阳性**证据：有测试红了，且失败测试名可归因。
> **存活**是**阴性**证据，有三个与「约束无保护」竞争的非缺陷解释——
> **(a)** 变异没真正落地（no-op / needle 不匹配）；
> **(b)** 变异落在死代码或不可达分支上；
> **(c)** 本该杀死它的测试**没有运行**（skip / 注册期门禁被同一变异一并关掉）。
> 因此**存活结论必须额外排除 (a)(b)(c) 才能成立，而杀死结论不需要**。

这条命题统起本文全部判据，也解释了为什么它们全部只服务于存活方向：

| 判据 | 排除的竞争解释 |
|---|---|
| §1 同快照配对判定 | 「测试自己红」——这是杀死方向的伪阳性，反向保护 |
| §2 D1 mtime / D3 半成品前置 | 「靶点被并发改了、覆盖尚未接上」 |
| §2 D5 可复现性 | 「读数本身是单次波动」 |
| §2 D7 窗口同一性 | 「多轮读数跨越了源码变更，测的不是同一个程序」 |
| §3 needle 自检 + 前后内容比对 | **(a)** 变异未落地 |
| 人读代码判可达性 | **(b)** 死代码 / 不可达分支 |
| §1 配对判定**同时比对 skipped 计数** | **(c)** 该杀它的测试没跑 |

**(b) 只能由人读代码判断，没有机械判据。** 本任务的范例：M5/M6/M9/M12 四项存活变异被定性为「门禁结构上不可达，非行为缺陷」——即变异改的分支在任何合法调用序列下都进不去。这类**应留绊线（结构断言）而非补行为测试**，把它们当作「测试缺口」去补，补出来的会是永远为真的空转测试，正是本轮在审计的那一类。

**(c) 是本任务第三次同形态发作（F1 / F2 / F10）后才补进来的**，它在观测面上与真存活**完全同形**。实测（`node:test`，注册期 `{skip}`）：

```text
control（门禁开，未变异）        pass 1  fail 0  skipped 0   exit 0
变异被杀（门禁开，变异存在）     pass 0  fail 1  skipped 0   exit 1   not ok: <测试名>
变异同时关掉门禁（假 skip）      pass 0  fail 0  skipped 1   exit 0   not ok: (无)
```

第三行**退出码为 0，失败测试名集合为空**——集合差归因得到空集，与「变异存活」逐字节同读数。所以 §1 的名字集合差**不足以**排除 (c)：它只看 `not ok`，而假 skip 根本不产生 `not ok`。

> **假 skip 比假 pass 更难发现，因为 skip 在报告里看起来像一个诚实的状态。** 假 pass 是一句可疑的断言，读者会去看它断言了什么；假 skip 是一句自称「本环境不适用」的说明，读者会认为已被负责任地处理。本任务在同一位置形态上发作三次（F1 CI 全红、F2 第二处假 skip、F10 `ACE_REQUIRE_STUB_BACKEND` 读法），三次都不是有人写错断言，而是**门禁的启用条件本身没有被任何测试校验**——即「声明了却无人校验」在门禁层的形态。

**机械判据（可加进配对判定，无需读代码）**：control 与 mutant 的 `skipped` 计数必须相等。不等 ⇒ 本次变异动了测试的**启用条件**而非被测行为，读数作废，不得记为存活。**(c) 与 (a) 都能被机械排除**（(a) 靠 needle 自检，见 §3），只有 (b) 必须由人读代码——所以 (a)(c) 没有理由不做。

**方向上的危险不对称**：漏排除 (a)/(b)/(c) 会把「无保护」误报成「有保护」——**高估测试保护力**。反向的错误（把有保护误报成无保护）只会浪费一次补测试的工。所以判据的严格性全部押在存活方向上。(c) 在这条不对称上最险：它连「有测试在管这件事」这个前提都是假的，而报告上只显示一个看起来负责任的 `skipped`。

**同族但不同轴的第二条命题：§2 D6 MECHANISM。** 本命题讲**证据强度的方向**（同一现象能支撑多强的结论），D6 讲**因果与相关的区别**（现象为真时，写下的机制是否成立）。两者的危险方向一致——写进报告的假机制，和被高估的保护力一样，都让系统显得比实际更被理解。

**全部判据共同的隐含前提：§2 D7 WINDOW INTEGRITY。** 上表每一格都默认「被测对象在测量期间是同一个程序」。该前提不成立时，本文其余判据全部同时失效，且失效方式看不出来——所以 D7 不是第七条并列判据，是前六条的前提条件。

**为什么这些判据必须存在**：变异验证的结论形如「若源码改成 X，测试仍全绿 ⇒ 该约束无保护」，它依赖一个隐含前提——**测试结果的差异只由我的变异引起**。并发编辑打破该前提，于是结论无效但看起来完全正常。这是「声明了却无人校验」缺陷类在**验证工具层**的形态：变异验证本身需要被验证。

第 8–17 次是**判据自身的缺陷**，不是使用者用错：第 8 次是判据集合缺了一项竞争解释（存活方向只列了 (a)(b)），第 9 次是某条判据的实现有恒绿盲区，第 10 次是**用于验证判据的度量自己未被验证**，第 11 次是**验证做了但只覆盖了一个方向**，第 12 次是**证据本身会随时间消失**，第 13 次是**度量的分辨力与它要服务的变异族不匹配**，第 14 次是**自证探针从未真正执行**，第 15 次是**门禁自身空转**，第 16 次是**判据的作用域小于使用者的实际动作**，第 17 次是**观测方不在自己的观测模型里**。**这十次的存在方式与前七次不同**——前七次由跑测量发现，这十次只能由**审判据本身**发现，测量再多都不会暴露：一个恒绿的探测器在每一轮都表现正常。这也是 §5 自证节存在的全部理由。

第 13–16 次有一个共同的新形态，值得单独指出：**它们全部落在「验证工具」这一层，且全部以成功退出**。第 13 次的自检报 no-op、第 14 次的探针不触发、第 15 次的门禁零匹配、第 16 次的报告并列两档不同有效性的结论——**没有一次是断言失败**。这正是本文第一节那条不对称在工具层的推论：**阴性结论（「没问题」「无变化」「不适用」）的伪造只需要一个不执行，而阳性结论必须真的发生。**

第 17 次是这一族里唯一的**阳性**误读，也正因此它值得单列。前面每一格都是把「没发生」读成了「验过了」；这一格相反——**信号确实存在，写入确实发生了，只是发出信号的是观测方自己**。它说明恒绿不是这层的唯一失效模式：**一个把自己的动作计入环境的观测者，会读到一个持续为真的阳性信号，而这个信号完全不携带关于环境的信息。** 恒绿探测器让人漏掉真缺陷，自反探测器让人确认不存在的缺陷；两者都不会有任何一次断言失败。

第 18 次单独说明，因为它是**第六次（机制为假）的一个新形态，而且是这份表里最容易自我说服的一格**：前面每一格的错误都发生在「只做了一次观测」或「工具有盲区」，这一格**做了 12 次观测、跨了 4 个档位、覆盖了边界两侧**，方法上看不出任何毛病——错的是自变量。**「跨边界扫过了、两侧一致」这句话在自变量错的情况下依然为真**，而它读起来与一次成功的排除完全一样。抓住它的是那个极端档（0ms 也是 0），不是轮次数。**加轮次不能纠正扫错的轴，这与「提高采样频率不能关闭改了又改回」是同一个道理：量变治不了方向错。**

第 19 次与第 17 次同根而落点不同，所以单列。第 17 次是观测方的写入被**误读成别人的**；第 19 次是观测方的写入**变成了一个红**，而那个红被摆进了统计口径。读数是：

```text

full 4  RED    ✖ tests/dispatch-stream-completeness.test.mjs ← 别的 Agent 正在半写这个文件
```

`SKILL_MD` = 6 KiB = 6144，`SKILL.md` = 6125，**余量 19 B**（已核盘：`lib/budgets.mjs:16` 与 `wc -c`）。追加 21 B 即越界——**门禁是对的，越界的是探针**。

要命的是形状：`green 6 / red 2 of 8` 与先前测到的 ghost flake 率 ~1/8 **同一数量级**。若只报这个比例，它会被读成「flake 仍在」，而真相是那个 flake 一次都没出现。

救下这一格的是 `probe-fullsuite-flake.cjs` 里那段**按断言名分类而非只计数**的代码（`artifacts/probe-fullsuite-flake.cjs:26-33`：先匹配 `late bytes must still be captured`，再匹配 `past the … ms ceiling`，都不中才回落到通用 `✖` 抓取，并在收尾按 `tally` 逐类打印）。它与 §3 里救命的 `assert.ok(assignments > 0)` 同族：**都是在数字旁边留一个「这个数字由什么构成」的字段。** 注意它成立的条件——**分类必须先于聚合写下来**，事后拿着一个 `2/8` 回去分类已经无从下手，日志早就滚掉了。这也是「凡是靠读者记住才成立的前提，都要变成读数自带的字段」（§7）的第三处独立收敛。

第 20 次是这份表里**唯一一个「同一个根因在两处可见性不同」**的格子，而更贵的那一处更安静。同一个竞态（kill 抢在 stub 的 spawn-out 之前）在 `raw_bytes > 0` 那条断言上表现为**红**——1/8 的概率，吵闹、被追查、最终被修；在隔壁 grace 测试里表现为**全绿**：没有 writer 持有管道，`'close'` 立刻到达，于是 `timed_out` 为真、reason 正确、elapsed 远低于上界，**每个断言都通过而什么都没测**。

> **红是自曝的，空转不是。** 一个竞态若同时污染两处，被发现的一定是有断言会红的那处；另一处会以「一直是绿的」的形式留下来，而它的代价更高——红最终会被修，空转会被当成覆盖面。

盘上的修法值得记录，因为它比「把参数调对」更进一层（`tests/dispatch-stream-completeness.test.mjs`）：`measureDetachLatency()` 实测 5 次取 max，`safeTimeoutMs() = 3 * max + 200`（`:203-232`）；**两个调用点都改用派生值**（`:321`、`:372`），并且在 grace 测试补了下界断言把空转形态关死（`:396-399`）：

```js
assert.ok(
  elapsed >= CLOSE_GRACE_MS,
  `dispatch settled in ${elapsed} ms, under the ${CLOSE_GRACE_MS} ms grace budget: nothing held the pipe, so the budget was never exercised`,
);
```

三点是被要求之外做的，且每一点都对应本文的一条判据：**（a）** 余量取观测最大值的倍数而非固定常数，理由写在 `:196-199`——「五个样本无法界定进程创建分布在负载机器上的尾部」，即**不把一次采样的极值当成分布的上界**；**（b）** 测量对象从「整次 dispatch」换成「stub 父进程自身的 spawn→exit」，因为 `ACE_GHOST_DELAY_MS: 0` 会让 writer 的工作与父进程退出重叠、采到低至 76 ms 的样本，**从而给出一个低于被测竞态区间的 deadline，把它本要消除的 flake 又装回去**（`:190-194`）——这是第 13 格「度量选错」的一个正面修复实例；**（c）** 上界断言绑 `CLOSE_GRACE_MS` 常量而非硬编码数字（`:324`、`:351`），杜绝跨层漂移。

**而 team-lead 自曝的那条错误建议，其价值在这一格里不低于修复本身**：它曾建议把 `raw_bytes > 0` 挪进 grace 测试，理由是「那里 writer 必然存在」。这是错的——那里 `ACE_GHOST_DELAY_MS = timeoutMs + CLOSE_GRACE_MS + 4000`（`:373`），writer 活过整个 grace 窗口，late bytes 永不落盘，`raw_bytes` 恒 0。

> **「writer 存在」与「writer 的字节落在观测窗口内」是两个命题**，前者不蕴含后者。把它们当成一件事，等于把「被测对象存在」当成「被测对象产生了读数」——而这正是 D7 `--run` 里 `WINDOW INTACT, BUT THE RUN FAILED` 那个分支要拦的东西（树静止得完美，读数为空）。同一个混淆在两个完全不同的层面上出现过。

第 21 次是这份表里**唯一一格「修复正确、而修复所依据的归因是错的」**，所以它与前二十格都不同：前面每一格错的都是结论，这一格结论对、动作对、代码对，**只有理由错**。而理由会被下一个人引用。

被否证的归因是「整次 dispatch 计时会让 writer 的工作与 parent 的退出重叠，所以采到 76ms」。检验它的排布不是各自再测一遍——两个数出自不同时段、不同负载，比它们无法分离原因——而是**把两种测法在同一个二进制、同一段时间里交替跑**。隔离副本（stub 现场 `gcc -O0` 编译到 tmpdir，仓库不动）：

```text
第一步 同测法交替自对照        A 191-315   B 201-315        ← 跨了双方两个区间，先动摇「差异来自测法」
第二步 delay=1000 vs delay=0   中位 223  vs  中位 219        ← 几乎重合：delay=0 本身不产生低值
第三步 整次 dispatch vs parent-only（delay=0，交替）
        整次 dispatch   342 370 390 365 374 387 370 374     中位 374
        parent-only     181 191 214 180 181 190 185 273     中位 190
```

**整次 dispatch 一贯地高于 parent-only，不是低于。** 归因的方向是反的：76ms 不可能出自「测整体」。

第三步逼出唯一剩下的竞争解释——低值来自 dispatch **被 kill 后提前返回**，即读数其实是 `timeoutMs`。扫它：

```text
timeoutMs=   50   整次 dispatch elapsed:  88  74  78  90
timeoutMs=   76   整次 dispatch elapsed: 102 105 104 107
timeoutMs=  150   整次 dispatch elapsed: 186 183 182 186
timeoutMs=60000   整次 dispatch elapsed: 414 395 401 396
```

读数随 `timeoutMs` **线性走**。76ms 那类样本测的既不是 spawn 也不是 writer，而是**当时那个 `timeoutMs` 自己**。

> **判据：校准量不得依赖被校准量。** 用「一次会被 `timeoutMs` 截断的整体计时」去推 `timeoutMs`，构成一个自我实现的读数——它总会返回一个略大于当前 `timeoutMs` 的数，因此**永远看起来自洽，且永远把 deadline 钉在竞态带里**。这一格的危险不在于数字错，在于**这个错误自带一致性**：换机器、加轮次、提高精度都不会暴露它，因为每一轮的读数都确实是那一轮测出来的。

它与第 13 格（度量选错）的区别在于**反馈方向**：第 13 格的度量是坏的但独立于被测量，多测几次仍是同一个坏读数；这一格的度量**被自己的输出驱动**，所以它对参数的每次调整都给出「配合」的响应。**独立于被测量的坏度量会一直错在同一处；被被测量驱动的坏度量会跟着你走。** 后者无法靠重复观测发现，只能靠**扫描该量的极端档**——与第 18 格的检验手段同一条（`timeoutMs=50` 与 `=60000` 相差 5 倍，读数也差 5 倍，这就是它不是常量的证据）。

顺带一处机制核实（窗口 `all-89:891c21fa1bf6`，首尾 INTACT）：`ACE_GHOST_DELAY_MS` 的 `NAP_MS` 在 `dispatch-ghost-stub.c:129`，位于 `detach_writer()`（`:124`）**之后**，而 parent 在 `:125` 就 `return` 了——**delay 根本不在 parent 的路径上**。所以「delay=0 让 writer 与 parent 退出重叠」在这个 stub 上不成立，第二步的重合是这个结构的直接后果，而不是巧合。**两种测法在机制上本就是同一件事**，这也是为什么它们不该有近两倍的系统性差异。

**这一格不要求回退任何代码。** 现行修法（`measureDetachLatency()` 直接测 parent 的 spawn→exit，`3 * max + 200`）是对的，而且**恰恰因为它不再让被校准量参与测量**——它避开了这个陷阱，只是当初避开的理由不是这个。**修复正确而理由错误，仍然要改理由**：理由是下一个人做同类决定时唯一能继承的东西，代码只告诉他做了什么，理由才告诉他为什么不能改回去。

第 22–25 次是同一次调查的四段，值得连起来读，因为它们演示了**一个正确的机制发现如何被自己的实现连续四次几乎毁掉**。

第 22 次是「朝确认方向坏掉的度量」。探针第一版按错的字段序取 reason 位，六条记录全返回 `null`，于是打印 `DATA_* : false` / `NOT distinguishable`。**「探测器读不懂日志」与「日志里没有那些位」产出同一个 `false`**，而这个 `false` 恰好确认了双方本就倾向相信的结论——我写的那句「原理上取不到」。

> **判据：任何「未检测到 X」的输出，必须先说明检测器本身是否工作。** `INCONCLUSIVE`（检测器不可用）与 `false`（检测器可用且确实没有）必须分开印，因为它们在报告上是同一个字。这条与假 skip（核心命题 (c)）、与第 15 格的门禁零匹配同根：**阴性结论的伪造只需要一个不执行。**

它比第 13 格更险的地方在于**方向**：一个随机坏掉的度量会给出与预期无关的读数，容易被察觉；一个**朝着你已经相信的方向**坏掉的度量，会被当成印证。**最难自查的度量错误，是那些确认了你原有结论的。** 这次救回来靠的是 team-lead 在探针里补的空值记账，以及原始输出还在——**这正是「分类必须先于聚合」那条判据要加的一句：原始输出必须与聚合一并留存，否则「分类先于聚合」事后无法核验。**

第 23 次是我自己的：我把「首尾采样取不到」写成了「原理上取不到」。**这是把采样器的属性说成了世界的属性。** 文件系统是第二个观察者。

> **判据：「取不到」这句话必须指明是谁取不到。** 「不在被观测对象里」只能记残余风险；「我这个采样器取不到」意味着换一个观察者可能就有答案，是可修的。把后者写成前者，会把一个待接线项永久归档成风险。

第 24 次是机制为真之后、诊断落地时的归属错误，也是这三段里唯一**会让系统看起来更安全**的一格。卷日志是**全卷**的，而探针按 basename 匹配记录：

```text
真相构造：守护面内 SKILL.md 只受纯 touch（乙，零字节）
          未采样区同名 SKILL.md 诱饵受写—还原（甲）
按 basename → 8 条记录 / 2 个 fileId / DATA_* = true → 判「甲」   ✗ 真相是乙
按 fileId   → 2 条记录 / 全 BASIC_INFO_CHANGE       → 判「乙」   ✓
```

本卷 `SKILL.md` 有 1376 个实例。守护面 89 个 basename 彼此唯一，**但唯一性必须在证据的作用域里成立，而证据来自整个卷**。

> **判据：归属键必须与证据来源同一作用域。** 全卷的证据要一个全卷唯一的键。「我的集合内没有重名」不构成归属依据——**作用域不匹配的唯一性是伪唯一性**。

第 25 次是同一句判据的另一个方向，而且它推翻了我上一段刚写下的修法：**fileId 是对的键，「现在从路径解析出的 fileId」是错的取法。** `sed -i` 写临时文件再改名覆盖，路径于是指向一个全新 inode，**新文件的诞生必带 `DATA_EXTEND|FILE_CREATE`——即使写进去的字节与原文逐字节相同**。实测（`sed -i` 模式匹配零处，字节完全未变）：按现在的 fileId 查得 6 条 `FILE_CREATE|RENAME_*`，判「甲」；按开窗时的 fileId 查得 1 条 `FILE_DELETE|CLOSE`，判非甲。

> **判据：归属键还必须与证据同期。** 第 24 格错在键的**作用域**太窄，这一格错在键的**时刻**取错。**路径与 inode 的绑定关系本身就是被观测的变化之一，用变化之后的绑定去查变化，是把答案当成了键。** 一个键要能归属证据，必须同时在作用域和时刻上与证据对齐。

抓住它的不是判据，是「三个 `TOUCHED` 文件的 reason 集合逐项相同」这个不像话的巧合——若那三处恰好各被独立编辑过，我会拿到三个看似合理的「甲」，把一个正确的 VOID 用一个错误的理由报出去。**而诊断的错误方向偏向「甲」，也就是偏向「判决是对的」，所以它不会引起怀疑**：第 22 格那条「朝确认方向坏掉的度量」在诊断层的第三次复发。

而修法自带第二个陷阱：`fs.statSync(p).ino` 走 `Number`，NTFS 的 64 位 file ID 撞上 53 位有效位，实测**静默错 1**（`…fdfc` vs 真值 `…fdfb`）。错 1 的 ID 匹配零条记录，诊断于是输出「零条 ⇒ 什么都没写」——**又一次静默空集，与第 12 格的 mtime 回扫同形**。必须 `{bigint:true}` 并零填充到 16 位十六进制。

这三段合起来还纠正了「其九」那条禁令的**根据**。我原先按「回扫 vs 快照」立禁令，实测表明真正的判别轴是**失效模式响不响**：

```text
mark == firstUsn        → exit 0，396158 条     合法空集
mark == firstUsn - 1e6  → exit 1                已滚出，响
mark == 0x1             → exit 1                响
```

**「什么都没写」= exit 0 + 零记录；「我无法判断了」= 非零退出。** mtime 回扫不可用不是因为它是回扫，而是因为它把这两者塌缩成同一个干净空集。**回扫只是静默失效最常见的形态，不是禁令本身。** 卷日志的保留期同样有界（配额 32 MB，一次全套跑消耗 1.04 MB，≈31 次跑后 mark 滚出），但界一到它就喊。

第 11 次单独值得记住，因为它是**证明与逆命题的混淆**，形态比恒绿盲区更普遍：> **控制组只在它实际检验的那个方向上有效。** 「度量稳定」不是一个命题而是两个——「有变化时值会变」（灵敏度 / 阳性方向）与「值不变时确实没变化」（恒等可信度 / 阴性方向）。前者过关不蕴含后者，**必须分别检验**。本次实测：mtime 快照的阳性方向完好（三次连采无噪声），阴性方向 65% 谎报。用阳性方向的控制组给整个度量背书，等于「证了一个命题，当成证了它的逆」。

这与核心命题同源：阳性方向便宜，阴性方向才是要防的那个。凡是要用「值没变」下结论的度量，都必须为**阴性方向**单独准备控制组。

第 10 次还多一层：它是「声明了却无人校验」递归到**第三层**。第一层是产品代码的门禁没人校验；第二层是变异验证这个校验工具本身没被验证（本文的由来）；第三层是**验证工具所依赖的度量没被验证**。每一层的失效方式都相同——看起来在工作，且失效不可见。**递归在何处停止：当一个度量的两个方向（有噪声会暴露 / 没变化需额外证据）都被控制组覆盖时。** 那是本文能给出的终点，不是无限退。

**为什么这个停点不是任意选的**（team-lead 补的论证，我核过并接受）：两个方向都被覆盖之后，该度量的错误只剩一种可能——**两个控制组被同一个原因同时骗过**。而阳性控制组问的是「有噪声吗」，阴性控制组问的是「看得见变化吗」；一个共同原因要同时满足「不引入噪声」与「不感知变化」，就只剩**度量恒定**这一种形态，**而恒定正是阴性控制组直接检验的东西**。所以第三层是自封闭的，不是递归到这里我们累了。

反过来说，这也给出了何时**必须**再递归一层的判据：**若某一层的两个控制组可以被同一原因骗过，则该层未封闭。** 本文第 13 格就是一例——size 指纹的两格控制组都能被「随机改一字节」这个共同输入骗过（随机改动几乎必然改变大小），所以那一层要再往下问一句「按真实变异族检验」。

第 3 次是最关键的一次：**控制组全绿，配对判定也无能为力**。配对能排除「测试自己红」，排不掉「修复方刚把靶点周围改了、覆盖尚未接上」。所以配对判定是必要条件，不是充分条件。

第 4、5 次的共同点是**错误方向都指向「系统比实际更健康 / 接线比实际更有问题」**：第 4 次会把真实缺口标成已覆盖（高估保护力，见核心命题），第 5 次会让人去改一段本来正确的代码。两者都是单次观测直接当结论的产物。

第 6 次是**唯一一条现象为真的**：前五条的错在读数，它的错在解释。它也是唯一一条**不能靠多跑几次挡住**的——重跑只会更确认现象存在，不会检验机制。因此 D6 要求的证据必须来自源码或最小复现，不能来自重复观测。

第 7 次是**在忠实执行 D6 的过程中发生的**：为验证第 6 次的机制而构造最小复现，正确地跑了 72 轮，读数却整体作废。它证明了一件比任何单条判据都重要的事——**执行判据不能保证判据前提成立**。前六格全都默认「被测对象在测量期间不变」，而这个前提在此之前从未被写下来。

## 1. 同快照配对判定（必要条件）

**原理**：不比较「我的变异结果」与「记忆中/几分钟前的基线」，而是同一快照复制两份——一份变异、一份不变异——**杀死只按失败测试名的集合差归因**。

绝不用 `fail > 0` 判定杀死。跨时间的测试计数比较**不可作为归因依据**。

```bash
# pair.sh <id> <relFile> <oldText> <newText>
SNAP=$ROOT/snap-$ID; MUT=$ROOT/mut-$ID
cp -r "$SRC" "$SNAP"; cp -r "$SNAP" "$MUT"      # 两份同源，MUT 从 SNAP 复制
node mutate.mjs "$MUT" "$REL" old.txt new.txt    # 只变异 MUT

fails() { cd "$1"; node --test tests/*.test.mjs 2>&1 \
  | sed -n 's/^not ok [0-9]* - //p;s/^✖ \(.*\) ([0-9.]*ms)$/\1/p' \
  | sed 's/ ([0-9.]*ms)$//' | sort -u; }

fails "$SNAP" > fc.txt        # control 的失败名集合
fails "$MUT"  > fm.txt        # mutant 的失败名集合
NEWFAILS=$(comm -13 fc.txt fm.txt)   # 只有 mutant 才有的失败 = 真正的杀死
[ -n "$NEWFAILS" ] && echo KILLED || echo SURVIVED
```

**要点**：
- `MUT` 从 `SNAP` 复制而非从源再复制一次，确保两份**逐字节同源**；从源二次复制会把期间的编辑带进来。
- 输出必须打印 control 的既有失败数。`control 有 N 个既有失败` 本身就是快照可疑的信号。
- 归因用**测试名**，不用计数。并发期用例总数持续增长，计数会被并发新增的测试搅乱。

**不要引用任何写死的基线用例数——必须自建基线。** 本任务在并发期共测到五个互不相同的时点值；任何一个被当成「应有的数」都会导致误判。基线的唯一合法来源是**同一快照的 control 组当场跑出来的那一份**。本文以下所有实测输出中的用例数均写作占位符，正是为此。

**更强的实证：失败数本身也会跨时间翻转。** 我与 docs-wiring 在 03:20 前的窗口各自读到 `fail 0`，两份读数在各自时刻都是真的；03:20 有一批代码落盘后，同一入口读到两位数的失败。**若把任一方的 `fail 0` 当作「该有的样子」，就会把一批真实失败误判为自己引入的**——而它们与谁都无关。这不是「谁读错了」，是**跨时间引用基线这个动作本身无效**，无论被引用的那次读数多么正确。

> **这一条是读者侧，另有观测者侧：见 §2 D7。** 本条讲的是引用了别人或自己几分钟前的旧读数。D7 讲的是不引用任何旧读数，而在**自己单次测量的内部**跨越了源码变更——全部读数都是「我刚才亲手跑出来的」，因此更难发现。同一个根，两个方向。

## 2. 开工前的可用性判定（`preflight.sh`）

**这一节是本文的重点**：二十五次踩坑里有两次（§0 的 1、2），仅凭「先在未变异副本上跑一遍，`fail > 0` 即整轮作废重取」就能挡住。

七个**互相独立**的探测器，因为没有任何单一探测器能挡住全部二十五次（§0 的第 8 次由核心命题 (c) 挡，第 9–14、16、17 次由 §5 自证挡，第 15 次由 §3 的门禁前提断言挡，第 18 次由 D6 的极端档检验挡，第 19 次由「聚合数字必须可拆回个体事件」挡，第 20 次由 §1 空转族的下界断言挡，第 21 次由「校准量不得依赖被校准量」+ 极端档扫描挡，都不属探测器）。D1–D4 在 `preflight.sh` 内；D5–D6 是执行纪律，D7 是包住「跑」的 runner 包装器——都无法由单次前置检查代替：D5 需要重复观测，D6 需要读源码，D7 需要先验采样函数、再在窗口**首尾各测一次**。

**D7 与其余六格不并列**：它是其余六格的前提（详见该节）。执行顺序上它包住全部：先取窗口开快照 → 跑 D1–D6 → 取窗口闭快照 → 首尾不一致则本窗口全部结论作废。

### D1 QUIESCENCE — 静默期
被测文件与 `tests/` 在最近 N 秒内有写入 ⇒ 作废。默认 N=180s。

这条挡住的是**配对判定看不见的那一类**：修复方刚改了靶点周围、覆盖还没接上，此时套件是绿的。

两个实现陷阱（都已实测）：
- **必须扫活的源码树，不能扫副本**。`cp -r` 会把所有 mtime 重写成复制时刻，使该探测器退化为恒真谎报。实测：`cp -r` 重置 mtime，`cp -a`/`cp -p` 保留。脚本内置「全部 mtime 相同 ⇒ 判为 copy-flattened 树」的反检测。
- **负数龄期要 clamp 到 0**。mtime 晚于 `date`（时钟偏移，或写入正落在扫描期间）会算出 `-1s`，若不 clamp 则被 `< 180` 误判为……实际仍会 FAIL，但报出的 `-1s ago` 会误导读者。它是「有人正在写」的最强信号。

### D2 CONTROL — 控制组先行
**未变异**副本先跑一遍，非全绿即整轮作废，不得继续往下归因。

这就是任务已记录的「控制组先行」规则用在快照层。挡住踩坑 1、2。

### D3 ORPHAN — 半成品探测
`tests/fixtures/` 下有**零引用**的 fixture ⇒ 有人正在做某项覆盖但还没接上 ⇒ 该区域的存活结论不可信。

这条是从 M24 学到的，且是**唯一**能在套件全绿时报警的探测器。实测能精确点名 `argv-echo-stub.c`（0 refs），而同期 `stub-backend.c`、`dispatch-pipeline-stub.c`、`kernel-fixtures.mjs` 均有引用。

> 该实测有时效：`argv-echo-stub.c` 在 02:47 建立时 0 refs，03:05 `dispatch-argv-integrity.test.mjs` 落地后变为 1 ref，D3 随之转 ok。**这正是探测器有效的证据**——它在「半成品」窗口内报警，窗口关闭后自动静默。复现时请另找当时的零引用文件，或人为造一个。

### D5 REPRODUCIBILITY — 跨格差异必须可复现

**单次观测不足以支撑因果。** 比较两种配置（有/无编译器、开/关某环境变量、两个平台格）时，**单跑一格一次就收尾会把偶发波动当成语义**。

实测案例（docs-wiring 验 CI 接线）：首轮「有编译器 + `ACE_REQUIRE_STUB_BACKEND='0'`」读出 `0 pass / 8 skipped`，形式上像 `'0'` 这个取值真有语义（真有的话 CI 矩阵的 windows 分支就有 bug）。加跑 23 次，**全部** `8 pass / 0 skipped` ⇒ 首轮是单次 flake。若只跑一格收尾，会让人去改一段**本来正确**的 CI 接线。

> **注意这条实测的边界**：它只证明「首轮读数不可复现，因此不是 `'0'` 的语义」。它**不**证明 flake 的成因。原始报告把成因写成「并发 sub-agent 争抢资源」，那是猜测而非实测——见 §2 D6，该猜测后被查明机制不成立。「不是 X」与「是 Y」是两个结论，D5 只支持前者。

这与 D2 是同一条规则的两个方向：
- **D2** 防「基线本来就红」——把既有失败误读为变异效果；
- **D5** 防「单次波动被当成信号」——把偶发差异误读为配置语义。

判据：任何跨格差异，在两格各复现 ≥3 次且方向一致，才算差异。并发期建议提到 10 次以上；上例用 23 次才把 flake 压成明确结论。

**但「≥3 次 / 10 次以上」这个固定数字是错的，且错的方向危险**——见下面 D5b。上面那句只适用于**高频**差异（每格必现或近乎必现）；被测事件一旦是低频的，固定次数会稳定地产出形式完整的错误结论。

### D5b SAMPLE SIZE — 对照组的样本量必须由被测事件的基础率决定

**D5 的固定次数在低频事件上失效，而失效方式是给出一个干净的因果差异。**

实测案例（本任务 §3.6.4，#20 归因）：我把「共享 stub 二进制」当自变量分两格，各跑 192 次 dispatch，读出 `load` 格 1/192、`distinct` 格 **0/192**。形式上这是一个干净的因果差异——一格有、一格没有，几乎就写成「映像共享是成因」。把两格各加到 480 次后，两者不可区分（2/1/4 对 1/4/4），**那个 0/192 是抽样运气**。该族归因至此被第四次否证，第四次是本探针自己提出的版本。

把它算出来（可执行，不是格言）。事件基础率 `p`，跑 `n` 次，**该事件完全缺席的概率是 `(1-p)^n`**：

| 基础率 | n=192 | n=480 | n=960 | 95% 信心所需 n | 99% 所需 n |
|---|---|---|---|---|---|
| 0.6% | **31.5%** | 5.6% | 0.3% | 498 | 766 |
| 0.8% | 21.4% | 2.1% | 0.0% | 373 | 574 |
| 2% | 2.1% | 0.0% | 0.0% | 149 | 228 |
| 8% | 0.0% | 0.0% | 0.0% | 36 | 56 |

（`n(1-α) = ⌈ln α / ln(1-p)⌉`。）

**最锐的一格不在表里，要单独算**：两格对照、`p=0.6%`、每格 192 次时，**「恰好一格 0、另一格 ≥1」的概率是 43.1%**——`2·(1-p)^n·(1-(1-p)^n)`。也就是说，那个「读起来像干净因果差异」的结果，**是这个实验设计下最可能的单一结局**，而不是一次罕见的坏运气。**第一轮对照的结论方向基本随机。**

**判据**：
1. 低频事件的对照，**必须先估基础率、再定 n**；`n` 至少取 `⌈ln 0.05 / ln(1-p)⌉`，即在无效假设下事件缺席概率 <5%。
2. **基础率往往正是这次调查要测的东西**——所以第一轮的作用是估率，不是判因果。用第一轮的率去定第二轮的 n，第一轮本身不出因果结论。
3. **报「某格 0 次」时必须同时报该格的 n 与该 n 下的缺席概率**。「0/192」不是证据，「0/192，此率下缺席概率 31.5%」才是一个读者能判强弱的读数——又一次「凡是靠读者记住才成立的前提，都应变成读数自带的字段」。
4. 反向同样适用：**全绿批次不是反证**。本任务另一处（§3.6.5 七）事件率约 8%，8 轮全绿的概率 51%、25 轮全绿 12.4%；先前那两批各 4 轮全绿被误读成「现象消失」，实为样本量不足。

**与 v2-review 第 18 格（扫错自变量）同族但不同轴**，team-lead 建议单列，我同意：
- 第 18 格：**自变量选错**——测了一个与结果无关的东西，得到干净的无差异；
- 本格：**样本量不足**——自变量可能选对了，但 n 撑不住结论，得到干净的有差异。

两者都产出**形式完整、过程无报错、方向确定**的错误结论，且都不会在任何一次运行的输出里露出破绽。这是它们最该被单列的理由：**没有任何一条「跑起来看看」的纪律能发现它们。**

### D6 MECHANISM — 根因机制需独立于「现象消失」的证据

前五条都在防**把噪声当信号**或**把未执行当已通过**。D6 是反方向的形态：**现象为真，归因为假**。

**判据**：任何写进报告的根因机制，必须有一条**独立于「现象消失」**的证据支持——二者取一：
- **读源码确认该机制的前提成立**（该机制若要发生，必须先有什么？那个前提在代码里真的存在吗？）；
- **构造该机制的最小复现**（人为放大该机制，现象应随之变频或变强）。

**「改了 X 之后现象没了」证明不了「现象由 X 引起」。** 低频事件在任何一次修改后都很可能「没了」——正因为它本来就大部分时候不出现。观测到消失所需的样本量，与观测到出现所需的一样大；报告里通常只给了前者一次。

#### 实测案例：一个被认错的机制

`dispatch-argv-integrity.test.mjs:99` 出现单红。原始报告的归因是「**并发编译同一 stub 二进制的资源竞争**」。走 D6 第一路——读源码查该机制的前提「两套是否真的共享编译产物」：

| | `dispatch-argv-integrity` | `stub-backend-rejection` | `dispatch-pipeline` |
|---|---|---|---|
| 源文件 | `fixtures/argv-echo-stub.c` | `fixtures/stub-backend.c` | 第三份 |
| 输出目录 | `mkdtempSync(tmpdir(), 'ace-argv-stub-')` | `mkdtempSync(tmpdir(), 'ace-stub-backend-')` | `'ace-pipeline-stub-'` |
| 输出文件名 | `claude.exe` / `claude` | `claude.exe` / `claude` | 同 |

`mkdtempSync` 每次返回**新建的唯一目录**，三套的编译输入与输出路径全不相交。**唯一相同的是文件名**——而文件名相同是 backend resolver 要求的，不构成共享：路径不同的两个 `claude.exe` 不是同一个文件。**该机制的前提不成立，归因作废。**

该机制被**三条独立证据**否证，三条都不依赖「现象是否消失」：
1. 三套 stub 的编译输入与输出目录互不相交（上表；`dispatch-pipeline.test.mjs:75` 是第三份，所以「三套争抢同一二进制」这个更宽的版本也不成立）；
2. `lib/` 与 `scripts/` 全树**零处** `tmpdir`/`mkdtemp` —— 共享面在 dispatcher 侧同样不存在；
3. `candidatePaths()`（`scripts/backend-resolve.mjs:41-42`）对显式 `ACE_CLAUDE_BIN` 直接 `yield` 并优先返回 `via: 'explicit'`，而两套测试各自传自己的 `stubBin` 且 `PATH: ''`，故解析结果不可能串到对方的二进制。

> **`readManifestIndex` 定义在 `lib/artifacts.mjs:122`，该文件 mtime 为 00:38:02，即整场并发期未被改动。** 这一点值得单独记：D7 的那次污染里，`ReferenceError: readManifestIndex is not defined` 看起来像是 `artifacts.mjs` 出了问题，实际是 `dispatch-worker.mjs`（03:45:18 被写）处于半写状态。**报错点名的文件不一定是被改的文件**——这是 D6 在诊断读数时的一个常见陷阱。

关键在于**现象本身是真的**：同进程跑两套，第 1 轮即复现 1 fail；随后同进程 14 轮 + 带两路并发竞争 10 轮，共 30 轮全绿。所以这是低频真事件，只是机制被认错了。

**该项按三档规则的当前状态（不得升格）**：
```text
现象：同进程跑两套曾复现 1 fail（约 03:0x，dispatch-argv-integrity.test.mjs:99）
成因：未查明
```
后续的 3 配置 × 24 轮尝试**整体作废**（D7，见下节），既不得读作「flake 已消失」，也不得读作「flake 已加重」——它对成因**零贡献**。任务 #20 保持在第二档，并写明**禁止因为重跑变绿就记为已解决**。

#### 为什么这一条必须单列

三步归因（单独跑、绕过自己的改动跑、复跑）能正确回答「**是不是我引入的**」，回答不了「**是什么引入的**」。但报告里写下的机制会被后来者当作已知事实继续引用——下一个人会去修一个不存在的共享二进制，而真因继续在。**假机制比没有机制更糟**：没有机制会留下一个待查问题，假机制会关闭这个问题。

它与核心命题（存活/杀死的证据不对称）同族而不同轴：核心命题讲**证据强度的方向**，D6 讲**因果与相关的区别**。危险方向一致——写进报告的假机制，和被高估的保护力一样，都让系统显得比实际更被理解。

**推论**：报告里的机制陈述必须能区分三档，不得混写。
```text
已读源码确认前提成立 / 已构造最小复现   → 写作「机制：…」
只知现象可复现，成因未查                → 写作「现象：…；成因未查」——这是合法的交付状态
成因来自推测                            → 标注「推测，未验证」，或不写
```
第二档「成因未查」是**合法**的交付状态。把它升格成第一档，才是缺陷。

#### D6 的一个特定形态：跨边界扫描两侧全同，先疑「我扫的不是那个边界」

实测案例（team-lead，#23 的归因过程）：`ghost deadline` 测试偶发 `raw_bytes == 0`，第一判断是撞 `CLOSE_GRACE_MS` 边界。于是扫延迟 `0 / 450 / 2900 / 4000 ms` 各 3 次——**`raw_bytes` 全部为 0，包括 0ms 那一档**。

```text
delay=   0ms   raw_bytes 0 0 0      ← 决定性的一档
delay= 450ms   raw_bytes 0 0 0
delay=2900ms   raw_bytes 0 0 0
delay=4000ms   raw_bytes 0 0 0
```

**「两侧读数完全相同」有两种读法，而它们在数据上不可区分**：「该边界对结果无影响」与「我扫的那个轴根本不是控制变量」。0ms 那一档把二者分开了——若延迟真是控制变量，0ms 必须与 4000ms 不同。真机制是另一根轴：ghost stub 的进程创建 → `_spawnl` 延迟实测 226–377ms，而测试在 `timeoutMs=150ms` 就 SIGKILL，**kill 常赶在 writer 被派出之前**，所以无论请求什么延迟都没有 writer 可写。

> **判据**：**一个跨边界扫描若两侧读数完全相同，首先要怀疑的不是「边界无影响」，而是「我扫的不是那个边界」。** 检验方法是取该轴的**极端档**（此处是 0）——若极端档与其余档读数一致，这根轴没有在起作用，扫描本身无效。

**这与第 13 格（size 指纹对同长度替换全族失明）同源**：都是**度量/自变量与被研究的现象不在同一根轴上**，而扫描过程一切正常、每一档都有读数、没有任何一次报错。区别在于第 13 格是**度量**选错，这一格是**自变量**选错；相同点是二者都会产出一份形式完整、内部一致、结论错误的扫描表。**「跨边界扫过了、结论一致」这句话，在自变量错的情况下依然为真。**

停在那个错误结论上的代价，正是上面「假机制」那条：#23 会被写成「`CLOSE_GRACE_MS` 与该测试无关」，而真因（测试侧的 kill/spawn 竞态）继续在。

### D7 WINDOW INTEGRITY — 测量窗口内被测对象必须同一

D1–D6 全都假设了一件从未被写下来的事：**被测对象在整个测量期间是同一个程序**。D7 把这个前提显式化。

**判据**：凡引用多轮读数，必须给出被测树在**窗口首尾**的同一性证据（mtime 或内容 hash 快照）。缺此证据 ⇒ 读数标注「窗口未验证」，不得引用。

**它与前六格都不同交**：
| | 防的是 | D7 为何不被它覆盖 |
|---|---|---|
| D1 QUIESCENCE | 开工**前**树在动 | 开工时静默，不保证跑动**期间**静默；长循环的窗口远大于 D1 的一次检查 |
| D2 CONTROL | 基线本来就红 | control 与 mutant 同源，但若二者跑在窗口两端，同源的是快照、不是被测程序 |
| D5 REPRODUCIBILITY | 单次读数当稳定 | **重复本身可能跨越源码变更**；那时重复不增加效力，只是在测不同的程序 |
| D6 MECHANISM | 机制未验证 | D6 的两条路径**都**建立在「被测对象不变」上——D7 是 D6 的前提 |

最后一行是这条判据的来由：team-lead 按 D6 第二路径（构造最小复现）跑 3 配置 × 24 轮，是 D6 的忠实执行者，**依然产出了一份全假读数**。**执行判据不能保证判据前提成立。**

#### 最危险的推论：并发写入期间的**绿**同样无效

本轮全红所以显眼。**若污染恰好落在测试文件而不是产品代码，72 轮全绿会被读作强证据，而它同样什么都没测。** 全红会让人作废重取，全绿会让人收工——所以这条判据必须在读数为绿时也照样执行，不能只在异常时才想起来查窗口。

这是 **D3 ORPHAN 的时间版本**：D3 抓「测的东西不存在」，D7 抓「测的东西不是同一个」。两者都能在套件全绿时报警，这也是它们比其余各格更值钱的原因。

#### 与 §1 的关系：同一个根，两个方向

§1 的「跨时间引用基线这个动作本身无效」是**读者侧**——引用了别人或自己几分钟前的旧读数。D7 是**观测者侧**——不引用任何旧读数，而是在自己**单次测量的内部**跨越了变更。后者更难发现，因为全部读数都是「我刚才亲手跑出来的」。

**实现**：窗口首尾各取一次快照并比对。**必须同时取 mtime 与内容 hash**——单用任何一个都有恒等盲区，理由见下节自审。

```bash
# 纳入集合的判据见下节「覆盖面」：整棵树减去 node_modules，不是目录清单。
snapshot() {
  find "$SRC" -type f -not -path '*/node_modules/*' -printf '%T@ %p\n' | sort
  find "$SRC" -type f -not -path '*/node_modules/*' -print0 | sort -z | xargs -0 md5sum
}
snapshot > win-open.txt
# … 多轮测量 …
snapshot > win-close.txt
diff win-open.txt win-close.txt || echo 'WINDOW VIOLATED: 本窗口全部读数作废，不得引用'
```

实测成本（87 文件、889 KB 的本树）：mtime 面 0.20s，hash 面 0.29s，两面合计约 0.5s。**成本不是不做的理由。**

#### D7 自审：它自己会不会恒绿

按 §5 的自证要求，D7 必须能被它自己的探测器审。**结论：判据成立，但查出六处缺陷**——两处会使它恒绿（已在上方实现中修掉）；一处覆盖面漏报（改为全树判据）；一处原判为不可消除的残余风险、后经构造改判为可结构性关闭（「其四」）；一处是**一条看似等价的替代做法必须被排除**——事后 `-newermt` 回扫会随时间静默转为恒绿（「其五」）；一处不在判据里而在**使用判据的人**身上——观测方把自己的写入读成了环境的证据（「其八」）。

**其零、先验采样函数，再用它立判据。** 这一层比下面任何一条都靠前：**在把「三次快照互异」读作「树在动」之前，必须先证明采样函数本身稳定。** 实测（team-lead 在立判据前跑的控制组，背靠背连采三次、中间无写入）：

```text
probe1 = 59bb63feed01
probe2 = 59bb63feed01
probe3 = 59bb63feed01      三连相同 ⇒ 采样函数稳定，A≠B≠C 是真写入而非采样噪声
```

这一步不是形式主义。**若三个 probe 也各不相同，那就是在用一个不稳的度量立判据**——而它照样会「抓到」污染，永远为真，是恒绿探测器的镜像形态：**恒红探测器**。两者都无信息量，且恒红更隐蔽，因为它每次都像在尽责工作。

**但稳定性控制组有一个必须补的方向：它对「瞎采样」同样通过。** 实测——把 `find` 的相对路径在错误 cwd 下执行（匹配不到任何文件），采样函数依然三连相同：

```text
错误 cwd 下三连： d41d8cd98f00 / d41d8cd98f00 / d41d8cd98f00
                  ^^^^^^^^^^^^ 这是「空输入的 md5」，不是树的指纹
随后真写入一次：  d41d8cd98f00（不变）—— 采样函数对任何变更都失明
```

`d41d8cd98f00` 是 `md5sum` 读到空输入时的常量。**一个什么都没测的采样函数，稳定性控制组给满分。** 所以自证需要两格而非一格：

| 控制组 | 问的问题 | 缺了它会怎样 |
|---|---|---|
| **稳定性**：无写入连采 N 次，值必须相同 | 采样有没有噪声？ | 噪声被读作污染 → **恒红** |
| **灵敏度**：故意改一个字节，值必须变化 | 采样看得见变化吗？ | 什么都看不见 → **恒绿** |

灵敏度那格实测（同一函数、正确 cwd）：改一字节后 `b696961c2309` → `f79f3ba1a8a5`，正确变化。**两格都过才算采样函数可用。** 这正是核心命题在工具层的复现——稳定性是阳性方向（有噪声就会暴露），灵敏度是阴性方向（「没有变化」这个结论需要额外证据），而阴性方向才是要防的那个。

> **本次的判定**：team-lead 的 `59bb63feed01` **不是**空输入常量（`d41d8cd98f00`），A/B/C 三值亦非，所以该采样函数确实在读真实文件——**其稳定性控制组结论有效**。我核对了这一点而不是默认它成立：若一个采样函数恰好落在瞎采样上，它的控制组数据看起来与有效数据完全一样，唯一的区别就是那个常量值。**记住 `d41d8cd98f00`。**

**稳定性控制组有效，但它只覆盖一个方向——这是本节最容易被误读的一句。** 「连采三次同值」证明的是：**快照不同 ⇒ 树真的变了**（排除采样噪声导致的假阳性）。而 D7 的判定用的是**逆方向**：**快照相同 ⇒ 树没变**。后者不被前者蕴含，且实测 65% 谎报（见「其二」）。

| 方向 | 命题 | 由哪个控制组证 | 本次实测 |
|---|---|---|---|
| 阳性 | 快照不同 ⇒ 树真变了 | 稳定性（无写入连采同值） | **通过**（`59bb63feed01` ×3，mtime 面无噪声） |
| **阴性** | **快照相同 ⇒ 树真没变** | **恒等可信度（改一字节 / 保留 mtime 改内容）** | **只看 mtime 时 65% 谎报** |

所以「A≠B≠C 是真写入」这个结论有效，而「该度量可支撑 D7」这个结论**不成立**——后者要的是阴性方向。**拿阳性方向的控制组给整个度量背书，就是把一个命题的证明当成它逆命题的证明。** 这条与恒绿/恒红那对镜像形态不同：那对讲的是探测器输出恒定，这条讲的是**验证覆盖不全**，探测器输出是变化的，只是变化只在一半的输入上正确。

**其零之二、指纹的分辨力必须覆盖你打算做的变异族。** 灵敏度控制组问「改一字节值会变吗」，但这个问法有个陷阱：**「一字节」是随机选的，而变异不是随机的。** docs-wiring 的 no-op 自检用**文件大小**做指纹，而 F10 的核心变异是 `=== '1'` → `!== '0'`：

```text
if (a === '1') {      17 字节   md5 7e046a041545
if (a !== '0') {      17 字节   md5 e5d406fe81fa
                      ^^^^^^^ 字节数完全相同 → size 指纹恒等 → 自检报「no-op」
```

**它的自检机制恰好对它最需要检测的那一类变异瞎。** 这不是巧合：变异测试的主力手段就是**同长度算子替换**（`===`↔`!==`、`<=`↔`>=`、`&&`↔`||`、`'1'`↔`'0'`、`>`↔`<`、`+`↔`-`），它们**按定义保持字节数**。本树实测这类替换点位共 **631 处**（`===` 299 / `!==` 98 / `&&` 100 / `||` 76 / `<=` 40 / `>=` 18，仅 `*.mjs`）——**size 指纹对整个主力变异族失明，而那正是它要服务的族**。

> **判据**：选指纹前先列出打算做的变异族，再问**这个指纹能不能区分它们**。「文件变了吗」是个泛泛的问题，答对它不等于答对「我这一族变异发生了吗」。
>
> 通用化：**一个度量的分辨力要按它的实际输入分布检验，不是按随机输入检验。** 随机改一字节几乎必然改变文件大小，所以 size 指纹能轻松通过一个用随机输入做的灵敏度控制组——**它通过的是一个与真实用途无关的检验**。这与 §0 第 11 格同源：控制组只在它实际检验的那个输入集上有效。

**其一、单一指标各有恒等盲区，且两个盲区互补。** 实测（每格独立构造，见下表「实测」列）：

| 中段发生的真实变更 | 只看 mtime | 只看内容 hash | 两面同取 | 实测 |
|---|---|---|---|---|
| 内容改了、mtime 被工具保留（`cp -p` / `touch -r` 类） | **恒等 → 谎报绿** | 差异 → 正确报红 | 正确报红 | 同长度算子替换 + `touch -r`：size 27905 = 27905、mtime 逐位相同，仅内容哈希抓到（`42483a4d050e` → `aa45a3ac9f35`） |
| 改了又改回（A → B → A），中段读数跑在 B 上 | 差异 → 正确报红 | **恒等 → 谎报绿** | 正确报红 | **已实测**（来源 team-lead）：`registry.mjs` 追加一字节后还原，`cmp` 逐字节相同，而全树 digest `9d9ef16c902a` → `32dcc1840267` |
| **纯 `touch`：一个字节都没写过** | 报红 | 报绿 | **报红 —— 而真相是没变** | **已实测**（本文作者，隔离副本）：`fs.utimesSync` 后 `--run` 判 `WINDOW VIOLATED / VOID`，两侧 `6125 / 71244ccd19586f41` 逐位恒等 |

所以**「mtime 够用，要更硬就用 hash」这个说法是错的**——两者不是强弱关系，是**互补关系**，各自漏掉对方能抓的那一类。原实现只取 mtime，落在第一行的盲区里；改成只取 hash 会落进第二行。**两面都取**才同时覆盖，这也是上方实现改动的原因。**前两行都已有实测构造，方向相反**：第一行由本文作者构造（双恒等，只有内容面能抓），第二行在真实协作中自然发生（内容恒等，只有 mtime 面能抓）。**一个方向的数据不能替另一个方向背书**——这与第 11 格是同一条。

注意第二行的判定方向：改回原样后**内容确实相同**，但**中段读数跑的是 B**，那些读数确实被污染。因此「首尾内容一致」不等于「读数有效」——这正是残余风险那一条。

**而第三行推翻了前两行合起来暗示的那条结论。** 前两行说「少取一面会谎报绿」，读者很容易把它读成「取得越多越严越好」。第三行说**两面同取会谎报红**：它不是前两行的严格加强，它引入了前两行没有的**假阳性**，代价是把一个本可引用的窗口判死。

> **判据：多指标合取不是单指标的严格加强。** 每加一面，就同时加了一类新的假阳性。所以要问的不是「够不够严」，而是**「每一面各自在回答哪个问题」**：内容 hash 回答「字节变了吗」，mtime 回答「有人写过吗」。第 17 格（自反探测器）需要的恰好是后者，所以 mtime 那一面必须留；但它**不该有权把窗口判死**。

**这条判据与第 17 格是耦合的，不能分开裁决：检出自反写入所依赖的那一面（mtime），正是会产生假阳性的那一面。** 删掉它就瞎了第 17 格，留着它就带上第三行的假阳性。

#### 第三行的两种成因必须再分开，因为它们的判决相反

team-lead 提出把这类单独印成 `TOUCHED` 而不是 `CHANGED`，理由是「`CHANGED` 这个词把读者推向与真相相反的方向」。这个改动**已落地**（`tree-snapshot.mjs:132-166`，注释里就引着 `6125 / 71244ccd19586f41` 这组读数）。但实测下来，**标签改了，判决没改**——两种成因在 `TOUCHED` 下读数完全相同，而它们该被判成不同的东西。隔离副本（`plugin/skills/auto-goal-v2` 全量 89 文件复制到临时树，仓库不受影响）：

```text
成因甲  写入后字节还原（append 21B → writeFileSync 还原）
  被守护的命令窗口中途读到  SKILL.md = 6146 B  hash=a1b6859dd9a4b6e4   ← 首尾快照都没出现过的状态
  WINDOW VIOLATED / VOID    before: 6125 …622.4531 71244ccd19586f41
                            after:  6125 …240920.4336 71244ccd19586f41

成因乙  纯 touch（fs.utimesSync，零字节写入）
  WINDOW VIOLATED / VOID    before: 6125 …240920.4336 71244ccd19586f41
                            after:  6125 …265519      71244ccd19586f41
```

**成因甲的判死是正确的,不是假阳性。** 中途读数跑在 `6146 / a1b6859dd9a4b6e4` 上——那个状态在首尾两次快照里都不存在，所以「真相是没变」只对**首尾两个时刻**成立，对**读数实际跑的那个时刻**不成立。这就是「其四」（首尾两点不足以证明中间无变更）的又一个实例。只有成因乙才是真假阳性：字节从头到尾没变过，任何时刻的读数都有效。

而**两行读数逐位相同**：`6125 / 71244ccd19586f41` 两侧恒等，甲乙无法区分。所以

> **`TOUCHED` 是个正确的标签，但它标注的是两件判决相反的事。** 「mtime 动了而字节没变」既可能是无害的 `touch`（不该判死），也可能是写—还原（必须判死，因为中途存在过第三个状态）。**区分它们所需的信息——中途是否存在过别的字节——不在被观测对象里。**

这与「其八」是同一个形状：**读数缺的那个字段不在被观测对象里。**

#### 更正：我先前把「不在快照里」写成了「原理上取不到」

这一格原文写的是「首尾采样在原理上取不到」。**前半句对，后半句错，而错法正是第 13 格。** team-lead 实测推翻了它：文件系统是第二个观察者，NTFS 每卷有变更日志，`Reason` 位直接命名变更的**种类**。我独立复核了这个机制（`.ace/` 下未采样区，`fsutil usn readjournal`，按位置取第一个 `0xNNNNNNNN:` 掩码而非按本地化标签匹配——本机标签确实是 `Ô­Òò` / `Êý¾Ý½Ø¶Ï`）：

```text
成因甲  写入后字节还原   → DATA_TRUNCATION / DATA_EXTEND|DATA_TRUNCATION   （6 条）
成因乙  纯 utimesSync    → BASIC_INFO_CHANGE                              （2 条）
逐位相同的两个首尾读数，在卷日志里判决相反。
```

**「不在被观测对象里」和「取不到」是两句不同的话，修法完全不同**：前者只能记残余风险，后者可以去取那个字段。我把采样器的属性写成了世界的属性——这是第 9 格自己那个形状（把「我的仪器读不到」当成「它不存在」）在元层面上的复发。

**但机制可取 ≠ 诊断可信。** 团队提议把甲/乙诊断接到 `--run` 的 VOID 输出里（判决不变，只多一行诊断）。我实测了这个接线的两个前提，**第一个不成立**：

**前提一（不成立）：记录归属。** 探针按 `chunk.includes(name)`（basename）匹配记录。卷日志是**全卷**的，而 basename 不是标识符。构造：守护面内的 `SKILL.md` 只受成因乙（纯 touch，零字节写入），同时在未采样区放一个同名 `SKILL.md` 诱饵受成因甲：

```text
按 basename 匹配 → 8 条记录，2 个不同 fileId，DATA_* = true → 判「甲」
                     真相是乙。诱饵的字节写入被记到了守护文件头上。
按 fileId 匹配   → 2 条记录，全部 BASIC_INFO_CHANGE，DATA_* = false → 判「乙」  正确
```

本卷 `D:` 上 `SKILL.md` 这个 basename 有 **1376** 个实例（`/d/Users/r.shi` 下，20 s 内界定），其中 23 个在本仓库内。守护面 89 个文件的 basename 彼此唯一，**但这与卷内唯一性无关**——日志匹配的是卷。**一个按 basename 归属全卷记录的诊断，会系统性地把别处的写入判到被守护的文件上，且偏向报「甲」（更严的那一侧）。**

修法现成：记录里就带 `文件 ID` / `父文件 ID`，`fsutil file queryfileid` 对路径返回同一个值（`0x…005d00000007fdfb`，与日志记录逐位相同）。**但取它有个陷阱**：

```text
fs.statSync(p).ino               = 26177172834614780   → hex 5d00000007fdfc   ✗ 差 1
fs.statSync(p,{bigint:true}).ino = 26177172834614779n  → hex 5d00000007fdfb   ✓
fsutil file queryfileid          =                        0x…005d00000007fdfb
```

NTFS 的 file ID 是 64 位，`Number` 只有 53 位有效位——默认 `ino` **静默损失精度**，这里正好错 1。而错 1 的 ID 大概率不匹配任何记录，于是诊断输出「零条记录」= 「什么都没写」，**又是一次静默失效**。所以：**用 `{bigint:true}`，并且零填充到 16 位十六进制再匹配。**

**前提二（成立，但有界）：日志保留期。** 这是关键差别，也是 team-lead 那条落点里最有价值的一半——它的失效是**响的**，不像 mtime 回扫：

```text
mark == firstUsn        → exit 0，396158 条        合法空集
mark == firstUsn - 1e6  → exit 1                   已滚出，响
mark == 0x1             → exit 1                   响
```

**「什么都没写」= exit 0 + 零记录；「我已经无法判断了」= 非零退出。** mtime 回扫把这两者塌缩成同一个干净空集，这才是它不可用的真正原因。所以「其九」那条禁令的**根据要改**：不是「回扫 vs 快照」，而是**失效模式是静默的还是响的**。回扫只是静默失效最常见的形态，不是禁令本身。

保留期实测有界但够用：配额 32 MB，一次全套跑（13.5 s）消耗 1.04 MB 日志，即 **≈31 次全套跑后 mark 滚出**。`C:` 与 `D:` 日志均已启用，`fsutil usn` 无需管理员权限。

**结论（四条，都不改判决）：**

1. 判决保持 VOID（保守，代价不对称那条仍然成立）；**代价不对称是判决的理由，不是不诊断的理由**——这两件事先前被我合在一起了，拆开它与把 `TOUCHED` 的标签和判决拆开是同一个动作。
2. 诊断可以加，但**必须按 fileId 归属，不能按 basename**；取 ID 必须走 `{bigint:true}`。按 basename 接线会把一个假阳性换成一个更难发现的误判。
3. 诊断必须自报可用性：`exit != 0` → `INCONCLUSIVE`（日志不可判），而不是 `DATA_* = false`。
4. **fileId 也不够——它必须是窗口开始时那个 fileId，不是现在从路径解析出来的那个**（第 25 格，见下）。

#### 第五个陷阱：fileId 是对的键，但「现在的 fileId」是错的取法

上面第 2 条我写完就在一次真实 VOID 上试了它，读数如下（守护面 89 文件，`--verify` 判 BROKEN，四个 `TOUCHED`）：

```text
lib/budgets.mjs                  9 rec  FILE_CREATE|DATA_EXTEND|RENAME_OLD|RENAME_NEW|DATA_TRUNCATION → 判「甲」
schemas/worker-input.schema.json 9 rec  同一组 reason                                                  → 判「甲」
scripts/ingest-audit.mjs         9 rec  同一组 reason                                                  → 判「甲」
SKILL.md                         4 rec  BASIC_INFO_CHANGE                                              → 判「乙」
```

**三个文件的 reason 集合逐项相同、且都含 `FILE_CREATE` / `RENAME_*`**——这不像三次独立的内容编辑。查记录里的文件名字段，答案是 `sedmdBsXw`：一个 `sed -i` 的临时文件。而那三个文件正是我自己刚才用 `sed -i` 扫版本号时碰过的（`SKILL.md` 不同，它是别处的纯 touch）。构造最小复现：

```text
sed -i 's/NO_SUCH_PATTERN/x/' t.md        ← 模式匹配零处，字节完全没变
  bytes identical : true
  fileId before   : 0349000000303f76
  fileId after    : 004c0000002530b3     ← 不是同一个文件了
  按「现在的 fileId」查 → 6 rec  FILE_CREATE|DATA_EXTEND|RENAME_OLD|RENAME_NEW  DATA_* = true  → 判「甲」  ✗
  按「窗口开始时的 fileId」查 → 1 rec  0x80000200(FILE_DELETE|CLOSE)          DATA_* = false → 不是甲   ✓
```

**`sed -i` 不是原地编辑，它写一个临时文件再改名覆盖。** 于是路径指向一个全新的 inode，而**新文件的诞生必然带 `DATA_EXTEND|FILE_CREATE`**——即使写进去的字节与原文逐字节相同。按「现在的 fileId」查，任何 rename-based 的写入（`sed -i`、`git checkout`、多数编辑器的原子保存、`writeFileSync` 到临时文件再 `renameSync`）都会被判成「甲：中途有别的字节」。

> **判据：归属键必须与它要归属的那段时间同期。** fileId 是正确的键（它在卷这个作用域里唯一），但**「现在从路径解析出的 fileId」回答的是「此刻这个路径是谁」，而窗口要问的是「窗口开始时那个对象后来怎么了」**。路径与 inode 的绑定关系本身就是被观测的变化之一，**用变化之后的绑定去查变化，是把答案当成了键**。

这一格与第 24 格是同一句判据的两个方向：第 24 格错在键的**作用域**太窄（basename 在卷里不唯一），这一格错在键的**时刻**取错（fileId 在窗口两端不是同一个）。**一个键要能归属证据，必须同时在作用域和时刻上与证据对齐。**

实现后果：快照必须**在开窗时就记下每个文件的 fileId**（`{bigint:true}`），闭窗诊断用记下的那个查，并把「fileId 变了」本身作为一条独立结论印出来——**它恰恰是 rename-based 写入的正面证据，比 reason 位更直接**。反过来说，`TOUCHED` 里若 fileId 未变而 reason 只有 `BASIC_INFO_CHANGE`，那才是干净的「乙」。

顺带一条：**这次抓住它的不是判据，是「三个文件读数逐项相同」这个不像话的巧合。** 若那三个文件恰好各被独立编辑过，我会拿到三个看似合理的「甲」，然后把一个正确的 VOID 用一个错误的理由报出去——**诊断的错误方向偏向「甲」，也就是偏向「判决是对的」**，所以它不会引起怀疑。这是第 22 格「朝确认方向坏掉的度量」在诊断层的复发，第三次。

原残余风险结论**作废**：这一格不再是「原理上取不到」的残余风险，而是**一个有明确修法、且修法自身带三个静默陷阱（basename 归属、`Number` 精度、fileId 时刻）的待接线项**。`--verify` 那一侧已经用内容面兜住了（实测：`READ WINDOW INTACT (bytes)`，digest 不同但每个文件内容哈希相同，正确放行），所以缺口只在 `--run`。另两条收口路径仍然有效且不依赖卷日志：让被守护的命令自己汇报它读到了什么（把前提变成读数自带的字段，§7 那条判据），或在窗口内多次采样把「中途第三态」抓成正面证据（D5，而不是加强 D7）。

**其二、mtime 刻度内的碰撞是真实的，不是理论风险。** 本机（NTFS via MSYS，`find` 4.8.0，`%T@` 100ns 精度）实测：

```text
2000 次连续写入 → 只产生 624 个不同的 mtime 值
碰撞（一个 mtime 值被多次写入共享）：583 次；单刻度最多 44 次写入
刻度间隔：最小 0.34ms，中位 1.0ms，最大 15.4ms
「取快照 → 立刻改写 → 再取快照」400 次试验：260 次（65.0%）首尾 mtime 相同而内容不同
```

`%T@` 的显示精度（小数 10 位）**远高于**文件系统的实际更新粒度（约 1ms）。一个只信 mtime 的 D7，在 65% 的紧邻写入上会谎报窗口干净。这就是 team-lead 指出的「D1 翻版」风险，且它已经量化：**不是罕见边角，是多数情况**。内容 hash 不受此影响——碰撞率由摘要算法决定，与文件系统时钟无关。

**其三、覆盖面：原集合漏掉 46/87 个文件，其中 12 个是可执行运行时代码。** 实测（`comm -13` 当前集合 vs 全树）：

```text
当前 D7 集合：lib|scripts|tests 的 *.mjs        = 41 文件
全树（去 node_modules）                          = 87 文件
漏掉                                             = 46 文件
```

**这三个数字本身就在漂移，而漂移方向印证了判据。** 同一命令 22 分钟后复测：

```text
lib|scripts|tests 的 *.mjs                       = 42（+1）
再加 tests/fixtures/*.c                          = 46
全树（去 node_modules）                          = 89（+2）
漏掉                                             = 47（只算 *.mjs）/ 43（含 .c）
```

新增的两个文件（`tests/stub-gate-cohesion.test.mjs`、`tests/fixtures/dispatch-ghost-stub.c`）恰好落在窄集合内，所以这次没扩大缺口；但**任何写死数字的覆盖面论证都会在下一次新增目录时失效**，这正是下面取「根因层判据」而非清单的原因。引用本节数字时须连同时刻一起引用。

漏掉的不只是文档：

- `protocols/runtime/*.mjs`（11 个）+ `schemas/registry.mjs` — **是被 import 的运行时代码**。`lib/artifacts.mjs:21`、`lib/journal.mjs:55`、`lib/reducer.mjs:18`、`scripts/dispatch-worker.mjs:27` 全部 `import { getSchema } from '../schemas/registry.mjs'`；`lib/vocabulary.mjs` 引用 `protocols/runtime`。改这些文件与改 `lib/` 对读数的影响没有区别。
- `tests/fixtures/*.c`（3 个）— 编译进 stub 二进制，改了读数同样不可比。
- `schemas/*.schema.json`（8 个）— 校验行为的实际输入。
- `protocols/*.md`、`methods/**/*.md`、`templates/*.md`、`SKILL.md`（22 个）— `control-cohesion.test.mjs:154/162/172`、`kernel-cohesion.test.mjs:257` 直接读它们做断言。

**纳入判据（根因层，不是目录清单）**：

> **被测树内除 `node_modules` 外的全部文件，一律纳入窗口快照。**

**它的可操作形式是：枚举排除项，不枚举包含项。** 这个区分比这次的具体修复更普适：

| | 失效方式 | 谁来维持它正确 |
|---|---|---|
| 枚举**包含**项（`WATCHED = ['lib','scripts','tests']`） | 新目录默认**不被监视** → 守护对它恒绿 | 需要有人随树生长持续更新，无人能做到 |
| 枚举**排除**项（`EXCLUDED = {node_modules, .git}`） | 新目录出现即被纳入；漏掉一个必须是**显式可评审的动作** | 默认正确，无需维护 |

**枚举包含项只在枚举正确时 fail closed，而没人能随树生长维持它正确；枚举排除项默认 fail closed。** 这是判据的形式要求，不只是这次选对了目录。

**还有一条藏在后面的第二个枚举猜测**：即便目录范围取全，一个 `.(mjs|cjs|js|json|c|h)$` 后缀过滤会把 `SKILL.md`、`templates/`、协议 markdown 排除掉——而它们是控制器运行时读的输入。**「是不是代码」不是正确的问题；正确的问题是「两次运行之间它会不会不同」，而任何文件都会。** 一个枚举猜测被修掉后，往往还有第二个躲在它后面。

理由与 docs-wiring 那条守护同构：任何「哪些目录/后缀参与测试」的清单都会过期，而**过期方向是漏报**——新增目录默认不被监视，D7 对它恒绿。仓库本身已经采用同一思路：`kernel-cohesion.test.mjs:64-70` 的注释写明「Walking the tree, rather than consulting a list of directories, is what makes a newly added runtime directory covered on the day it appears」。既然被测方用全树遍历，观测方没有理由用白名单。反向的代价（把一个与测试无关的文件纳入 → 偶尔多作废一个窗口）是**多花一次重测**；漏报的代价是**引用一份假读数**。方向不对称，取全集。

实测成本已在上方给出：全树两面快照约 0.5s，**没有性能理由做裁剪**。

**一个正面数据点：写入确实会落在产品代码上，不只测试文件。** team-lead 用 `-newermt 03:47:07` 取到的具体清单：

```text
03:47:49  tests/dispatch-pipeline.test.mjs
03:51:25  tests/kernel-semantics.test.mjs
03:51:55  lib/semantic-validator.mjs      ← 产品代码（journal-fix 的 #18）
```

第三行是最能让读数失效的那一类：**测试文件没动，产品代码变了，于是同一个测试测的是不同的程序**。若窗口集合只扫 `tests/`，这次写入被完全漏掉，而漏掉它的后果最重——测试文件变更至少会让人怀疑读数，产品代码变更不留任何在测试侧可见的痕迹。这条清单同时也是「全树纳入」判据的实证：**`lib/` 和 `tests/` 都必须在集合内，而它们只是全树的两个子集，凭什么恰好是这两个。**

**「漏掉的都是文档」这个假设为什么不成立——用静态依赖证据，不用观测证据。** 本文曾在此处引用一组 mtime 观测（`04:29:10 schemas/registry.mjs`、`04:29:53 protocols/dispatch.md`）作为「窄集合外的文件确实会被写」的正面证据。**该证据已撤回：那两次写入是 team-lead 按本文阴性判据去审守护时的灵敏度探针（往 `registry.mjs` 追加一字节看 digest 会不会动，随后还原）。** 核对到毫秒：文件当前 `mtimeMs = 1786566550405.1672`，team-lead 探针打印 `1786566550405`，同一毫秒同一次写入；内容 `cmp` 与探针前逐字节相同。**用观测方自己的探针去证明「树在被别人改」，是把自己的动作读成了环境的证据。**

论证本身不受影响，因为它有一条不依赖任何观测的替代证据——**静态 import 关系，读源码即可确认**（读窗口 `79fd00dba167`，首尾同 digest）：

```text
plugin/skills/auto-goal-v2/lib/artifacts.mjs:21        import { getSchema, SCHEMA_IDS } from '../schemas/registry.mjs';
plugin/skills/auto-goal-v2/lib/journal.mjs:55          同上
plugin/skills/auto-goal-v2/lib/reducer.mjs:18          同上
plugin/skills/auto-goal-v2/scripts/dispatch-worker.mjs:27  同上
```

四个运行时文件共同依赖 `schemas/registry.mjs`，而它落在窄集合之外——**改它与改 `lib/` 对读数的影响没有区别，一个窄集合下的 D7 会对它报绿**。这条结论只需要 import 关系成立，不需要任何人在任何时刻真的写过它。**当一个论证同时有观测证据和结构证据时，优先写结构证据：结构证据不会因为「观测方就是写入方」而作废，也不会随时间过期。**

**其四：首尾两点不足以证明中间无变更——但这不必作为残余风险接受。** team-lead 给的 `A ≠ B ≠ C` 三值本身就是现成的反例形态——若只取首尾且恰好 `A = C`，中段的 `B` 会被完全漏掉。上面「改了又改回」那格是它的最小构造：内容与 mtime 在首尾**两面都恒等**，而中段读数确实跑在 B 上。

**先看为什么「提高采样频率」不是答案。** 建模：窗口 `W` 内采 `N` 次，一对「改了又改回」持续 `d`，只要 `d` 完整落在相邻两次采样的间隙内就漏检：

```text
N=  2  gap=100.00   d=1: P(漏)=99.0%   d=5: P(漏)=95.0%
N= 10  gap= 11.11   d=1: P(漏)=91.0%   d=5: P(漏)=55.0%
N= 50  gap=  2.04   d=1: P(漏)=51.0%   d=5: P(漏)= 0.0%
N=100  gap=  1.01   d=1: P(漏)= 1.0%   d=5: P(漏)= 0.0%
```

`P(漏)` 归零的条件是 `gap ≤ d`，即 `N ≥ W/d + 1`。**而 `d` 由并发写入方决定，不由观测方决定**——所以**没有任何 `N` 是可证充分的**。把两点改成 N 点只是把漏检窗口从整轮缩到一个间隙，是量变；声称它解决了问题就是把量变写成质变，正是 D6 要防的那种升格。**采样频率这条路走不通，不是没走够，是方向错了。**

**真正的解法是换判定对象：不验证「树没变」，而是记录「每一轮实际跑的是哪棵树」。** 每轮开跑前 `cp -rp` 一份冻结副本，**对副本取指纹并与该轮读数绑定**。实测（本树 87 文件，每轮复制 0.31s）：

```text
round 1  tree=e88b51fe8665  pass 11  fail 0  skipped 0
round 2  tree=e88b51fe8665  pass 11  fail 0  skipped 0
round 3  tree=e88b51fe8665  pass 11  fail 0  skipped 0
```

**它能抓到首尾采样必然漏掉的那个洞。** 同一个 A→B→A 构造下的对照实测：

```text
window OPEN  = 819fb2b7fce5
  round 1 ran against tree=f143197b549a
  round 2 ran against tree=3b0565bc67a4   ← 中段的 B，跑的是另一个程序
  round 3 ran against tree=f143197b549a
window CLOSE = 819fb2b7fce5

首尾采样判定： OPEN == CLOSE ⇒ 报「窗口干净，三轮读数均可引用」   ← 错
逐轮绑定判定： 读数分布在 2 棵不同的树上 ⇒ 抓到
```

**为什么这是结构性关闭而非概率改善**：首尾采样问的是「这段时间树变了吗」，答案依赖采样恰好落在变更两侧，因此永远是概率的。逐轮绑定问的是「这一轮跑的是什么」，而这一轮跑的**就是那份副本**——副本在该轮内不可被写（实测：源码随后被改写，副本内容不变），指纹取自副本自身。**问题从「需要证明没被写」变成「结构上不可写」，概率消失了。**

于是判定分层，代价递增：

| 层级 | 做法 | 关闭什么 | 代价 |
|---|---|---|---|
| 0 | 只在窗口首尾采样 | 密集写入（写入频繁时首尾必然抓到） | ~0.5s / 窗口 |
| 1 | 每轮一份冻结副本 + 指纹绑定读数 | **含「改了又改回」在内的全部跑动期污染** | ~0.3s / 轮 |
| — | 提高采样频率至 N 点 | 只缩小漏检窗口，**不关闭** | 线性增长，收益不可证 |

**层级 0 是必要但不充分**（team-lead 的判断，我实测同意）：这次它确实抓到了每一段的变化——`dispatch-pipeline.test.mjs` 03:47:49 落在 A/B 之间、`kernel-semantics.test.mjs` 两次连写跨了 B 与 C——但**那是因为写入足够密集**。密集时首尾够用，稀疏时不够，而观测方无法预先知道写入密度。**所以层级 0 的正确读法是「本窗口未检出污染」，不是「本窗口干净」。**

**层级 1 仍然需要 D7，只是 D7 下降一层。** `cp -rp` 遍历需要时间，中途落盘的写入会让副本本身成为两个版本的拼接（正是 72 轮那次的半写快照形态）。所以**复制前后各取一次快照**，一致才说明该副本取自一致瞬间。D7 在这里从「验证读数」变成「验证快照」，它不会消失——**这也说明层级 1 不是 D7 的替代品，是 D7 的载体**。

**其五、事后回扫不能替代窗口内的快照：证据会随时间被覆盖掉。** 一个窗口若当时忘了取快照，事后用 `find -newermt <开> ! -newermt <闭>` 回扫看起来能补救。**它只在很短的时间内有效，之后会静默转为恒绿。** 机制：mtime 只记录**最后一次**写入，所以窗口后的任何一次改写都会把该文件的窗口内痕迹抹掉，回扫从此再也看不见它。

最小构造实测（隔离目录，三次写入）：

```text
窗口 = [04:22:54, 04:22:56]，窗口内写入 f.mjs @04:22:55
闭窗后立刻回扫：  HIT 04:22:55 ./f.mjs        ← 抓到
再写一次 f.mjs（04:22:58，窗口外、完全无辜）
同一条回扫再跑：  （空）                        ← 窗口内那次写入已不可见
```

本树上的实际衰减（对 team-lead 那个 `[03:55:45, 03:56:02]` 窗口，统计「当前 mtime 已晚于闭窗时刻」因而无法排除的文件数）：

```text
回扫于 03:56:02（闭窗即刻）  失明 0 / 89 文件   ← 证据完整
回扫于 03:59:00              失明 1 / 89
回扫于 04:02:30              失明 4 / 89
回扫于 04:16:30              失明 6 / 89
回扫于 04:24:00              失明 8 / 89        ← 28 分钟内单调增长
```

失明集合只会增长，永不缩小。**所以回扫得空集有两种读法，而它们无法从读数上区分**：「窗口内真的没人写」与「写过，但之后被覆盖了」。回扫的正确读法是「**79/89 个文件可排除，10 个无法排除**」，而不是「窗口干净」。这是第 12 格。

> **补救的界限**：回扫在闭窗后**立刻**执行仍有完整证据力，越晚越弱，且弱化不可见——这是它比「忘了取快照」更危险的地方。忘取快照会让人标注「窗口未验证」；晚做的回扫会给出一个空集，让人以为验过了。**窗口快照必须在窗口内取，这是它与回扫的本质区别，不是严格程度的差别。** 回扫不是弱一点的快照，**是另一种东西**——快照回答「此刻树是什么」，回扫回答「此后没人再写过」，而后者的答案会随时间腐烂。

**这一格与前三处假 skip 同构，不是一条孤立技巧。** F1 / F2 / F10 的形态是门禁自称「本环境不适用」于是被跳过；这一格的形态是回扫自称「窗口内无写入」于是读数被采信。**共同点：自称的那个状态，它的成立条件本身没有被任何东西校验。** 门禁没校验「我确实处在适用环境」，回扫没校验「窗口内的痕迹此刻仍然存在」。两者都以成功退出，两者的输出都与真通过逐字节相同。**凡是一条判据以「没有发现问题」结束，就要问一句：它此刻还有能力发现问题吗？**

**其六、在自己被阻塞的进程里模拟并发，模拟出来的是「没有并发」。** 这条是 D7 守护自证时踩出来的，docs-wiring 原话值得原样收录。它前两次自检用同进程 `setTimeout` 排一次「窗口中途写入」，**从未触发**——因为 `spawnSync` 把事件循环堵死了，定时器要等被守护的命令跑完才轮到，而那时窗口已经关了。

改成**独立进程**后立刻成功：开窗 1.5s 后由外部进程追加一个字节 → `WINDOW VIOLATED`，守护 `exit 3`，**而那一轮测试本身 `exit 0`**。

> **这是 D7 至今最有说服力的一次自证**：**守护在测试全绿的情况下判 VOID**。它同时兑现了本节前面那句「并发写入期间的绿同样无效」——那句原本只是论证，现在有了实测。

判据（通用，不限于 D7）：**验证守护并发能力的探针，必须真正独立于被守护的进程。** 同进程的定时器、`process.nextTick`、`Promise` 微任务都不是并发——它们与被守护代码共享同一个执行线，被守护代码一阻塞，探针就停。**一个从不触发的探针与一个被正确处理的探针，在输出上都是「没报错」。** 这是恒绿形态在测试构造层的又一次复现：探针没跑，看起来像守护通过了。

**其七、D7 守住了「跑」，没守住「解释」。** team-lead 在一个完整窗口内取到 `488 / 481 / fail 2`（digest `3ee4f8e4a2ec` 首尾一致，读数有效），随后**去读源码解释那两条红**——而此时树已移到 `fadd42b7115a`，他差点基于一行**不存在于那次运行**的测试代码报出机制。

```text
运行窗口：  digest 3ee4f8e4a2ec  首尾一致  → 计数有效：488 / 481 / fail 2
阅读时刻：  digest fadd42b7115a  ← 已是另一棵树
           计数仍可引用（它在闭合窗口内测得）
           机制不可引用（引用的代码行可能不曾参与那次运行）
```

> **计数可引用，机制不可引用，而两者写在同一份报告里看起来同样可信。** 这是这条缺口便宜的原因：报告里「fail 2」与「因为 `foo.mjs:123` 那行 …」并排出现，读者没有任何线索区分二者的有效性等级。

**这是 D7 的自然延伸，不是新判据**：窗口只覆盖「跑」这个动作。**若在窗口关闭后读源码来解释读数，那次阅读需要它自己的窗口**——或至少记录阅读时刻的 digest 并与运行时 digest 比对。两者的判定不同，因为「只有 mtime 动了」对跑与读的影响不同：

| | 计数（跑） | 机制（读） |
|---|---|---|
| 内容变了 | 作废 | 作废 |
| 只有 mtime 变了（`touch` / checkout） | 作废（这一轮可能与写入赛跑过） | **仍可引用**——屏幕上的字节就是跑过的字节 |

区分这两档不是宽松，是必要的：**一个对「只有 mtime 动了」也报警的读窗口守护会不断误报，然后被忽略，那比它不存在更糟。**

**其八、观测方自己的写入必须先被排除，而排除它所需的信息不在树里。** 这一格由本文作者踩出，形态与前面每一格都相反，所以单列。

本节曾把两次 mtime 变化（`schemas/registry.mjs` @ 04:29:10、`protocols/dispatch.md` @ 04:29:53）当作「窄集合外的运行时文件确实会被别人改」的正面实证。**那两次写入是 team-lead 按本文的阴性判据去审守护时的灵敏度探针**：往 `registry.mjs` 追加一字节，确认 digest 会动（`9d9ef16c902a` → `e41172696bc5`），然后还原。核对：

```text
文件当前 mtimeMs      1786566550405.1672
探针方打印的 mtime     1786566550405        ← 同一毫秒，同一次写入
内容与探针前            cmp 逐字节相同
```

**我们两个都在测量，而测量动作本身进入了被测量的树。** 这不是谁违规，是这个设置的固有属性：D7 判定窗口时看到的 mtime 变化里，有一部分是观测者在看它。

> **凡是把 mtime 变化解释为「某人在改产品代码」的推断，都必须先排除观测方自己。而做这个排除所需的信息（谁在什么时刻跑了什么探针）根本不在树里**——树只记录「有人写过」，不记录「是谁、为什么」。

这就是它不能靠加强守护来关闭的原因：**守护能看见的一切都不足以做这个区分。** 可行的做法只有两条，且都在树之外：

- **优先用结构证据代替观测证据。** 本节的结论（窄集合会漏掉四处 import 的 `schemas/registry.mjs`）只需要 import 关系成立，读源码即可确认，不依赖任何人在任何时刻写过它。**当同一个结论既有观测证据又有结构证据时，写结构证据**——它不会因为「观测方就是写入方」而作废，也不随时间过期。
- **观测方的探针必须留下可被别人查的记录**（时刻 + 文件 + 是否还原）。这是协作纪律，不是工具能力。

**与第 16 格的关系**：其七说窗口守住了「跑」没守住「读」；其八说**连「跑」这一侧看见的信号也可能是自己发出的**。两者合起来划出 D7 的真实边界——它回答「这棵树在这段时间里变了吗」，它**不**回答「变化来自哪里」，而后者才是绝大多数归因所需要的。**把前一个答案当后一个用，是这一族里最容易发生的越界。**

顺带，这次探针**同时把「其一」表格第二行的反向数据点实测了**（数据来源：team-lead）：那次写入还原后**内容与之前逐字节相同**（`cmp` 确认），而全树 digest 从 `9d9ef16c902a` 变成 `32dcc1840267`——**内容哈希那一面报「没变」，mtime 那一面报「动过了」**。这正是 A→B→A 在真实协作中的自然发生形态：**只取内容哈希会漏掉这次改动，而中段任何读数都跑在 B 上。** 它与「其零之二」那格（size 与 mtime 双恒等、只有内容哈希抓到）方向恰好相反，两格合起来才说明两面同取是必需而非冗余。

#### 裁决：「窗口完整 ≠ 读数确定」这个命题成立，但本地证据不成立

docs-wiring 报了一组数据：同 digest 的相邻 INTACT 窗口 fail 数为 2/3，另一 digest 上为 3/3/4，据此主张 D7 必要非充分，并建议「单点计数需附同 digest 多次读数」。**这里有两件事必须分开判，因为它们的证据要求不同。**

**命题独立成立。** 套件确实可以自身不确定（超时、端口、`Date.now()`、并行调度、临时目录竞争），而 D7 管不了这个——它只保证「被测程序是同一个」，不保证「同一个程序每次给出同样的读数」。这一点无需本地数据支持，它是 D7 作用域的直接推论：**D7 关闭的是被测对象的同一性，不是被测对象的确定性。**

**但那组数据不足以支撑它。** 按 D6，写进报告的机制必须有独立于「现象出现」的证据。这组数据有**第二个解释**，且该解释已被证实存在：它跑的时候守护只看 46/89 个文件，`schemas/`、`protocols/runtime/` 的 21 个运行时模块在视野外，而同期有人正在改 `lib/`/`scripts/`。**视野外的连带改动完全可以落在它两次 INTACT 之间**——那时报的 INTACT 本身就是假的，fail 数漂移的成因是 D7 失效而非套件不确定。

盲区已修（守护现覆盖 89/89）。**在修后的守护上重测，不复现**：

```text
team-lead  digest 9dfd2fc38ea6   4 轮   tests 489  fail 1  skipped 5   ×4，失败项每轮同一个
本文作者    digest 42483a4d050e   8 轮   tests 489  fail 0  skipped 5   ×8，逐字段一致
                                  ——累计 12 轮同 digest 零漂移
```

（两组 digest 不同、fail 数不同，是因为期间那一项跨层预算未登记被修掉了；**同 digest 内部零漂移**才是这里要看的量。）

> **裁决**：该命题**保留在文档里，但降为第二档表述**——「套件自身的不确定性是 D7 作用域之外的一个独立风险，本仓**尚无**证据表明它实际发生」。原数据按 D6 第二档记：「现象：曾观测到同 digest 下 fail 数不一致；成因有两个候选（套件不确定 / 守护盲区），盲区已修，修后 12 轮不复现。」
>
> **不把它写成已确认事实**，理由正是 D6 那条：**「现象出现过」不等于「机制成立」，尤其当另一个已证实存在的机制能同样解释它时。** 这里的取舍不是怀疑对方，而是这份文档的引用者会把「已确认」当作行动依据——它会催生「每个计数都必须跑 N 轮」这条昂贵纪律，而目前没有本地证据支持这笔开销。
>
> **但保留命题本身是有价值的**：它标出了 D7 的作用域边界。**读数有效性有两个正交的前提——被测对象同一（D7）与被测对象确定（D5）**，而 D5 早已在文档里要求跨格差异复现 ≥3 次。所以真要防套件不确定性，用的是 D5 而不是加强 D7，**不需要新判据**。

这一裁决本身也是一次 D6 应用：**推翻机制不等于推翻现象**（§2 D6 反向那格）。docs-wiring 观测到的漂移可能真发生过，只是不能归因到「套件不确定」。

**这一裁决省下的具体东西，值得写明，否则「谨慎」看起来只是没做决定。** 若把它记成已确认事实，随之而来的纪律是「每个计数都必须跑 N 轮」。而按上面的分解，那条纪律是**误配**的——它想防的是确定性风险，却挂在了同一性判据上。

> **一条误配的判据比没有判据贵。** 它让每个人为一个已被别处覆盖的风险重复付钱，而且**因为它看起来严谨，没人会去质疑它**。判据的成本是永久的、按次计的；而「多加一条总比少一条好」这个直觉在这里恰好是错的。

**并且这里有本任务反复撞到的那件事的第三个面：自称的确信度。**

```text
F1 / F2 / F10      门禁自称「本环境不适用」          → 假 skip
-newermt 回扫      自称「窗口内无写入」              → 假窗口证明（第 12 格）
「已确认」          结论自称「机制已查明」            → 假机制
```

**三者同一句话：那个自称的状态，它的成立条件没有被任何东西校验。** 前两个是工具的自称，第三个是**报告作者的自称**——而它比前两个传播得更远，因为引用者会把「已确认」直接当作行动依据，不会回头看它当初凭什么被标成已确认。**确信度是报告里唯一一个不由数据决定、却决定读者行为的字段。**

**一份靠运气成立的读数，与一份无效读数在方法上同级。** team-lead 的 `477 tests / pass 471 / fail 1 / skipped 5 @19:55:51Z` 经我独立按全树范围复验，该 11 秒窗口内确实无写入，**读数站得住**。但它站得住需要三层限定同时成立，缺一层就不成立：

| 层 | 限定 | 若不成立会怎样 |
|---|---|---|
| 1 | **范围窄**：判定用的集合只有 46/89（`lib|scripts|tests` 的 `*.mjs`/`*.c`，2026-08-12 20:xxZ 时的值） | 视野外 43 个文件的写入完全不可见，INTACT 是假的 |
| 2 | **回扫做得早**：复验时那次回扫仍处于证据完整期 | 晚一点做就返回空集，而空集会被读成「验过了」（第 12 格） |
| 3 | **运气**：那 11 秒恰好没人动视野外那 43 个文件 | 同一套方法给出一份看起来同样可信的假读数 |

第 3 层最要紧，因为**当时无人知道第 1 层成立**——范围窄这件事是事后审出来的。**一个读数可以同时「有效」和「不该被后续引用」，这两件事不矛盾**：它有效是相对当时的判据，不该被引用是因为判据升级了（现覆盖 89/89）。方法层面必须记的是范围缺陷，不是这次的好结果：**结果站住不构成对方法的背书。**

**这条对本文自己的数字同样成立。** 上面「其三」那节的 `46/87`、`42/89`、`89/89` 全都是**某一时刻的值**，引用时必须连时刻一起引用；本文早先写下的覆盖面数字已经是历史值。**一份指出「写死数字会过期」的文档，不能例外地相信自己的写死数字。**

#### D7 不越的界：它是判据，不是流程管制

D7 不要求任何人停止写代码，也不要求锁仓库。并发写入是多 Agent 协作的常态，不是违规。D7 只做一件事：**让读数带上自己的有效性边界**。

**读数作废不等于工作作废**——那 72 轮的产出就是 D7 本身，成本已经收回。而 D7 还有一个此前未写明的**正向用途**：它能在**开跑前**判定「现在不可测」。team-lead 实测三个连续 hash（`bd4a7a4a6e86` @19:47:07Z、`4c45b1b57fde` @19:48:31Z、`fbf42231759c` @19:49:41Z，间隔 84s / 70s，`tests/kernel-semantics.test.mjs` 在 19:48:21 与 19:49:04 被连写两次）后判定当前树不可测，**一轮都没跑**。与「跑完 72 轮才知道作废」相比成本差一个数量级。

> **所以 D7 有两个用法**：事后作为读数的有效性标注（被动），事前作为可测性判定（主动）。第二种便宜得多——两次快照相隔一个采样间隔即可，不必等一整轮测量结束。

**我自己刚踩到同一个坑**：审这一节时我用 2 秒间隔取了两次全树 hash，两次相同，而 `lib/ledger.mjs` 在 6 秒前（04:01:07）刚被写过。**2 秒的静默不是静默**，它只说明「这 2 秒内没写」。主动用法的采样间隔必须与 D1 的静默阈值同量级（本任务观测到的落地窗口是 2 分钟量级），不能随手取一个短间隔就宣布树静止——那是把 D7 主动用法降级成又一个恒绿探测器。

### 附：`diff -r` 必须看差异方向

比对副本与源码时，「有差异」不等于「我污染了源码」。实测：docs-wiring 报 `journal-append.test.mjs` 有差异，方向是**仓库比其副本多两个用例**（B1 修复方并发新增的），副本没动过源码。只看「有差异」会误判为污染，进而去「清理」——那才是真的污染。

始终读 `<` / `>` 的方向，并对照 mtime 判断是谁动的。

## 3. 靶点存在性与 no-op 自检

这一节排除核心命题里的竞争解释 **(a)**。

**靶点不在当前磁盘版本里，不得报 `PATCH-TARGET-MISSING` 了事**。这只说明代码变了，不说明约束被守住了；必须按真实源码重写变异后重跑。把「靶点没找到」当成「无需再验」，就是又一次把「未执行」误报成「已通过」。

**替换前后内容相同即 void**。只校验 needle 存在不够——缩进不匹配会让 `replace` 静默 no-op 却打印 "applied"。变异器必须：

```js
if (!before.includes(old))  { exit(9); }        // PATCH-TARGET-MISSING：须重写变异
const after = before.replace(old, neu);
if (after === before)       { exit(8); }        // VOID-MUTATION：替换无效果
writeFileSync(file, after);
if (readFileSync(file,'utf8') === before) { exit(8); }   // 落盘后复读，确认磁盘真的变了
console.error(`APPLIED occurrences=${n} bytes ${before.length}->${after.length}`);
```

打印 `occurrences` 有额外价值：`>1` 说明 needle 不唯一，只改了第一处，变异范围与描述不符。

### 实测案例：跨层协同漂移变异（acceptance-trace）

这是本条判据**唯一的实测案例**，比抽象规则更能说明它挡下了什么。

验证「跨层预算常量协同漂移是否被拦住」需要同时改两侧：`scripts/` 与 `lib/budgets.mjs`。lib 侧的 needle 按 `WORKER_OUTPUT_ENVELOPE: 1 * 1024` 构造，而真实文本是：

```js
// lib/budgets.mjs
WORKER_OUTPUT_ENVELOPE: 1 * KIB,      // 用的是 KIB 常量，不是字面量 1024
```

`VOID-MUTATION: needle absent` 以退出码挡下，整轮作废重构 needle。

**若无这道自检会发生什么**：lib 侧半边不落地，变异退化为 `scripts/` 单侧修改；单侧修改本就该被跨层一致性测试拦住，于是套件报 `fail 2`。这两个失败会被读成「协同漂移已被拦住」——**与真相相反**。真相是协同漂移这一路径根本没被施加过。

注意错误的方向：它**高估了测试的保护力**。这比低估危险得多——低估只让人多写一条测试，高估让人把一个真实缺口标成已覆盖然后收工。

**推广**：任何需要同时改 N 处的变异，必须 N 处全部确认落地才能解读结果；任一处 void 而其余落地，产出的是**另一个变异**的结果，且通常更容易被杀死。

### 同一条判据的镜像：门禁也需要「我确实匹配到了东西」

上面讲的是**变异**必须证明自己落地。反方向同样成立：**门禁必须证明自己匹配到了东西。** 二者是同一条判据的两面——「未执行」与「已通过」在输出上不可区分。

实测案例（本任务，抓住作者本人）：docs-wiring 给 `.github/workflows/ci.yml` 写生产端门禁，用 `^`-anchored regex 逐行匹配；而 `ci.yml` 是 **CRLF**，尾随 `\r` 让 regex 零匹配——**门禁自己成了空转断言**。抓住它的不是变异，是它自己写的兜底：**「赋值计数必须 > 0」**。

```text
门禁匹配到 3 处并全部校验通过   →  exit 0，无输出
门禁匹配到 0 处（CRLF 导致）    →  exit 0，无输出      ← 逐字节同读数
```

> **判据**：每个门禁都要有一条**「我确实匹配到了东西」的前提断言**（匹配数 / 遍历文件数 / 断言执行次数 > 0），否则门禁的空转与门禁的通过在输出上不可区分。

**这条与 F1 / F2 / F10 三次假 skip 同根**：*门禁的启用条件本身没有被任何测试校验*。假 skip 是启用条件求值为「不适用」，空转门禁是启用条件求值为「无对象」——两者都不是断言失败，都以成功退出，都在报告里表现为一个体面的状态。

**这个缺陷在本仓已经发生过并被修掉，现场还在，所以这条判据有一个真实案例而不只是构造。** `tests/ci-stub-gate-wiring.test.mjs:79-82` 的注释与 `:111` 的兜底：

```js
// `\r` is stripped per line: the workflow files are CRLF here, and an `$`-anchored
// ... zero lines is the vacuous-assertion shape, so the assignment count is checked below.
source.split('\n').map(line => line.replace(/\r$/, '')).forEach((line, index) => {
...
assert.ok(assignments > 0, `no workflow assigns ${GATE_VARIABLE}; the CI enforcement wiring is gone`);
```

**我独立复现了那个 CR-strip 是不是承重的**（读窗口 `f1713d5c3280`，首尾同 digest）：

```text
ci.yml 形态        strip=yes   strip=no
现状（CRLF）           1          0      ← 不 strip 就零匹配
强制转 LF              1          1
强制全 CRLF            1          0
```

**不带 strip 就是 0 处赋值，门禁匹配零行然后绿。** 而在那个状态下唯一会喊的是 `assert.ok(assignments > 0)`——**「匹配到的数量必须非零」这条断言是行锚门禁唯一的活口**。这一格比构造的例子有力，因为它证明的不是「这种缺陷可能发生」，而是**它已经发生、已经绿过、且是那条兜底断言把它抓回来的**。

**本仓 CRLF 的真实分布（读字节，不用 `grep`）**：

```text
src/                          14 / 14   全 CRLF
.github/                       5 / 5    全 CRLF
scripts/                       0 / 1
plugin/skills/auto-goal-v2/    0 / 89   全 LF
```

我早先只报了 `.github/` 的 5 个，**漏了 `src/` 的 14 个**（team-lead 补的，我已按字节复核）。这让结论更强而不是更弱：**CRLF 的边界正好落在「skill 树内」与「skill 树外」之间**，全仓 19 个 CRLF 文件全在树外，树内 0 个。所以**任何在 skill 目录里验过的行锚门禁，往树外搬**（`.github/` 或 `src/`，两个方向）**都会静默失效**——而 skill 树内的测试永远不会暴露这一点。跨目录不一致比全仓 CRLF 更危险，正是因为「在本地验过了」这句话在这里是真的，却不可迁移。

> **我在核这条时踩到它的一个变体，值得记下来**：我第一次用 `grep -q $'\r'` 扫全仓，得 **0 / 36**——**因为这个 MSYS 环境下的 `grep` 会剥掉 CR 再匹配**（team-lead 独立复现：`grep -c $'\r'` 得 0 且 exit 1，`grep -Uc $'\r'` 得 2 且 exit 0，`od -c` 确认字节在）。换 `od -c` 与 `grep -U` 才看到真相。**用来检测该问题的工具自己隐藏了该问题**，而它给出的是「没有 CRLF」这个干净结论。
>
> 这一格与「探针从不触发」是同一族，落点比第 11 格更一般：**否定性结论的成立条件通常不在被观测对象里，而在观测手段里。** 「没有 CRLF」「没有并发问题」「没有匹配到违规」——这三句话的真假都不由被观测对象单独决定，而任何「没找到」的结论都要先证明这个工具在同类输入上找得到。

## 4. mtime 前置与结论的版本绑定

变异**前**记录被测文件与 `tests/` 的 mtime，复验**后**重记。期间有变动 ⇒ 结论标注「绑定该时刻代码版本」或直接作废。

配对判定挡不住这条：配对能排除「测试自己红」，排不掉「修复方刚把靶点改了」。

**推论：任何变异结论都必须写上它绑定的代码版本**，否则几分钟后就可能被推翻而无人知晓。本任务的实例——同一批 12 项存活变异，在早期快照与后期快照下结论不同（用时刻标定，**不用用例数标定**）：

| 变异 | 早期快照 | 后期快照 | 期间发生了什么 |
|---|---|---|---|
| M1b | 存活 | KILLED | B3 修复 + 3 条空索引测试 |
| M22/M25 | 存活 | KILLED | 跨层预算常量哨兵 |
| M40 | 存活 | KILLED | `dispatch-argv-integrity.test.mjs`（03:05 落地） |
| M24 | 存活 | 存活 → **KILLED** | 见下 |

M24 这一行是本文最完整的一个例证，它在**我写这份文档的过程中**连续变了三次状态：

| 时刻 | 状态 | 判据读数 |
|---|---|---|
| 02:47 | 存活 | fixture `argv-echo-stub.c` 已建、0 refs ⇒ D3 报警：修复在做，未接上 |
| 03:05 | **仍存活** | `dispatch-argv-integrity.test.mjs` 落地、3 用例，但只覆盖 `shell:false`（杀 M40），**未覆盖 `assertIsolatedArgs` 调用点** |

1. **「有人在修」≠「已修好」** —— team-lead 判 M24「正在被修」是对的（fixture 就是半成品），但修复第一版落地后它**依然存活**：同一次提交杀掉了 M40 却没杀 M24。

3. **必须在修复落地后重跑，且要看杀死它的测试名**。只看 KILLED/SURVIVED 无法区分「我的约束被守住了」与「隔壁约束顺带红了」。

| **反向（恒绿检验）** | 窗口内写一次，窗口后再写一次，然后事后 `-newermt` 回扫 | **不得**报空集即算窗口干净 | 闭窗即刻回扫抓到；一次窗口外改写后同一回扫**返回空集**（第 12 格） |
| **反向（恒绿检验）** | 同长度算子替换（`===`→`!==`）**且** `touch -r` 还原 mtime | **不得**报绿——size 与 mtime 双恒等 | `42483a4d050e` → `aa45a3ac9f35`；**size 27905 = 27905、mtime 逐位相同**，仅内容哈希抓到 |
| **反向（恒绿检验）** | A→B→A：改一字节后还原，内容逐字节复原 | **不得**因内容恒等而报绿 | **协作中自然发生**（来源 team-lead）：`cmp` 逐字节相同，而 digest `9d9ef16c902a` → `32dcc1840267`——**只有 mtime 面抓到**，与上一格方向相反 |
| **反向（自反检验）** | 把观测方自己的探针写入当作「环境在变」的证据 | **不得**据此归因于他人 | 核到毫秒：`1786566550405.1672` = 探针打印值；该行论证已撤回，改用静态 import 证据（其八） |
| **反向（恒绿检验）** | 同进程 `setTimeout` 排一次窗口中途写入 | **不得**因探针不触发而算通过 | `spawnSync` 堵死事件循环，探针从未执行；改独立进程后 `WINDOW VIOLATED` / 守护 exit 3，**而测试本身 exit 0** |
| **反向（瞎采样断言）** | 把守护指向一棵无文件的树 | **必须**抛错，不得给出 digest | `Error: snapshot read 0 files … a sampler that sees nothing cannot report INTACT`，exit 1 |
| **正向（补齐）** | **活树上取得静止窗口 ⇒ 读数可引用** | 判 INTACT，读数可引用 | **已实测**：末次写入后静置 7 分钟、跨 4 分钟两次采样同值 `42483a4d050e` → `--run npm test` 首尾同 digest、`WINDOW INTACT`、`tests 489 / pass 484 / fail 0 / skipped 5` |
| **反向（假阳性方向）** | 纯 `touch`（`fs.utimesSync`，零字节写入）后 `--run` | 理想应放行：字节从未变过，任何时刻的读数都有效 | **本轮已修**：判 `WINDOW TOUCHED`、exit 0、逐文件点名 `TOUCHED`，并警告计时类读数被污染（22:35:41Z 隔离副本实测；先前两版守护判 `VIOLATED / VOID`，即假阳性） |
| **正向（TOUCHED 不得成为洞）** | `--run` 期间真改字节 | **仍必须** VOID，不得被 `TOUCHED` 软化 | `WINDOW VIOLATED` + `CHANGED`，exit 3（变异 `touchAlways` 可杀，V11） |
| **反向（新分支无杀手）** | 新增 `status` 分叉后跑变异探针 | **不得**因全绿即认为该分支被覆盖 | 探针报 11/11「每例可证敏感」，而杀手清单里**无一格触及该分支**；补 V12–V14 后 14/14（见下「第 14 格」） |
| 正向（同 digest 复现） | 同一 digest 上重复 8 轮 | 读数逐字段一致 | `42483a4d050e` ×8 全部 `489 / 484 / fail 0 / skipped 5`；与 team-lead 4 轮合计 12 轮零漂移 |

**恒绿检验是 D7 自证的重点**，理由与下方「自证的方向要求」同源：D7 输出的是「窗口干净」这一**阴性**结论（没有污染），而阴性结论的伪造只需要一个看不见的盲区。前八格反向用例各抓到一处真缺陷或排除一条替代做法——前两格改掉了实现（**mtime 与内容 hash 两面同取**），第三格改掉了判据形态（**加层级 1 逐轮绑定**），第四格排除了「事后回扫」，第五格是**双恒等中最强的一格**（size 与 mtime 同时恒等，只有内容哈希能抓，同时兑现第 9 与第 13 格），第六格抓到**探针自己从未执行**，第七格是第五格的**反方向**（内容恒等、只有 mtime 面能抓），第八格不是恒绿而是**自反**——观测方把自己的动作读成了环境的信号。

**第九格与前八格的方向相反，所以它不是又一格，而是一个边界。** 前八格全在问「守护会不会漏」，第九格问「守护会不会多」，而它当时**实测为多**：纯 `touch` 被判 VOID。

**这一格本轮被裁决了，且裁决方向与我先前写下的相反，所以先记原判**：我曾判「必须留成未修状态」，理由是它与第八格共用 mtime 那一面——**删掉 mtime 就修好了第九格并同时瞎掉第八格**，两格只能一起裁决，而在不对称代价下应偏向更便宜的错误（漏判让人引用无效读数，多判只是白重跑一次）。

**该理由的前提是错的：可选项不止「保留 mtime 面」与「删掉 mtime 面」两种。** 第三种是**两面都保留、但分开报**——mtime 面判「有人动过」，内容面判「字节是否变过」，两者交叉出第三种结局：

| mtime | 内容 | 结局 | 可引用性 |
|---|---|---|---|
| 恒等 | 恒等 | `INTACT` | 全部可引用 |
| 变化 | **恒等** | **`TOUCHED`**（新增） | 字节类读数可引用；**计时类不可** |
| 变化 | 变化 | `VIOLATED / VOID` | 全部作废 |

**为什么 `TOUCHED` 不是 `INTACT`**：touch 不可能改变读数计算所依据的字节，所以字节类结论成立；但一次**以时间分布为读数**的运行（延迟、分位数、flake 率）与那个 touch 共享机器，动手的那一方是一个负载源。所以这一格的正确答案不是「放行」也不是「判死」，而是**按读数种类分别放行**——而这正是原判据表达不出来的东西：`VOID` 与 `INTACT` 两个格子里没有一个能写下「字节可引、计时不可引」。

**我原判错在哪，值得单记**：我把「两面同取」当成了一个**合取判定**（任一面变即判死），于是自然推出「要修第九格只能拆掉一面」。实际上两面是**两个独立的观测量**，合取只是我对它们的一种消费方式。**把两个信号压成一个判定，然后论证这个判定无法改进——被论证的其实是那次压缩，不是那两个信号。** 与本轮另两处同族：`(exit N)` 递出数字而不递出结论、`If this exit came from...` 递出条件而不递出判断——**三处都是把已经拿到的信息在最后一步丢掉。**

代价并未消失，只是搬了位置：`TOUCHED` 若被读成「没事」，计时读数就会被错引。所以它**不是** exit 0 静默放行——逐文件点名 `TOUCHED`、显式打印「计时类读数视为已污染，需重取」，并由 V10/V11 两格双向守住（`touchIsVoid` 杀「退回一律 VOID」，`touchAlways` 杀「真改字节也被软化」）。**残余风险改写为：`TOUCHED` 的警告若被忽略，计时读数会被错引；这一条现在有杀手，不再只是一段文字。**

**第五格与第七格必须成对读。** 单看第五格会得出「内容哈希更强，mtime 可省」；单看第七格会得出反面。两格合起来才给出正确结论：**两个方向各有一格实测反例，所以两面同取是必需而非冗余。** 这也是第 11 格（控制组的方向性）在具体判据上的落地——**一个度量的强弱不能只在一个方向上评定。** 而第九格给这条加了一个**修正后的**上限：两面同取覆盖了两个漏判方向；把它们**合取成单一判定**会引入一个多判方向，而把它们**分开报**则不会。**不是合取加强了判据，是合取丢掉了信息。**

### 第 14 格：性质没有被写进用例表，在任何一次运行里都不可见

**来源：本轮 team-lead 修 `--run` 假可采纳、我随后跑变异探针。**

他给 `--run` 加了按 `status` 的分叉（命令没启动时不再印 "reading is admissible"）。我在**该分叉已在场之后**跑变异探针，读到 **11/11 `PASSED-AND-SENSITIVE`「每例都可证敏感」**。实测该分叉当时**没有任何一个杀手变异触及它**（对杀手清单搜 `status === 0` / `admissible =`，命中 0）。

**这是空转家族里最难察觉的一种形态**：探针没出错、没跳过、没有豁免名单——**它只是没有那一格**。

| 形态 | 在输出里的痕迹 |
|---|---|
| 断言写错 | 变异下暴露 |
| 用例被 skip | 报告里有 skip 计数 |
| 豁免名单 | 名单上有一行 |
| **性质不在用例表里** | **无任何痕迹** |

原因是算术性的：**满分报告的分母是用例数，不是性质数。** 「14/14 每例可证敏感」是关于那 14 个断言的真命题，而它对第 15 个未被写下的性质一无所知——**探针的覆盖率永远无法自我度量，因为分母在探针之外。**

**同一族的第二层，补齐时立刻踩中，且是探针自己抓出来的**：我给 V13（正面断言「exit 0 仍称可采纳」）挂的杀手是 `alwaysUnstarted`，但该变异改的是失败分支，**V13 走 exit 0 分支、根本到不了被改的代码**，于是它在变异体下照样通过。探针判 `VACUOUS` 并拒绝给全绿。**「挂了一个杀手」与「挂了一个能到达它的杀手」是两个命题**——这是「正面/反面断言需要方向相反的杀手」在可达性上的加强版：方向对了还不够，路径得能走到。

**判据**：
1. **每新增一个分支，同时回答「哪一格会因为删掉这个分支而变红」**；答案是「没有」时，该分支在探针意义上不存在，与探针得分无关。
2. **杀手必须落在被测例实际执行的路径上。** 挂完即跑一次，看它是否真被判为该例的杀手；`VACUOUS` 是这条判据唯一可靠的执行者。
3. **三向分叉需要三格**，不是「一格加一条注释」。`--run` 的三种结局（exit 0 / 跑过但失败 / 从未启动）由 V13 / V14 / V12 各自守住，各有一个只杀它的变异。

**与「豁免名单本身是一处待查的空转」的关系**：豁免是**显式**的漏，这一格是**隐式**的漏，后者严格更难发现。**所以「无豁免项」不能作为覆盖完整的证据——它只说明没有显式的漏。**

> **正向那格补齐的方式本身值得记**：它一直标「未实测」而不是硬凑，直到 D7 的**主动模式**判定当前可测（末次写入静置 7 分钟 > D1 的 180s，且跨 4 分钟两次采样同值）才跑。**先判能不能测，再决定测不测**——把表填满的冲动正是本文第一节批的那种空转自证。

自证的方向要求：**只有正向用例不够**。一个恒报 KILLED 的坏实现能通过全部正向用例。这与 `stub-backend-rejection.test.mjs` 的 control 正例是同一条规则，也是核心命题的直接推论——阴性结论需要额外证据，所以检验阴性通道的反向用例才是自证的重点。

```text
     fileId 而非 basename（第 24 格），且检测器不可用时须印 `INCONCLUSIVE`（第 22 格）
```

第 0 步不可省：**它验的是度量本身，其余各步都建立在度量可用之上。** 第 0b 步与第 8 步是一对，**不可只做其中一个**：只有开快照挡不住窗口中段的写入，只有闭快照无从比对。两步都必须**两面同取**——只取 mtime 会被保留时间戳的工具和 1ms 刻度碰撞骗过，只取 hash 会被「改了又改回」骗过（实测见 D7 自审）。**两面同取本身带一个假阳性方向（纯 `touch`）；它不是原理性残余风险——卷日志能区分，见第 23–24 格——而是一个有明确修法、修法自身带两个静默陷阱的待接线项。**

第 10 步是新增的，因为第 0b/8 步这对只包住「跑」：**窗口关闭后去读源码解释读数，那是第二个窗口**，而计数与机制会并列写在同一份报告里、看起来同样可信（实测见 D7 其七）。

## 7. 边界

- 三个脚本随本文存放于 `artifacts/mutation-tools/`（`preflight.sh`、`pair.sh`、`mutate.mjs`），均为本文所述且已自证的版本。它们默认 `SRC` 指向 `plugin/skills/auto-goal-v2`，换仓需改该变量。**D5–D6 无脚本**——D5 是「同一命令重复跑并比对」的纪律，D6 是「读源码验机制前提」的纪律。**D7 有脚本但形态特殊**：`artifacts/tree-snapshot.mjs --run "<cmd>"` 是 **runner 包装器**，不是前置检查，见下条。
- **D7 的载体必须与它的作用域同构**：
  - **不能是 `preflight.sh` 的一格。** D7 的判定是「两次快照相同」，而 `preflight` 按定义在跑之前结束——它最多能做 OPEN 那一半，而只有开快照挡不住窗口中段的写入。**把双端判据实现成单端检查，会让人以为过了 preflight 就安全**，那是新造一个恒绿探测器，正是第 9 格的形态。
  - **判定对象是读数，不是仓库状态。** 同一棵静止的树上，跑套件与跑 lint 是两段测量，各自需要自己的窗口。做成「环境检查」会让人读作通过一次、全程有效，而这恰恰是它要防的那种读法。
  - **正确形态是包住「跑」这个动作的 runner 包装器**：`--run` 使判定成为该次运行的属性，而不是某个人事后记得去检查的事。层级 1（逐轮冻结副本 + 指纹绑定）是同一形态的升级——把 `--run` 的「首尾比对」换成「复制 + 绑定」，**它同样不能进 `preflight`：层级 1 的产出是一条读数与一份副本指纹的绑定，而 `preflight` 绑不了它没见过的读数。**
  - 通用化：**判据的载体必须与判据的作用域同构。** 单端的检查装不下双端的判据；跑之前的钩子装不下关于「跑」的结论。
  - **升格为独立判据（两处独立实例收敛）：凡是靠读者记住才成立的前提，都要设法变成读数自带的字段。** 两处实例互不知情却收敛到同一形态：`--run` 让窗口完整性成为该次运行的属性而不是事后回忆；`--verify` 没有留一句「记得验证阅读窗口」，而是让 INTACT 的 `--run` **主动把 `--verify <digest>` 递到手上**。判别式很简单：**一条前提若只存在于文档或注释里，它的失效方式是「有人忘了」，而那不会留下任何痕迹**；变成读数字段后，失效方式变成「字段对不上」，那是看得见的。
    - 由此可推出一条**已由守护兑现**的项：**digest 本身不携带采样面**，裸 `42483a4d050e` 无法自证它出自 89 个文件还是 46 个。守护现已印成 `all-89:891c21fa1bf6`（`tree-snapshot.mjs:97` 的 `surfaceLabel`，ledger 头写 `# surface all-89`，`--verify` 兼收裸形式并对无标签旧 ledger 退回带标签前的行为）。**遗留在本文里的裸 digest 都产生于该标签之前，按这条判据应读作可疑。**
- **多指标合取不是单指标的严格加强，每加一面就加一类新的假阳性。** 实测三格：内容改 + `touch -r`（只取 mtime 谎报绿）、A→B→A（只取 hash 谎报绿）、**纯 `touch`（两面同取谎报红，而真相是没变）**。前两格让人得出「取得越多越严越好」，第三格推翻它。正确的问法不是「够不够严」，而是**每一面各自在回答哪个问题**：hash 答「字节变了吗」，mtime 答「有人写过吗」。第 17 格需要的恰是后者，所以 mtime 必须留，但**它不该有权把窗口判死**。**这条与第 17 格耦合、不能分开裁决：检出自反写入所依赖的那一面，正是产生假阳性的那一面。**
- **`TOUCHED` 这个标签正确，但它标注的是两件判决相反的事**：无害 `touch`（不该判死）与写—还原（必须判死，因为中途存在过第三个状态——实测中途读数 `6146 B / a1b6859dd9a4b6e4`，一个首尾快照里都不存在的状态）。两者读数逐位相同（`6125 / 71244ccd19586f41` 两侧恒等），**而区分它们所需的信息「中途是否存在过别的字节」不在被观测对象里**——与其八同形。**但「不在被观测对象里」不等于「取不到」**（第 23 格更正）：文件系统是第二个观察者，卷日志的 `Reason` 位带这个字段，实测甲判 `DATA_*`、乙判 `BASIC_INFO_CHANGE`，**判决相反**。`--verify` 已用内容面兜住（实测 `READ WINDOW INTACT (bytes)` 正确放行），缺口只在 `--run`。**判决保持 VOID**——漏判让人引用无效读数，多判只是让人白重跑一次；**代价不对称时判据应偏向更便宜的那种错误，但必须写下来，否则下一个人会把它当缺陷去修。** 而**代价不对称是判决的理由，不是不诊断的理由**：VOID 时多印一行「甲 / 乙 / INCONCLUSIVE」，多判仍然多判，但人知道自己遇到的是哪一种。把判决与诊断拆开，与把 `TOUCHED` 的标签与判决拆开是同一个动作。
- **聚合数字必须能拆回它由哪些个体事件组成**：`green 6 / red 2 of 8` 与被测 flake 的 ~1/8 同数量级，而两个红实为测量装置自己的动静（探针追加 21 B 越了 `SKILL_MD` 余量 19 B；另一 Agent 半写测试文件），**被测的那个 flake 一次没红**（`grep "late bytes"` = 0）。比例本身不携带区分两个机制的信息。救它的是「按断言名分类而非只计数」，与 `assert.ok(assignments > 0)` 同族；**且分类必须先于聚合写下来**——事后拿着 `2/8` 回去分类，日志早滚掉了。这是「前提要变成读数字段」的第三处独立收敛。
- **同一个根因在不同位置的可见性不同，而更贵的那处更安静**：kill 抢在 spawn-out 之前这一个竞态，在 `raw_bytes > 0` 上表现为 1/8 的**红**（吵闹、被追查、被修），在隔壁 grace 测试里表现为**全绿空转**（无 writer 持管道 → `'close'` 立刻到达 → `timed_out` 真、reason 对、elapsed 远低于上界，每个断言都过而什么都没测）。**红是自曝的，空转不是**；只报红的那处等于只修了便宜的一半。收口是下界断言（`assert.ok(elapsed >= CLOSE_GRACE_MS)`），把空转形态关死。
- **「被测对象存在」不蕴含「被测对象产生了读数」**：曾有一条建议把 `raw_bytes > 0` 挪进 grace 测试，理由「那里 writer 必然存在」——错，那里 writer 活过整个 grace 窗口（`ACE_GHOST_DELAY_MS = timeoutMs + CLOSE_GRACE_MS + 4000`），late bytes 永不落盘，`raw_bytes` 恒 0。**「writer 存在」与「writer 的字节落在观测窗口内」是两个命题。** 同一混淆在另一层出现过：D7 `--run` 的 `WINDOW INTACT, BUT THE RUN FAILED` 分支拦的正是「树静止得完美而读数为空」。
- **校准量不得依赖被校准量**：用一次会被 `timeoutMs` 截断的整体计时去推 `timeoutMs`，读数随 `timeoutMs` 线性走（实测 50→74-90、76→102-107、150→182-186、60000→395-414），**因此永远自洽、且永远把 deadline 钉在竞态带里**。与第 13 格（度量选错）的区别是**反馈方向**：独立于被测量的坏度量会一直错在同一处，多测几次仍是同一个坏读数；**被被测量驱动的坏度量会跟着你走**，对参数的每次调整都给出配合的响应，因此重复观测无法发现它，只能扫**极端档**（与第 18 格同一手段）。
- **两个数相差一倍时，不要用「应该来自测法」结案**：正确排布是**把两种测法在同一二进制、同一段时间里交替跑**——不同时段、不同负载的两组数无法分离原因。实测三步：同测法交替自对照即跨了双方两个区间（191-315）；`delay=1000` 与 `delay=0` 中位重合（223 vs 219）；整次 dispatch **一贯高于** parent-only（374 vs 190），即被指控的测法产生的是**高**值而非低值，**归因方向是反的**。
- **修复正确而理由错误，仍然要改理由**：`measureDetachLatency()` 改测 parent 的 spawn→exit 是对的，且恰因它不再让被校准量参与测量——但当初写下的理由（「delay=0 让 writer 与 parent 退出重叠」）在这个 stub 上不成立（`NAP_MS` 在 `dispatch-ghost-stub.c:129`，位于 `detach_writer()` 之后，parent 在 `:125` 就 return，**delay 不在 parent 路径上**）。**理由是下一个人做同类决定时唯一能继承的东西**：代码告诉他做了什么，理由才告诉他为什么不能改回去。**这一格的危险是它自带一致性——换机器、加轮次、提高精度都不会暴露它。**
- **判据只保证结论可归因，不保证结论正确。** 存活方向的 (b)「死代码 / 不可达分支」与 D6 的机制前提，都必须由人读代码判断，本文给不出机械判据。(c)「假 skip」可机械排除（比 `skipped` 计数），(a) 亦可（needle 自检）。
- **D7 的「改了又改回」不再是残余风险，但代价升了一级**：首尾采样（层级 0）无法关闭它，**提高采样频率也不能**（`P(漏)` 归零需 `N ≥ W/d + 1`，而 `d` 由并发写入方决定）；关闭它需要层级 1——每轮冻结副本 + 指纹绑定读数，约 0.3s/轮。**层级 0 的正确读法是「未检出污染」，不是「窗口干净」。**
- **D7 的反向自证已完成，正向已补齐，且假阳性方向也已实测**：八格恒绿/自反检验各抓到一处真缺陷或排除一条替代做法，且**两个方向各有一格实测反例**（size+mtime 双恒等 → 只有内容面能抓；A→B→A 内容恒等 → 只有 mtime 面能抓），两面同取由此是必需而非冗余；**第九格测的是相反方向（守护会不会多判），实测为多**（纯 `touch` 判 VOID），它与第八格共用 mtime 那一面，**删掉即同时瞎掉第八格，故两格只能一起裁决**；采样函数四格控制组已实测；**「活树上取得静止窗口 ⇒ 读数可引用」这一正向格已实测**（末次写入静置 7 分钟、跨 4 分钟两次采样同值后开跑，首尾同 digest `42483a4d050e`，`tests 489 / pass 484 / fail 0 / skipped 5`），并在同 digest 上重复 8 轮零漂移。
- **D7 只覆盖「跑」，不覆盖「解释」**：窗口关闭后读源码来解释读数，那次阅读需要它自己的窗口。**计数可引用，机制不可引用，而两者写在同一份报告里看起来同样可信。** 判定分档：内容变了则机制作废；只有 mtime 变则机制仍可引用（屏幕上的字节就是跑过的字节）——不分档的守护会不断误报然后被忽略。
- **D7 回答「树变了吗」，不回答「变化来自哪里」**：把 mtime 变化归因给他人之前必须先排除观测方自己——审判据的灵敏度探针、副本比对、`touch` 都会写进被测树。**树只记「有人写过」，不记「是谁、为什么」，而这个信息不在树里**，只能靠观测方自报，所以这一格无法靠加强守护关闭。实证：本文曾把 team-lead 的探针写入（核到毫秒）当作「他人在改产品代码」的正面证据，结论已撤回。**同一结论若能用静态证据（import 关系、调用链）表述就优先用它**——静态证据不会因为「观测方就是写入方」而作废，也不随时间过期。这也是这一族里唯一的**阳性**误读：其余各格是把「没发生」读成「验过了」，这一格是信号为真而信号源是自己。
- **度量的分辨力要按它的实际输入分布检验**：size 指纹能通过一个用随机字节做的灵敏度控制组，却对同长度算子替换（`===`↔`!==` 等，本树 631 个点位）全族失明——**而那正是变异测试的主力族**。选指纹前先列出打算做的变异族，再问这个指纹能不能区分它们。
- **验证并发能力的探针必须独立于被守护的进程**：同进程 `setTimeout` 会被 `spawnSync` 堵死而从不触发，**在自己被阻塞的进程里模拟并发，模拟出来的是「没有并发」**。而一个从不触发的探针与一个被正确处理的探针，在输出上都是「没报错」。
- **每个门禁都要有一条「我确实匹配到了东西」的前提断言**：否则门禁的空转与门禁的通过在输出上不可区分（实测：CRLF 令 `^`-anchored regex 零匹配，门禁自己成了空转断言）。这与 F1/F2/F10 三次假 skip 同根——**门禁的启用条件本身没有被任何测试校验**。**这条有已发生案例而非构造案例**：`tests/ci-stub-gate-wiring.test.mjs:79-82` 的 `\r`-strip 修复是承重的（去掉它则匹配 0 处赋值并绿），救回它的正是同文件 `:111` 的 `assert.ok(assignments > 0)`。本仓 CRLF 边界正好落在 skill 树内外之间（树外 `src/` 14/14 + `.github/` 5/5 全 CRLF，树内 0/89），**所以在 skill 目录里验过的行锚门禁，往树外搬两个方向都会静默失效**。
- **否定性结论的成立条件通常不在被观测对象里，而在观测手段里**：「没有 CRLF」「没有并发问题」「没有匹配到违规」——这三句的真假都不由被观测对象单独决定。实测：MSYS `grep` 剥 CR 后报「全仓 0 个 CRLF 文件」（`grep -c $'\r'` 得 0/exit 1，`grep -Uc` 得 2/exit 0），**用来检测该问题的工具自己隐藏了该问题并给出干净结论**。任何「没找到」的结论，都要先证明这个工具在同类输入上找得到。
  - **实现上要求把两种「没找到」分开印**：`INCONCLUSIVE`（检测器不可用）与 `false`（检测器可用且确实没有）。实测一例：卷日志探针按错字段序取 reason，六条记录全 `null`，打印 `DATA_* : false`，而事实是六条全带 `DATA_*`（第 22 格）。
  - **朝确认方向坏掉的度量最难自查**：那个 `false` 恰好印证了双方本就相信的结论，所以两个人都差点直接引用它。随机坏掉的度量会给出与预期无关的数而被察觉；**沿着预期坏掉的度量读起来像证据。** 判别法与第 0 步同一条：先在**已知有 X** 的输入上跑检测器，看它是否报得出来。
  - **同一形态的第三个实例是本地化标签**：`fsutil` 输出的字段名在本机是 `Ô­Òò` / `Êý¾Ý½Ø¶Ï`，任何按英文标签 grep 的解析都会静默返回「无证据」。**按位置或按数值取，不按人类可读文本取**——译文是环境属性，不是数据属性。
- **跨边界扫描若两侧读数完全相同，先疑「扫的不是那根轴」**：实测 `CLOSE_GRACE_MS` 两侧 4 档 × 3 次 `raw_bytes` 全 0——连 0ms 档也是 0，说明延迟不是控制变量（真因是 `_spawnl` 226–377ms 与 150ms kill 的竞态）。检验方法是取该轴的**极端档**。**加轮次不能纠正扫错的轴**，与「提高采样频率不能关闭改了又改回」同理：量变治不了方向错。
- **凡是靠读者记住才成立的前提，都要设法变成读数自带的字段**（三处独立实例收敛：`--run` 让窗口完整性成为运行的属性；`--verify` 由 `--run` 主动递出而非留一句提醒；**聚合比例旁必须带「由哪几条断言构成」，且分类先于聚合写下**）。判别式：**一条只存在于文档或注释里的前提，失效方式是「有人忘了」，不留痕迹**；变成字段后失效方式是「字段对不上」，看得见。**本文曾欠这条的账，现已由守护兑现**：digest 从裸 `42483a4d050e` 改为 `all-89:891c21fa1bf6`（`tree-snapshot.mjs:97`，`--verify` 两种形式都收，且 ledger 头部写入 `# surface all-89` 以便拒绝跨采样面比较）。**本文中此前写下的裸 digest 全部属于该标签存在之前，引用时须补「采样面 89」这个记忆式前提——这正是该标签要消除的形态，遗留处按判据应读作可疑而非可信。**
- **一条误配的判据比没有判据贵**：它让每个人为一个已被别处覆盖的风险重复付钱，且**因为看起来严谨，没人会质疑它**。实例：把「同 digest 下 fail 数漂移」记成已确认，会催生「每个计数跑 N 轮」这条纪律，而该风险属 D5（确定性）而非 D7（同一性）。「多加一条总比少一条好」这个直觉在判据上是错的。
- **自称的确信度是第三个「自称而无人校验」的面**：F1/F2/F10 是门禁自称适用性，`-newermt` 回扫是自称窗口无写入，「已确认」是**报告作者自称机制已查明**。第三个传播最远——引用者把它当行动依据，不会回头看它凭什么被标成已确认。**确信度是报告里唯一一个不由数据决定、却决定读者行为的字段。**
- **枚举排除项，不枚举包含项**：枚举包含项只在枚举正确时 fail closed，而没人能随树生长维持它正确；枚举排除项默认 fail closed——新目录出现即被纳入，漏掉一个必须是显式可评审的动作。并注意**第一个枚举猜测后面往往躲着第二个**（目录范围取全之后，后缀过滤仍会漏掉运行时读的 markdown）。
- **套件自身的不确定性是 D7 作用域外的独立风险，本仓尚无证据表明它实际发生**：曾观测到同 digest 下 fail 数不一致，但成因有两个候选（套件不确定 / 守护盲区 46/89），盲区已修，修后累计 12 轮同 digest 零漂移。**真要防它用的是 D5（跨格差异复现 ≥3 次），不是加强 D7**——D7 关闭的是被测对象的同一性，不是它的确定性。
- **任何度量在用于立判据前必须先验它自己，且必须两个方向分别验**：稳定性控制组（无写入连采同值）只证明了「快照不同 ⇒ 树真变了」这一阳性方向；D7 依赖的「快照相同 ⇒ 树真没变」是阴性方向，须由灵敏度控制组单独证。实测：mtime 面阳性方向满分而阴性方向 65% 谎报；错误 cwd 下的采样函数三连输出空输入 md5 `d41d8cd98f00`，稳定性满分而对任何写入失明。**恒绿探测器有一个镜像形态：恒红探测器**，它每次都像在尽责工作；而**「只验了一个方向」比这两者更常见**，因为探测器看起来确实在变化。
- **窗口证据会过期，且过期不可见**：`-newermt` 回扫只在闭窗后立刻执行才有完整证据力（本树实测失明文件数 0 → 8/89 用了 28 分钟，且只增不减）。晚做的回扫返回空集，读者会当作验过了。**回扫不是弱一点的快照，是另一种东西**——快照回答「此刻树是什么」，回扫回答「此后没人再写过」，后者的答案会腐烂。**快照必须在窗口内取。** 这是**假 skip 的第四处形态**（前三处 F1/F2/F10 是门禁自称「本环境不适用」），同根一句：**自称的那个状态，它的成立条件本身没被任何东西校验。**
  - **但这条禁令的根据要按失效模式立，不按「回扫 / 快照」立**（第 23–24 格实测更正）。同为事后追溯的卷日志不共享这个缺陷：mark 已滚出时 `fsutil usn readjournal` **非零退出**，而不是返回干净空集（实测 `firstUsn` → exit 0 / 396158 条；`firstUsn - 1e6` → exit 1；`0x1` → exit 1）。**「什么都没写」= exit 0 + 零记录；「我无法判断了」= 非零退出。** mtime 回扫不可用是因为它把这两者塌缩成同一个空集，**回扫只是静默失效最常见的形态，不是禁令本身**。卷日志的保留期同样有界（32 MB 配额，一次全套跑耗 1.04 MB，≈31 次跑后滚出），但界一到它就喊——**有界而喧闹的证据可用，无界而沉默的证据不可用。**
- **一个正确的机制发现，可以被它自己的实现连续四次几乎毁掉**（第 22–25 格是同一次调查）：机制真（卷日志确实带那个字段）→ 解析器按错字段序取值，把「读不懂」印成 `false` → 归属按 basename，把别处的写入判到守护文件上 → 取 ID 走 `Number` 静默丢精度，错 1 的 ID 匹配零条记录 → 键的时刻取错，`sed -i` 换掉 inode 而新 inode 必带 `DATA_EXTEND|FILE_CREATE`。**五步里只有第一步是关于世界的，其余都是关于实现的，而它们全部以「看起来是结论」的形式输出。** 所以一条新证据源接线时，要分别问：字段在吗、我读对了吗、我归属对了吗、我的键精度够吗、**我的键和证据同期吗**——**这五个问题的失败都长得像一个答案。**
- **归属键要同时在作用域和时刻上与证据对齐**：作用域不够宽 → 把别人的证据算到自己头上（basename 在卷里有 1376 个同名）；时刻不够早 → 查的是另一个对象（`sed -i` 后路径指向新 inode）。**「唯一」和「正确」是两个条件，前者不蕴含后者。** 实测两次误判都偏向更严的那一侧，也就是偏向「我原本的判决是对的」——**偏向确认的误判不会引起怀疑，这是本文里第三次遇到同一个方向性问题。**
- **结果站住不等于方法站住**：本任务有一份读数（`477 tests / pass 471 / fail 1 / skipped 5 @19:55:51Z`）经全树复验仍然有效，但它需要三层限定同时成立——范围窄（46/89）、回扫做得早、以及**运气**（那 11 秒恰好没人动视野外的 43 个文件），而当时无人知道第一层成立。**一个读数可以同时「有效」和「不该被后续引用」**：有效是相对当时的判据，不该引用是因为判据升级了。**一份靠运气成立的读数与一份无效读数在方法层同级。**
- **本文自己的写死数字同样会过期**：`46/87`、`42/89`、`89/89`、`631 个点位` 全是某一时刻的值，引用须连时刻一起引用。一份指出「覆盖面清单会过期」的文档不能例外地相信自己的数字。
- **D7 是观测者侧判据，不是流程管制**：它不要求锁仓库、不要求任何人停止写代码，只要求读数带上有效性边界。把它写成「测量前必须冻结仓库」会挡不住真正的问题（并发写入是协作常态），且会让人因为代价太高而整条跳过。实证：本任务观测期内至少四个互异快照（A / B / C / probe），树在数十秒量级持续变动——这是常态而非异常。
- 判据针对**离线**套件。live 用例花真钱，不纳入变异复验。
- D1 的 180s 是经验值：本任务观测到的修复落地窗口为 2 分钟量级（B2 门禁 02:44 → 测试 02:46；fixture 02:47 → 测试 03:05 则达 18 分钟）。**D3 正是为了覆盖 D1 阈值兜不住的长窗口**。

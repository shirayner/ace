## 1. 背景与目标

### 1.1 问题定义

软件研发是知识密集型工作，但大量时间消耗在**低创造性但高复杂度的转换环节**：需求 → 设计、设计 → 代码、代码 → 测试。这些环节高度依赖经验积累，却难以沉淀和复用。

AI Coding 工具（Claude Code、Codex）已在局部环节被验证有效，但存在以下问题：
1. **孤岛化**：每个工具各自为战，上下游数据不流通
2. **无记忆**：团队经验、历史决策不能被 AI 感知
3. **不可观测**：AI 做了什么、为什么、质量如何，无法追踪
4. **无标准流程**：AI 介入方式因人而异，质量参差不齐

### 1.2 平台目标

设计一个 **AI 驱动的端到端需求交付平台**，实现：

| 目标 | 度量指标 |
|------|----------|
| 需求到交付 Lead Time 降低 | 目标降低 40% |
| AI 辅助率提升 | 目标代码 AI 生成率 > 60% |
| 人工干预次数降低 | 单需求人工确认 < 5 次 |
| 质量不下降 | 评审一次通过率 > 85% |

### 1.3 设计原则

- **流程驱动**：每个研发阶段有明确的 AI 介入点、输入/输出规范和质量门禁
- **知识复用**：团队经验和历史决策被系统化沉淀，在后续任务中自动注入
- **人机协同**：AI 负责生产，人类负责决策审批；关键节点强制对齐
- **可观测优先**：所有 AI 操作链路可追踪、可审计、可度量

## 3. 用户交互层设计

平台提供三种交互入口，共享同一套后端 API，保持体验一致性。

### 3.1 CLI（命令行界面）

**定位**：开发者的主要日常交互入口，集成到终端工作流。

```bash
# 创建需求
ace req new "用户可以通过手机号注册，系统发送验证码"

# 查看需求交付进度
ace req status REQ-2024-001

# 推进到下一阶段
ace req advance REQ-2024-001

# 在当前阶段调用 AI
ace ai generate --phase design --req REQ-2024-001

# 查看当前任务
ace task list

# 触发 AI 编码
ace code --task TASK-001

# 查看 AI 决策日志
ace log decisions --req REQ-2024-001
```

**关键设计**：
- 所有命令支持 `--dry-run` 预览即将发生的操作
- 支持 `--interactive` / `--auto` 两种模式（默认 interactive，CI 中用 auto）
- 输出支持 `--format json/table/markdown`，便于管道处理

### 3.2 Portal（Web 界面）

**定位**：产品经理、技术 Lead 的管理视图；可视化需求交付全貌。

**核心页面**：

| 页面 | 主要功能 |
|------|----------|
| 需求看板 | 需求列表、状态流转、阶段进度 |
| 需求详情 | PRD、设计文档、代码 PR、测试报告的关联视图 |
| AI 操作历史 | 可视化 AI 在每个阶段做了什么、耗时/Token 消耗 |
| 知识库管理 | 浏览/编辑团队规范、内部框架文档、历史决策 |
| 效率大盘 | Lead Time 趋势、AI 辅助率、质量指标 |

### 3.3 Desktop（桌面应用）

**定位**：深度集成 IDE 工作流，让开发者不离开编辑器即可感知需求上下文。

**核心能力**：
- 在 VS Code / IntelliJ 侧边栏展示当前任务的需求上下文
- 代码生成时自动注入项目画像和规范
- Review 意见直接在编辑器中呈现
- 与 Claude Code 插件深度集成

## 4. 端到端研发流程设计

### 4.1 需求阶段

#### 4.1.1 需求撰写：灵感 → PRD 草稿

**AI 介入方式**：主动式，AI 辅助将非结构化想法转化为标准 PRD。

```
输入：
  • 自然语言描述（必填）
  • 参考链接/竞品截图（可选）
  • 相关历史需求 ID（可选，触发关联检索）

处理流程：
  1. Context Factory 注入：
     - 项目技术画像（技术栈约束）
     - 同领域历史需求（TOP-3 相似）
     - 团队 PRD 规范

  2. AI 澄清问题（Hard Gate）：
     - 必须澄清项：用户角色？核心场景？验收标准？
     - AI 主动识别歧义，一次性提问

  3. 生成结构化 PRD：
     - 用户故事（Given/When/Then 格式）
     - 业务规则
     - 非功能性需求（性能/安全约束）
     - 验收标准（可测试）

  4. PRD 人工确认（Hard Gate）：
     - 必须经过人工审阅并确认

输出：
  • PRD 文档（Markdown）：
    - 需求背景与价值
    - 用户角色定义
    - 用户故事列表（US-1...US-N）
    - 业务规则
    - 验收标准
    - 不在范围内的事项

质量门禁：
  ✓ 所有必须澄清问题已回答
  ✓ 每个用户故事有明确验收标准
  ✓ 人工确认通过
```

#### 4.1.2 需求评审：PRD 草稿 → PRD 定稿

**AI 介入方式**：辅助式，AI 提供评审检查清单和潜在问题识别。

```
AI 在评审阶段的角色：
  1. 自动运行 PRD 质量检查：
     - 完整性检查（验收标准是否可测试？）
     - 一致性检查（需求间是否有矛盾？）
     - 可行性预评估（技术约束是否可满足？）

  2. 生成结构化评审报告：
     - ⚠️ 可能遗漏的场景
     - ⚠️ 模糊的描述（附修改建议）
     - ⚠️ 与历史决策冲突的设计

  3. 多角色评审协调：
     - 产品视角：用户价值是否清晰？
     - 技术视角：技术可行性与实现复杂度？
     - 运营视角：上线后如何度量效果？

输出：
  • PRD 定稿（版本号递增）
  • 评审意见记录（含解决方案）
  • 变更说明（相比草稿的差异）
```

### 4.2 技术设计阶段

#### 4.2.1 技术设计：PRD → 技术方案

**AI 介入方式**：主导式，AI 完成技术方案的主体，人类审批关键决策。

```
输入：
  • PRD 定稿
  • 项目技术画像（自动注入）
  • 相关历史决策（语义检索注入）
  • 内部框架文档（按涉及技术域注入）

处理流程（七步正向设计）：

  Step 1 - 系统定位
    AI 给出一句话系统本质（如"一个基于 OTP 验证的用户注册服务"）

  Step 2 - 范围界定
    明确"做/不做"清单、外部依赖、接口边界

  Step 3 - 约束分析（六问）
    ├── 规模：DAU 多少？请求量 QPS？
    ├── 读写比：读多写少？
    ├── 一致性：强一致 or 最终一致？
    ├── 增长：未来 12 个月增长预期？
    ├── 风险：最大可接受故障时间？
    └── 约束：现有基础设施、团队熟悉度？

  Step 4 - 信封估算
    自动计算：QPS / 存储容量 / 带宽，识别设计瓶颈

  Step 5 - 关键技术决策（ADR）
    每个岔路口记录：
    ├── 问题：面对的技术问题是什么？
    ├── 选项：备选方案 A/B/C（含被否决的）
    ├── 选择：选了哪个？
    └── 理由：为什么？引用了哪些约束？

  Step 6 - 挑战验证（反脆弱检查）
    AI 主动质疑自己的设计：
    ├── 一致性/幂等：重复调用是否安全？
    ├── 韧性：依赖服务故障如何降级？
    ├── 热点/规模：高并发场景是否会有热点？
    └── 安全：是否有越权路径？

  Step 7 - 整合输出

输出：
  • 技术方案文档（Markdown）：
    - 系统架构图（组件交互）
    - 数据流图（核心请求链路）
    - 数据模型（核心实体 + ER 图）
    - SOA 契约（接口定义，OpenAPI 格式）
    - DB 设计（表结构 + 索引）
    - ADR 决策记录
    - 风险清单

  • 知识库写回：
    - 新增/更新 ProjectSpec
    - 新增 HistoricalDecision 记录

质量门禁：
  ✓ 所有 ADR 决策有理由记录
  ✓ 挑战验证通过（无严重风险未处理）
  ✓ 人工审批通过
```

#### 4.2.2 技术设计评审

```
AI 辅助评审：
  1. 设计 vs 需求一致性检查（PRD 中每个用户故事是否在设计中有实现路径）
  2. 性能可达性评估（信封估算是否支持需求中的性能要求）
  3. 与团队现有架构的一致性检查
  4. 安全检查（认证/授权/数据隔离）

输出：
  • 评审通过确认（进入编码阶段的前置条件）
  • 评审意见 + 修改记录
```

### 4.3 编码阶段

#### 4.3.1 编码实施

**AI 介入方式**：执行式，Coding Agent 按任务列表逐项实现。

```
输入：
  • 技术方案文档（design.md）
  • 任务列表（tasks.md，由 AI 从设计中拆解）
  • Context Factory 构建的上下文包：
    ├── 项目技术画像
    ├── 代码约定（命名规范/包路径规则）
    ├── 内部框架使用指南
    ├── 相关历史经验（特别是负面经验）
    └── 类似历史决策

执行流程（每个任务）：
  1. Agent Router 选择合适的 Coding Agent
  2. Context Factory 打包上下文（分层注入）
  3. Coding Agent 执行：
     ├── TDD：先写测试（RED） → 再实现（GREEN） → 重构
     ├── 每步输出：变更文件列表 + git diff
     └── 实现完成后：运行测试验证
  4. 双重审查：
     ├── Spec Review：实现是否符合任务规范？
     └── Code Review：代码质量是否达标？
  5. 人工确认（可选，配置化）

输出：
  • 代码变更（git commit per task）
  • 单元测试（覆盖率 ≥ 80%）
  • 任务完成报告（每个任务的验证证据）

质量门禁：
  ✓ 编译通过
  ✓ 单元测试全通过
  ✓ Spec Review 通过
  ✓ Code Quality Review 通过
```

#### 4.3.2 Code Review

```
AI Code Review 模式：

  三层分析：
  ├── 正确性层：逻辑错误、边界条件、并发竞态
  ├── 健壮性层：异常处理、资源释放、输入验证
  └── 设计质量层：命名、职责单一、DRY、耦合

  上下文感知：
  ├── 注入团队编码规范（自动）
  ├── 注入历史 Review 经验（相似代码的历史意见）
  └── 注入安全检查清单

  输出格式：
  [Critical] file.java:42 — 未处理 null 返回值，可能 NPE
    建议：添加 null 检查或改用 Optional

  [Warning] UserService.java:108 — 方法过长（>50行），违反 SRP
    建议：提取 validateUserProfile() 为独立方法

  [Suggestion] ...

  分级处理：
  Critical → 阻塞合并，必须修复
  Warning  → 人工判断是否修复
  Suggestion → 可选优化

  知识回写：
  ├── Review 意见存入经验记忆（用于后续类似代码的提前规避）
  └── 高频问题汇总为团队规范建议
```

### 4.4 测试阶段

#### 4.4.1 测试用例生成

```
AI 生成三类测试：

  单元测试（UT）：
  ├── 输入：被测类 + 框架信息
  ├── 覆盖：正常路径 + 异常路径 + 边界条件
  ├── 框架：JUnit 5 + Mockito（Java）/ Jest（TS）
  └── 质量门禁：行覆盖率 ≥ 80% / 分支覆盖率 ≥ 70%

  接口测试（IT）：
  ├── 输入：OpenAPI 契约（从技术设计输出）
  ├── 生成：每个接口的正常/异常/边界测试用例
  ├── 工具：REST-assured / Postman Collection
  └── 执行：每次 PR 合并后自动运行

  端到端测试（E2E）：
  ├── 输入：PRD 中的用户故事（Given/When/Then）
  ├── 自动将用户故事转换为 E2E 测试场景
  ├── 工具：Playwright（Web） / Appium（Mobile）
  └── 执行：每次 Release 前运行
```

#### 4.4.2 测试执行与修复

```
AI 参与测试失败修复：

  检测到测试失败时：
  1. 分析失败原因（错误堆栈 + 测试代码 + 被测代码）
  2. 判断是代码 Bug 还是测试用例本身的问题
  3. 生成修复方案（附置信度说明）
  4. 执行修复 + 重新验证（最多3次重试）
  5. 超过重试次数 → 升级为人工处理

  Red-Green 验证（Bug 修复专用）：
  1. 先确认回归测试能检测到 Bug（失败）
  2. 再确认修复后测试通过
  3. 防止修复了一个点引入另一个问题
```

### 4.5 发布阶段

#### 4.5.1 发布前预检

```
AI 辅助预检清单：

  代码质量检查：
  ├── Sonar/Checkstyle 扫描通过
  ├── 安全漏洞扫描（OWASP/Snyk）
  └── License 合规检查

  功能完整性检查：

  ├── AI 分析本次变更的影响范围

  └── 生成回滚方案

  • 预检报告（通过/失败/警告）
  • 发布风险等级（低/中/高）

```

  ├── 发布后 30min 内对比基线，识别异常
  └── 告警自动关联到对应的代码变更

  ├── 告警触发时，AI 自动分析：
  │   - 相关日志（Trace 关联）

  经验闭环：
  ├── 生产事故 → 经验记忆写入（用于后续预防）
  └── 告警模式 → 更新发布预检规则

集成说明：
  本层需与公司现有监控平台（如 Prometheus/Grafana/SkyWalking）集成，
  平台负责 AI 层的智能分析，不替代基础监控设施。

### 5.1 统一 Agent 接口

### 5.2 三种 Agent 能力对比与适用场景

| 维度 | Claude Code | Codex CLI | Aider / Open Code |
|------|-------------|-----------|-------------------|
| **最适场景** | 复杂多步骤实现、需要 MCP 工具的任务 | CI/CD 流水线中的安全隔离任务 | 成本敏感、批量修复、可使用本地模型 |
| **工具丰富度** | ★★★★★（15+ 专用工具 + MCP 扩展） | ★★★（基础文件+Shell） | ★★★（Git 深度集成） |
| **沙箱安全** | 需外部容器 | ★★★★★（原生 Docker Sandbox） | ★★★（无网络访问） |
| **上下文传递** | CLAUDE.md + @path 引用（最结构化） | --context flag（有长度限制） | --read 文件（充裕） |
| **可观测性** | 原生流式 SDK（逐步骤可观测）★★★★★ | REST API 轮询 ★★★ | CLI 输出解析 ★★★ |
| **成本** | Claude API 计费 | OpenAI API 计费 | 可接本地模型（零 API 成本）|
| **模型** | Claude 3.5 Sonnet / Opus | GPT-4o / o4-mini / o3 | 任意支持 OpenAI API 的模型 |

### 5.3 上下文传递协议

上下文分四层，按 Token 预算优先级依次注入：

```
Level 1 — 项目级永久上下文（每次任务都加载，不可裁剪）
  ├── 技术画像（架构/分层/技术栈）
  ├── 编码规范（命名/包路径/测试策略）
  └── 框架约定（内部框架使用方式）

Level 2 — 变更级上下文（当前需求生命周期内共享）
  ├── 需求文档（PRD）
  ├── 技术设计（design.md）
  └── 接口定义（OpenAPI）

Level 3 — 任务级上下文（单次任务执行时注入）
  ├── 具体任务描述
  ├── 目标文件列表
  ├── 验收标准
  └── 依赖任务产出物

Level 4 — 执行级上下文（失败重试时追加）
  ├── 上次执行日志
  ├── 错误信息
  └── 已完成步骤摘要

Token 预算分配（当上下文超出限制时）：
  强制保留 → L1（不可裁剪）
  高优先   → L2 + L3
  按相关度 → 经验记忆（负面经验优先）
  按相关度 → 历史决策
  最低优先 → 相似历史需求摘要
```

## 6. 知识记忆系统设计

### 6.1 知识分类与数据模型

平台管理两大类知识：**知识库**（相对稳定的项目/团队知识）和**记忆系统**（从 AI 操作中提炼的经验）。

```
知识库（6 类）：

  ProjectProfile     — 技术画像：技术栈、架构风格、分层规则、代码约定
  TeamConvention     — 团队规范：编码规范/评审规范/Git 规范（按域分类）
  InternalFramework  — 内部框架：API 签名、代码模板、已知坑点、升级指南
  ProjectSpec        — 项目 Spec：接口定义、数据模型、业务规则（关联需求）
  HistoricalReq      — 历史需求：交付结果、耗时、复杂度、关联 PR（供相似检索）
  HistoricalDecision — 历史决策：问题背景、备选方案、决策理由、事后影响

记忆系统（2 类）：

  ExperienceMemory   — 经验记忆：情境→行动→结果→教训（按强化次数加权）
  PreferenceMemory   — 偏好记忆：代码风格/工作流偏好（用户级/团队级）
```

### 6.2 存储架构

```
存储分层：

  关系库（MySQL）      — 元数据、版本管理、精确查询、生命周期管理
  向量库（Qdrant）     — 语义检索（相似需求/决策/经验的向量距离搜索）
  文件系统（Git 仓库） — 大文本内容（Spec 文档、代码模板）的版本化存储
  缓存（Redis）        — 热点知识（TTL 30min，减少 MySQL/Qdrant 压力）

检索策略：
  精确查询 → MySQL（按项目/类型/状态/版本）
  语义检索 → Qdrant（相似度 > 0.65，按权重/时效性排序）
  缓存优先 → Redis（命中则跳过下层检索）
```

### 6.3 Context Factory 工作流程

```
任务请求到达
    │
    ├── 解析任务：业务域、技术域、操作类型、涉及模块
    │
    ├── 并行检索（多路）：
    │   ├── [精确] 当前项目 ProjectProfile（全量）
    │   ├── [精确] 匹配业务域的 TeamConvention
    │   ├── [精确] 涉及框架的 InternalFramework
    │   ├── [语义] TOP-3 相似历史需求（摘要）
    │   ├── [语义] TOP-3 相似历史决策
    │   └── [语义] TOP-5 相关经验记忆（负面优先）
    │
    ├── 相关性过滤：
    │   ├── 向量相似度 < 0.65 → 丢弃
    │   ├── 超过 1 年未更新 → 降权 50%
    │   └── AI 生成且置信度 < 0.5 → 降权
    │
    ├── Token 预算分配：
    │   ├── 30% 项目画像 + 团队规范（固定）
    │   ├── 25% 框架知识
    │   ├── 20% 经验记忆（负面优先）
    │   ├── 15% 历史决策
    │   └── 10% 相似历史需求摘要
    │
    └── 输出 Context Packet：
        ├── systemContext（不可裁剪）
        ├── projectContext
        ├── relevantKnowledge
        ├── memoryInjections
        └── retrievalMetadata（用于可观测性追踪）
```

### 6.4 经验提取 Pipeline

```
触发事件（以下任一）：
  • 人工修改了 AI 输出
  • Code Review 被拒绝
  • 测试失败后 AI 修复了
  • 用户提供了显式反馈

提取流程：
  1. 上下文重建：读取 Trace（操作链路）+ AI 决策日志
  2. AI 分析：提炼"情境→行动→结果→下次建议"
  3. 去重合并：
     - 向量相似度 > 0.92 → 强化已有经验（weight++）
     - 0.75~0.92 → 关联标注
     - < 0.75 → 新建经验条目
  4. 置信度计算：f(来源权重, 强化次数, 时效性)
  5. 写入记忆系统

注入优先级（Token 有限时）：
  负面经验（outcome=negative）> 历史决策 > 正面经验示例
  理由：防止 AI 重复踩已知的坑，价值高于展示成功案例
```

### 6.5 知识生命周期管理

```
状态流转：
  draft（AI 生成，置信度低）
    → active（人工审核 or 高置信度自动激活）
    → deprecated（版本更新时旧版变为 deprecated）
    → archived（180天未引用 → 自动归档）

更新策略：
  ProjectProfile   → PR 合并触发增量分析，季度全量重建
  TeamConvention   → 人工审核门禁（AI 只提草稿，不自动激活）
  HistoricalDecision → 只追加 consequences（不允许修改原始决策记录）
```

### 7.2 核心指标体系

**效率指标**：

| 指标 | 度量方式 | 告警规则 |
|------|----------|----------|
| 需求交付 Lead Time（P50/P95） | release_time - requirement_time | 连续 3 个需求 > P95 基线 × 1.5 |
| 各阶段耗时 | phase_span duration | 设计阶段 > 3 天告警 |
| AI 辅助率 | ai_generated_lines / total_lines | < 50% 触发检查 |
| AI 输出修改率 | avg(modificationRatio) | > 0.6 连续 5 次 → 模型质量下降告警 |
| 人工干预次数/需求 | count(human_intervention) | > 8 次触发流程效率检查 |
| Token 消耗量/需求 | sum(tokens) per requirement | > 基线 × 2 → Context 膨胀告警 |

**质量指标**：

| 指标 | 度量方式 | 目标值 |
|------|----------|--------|
| 测试通过率 | passed / total | ≥ 95% |
| 测试覆盖率（行） | JaCoCo 报告 | ≥ 80% |
| Review 一次通过率 | approved / (approved + rejected) | ≥ 85% |
| Critical Review 意见数/需求 | count(critical) | < 3 |
| 生产缺陷中 AI 生成代码占比 | bug_blame → git_author | 持续追踪 |

## 8. 关键技术选型与决策

### ADR-001 流程引擎选型

**问题**：如何编排需求 → 设计 → 编码 → 测试 → 发布的多步骤、有状态的工作流？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Temporal（推荐）** | 工作流持久化、自动重试、可视化调试、支持长时间运行 | 引入额外依赖，学习曲线 |
| Spring Statemachine | Spring 生态集成简单 | 不支持分布式持久化，长流程可靠性差 |
| 自研状态机 | 完全可控 | 开发成本高，重复造轮子 |

**决策**：选用 **Temporal**。需求交付流程是典型的长时间运行工作流（天级别），Temporal 的持久化执行模型（Workflow 中断后可从上次断点恢复）与平台需求高度匹配。

---

### ADR-002 向量数据库选型

**问题**：如何存储和检索知识库中的语义向量？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Qdrant（推荐）** | 自托管（数据不出内网），支持 payload 过滤（精确+语义混合查询），性能优秀 | 需自行运维 |
| Pinecone | 托管服务，零运维 | 数据出公司，合规风险 |
| pgvector | 与 PostgreSQL 集成，无额外依赖 | 大规模场景性能不如专用向量库 |

**决策**：选用 **Qdrant 自托管**。内网数据合规要求；同时支持"向量相似度 + metadata 过滤"的混合查询，避免全量向量扫描。

---

### ADR-003 Coding Agent 主力选型

**问题**：哪种 Coding Agent 作为默认选择？

| 场景 | 推荐 Agent | 理由 |
|------|-----------|------|
| 默认/复杂多步骤 | Claude Code | MCP 扩展性最强，工具链最完整，SDK 可观测性最好 |
| CI/CD 安全隔离 | Codex CLI（Docker 模式） | 原生沙箱，不可信代码的安全执行 |
| 高频/批量/简单修复 | Aider + 本地模型 | 零 API 成本，可接 Ollama |
| 全栈/浏览器操作 | OpenHands | 原生浏览器 + 终端 + 文件系统 |

**决策**：**Claude Code 为默认 Agent**，其余 Agent 按路由规则按需启用。

---

### ADR-004 知识更新策略（人工 vs 自动）

**问题**：AI 提炼的知识可以自动激活吗？

**结论**：分类处理。

| 知识类型 | 更新策略 | 理由 |
|----------|----------|------|
| TeamConvention（团队规范） | **人工审核必须** | 规范影响全团队所有后续代码，误激活代价高 |
| HistoricalDecision（历史决策） | 只追加 consequences，不修改 | 决策历史是事实记录，不应被修订 |
| ProjectProfile（技术画像） | AI 生成草稿，PR 合并后季度重建 | 技术画像变化频率低，误差影响可接受 |
| ExperienceMemory（经验记忆） | 置信度 > 0.8 时自动激活 | 经验记忆的误激活影响局限于单次任务 |

---

### ADR-005 Context Token 有限时的裁剪策略

**问题**：当相关知识总量超过 Token 预算，裁剪优先级如何？

**决策**：**负面经验（经验记忆中 outcome=negative 的条目）优先保留**。

理由：防止 AI 重复踩已知的坑，比展示成功案例价值更高。相当于把团队历史教训前置注入。

## 附录：与 ACE Skill 生态的关系

本平台是 ACE（AI Coding Environment）理念的扩展实现，将 ACE 的单次任务能力扩展为端到端的平台工程能力。

| ACE Skill | 平台对应能力 | 关系 |
|-----------|-------------|------|
| `requirement-analysis` | 4.1 需求撰写 | 直接复用，封装为平台需求节点 |
| `tech-design` | 4.2 技术设计 | 直接复用，集成 Context Factory 注入 |
| `spec-coding` | 4.3 编码实施 | 作为 Coding Agent 的执行协议 |
| `code-review` | 4.3 Code Review | 直接复用，结果写入可观测性系统 |
| `ut` | 4.4 测试用例生成 | 直接复用，集成平台测试阶段 |
| `verify` | 所有质量门禁 | 作为横切验证机制 |
| `auto-goal` | 需求撰写/设计评审 | 作为开放式任务的 fallback |
| 暂无 | 发布后观测 | 需新建，是最大的能力缺口 |

ACE 的 shared 协议层（understanding → alignment → verification → experience）
直接作为本平台各 AI 节点的执行标准，保证每个节点的对齐质量和验证严谨性。
